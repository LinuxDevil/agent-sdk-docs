الأحداث التي يطلقها `agent.stream()`، وترتيبها، وطريقة ترقيم إصداراتها. إذا أردت معرفة كيفية استهلاك الـ stream، فراجع [Streaming](/ar/streaming).

## Event schema (version 1)

يحتوي كل event على الحقول التالية:

| Field       | Type     | Meaning |
| ----------- | -------- | ------- |
| `type`      | string   | نوع الـ event (الجدول أدناه). طبّق narrowing عليه في TypeScript. |
| `runId`     | string   | يحدد الـ run. وهو نفسه في كل events استدعاء `stream()` واحد. |
| `seq`       | number   | `0` لأول event، ثم `+1` لكل event، بلا فجوات. |
| `timestamp` | string   | وقت إصدار الـ event، بصيغة ISO 8601 (`2026-10-01T09:30:00.000Z`). |
| `v`         | `1`      | إصدار الـ schema، ويُصدَّر باسم `AGENT_EVENT_SCHEMA_VERSION`. |
| `subagent`  | object, optional | يظهر فقط في events الـ run الخاص بـ sub-agent - راجع [Sub-agents](/ar/streaming#sub-agents). |

أنواع الـ events وحقولها الإضافية:

| `type`               | Extra fields | Emitted |
| -------------------- | ------------ | ------- |
| `run.start`          | `agentName: string`, `agentId?: string` | أول event في كل run. |
| `step.start`         | `step: number` | تبدأ step: استدعاء model واحد إضافةً إلى الـ tool calls التي يطلبها. يبدأ عدّ `step` من 1 (والـ run الذي يكمل من checkpoint يواصل العد). |
| `text.delta`         | `text: string` | جزء من نص الـ model، فور وصوله. |
| `object.delta`       | `object: unknown` | فقط لـ agent لديه `output` schema: الرد الذي حُلِّل حتى الآن، object جزئي قدر الإمكان (تُقطع قيمة الـ string غير المكتملة عند آخر نص وصل؛ ويُحذف الـ key أو الـ number غير المكتمل). يأتي بعد `text.delta` الذي يغيّره. لا يخضع لـ validation؛ والـ object المعتمد هو `object` الخاص بـ `run.done`. |
| `text.done`          | `text: string` | النص الكامل للـ step: تسلسل أحداث `text.delta` مجمّعة. فقط للـ steps التي تحتوي على نص. |
| `reasoning.start`    | (none) | يبدأ الـ model الـ reasoning في هذه الـ step. فقط مع [خيار `reasoning`](/ar/reasoning) (أو model يُجري reasoning دائمًا). يتبعه `reasoning.delta` ثم `reasoning.done`، قبل أول `text.delta` أو `tool.start` في الـ step. |
| `reasoning.delta`    | `text: string` | جزء من نص الـ reasoning (أو من ملخصه). لا يدخل أبدًا في `text.delta` ولا في `text` الخاصة بـ `run.done`. |
| `reasoning.done`     | `text: string`, `tokens?: number` | انتهى الـ reasoning: يحتوي `text` على النص كله؛ و`tokens` موجودة إذا أبلغ الـ provider عن reasoning tokens حتى تلك اللحظة. وعندما يفشل استدعاء الـ model بعد reasoning فقط وتُعاد محاولته، ينتهي reasoning المحاولة الفاشلة هنا، قبل event الـ `provider.retry`؛ ويبدأ الـ reasoning في المحاولة الجديدة من جديد بـ `reasoning.start`. |
| `tool.start`         | `toolCallId: string`, `toolName: string`, `args: Record<string, unknown>`, `executedBy?: 'provider'`, `parentToolCallId?: string` | يبدأ tool call. `args` هي arguments الـ model بعد تحليلها من JSON (`{}` إذا لم تكن JSON صالحًا). الـ call الذي يُجريه script في [code mode](/ar/code-mode) يحمل `parentToolCallId`، وهو id استدعاء `run_code` (ويظهر أيضًا في `tool.partial` و`tool.done` و`tool.error` الخاصة به). والـ [hosted tool](/ar/hosted-tools) الذي شغّله الـ provider داخل استدعاء الـ model يحمل `executedBy: 'provider'`؛ أي أنه لم يمر على أي permission rule ولا guardrail ولا approval ولا hook. يوجد واحد بالضبط لكل tool call حتى لو حدث pause: الـ call الذي توقف بانتظار approval (أو sign-in) ثم عمل يُبلغ عن `tool.resume` في الـ run المكمل، وليس `tool.start` آخر. |
| `tool.resume`        | `toolCallId`, `toolName`, `args: Record<string, unknown>` | يعمل الـ call المحسوم في [استكمال بعد approval](/ar/streaming#الـ-streaming-بعد-الـ-approval). صدر `tool.start` الخاص به من الـ run الذي توقف؛ عامله مثل `tool.start` عندما تتتبع الـ calls. |
| `tool.partial`       | `toolCallId`, `toolName`, `output: unknown`, `index: number` | snapshot من output أداة قيد التشغيل: الأداة التي تكون `execute` فيها `async function*` ترسل snapshot مع كل `yield` (راجع [Streaming partial results](/ar/tools#streaming-للنتائج-الجزئية)). كل snapshot كاملة وتحل محل سابقتها؛ ويعدّ `index` الـ snapshots الخاصة بالـ call بدءًا من 0. آخر snapshot هي نفسها `result` في `tool.done`. و`output` مُرمَّزة بـ JSON مثل `result`. لا تصل الـ snapshots أبدًا إلى الـ model ولا إلى الـ transcript ولا إلى الـ checkpoints ولا إلى الـ traces. والـ snapshot الخاصة بـ sub-agent تحمل `subagent`. |
| `tool.done`          | `toolCallId`, `toolName`, `result: unknown`, `durationMs: number`, `replacedByHook?: string`, `executedBy?: 'provider'` | أرجع الـ tool call نتيجته. `result` هي القيمة كما تُرمَّز بـ JSON (`undefined` تصبح `null`، و`Date` تصبح string). ويُحسب `durationMs` من `tool.start` / `tool.resume` الخاص به. ويسمّي `replacedByHook` الـ [hook](/ar/hooks) الذي حلّت نتيجته `{ result }` محل نتيجة الأداة (أو قامت مقامها). واستدعاء الـ [hosted tool](/ar/hosted-tools) يحمل `executedBy: 'provider'` و`result` فيه لا تتجاوز 20,000 حرف JSON. |
| `todo.updated`       | `todos: Todo[]`, `counts: { pending, in_progress, completed, total }`, `toolCallId: string` | استدعاء `todo_write` ناجح من [todo tools](/ar/tools#todo-tools) استبدل القائمة، مباشرة بعد `tool.done` للـ call نفسه. `todos` هي القائمة الجديدة كاملة (`{ id, content, status }`)، و`toolCallId` هو استدعاء `todo_write`. والنسخة الخاصة بـ sub-agent تحمل `subagent`. وتحتفظ [UI bindings](/ar/react#todos) بالقائمة وتعرضها مباشرة (live). |
| `tool.error`         | `toolCallId`, `toolName`, `error: { name: string, message: string }`, `durationMs: number`, `executedBy?: 'provider'` | فشل tool call: رمى خطأً، أو لم تطابق الـ arguments الـ schema (`name: 'ToolArgumentsValidationError'`)، أو أن الأداة غير موجودة أصلًا. واستدعاء الـ [hosted tool](/ar/hosted-tools) الذي أبلغ الـ provider عن فشله يحمل `executedBy: 'provider'` وتكون `error.name` فيه `'HostedToolError'`. يتلقى الـ model الخطأ بوصفه result للـ call ويكمل الـ run. |
| `approval.requested` | `approvalId: string`, `toolCallId`, `toolName`, `args: Record<string, unknown>`, `kind?: 'question' \| 'sign-in'`, `question?: { text, options?, allowFreeText? }`, `signIn?: { provider, displayName?, url }` | يحتاج tool call إلى قرار من إنسان. يتوقف الـ run عندها؛ أكمله باستخدام `agent.approvals.resolve()` أو `resumeAfterApproval()` (راجع [Approvals](/ar/approvals))، أو اعمل stream للاستكمال (راجع [stream بعد approval](/ar/streaming#الـ-streaming-بعد-الـ-approval)). واستدعاء `ask_question` يحمل `kind: 'question'` و`question` الخاصة به؛ أجب عنها باستخدام `agent.approvals.answer()` (راجع [سؤال المستخدم](/ar/approvals#سؤال-المستخدم)). والأداة التي تنتظر OAuth sign-in تحمل `kind: 'sign-in'` والرابط في `signIn` (راجع [ما يراه المستخدم](/ar/oauth#ما-يراه-المستخدم)). |
| `permission.decision` | `toolCallId`, `toolName`, `decision: 'allow' \| 'deny' \| 'ask' \| 'default'`, `rule?: { index: number, reason?: string }`, `reason?: string`, `hook?: string`, `mode?: 'plan' \| 'acceptEdits' \| 'dontAsk'`, `args?: Record<string, unknown>`, `at: string` | كيف حسمت [permission rules](/ar/approvals#سياسات-الصلاحيات) الـ tool call: بعد `tool.start` الخاص به، وقبل `tool.done` / `tool.error` / `approval.requested` للـ call نفسه. ويسمّي `hook` الـ `preToolCall` [hook](/ar/hooks) الذي رفض الـ call، و`reason` هو سبب الرفض (منه أو من `needsApproval` الخاصة بالأداة). لا يصدر إلا إذا ضبط الـ run قيمة `permissions` أو `onPermissionDecision`، أو كان فيه [permission mode](/ar/permission-modes) غير `'default'` (ويكون `mode` موجودًا عندما يغيّر الـ mode النتيجة)؛ ويُحذف `args` مع `redactContent`. |
| `step.done`          | `step: number`, `finishReason: string`, `usage?: { promptTokens, completionTokens, totalTokens, inputTokens, outputTokens, estimated: boolean, costUsd?: number }` | انتهت الـ step. يأتي `finishReason` من الـ model (`'stop'`، `'tool_calls'`، `'length'`، ...)، أو يكون `'awaiting-approval'` أو `'aborted'` أو `'steered'` (أي أن `run.steer()` ألغى استدعاء الـ model، راجع [Steering](/ar/queue-and-steer#steering)) أو `'error'` عندما تنتهي الـ step بهذا الشكل (الـ run الذي يستنفد `maxSteps` بينما لا يزال الـ model يريد المتابعة ينتهي بـ `run.done` بالقيمة `'max-steps'`). ويخص `usage` استدعاء الـ model لهذه الـ step، ويغيب إذا لم يُنتج الاستدعاء response؛ و`promptTokens`/`completionTokens` أسماء بديلة (aliases) لـ `inputTokens`/`outputTokens`، و`estimated` تكون `true` عندما لا يُبلغ الـ provider عن أي شيء فتكون الأرقام تقديرية، و`costUsd` يغيب إذا لم يُستخدم أي model سعره معروف، و`costPartial: true` تشير إلى أن `costUsd` لا يشمل استدعاءً تسعيره مجهول. |
| `error`              | `error: { name: string, message: string }` | خطأ. إذا أنهى الـ run يتبعه `run.done` مع `finishReason: 'error'`. أما خطأ الـ provider الذي تُعاد محاولته تحت `surfaceRetryableProviderErrors` فتتبعه steps أخرى بدلًا من انتهاء الـ run. |
| `provider.retry`     | `attempt: number`, `maxRetries: number`, `delayMs: number`, `error: { message: string, category?: string }`, `provider: string` | فشل استدعاء model وتُعاد محاولته بعد `delayMs` (`createAgent({ retry })` أو أي provider مع `withRetry()`). `attempt` هي المحاولة التي فشلت (1 = الأولى)؛ و`category` مثل `'rate-limit'` أو `'timeout'` ... وتغيب إذا كانت مجهولة (خطأ 5xx مثلًا). |
| `provider.fallback`  | `from: string`, `to: string`, `fromModel?: string`, `toModel?: string`, `error: { message: string }` | لا يزال استدعاء الـ model يفشل بعد الـ retries، فيتولاه الـ provider التالي (`createAgent({ fallbackModels })` أو أي provider مع `withFallback()`). `from` و`to` أسماء providers؛ و`fromModel` و`toModel` هي ids الـ models، وبها تفرّق بين providerين لهما الاسم نفسه (مثلًا اثنان من models الـ OpenRouter). |
| `compaction.start`   | `strategy: string`, `tokensBefore: number`, `contextWindow: number`, `thresholdTokens: number`, `trigger?: 'manual'` | وجد الـ compaction hook (`createAgent({ compaction })`) أن طلب الـ model التالي يتجاوز الـ threshold فبدأ بضغطه. يتبعه `compaction.done` واحد بالضبط. وتشير `trigger: 'manual'` إلى استدعاء `session.compact()` (راجع `context.cleared`). راجع [Context compaction](/ar/compaction). |
| `compaction.done`    | `strategy: string`, `appliedStrategy?: string`, `tokensBefore: number`, `tokensAfter: number`, `prunedToolCallIds: string[]`, `summary?: boolean`, `error?: { message: string }`, `unchanged?: true`, `trigger?: 'manual'` | انتهى الـ compaction. تساوي `tokensAfter` قيمة `tokensBefore` وتكون `unchanged` هي `true` إذا لم يُضغط أي شيء (ولا تُصدر المحاولات اللاحقة التي لا تغيّر شيئًا على الـ transcript نفسه أي events)؛ و`summary` موجودة إذا استُبدلت الـ turns القديمة بملخص؛ و`error` موجودة إذا فشلت الـ strategy أو رجعت إلى fallback (ويكمل الـ run)؛ ويسمّي `appliedStrategy` الـ strategy التي طُبّقت نتيجتها عندما تختلف عن `strategy` (`'prune-tool-results'` بعد ملخص مرفوض). وتشير `trigger: 'manual'` إلى استدعاء `session.compact()`. |
| `heal.action`        | `action: 'hint' \| 'deny' \| 'stop'`, `toolName: string`, `reason: string`, `failure?: 'bad-input' \| 'timeout' \| 'missing-capability' \| 'permission' \| 'unknown'` | تدخّل hook لإخراج run عالق من تعثّره (راجع [`createProgressGuard()`](/ar/hooks#أوقف-run-لا-يتقدّم)). |
| `context.cleared`    | `sessionId: string`, `messagesCleared: number` | أفرغت `session.clear()` الـ transcript الخاص بـ session. يصل إلى مستمعي `session.on()`، لا إلى stream أي run. و`compaction.start` / `compaction.done` الصادران من `session.compact()` يصلان إلى `session.on()` أيضًا ويحملان `trigger: 'manual'`. |
| `budget.exceeded`    | `limit: string`, `value: number`, `max: number`, `scope: 'run' \| 'session'` | بلغت [`limits` budget](/ar/configuration#الميزانيات) حدها: `limit` هو `'maxTokens'` أو `'maxInputTokens'` أو `'maxOutputTokens'` أو `'maxCostUsd'` أو `'maxDurationMs'` أو `'maxSteps'`، و`value` هو ما استُهلك، و`max` هو الحد. يتبعه `run.done` (`'budget-exceeded'`)؛ ومع `onExceeded: 'throw'` يأتي `error` ثم `run.done` (`'error'`). |
| `input.queued`       | `id: string`, `text: string` | قبلت `run.enqueue()` الـ input (`id` هو `EnqueueResult.id`، و`text` نص المستخدم). قد يأتي في أي نقطة من الـ run، حتى داخل step. راجع [Queued input](/ar/queue-and-steer#queued-input). |
| `input.steered`      | `id: string`, `text: string`, `mode: 'immediate' \| 'queued'` | قبلت `run.steer()` الـ input (`id` هو `SteerResult.id`). `mode: 'immediate'`: أُلغي استدعاء الـ model الجاري بسببه، وتنتهي الـ step بـ `step.done` بالقيمة `'steered'`؛ و`'queued'`: ينتظر أقرب نقطة آمنة مثل `enqueue()`. راجع [Steering](/ar/queue-and-steer#steering). |
| `input.applied`      | `id: string`, `step: number` | انضم الـ input الذي كان queued (أو steered) إلى الـ transcript، مباشرة قبل استدعاء الـ model للـ step `step`: ويتبعه `step.start` للـ step نفسها. |
| `guardrail.tripped`  | `name: string`, `kind: 'input' \| 'output' \| 'tool'`, `reason: string`, `toolName?: string`, `info?: GuardrailTripInfo` (ما أثار الـ guardrail: الأنواع والـ offsets، وليس النص المطابق أبدًا؛ راجع [المجموعة الأساسية](/ar/guardrails#input-و-output-guardrails)) | منع [input أو output أو tool guardrail](/ar/guardrails#input-و-output-guardrails): قبل أول استدعاء model (input)، أو قبل `text.done` للـ step (output)، أو بعد `tool.start` للـ call (tool). يتبعه `run.done` (`'guardrail'`)؛ ومع `onTripped: 'throw'` يأتي `error` ثم `run.done` (`'error'`). |
| `guardrail.rewrote`  | `name`, `kind`, `reason`, `toolName?`, `info?` | أعاد guardrail كتابة الـ input، أو نص الـ step (قبل `text.done` الذي يحمل النص الجديد)، أو arguments لـ tool call. ويكمل الـ run. |
| `agent.drift`        | `model?: { from?: string, to?: string }`, `toolsAdded: string[]`, `toolsRemoved: string[]`, `toolsChanged: string[]`, `instructions: boolean` | run محفوظ في checkpoint أو متوقف بانتظار approval يكمله agent مختلف عن الذي حفظه، وقيمة `onAgentDrift` هي `'warn'` (الافتراضي): يوضح الـ event ما الذي تغيّر. يصدر مباشرة بعد `run.start` للاستكمال، قبل أي event لـ step أو tool؛ ويكمل الـ run. ومع `'error'` يُرفض الاستئناف بالخطأ `LOUSHO_AGENT_DRIFT` بدلًا من ذلك ولا يصدر هذا الـ event. راجع [الاستئناف بـ agent تغيّر](/ar/durable-execution#استئناف-run-بعد-تغيّر-الـ-agent). |
| `handoff`            | `from: string`, `to: string`, `toolCallId: string` | سلّم الـ run المحادثة إلى agent آخر ([Handoffs](/ar/handoffs)): بعد `tool.start` / `tool.done` لاستدعاء الـ handoff، وقبل أول `step.start` للهدف. وتخص steps الـ run من هذه النقطة الهدف؛ ويسمّي `run.result.agentName` الـ agent صاحب الرد النهائي. |
| `run.done`           | `finishReason: string`, `text: string`, `usage?: { promptTokens, completionTokens, totalTokens, inputTokens, outputTokens, estimated: boolean, costUsd?: number, modelCalls?: number, hostedToolCalls?: { [tool: string]: number } }`, `object?: unknown` | آخر event في كل run، مرة واحدة بالضبط، حتى لو أُلغي الـ run أو فشل أو توقف بانتظار approval. يطابق `finishReason` و`text` قيمة `run.result` (`'max-steps'` عندما تُستنفد ميزانية `maxSteps` بينما لا يزال الـ model يريد المتابعة)؛ والـ run الفاشل له `finishReason: 'error'` و`text: ''` وبلا `usage`. و`usage` للـ run كله: يعدّ `modelCalls` استدعاءات الـ model، ويعدّ `hostedToolCalls` استدعاءات الـ [hosted tool](/ar/hosted-tools) التي شغّلها الـ provider لكل tool name (رسومها ليست ضمن `costUsd`). و`object` هو الـ `object` المعتمد من `run.result` لـ agent لديه `output` schema (راجع [Structured output](/ar/structured-output))، ويغيب في غير ذلك. |

تُحذف الحقول الاختيارية إذا لم تكن لها قيمة. ولا تكون أبدًا `undefined`، أي أن `JSON.parse(JSON.stringify(event))` يُرجع object يساوي الأصل.

### ضمانات الترتيب

- يأتي `run.start` أولًا ويأتي `run.done` أخيرًا، وكلٌّ منهما مرة واحدة بالضبط.
- يتبع كل `step.start` حدث `step.done` واحد بالضبط بالقيمة نفسها لـ `step`، قبل `step.start` التالي. وكل ما تفعله الـ step يحدث بينهما. لكن ليس كل event يقع داخل step: `agent.drift`، و`guardrail.tripped` الخاص بـ input guardrail، وevents الـ call المحسوم في streamed approval continuation (أدناه)، كلها تأتي قبل أول `step.start` أو بين اثنين منها، ويذهب `context.cleared` إلى `session.on()` لا إلى run.
- داخل الـ step: `compaction.start` / `compaction.done` (إذا ضُغط الطلب، قبل استدعاء الـ model)، ثم events `provider.retry` / `provider.fallback` (إذا فشل استدعاء الـ model)، ثم `text.delta`، ثم `text.done`، ثم events الأدوات.
- تعمل الـ tool calls للـ step الواحدة بالتوازي (راجع `toolConcurrency`): تأتي events الـ `tool.start` بترتيب استدعاءات الـ model، و`tool.done` / `tool.error` بترتيب الاكتمال. طابقها باستخدام `toolCallId`.
- تبدأ الـ calls الداخلية لاستدعاء `run_code` ([code mode](/ar/code-mode)) وتنتهي بين `tool.start` و`tool.done` / `tool.error` الخاصين به.
- تأتي events الـ `tool.partial` للـ call بين `tool.start` و`tool.done` / `tool.error` الخاصين به، مع `index` = 0، 1، 2، ...؛ وتتداخل الـ partials الخاصة بالـ calls المتوازية. والـ call الذي يتوقف بانتظار sign-in أو approval ليس له `tool.done`؛ ويعمل من جديد من البداية عندما يُحسم، ويصدر باسم `tool.resume` (وليس `tool.start` آخر) ويبدأ `index` من 0.
- يأتي `input.queued` عندما تستدعي `run.enqueue()` (بعد `run.start`، حتى لو دخل الـ input الـ queue قبل انطلاق الـ run)، لذا قد يقع داخل step. ويأتي `input.applied` بين `step.done` للـ step التي كانت جارية و`step.start` التالي — الذي يحمل قيمة `step` نفسها التي ذكرها الـ event.
- يأتي `input.steered` عندما تستدعي `run.steer()`. ومع `mode: 'immediate'` تنتهي الـ step الجارية مباشرة بـ `step.done` (`'steered'`، بلا text events من الاستدعاء الملغى)، ثم `input.applied` ثم `step.start` التالي.
- عندما يحتاج call إلى approval، تعمل الـ calls التي قبله وتُبلغ عن نتائجها، ثم يأتي `approval.requested` و`step.done` (`'awaiting-approval'`) و`run.done` (`'awaiting-approval'`). ولا تبدأ الـ calls التي بعده أبدًا. والـ run الذي يكمل كـ stream (`agent.approvals.streamResolve()` / `streamAnswer()`، راجع [stream بعد approval](/ar/streaming#الـ-streaming-بعد-الـ-approval)) هو stream جديد: يُبلغ عن `run.start` خاص به، ثم `agent.drift` إذا تغيّر الـ agent، ثم `tool.resume` و`tool.done` للـ call المحسوم (`tool.error` عند الرفض) قبل أول `step.start` — لذا يرى من يتابع الـ streamين `tool.start` لهذا الـ call مرة واحدة فقط، في الـ run الذي توقف.
- عندما يمنع guardrail، يأتي `guardrail.tripped` قبل النهاية مباشرة: للـ input guardrail يأتي بعد `run.start` مباشرة (ولا تبدأ أي step)؛ وللـ output أو tool guardrail يأتي داخل الـ step، ويتبعه `step.done` و`run.done` (`'guardrail'`). والـ output الممنوع ليس له `text.done`؛ والـ calls التي تلي tool call ممنوعًا لا تبدأ أبدًا.

run يحتوي على نص فقط:

```
run.start → step.start → text.delta × n → text.done → step.done → run.done
```

run يحتوي على tool call واحد:

```
run.start
step.start(1) → tool.start → tool.done → step.done(1, 'tool_calls')
step.start(2) → text.delta × n → text.done → step.done(2, 'stop')
run.done('stop')
```

### TypeScript

`AgentEvent` هو discriminated union: طبّق narrowing على `event.type` فتحصل على الـ payload. وكل event type مُصدَّر أيضًا (`TextDeltaEvent` و`ToolDoneEvent` و`RunDoneEvent` ...)، ويختار `AgentEventOf<'tool.done'>` واحدًا منها بالاسم.

```ts
import { isAgentEvent, isToolEvent, type AgentEvent } from 'lousho';

function render(event: AgentEvent): string {
  switch (event.type) {
    case 'text.delta':
      return event.text;
    case 'tool.start':
      return `\n[${event.toolName}] ${JSON.stringify(event.args)}\n`;
    case 'tool.error':
      return `\n[${event.toolName} failed: ${event.error.message}]\n`;
    case 'run.done':
      return `\n(${event.finishReason})\n`;
    default:
      return '';
  }
}

// isToolEvent / isTextEvent / isStepEvent narrow to an event family:
const toolNames = (events: AgentEvent[]) => events.filter(isToolEvent).map((e) => e.toolName);

// isAgentEvent validates an event received over the wire:
const received: unknown = JSON.parse('{"type":"run.start","runId":"r","seq":0,"timestamp":"","v":1,"agentName":"a"}');
if (isAgentEvent(received)) console.log(render(received), toolNames([received]));
```

### Versioning

لا يتغيّر `v` إلا إذا تغيّر event موجود بشكل يكسر التوافق (حُذف حقل أو تغيّر اسمه أو نوعه). وقد تُضاف event types جديدة وحقول اختيارية جديدة بدون تغيير `v`، لذا تجاهل أي event type لا تعرفه.
