الأحداث اللي يطلقها `agent.stream()`، وترتيبها، وطريقة ترقيم إصداراتها. إذا تريد تعرف كيف تستهلك الـ stream، شوف [Streaming](/ar/streaming).

## Event schema (version 1)

كل event فيه الحقول هذه:

| Field       | Type     | Meaning |
| ----------- | -------- | ------- |
| `type`      | string   | نوع الـ event (الجدول تحت). اعمل narrowing عليه في TypeScript. |
| `runId`     | string   | يحدد الـ run. نفسه في كل events لـ `stream()` call واحد. |
| `seq`       | number   | `0` لأول event، وبعدها `+1` لكل event، بلا فجوات. |
| `timestamp` | string   | وقت إصدار الـ event، بصيغة ISO 8601 (`2026-10-01T09:30:00.000Z`). |
| `v`         | `1`      | إصدار الـ schema، ويُصدَّر باسم `AGENT_EVENT_SCHEMA_VERSION`. |
| `subagent`  | object, optional | يظهر فقط في events لـ run الخاص بـ sub-agent - شوف [Sub-agents](/ar/streaming#sub-agents). |

أنواع الـ events وحقولها الإضافية:

| `type`               | Extra fields | Emitted |
| -------------------- | ------------ | ------- |
| `run.start`          | `agentName: string`, `agentId?: string` | أول event في كل run. |
| `step.start`         | `step: number` | step تبدأ: model call واحد زائد الـ tool calls اللي يطلبها. `step` يعد من 1 (الـ run اللي يكمل من checkpoint يواصل العد). |
| `text.delta`         | `text: string` | جزء من نص الـ model، أول ما يوصل. |
| `text.done`          | `text: string` | النص الكامل للـ step: تسلسل أحداث `text.delta` مضمومة. فقط للـ steps اللي فيها نص. |
| `reasoning.start`    | (none) | الـ model يبدأ الـ reasoning في الـ step هذه. فقط مع [خيار `reasoning`](/ar/reasoning) (أو model يعمل reasoning دائمًا). يتبعه `reasoning.delta` ثم `reasoning.done`، قبل أول `text.delta` أو `tool.start` في الـ step. |
| `reasoning.delta`    | `text: string` | جزء من نص الـ reasoning (أو من ملخصه). ما يدخل أبدًا في `text.delta` ولا في `text` الخاصة بـ `run.done`. |
| `reasoning.done`     | `text: string`, `tokens?: number` | الـ reasoning خلص: `text` فيه النص كله؛ و`tokens` موجودة إذا الـ provider بلّغ عن reasoning tokens حتى وقتها. |
| `tool.start`         | `toolCallId: string`, `toolName: string`, `args: Record<string, unknown>`, `executedBy?: 'provider'`, `parentToolCallId?: string` | tool call يبدأ. `args` هي arguments الـ model بعد تحليلها من JSON (`{}` إذا ما كانت JSON صالح). الـ call اللي يعملها script في [code mode](/ar/code-mode) يحمل `parentToolCallId`، وهو id لـ `run_code` call (ويظهر أيضًا في `tool.partial` و`tool.done` و`tool.error` الخاصة به). والـ [hosted tool](/ar/hosted-tools) اللي الـ provider شغّله داخل الـ model call يحمل `executedBy: 'provider'`؛ يعني ما مر على permission rule ولا guardrail ولا approval ولا hook. واحد بالضبط لكل tool call حتى لو فيه pause: الـ call اللي وقف لـ approval (أو sign-in) ثم اشتغل يبلّغ `tool.resume` في الـ run المكمل، وليس `tool.start` ثاني. |
| `tool.resume`        | `toolCallId`, `toolName`, `args: Record<string, unknown>` | الـ call المحسوم في [استكمال بعد approval](/ar/streaming#الـ-streaming-بعد-الـ-approval) يشتغل. `tool.start` الخاص به طلع من الـ run اللي وقف؛ عامله مثل `tool.start` لما تتتبع الـ calls. |
| `tool.partial`       | `toolCallId`, `toolName`, `output: unknown`, `index: number` | snapshot من output لأداة قيد التشغيل: الأداة اللي `execute` فيها `async function*` ترسل snapshot مع كل `yield` (شوف [Streaming partial results](/ar/tools#streaming-للنتائج-الجزئية)). كل snapshot كاملة وتحل محل اللي قبلها؛ و`index` يعد snapshots الـ call من 0. آخر snapshot هي نفسها `result` في `tool.done`. و`output` مشفرة JSON مثل `result`. الـ snapshots ما توصل أبدًا للـ model ولا للـ transcript ولا للـ checkpoints ولا للـ traces. والـ snapshot الخاصة بـ sub-agent تحمل `subagent`. |
| `tool.done`          | `toolCallId`, `toolName`, `result: unknown`, `durationMs: number`, `replacedByHook?: string`, `executedBy?: 'provider'` | الـ tool call رجع. `result` هي القيمة كما تتشفر JSON (`undefined` تصير `null`، و`Date` تصير string). و`durationMs` يعد من `tool.start` / `tool.resume` الخاصة به. و`replacedByHook` يسمي الـ [hook](/ar/hooks) اللي نتيجته `{ result }` حلت محل نتيجة الأداة (أو قامت مقامها). والـ [hosted tool](/ar/hosted-tools) call يحمل `executedBy: 'provider'` و`result` فيه ما تتجاوز 20,000 حرف JSON. |
| `todo.updated`       | `todos: Todo[]`, `counts: { pending, in_progress, completed, total }`, `toolCallId: string` | `todo_write` call ناجح من [todo tools](/ar/tools#todo-tools) بدّل القائمة، مباشرة بعد `tool.done` للـ call نفسه. `todos` هي القائمة الجديدة كاملة (`{ id, content, status }`)، و`toolCallId` هو الـ `todo_write` call. والنسخة الخاصة بـ sub-agent تحمل `subagent`. و[UI bindings](/ar/react#todos) يحتفظون بالقائمة ويعرضونها live. |
| `tool.error`         | `toolCallId`, `toolName`, `error: { name: string, message: string }`, `durationMs: number`, `executedBy?: 'provider'` | tool call فشل: رمى خطأ، أو الـ arguments ما طابقت الـ schema (`name: 'ToolArgumentsValidationError'`)، أو الأداة أصلًا ما هي موجودة. والـ [hosted tool](/ar/hosted-tools) call اللي الـ provider بلّغ عن فشله يحمل `executedBy: 'provider'` وتكون `error.name` فيه `'HostedToolError'`. الـ model يأخذ الخطأ كـ result للـ call والـ run يكمل. |
| `approval.requested` | `approvalId: string`, `toolCallId`, `toolName`, `args: Record<string, unknown>`, `kind?: 'question' \| 'sign-in'`, `question?: { text, options?, allowFreeText? }`, `signIn?: { provider, displayName?, url }` | tool call يحتاج قرار من إنسان. الـ run يوقف وقتها؛ كمّله بـ `agent.approvals.resolve()` أو `resumeAfterApproval()` (شوف [Approvals](/ar/approvals))، أو اعمل stream للاستكمال (شوف [stream بعد approval](/ar/streaming#الـ-streaming-بعد-الـ-approval)). والـ `ask_question` call يحمل `kind: 'question'` و`question` الخاصة به؛ رد عليها بـ `agent.approvals.answer()` (شوف [تسأل المستخدم سؤال](/ar/approvals#سؤال-المستخدم)). والأداة اللي تنتظر OAuth sign-in تحمل `kind: 'sign-in'` والرابط في `signIn` (شوف [اللي يشوفه المستخدم](/ar/oauth#ما-يراه-المستخدم)). |
| `permission.decision` | `toolCallId`, `toolName`, `decision: 'allow' \| 'deny' \| 'ask' \| 'default'`, `rule?: { index: number, reason?: string }`, `reason?: string`, `hook?: string`, `mode?: 'plan' \| 'acceptEdits' \| 'dontAsk'`, `args?: Record<string, unknown>`, `at: string` | كيف [permission rules](/ar/approvals#سياسات-الصلاحيات) حسمت الـ tool call: بعد `tool.start` الخاص به، وقبل `tool.done` / `tool.error` / `approval.requested` للـ call نفسه. و`hook` يسمي الـ `preToolCall` [hook](/ar/hooks) اللي رفض الـ call، و`reason` سبب الرفض (منه أو من `needsApproval` الخاصة بالأداة). يصدر فقط إذا الـ run ضبط `permissions` أو `onPermissionDecision`، أو فيه [permission mode](/ar/permission-modes) غير `'default'` (`mode` يكون موجودًا لما الـ mode يغيّر النتيجة)؛ و`args` يتحذف مع `redactContent`. |
| `step.done`          | `step: number`, `finishReason: string`, `usage?: { promptTokens, completionTokens, totalTokens, inputTokens, outputTokens, estimated: boolean, costUsd?: number }` | الـ step تخلص. `finishReason` يجي من الـ model (`'stop'`، `'tool_calls'`، `'length'`، ...)، أو `'awaiting-approval'` أو `'aborted'` أو `'steered'` (يعني `run.steer()` ألغى الـ model call، شوف [Steering](/ar/queue-and-steer#steering)) أو `'error'` لما الـ step تنتهي بهذا الشكل (run يخلّص `maxSteps` والـ model ما زال يريد المتابعة ينتهي بـ `run.done` بقيمة `'max-steps'`). و`usage` يخص الـ model call للـ step هذه، ويغيب إذا الـ call ما أنتج response؛ و`promptTokens`/`completionTokens` aliases لـ `inputTokens`/`outputTokens`، و`estimated` تكون `true` لما الـ provider ما يبلّغ عن شيء فتكون الأرقام تقدير، و`costUsd` يغيب إذا الـ model المستخدم مجهول التسعير. |
| `error`              | `error: { name: string, message: string }` | خطأ. إذا أنهى الـ run يتبعه `run.done` مع `finishReason: 'error'`. أما خطأ provider تُعاد محاولته تحت `surfaceRetryableProviderErrors` فتتبعه steps ثانية بدل ما ينتهي الـ run. |
| `provider.retry`     | `attempt: number`, `maxRetries: number`, `delayMs: number`, `error: { message: string, category?: string }`, `provider: string` | model call فشل وتُعاد محاولته بعد `delayMs` (`createAgent({ retry })` أو أي provider بـ `withRetry()`). `attempt` هي المحاولة اللي فشلت (1 = الأولى)؛ و`category` مثل `'rate-limit'` أو `'timeout'` ... وتغيب إذا كانت مجهولة (خطأ 5xx مثلًا). |
| `provider.fallback`  | `from: string`, `to: string`, `error: { message: string }` | الـ model call ما زال يفشل بعد الـ retries، فيتولاه الـ provider التالي (`createAgent({ fallbackModels })` أو أي provider بـ `withFallback()`). `from` و`to` أسماء providers. |
| `compaction.start`   | `strategy: string`, `tokensBefore: number`, `contextWindow: number`, `thresholdTokens: number`, `trigger?: 'manual'` | الـ compaction hook (`createAgent({ compaction })`) وجد إن طلب الـ model التالي فوق الـ threshold فبدأ يضغطه. يتبعه `compaction.done` واحد بالضبط. و`trigger: 'manual'` تعلّم `session.compact()` call (شوف `context.cleared`). شوف [Context compaction](/ar/compaction). |
| `compaction.done`    | `strategy: string`, `tokensBefore: number`, `tokensAfter: number`, `prunedToolCallIds: string[]`, `summary?: boolean`, `error?: { message: string }`, `trigger?: 'manual'` | الـ compaction خلص. `tokensAfter` تساوي `tokensBefore` إذا ما انضغط أي شيء؛ و`summary` موجودة إذا استُبدلت الـ turns القديمة بملخص؛ و`error` موجودة إذا الـ strategy فشلت أو رجعت لـ fallback (والـ run يكمل). و`trigger: 'manual'` تعلّم `session.compact()` call. |
| `context.cleared`    | `sessionId: string`, `messagesCleared: number` | `session.clear()` أفرغت الـ transcript لـ session. يوصل لمستمعي `session.on()`، لا لـ stream لأي run. و`compaction.start` / `compaction.done` اللي يطلعون من `session.compact()` يوصلون `session.on()` أيضًا ويحملون `trigger: 'manual'`. |
| `budget.exceeded`    | `limit: string`, `value: number`, `max: number`, `scope: 'run' \| 'session'` | [`limits` budget](/ar/configuration#الميزانيات) بلغت حدها: `limit` هو `'maxTokens'` أو `'maxInputTokens'` أو `'maxOutputTokens'` أو `'maxCostUsd'` أو `'maxDurationMs'` أو `'maxSteps'`، و`value` اللي انصرف، و`max` هو الحد. يتبعه `run.done` (`'budget-exceeded'`)؛ ومع `onExceeded: 'throw'` يجي `error` ثم `run.done` (`'error'`). |
| `input.queued`       | `id: string`, `text: string` | `run.enqueue()` قبلت input (`id` هو `EnqueueResult.id`، و`text` نص المستخدم). ممكن يجي في أي نقطة من الـ run، حتى داخل step. شوف [Queued input](/ar/queue-and-steer#queued-input). |
| `input.steered`      | `id: string`, `text: string`, `mode: 'immediate' \| 'queued'` | `run.steer()` قبلت input (`id` هو `SteerResult.id`). `mode: 'immediate'`: الـ model call الجاري أُلغي بسببه، وتنتهي الـ step بـ `step.done` بقيمة `'steered'`؛ و`'queued'`: ينتظر أقرب نقطة آمنة مثل `enqueue()`. شوف [Steering](/ar/queue-and-steer#steering). |
| `input.applied`      | `id: string`, `step: number` | الـ input اللي كان queued (أو steered) انضم للـ transcript، مباشرة قبل الـ model call للـ step `step`: ويتبعه `step.start` لنفس الـ step. |
| `guardrail.tripped`  | `name: string`, `kind: 'input' \| 'output' \| 'tool'`, `reason: string`, `toolName?: string`, `info?: GuardrailTripInfo` (اللي أثار الـ guardrail: الأنواع والـ offsets، وليس النص المطابق أبدًا؛ شوف [المجموعة الأساسية](/ar/guardrails#input-و-output-guardrails)) | [input أو output أو tool guardrail](/ar/guardrails#input-و-output-guardrails) منع: قبل أول model call (input)، أو قبل `text.done` للـ step (output)، أو بعد `tool.start` للـ call (tool). يتبعه `run.done` (`'guardrail'`)؛ ومع `onTripped: 'throw'` يجي `error` ثم `run.done` (`'error'`). |
| `guardrail.rewrote`  | `name`, `kind`, `reason`, `toolName?`, `info?` | guardrail أعاد كتابة الـ input، أو نص الـ step (قبل `text.done` اللي يحمل النص الجديد)، أو arguments لـ tool call. والـ run يكمل. |
| `agent.drift`        | `model?: { from?: string, to?: string }`, `toolsAdded: string[]`, `toolsRemoved: string[]`, `toolsChanged: string[]`, `instructions: boolean` | run محفوظ في checkpoint أو موقوف على approval يكمله agent مختلف عن اللي حفظه، و`onAgentDrift` قيمتها `'warn'` (الافتراضي): الـ event يوضح ما الذي تغيّر. يصدر مباشرة بعد `run.start` للاستكمال، قبل أي event لـ step أو tool؛ والـ run يكمل. ومع `'error'` يُرفض الاستئناف بـ `LOUSHO_AGENT_DRIFT` بدلًا من ذلك وما يصدر الـ event هذا. شوف [الاستئناف بـ agent تغيّر](/ar/durable-execution#استئناف-run-بعد-ما-يتغير-الـ-agent). |
| `handoff`            | `from: string`, `to: string`, `toolCallId: string` | الـ run سلّم المحادثة لـ agent ثاني ([Handoffs](/ar/handoffs)): بعد `tool.start` / `tool.done` للـ handoff call، وقبل أول `step.start` للهدف. وsteps الـ run من هذه النقطة تخص الهدف؛ و`run.result.agentName` يسمي الـ agent صاحب الرد النهائي. |
| `run.done`           | `finishReason: string`, `text: string`, `usage?: { promptTokens, completionTokens, totalTokens, inputTokens, outputTokens, estimated: boolean, costUsd?: number, modelCalls?: number, hostedToolCalls?: { [tool: string]: number } }`, `object?: unknown` | آخر event في كل run، مرة واحدة بالضبط، حتى لو الـ run أُلغي أو فشل أو وقف على approval. `finishReason` و`text` يطابقون `run.result` (`'max-steps'` لما ميزانية `maxSteps` تخلص والـ model ما زال يريد المتابعة)؛ والـ run الفاشل له `finishReason: 'error'` و`text: ''` وبلا `usage`. و`usage` لكل الـ run: `modelCalls` يعد الـ model calls، و`hostedToolCalls` يعد calls الـ [hosted tool](/ar/hosted-tools) اللي الـ provider شغّلها لكل tool name (رسومها ليست ضمن `costUsd`). و`object` هو الـ `object` المعتمد من `run.result` لـ agent عنده `output` schema (شوف [Structured output](/ar/structured-output))، ويغيب غير ذلك. |

الحقول الاختيارية تنحذف إذا ما لها قيمة. وما تكون أبدًا `undefined`، يعني `JSON.parse(JSON.stringify(event))` يرجع object يساوي الأصل.

### ضمانات الترتيب

- `run.start` يجي أول و`run.done` يجي آخر، وكل واحد مرة واحدة بالضبط.
- كل `step.start` يتبعه `step.done` واحد بالضبط بنفس `step`، قبل `step.start` التالي. وكل اللي تعمله الـ step يصير بين الاثنين. لكن ليس كل event يقع داخل step: `agent.drift`، و`guardrail.tripped` لـ input guardrail، وevents الـ call المحسوم في streamed approval continuation (تحت)، كلها تجي قبل أول `step.start` أو بين اثنين منها، و`context.cleared` يروح لـ `session.on()` لا لـ run.
- داخل الـ step: `compaction.start` / `compaction.done` (إذا انضغط الطلب، قبل الـ model call)، ثم events `provider.retry` / `provider.fallback` (إذا فشل الـ model call)، ثم `text.delta`، ثم `text.done`، ثم events الأدوات.
- الـ tool calls للـ step الواحدة تشتغل بالتوازي (شوف `toolConcurrency`): events الـ `tool.start` تجي بترتيب calls الـ model، و`tool.done` / `tool.error` بترتيب الاكتمال. طابقها بـ `toolCallId`.
- الـ calls الداخلية لـ `run_code` call ([code mode](/ar/code-mode)) تبدأ وتخلص بين `tool.start` و`tool.done` / `tool.error` الخاصين به.
- events الـ `tool.partial` للـ call تجي بين `tool.start` و`tool.done` / `tool.error` الخاصين به، مع `index` = 0، 1، 2، ...؛ والـ partials للـ calls المتوازية تتداخل. والـ call اللي يوقف لـ sign-in أو approval ما له `tool.done`؛ يشتغل من جديد من البداية لما يُحسم، ويصدر باسم `tool.resume` (وليس `tool.start` ثاني) و`index` يبدأ من 0.
- `input.queued` يجي لما تنادي `run.enqueue()` (بعد `run.start`، حتى لو الـ input دخل الـ queue قبل ما الـ run ينطلق)، فممكن يقع داخل step. و`input.applied` يجي بين `step.done` للـ step اللي كانت جارية و`step.start` التالي — اللي يحمل نفس `step` اللي ذكرها الـ event.
- `input.steered` يجي لما تنادي `run.steer()`. ومع `mode: 'immediate'` تنتهي الـ step الجارية مباشرة بـ `step.done` (`'steered'`، بلا text events من الـ call الملغي)، ثم `input.applied` ثم `step.start` التالي.
- لما call يحتاج approval، الـ calls اللي قبله تشتغل وتبلّغ، ثم يجي `approval.requested` و`step.done` (`'awaiting-approval'`) و`run.done` (`'awaiting-approval'`). والـ calls اللي بعده ما تبدأ أبدًا. والـ run اللي يكمل كـ stream (`agent.approvals.streamResolve()` / `streamAnswer()`، شوف [stream بعد approval](/ar/streaming#الـ-streaming-بعد-الـ-approval)) هو stream جديد: يبلّغ عن `run.start` خاص به، ثم `agent.drift` إذا الـ agent تغيّر، ثم `tool.resume` و`tool.done` للـ call المحسوم (`tool.error` عند الرفض) قبل أول `step.start` — فاللي يتابع الـ streams الاثنين يشوف `tool.start` للـ call هذا مرة واحدة بس، في الـ run اللي وقف.
- لما guardrail يمنع، `guardrail.tripped` يجي قبل النهاية مباشرة: لـ input guardrail يجي بعد `run.start` مباشرة (ولا step تبدأ)؛ ولـ output أو tool guardrail يجي داخل الـ step، ويتبعه `step.done` و`run.done` (`'guardrail'`). والـ output الممنوع ما له `text.done`؛ والـ calls اللي بعد tool call ممنوع ما تبدأ أبدًا.

run فيه نص بس:

```
run.start → step.start → text.delta × n → text.done → step.done → run.done
```

run فيه tool call واحد:

```
run.start
step.start(1) → tool.start → tool.done → step.done(1, 'tool_calls')
step.start(2) → text.delta × n → text.done → step.done(2, 'stop')
run.done('stop')
```

### TypeScript

`AgentEvent` هو discriminated union: تعمل narrowing على `event.type` فتحصل على الـ payload. وكل event type مُصدَّر أيضًا (`TextDeltaEvent` و`ToolDoneEvent` و`RunDoneEvent` ...)، و`AgentEventOf<'tool.done'>` يختار واحد بالاسم.

```ts
import { isAgentEvent, isToolEvent, type AgentEvent } from '@lousho/build-ai-agent';

function render(event: AgentEvent): string {
  switch (event.type) {
    case 'text.delta':
      return event.text;
    case 'tool.start':
      return `\n[${event.toolName}] ${JSON.stringify(event.args)}\n`;
    case 'tool.error':
      return `\n[${event.toolName} failed: ${event.error.message}]\n`;
    case 'run.done':
      return `\n(${event.finishReason})\n`;
    default:
      return '';
  }
}

// isToolEvent / isTextEvent / isStepEvent narrow to an event family:
const toolNames = (events: AgentEvent[]) => events.filter(isToolEvent).map((e) => e.toolName);

// isAgentEvent validates an event received over the wire:
const received: unknown = JSON.parse('{"type":"run.start","runId":"r","seq":0,"timestamp":"","v":1,"agentName":"a"}');
if (isAgentEvent(received)) console.log(render(received), toolNames([received]));
```

### Versioning

`v` ما يتغيّر إلا إذا event موجود تغيّر بشكل يكسر التوافق (حقل حُذف أو تبدّل اسمه أو تغيّر نوعه). وممكن تنضاف event types جديدة وحقول اختيارية جديدة بدون تغيير `v`، فتجاهل أي event type ما تعرفه.
