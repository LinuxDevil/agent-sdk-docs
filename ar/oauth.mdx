الأدوات وخوادم MCP اللي تستدعي API بالنيابة عن أحد تحتاج access token من OAuth، وعادةً refresh token حتى تجلب اللي بعده. هذه الصفحة تغطي أين تعيش هذه الـtokens: في جزء `tokens` من `AgentStore`، مفهرسةً بالـprovider وبمالك الـcredential. وتغطي كيف تحصل الأداة على واحد: تنادي `ctx.getToken(provider)`، وإذا المستخدم ما ربط حسابه بعد يوقف الـrun إلى أن يسجّل الدخول ([أدوات تحتاج تسجيل دخول](#أدوات-تحتاج-تسجيل-دخول)). وخوادم MCP عبر HTTP تسجّل الدخول بـOAuth أيضًا ([خوادم MCP مع OAuth](#خوادم-mcp-مع-oauth)).

## من يملك credential

كل credential مخزَّن له provider (اسم مثل `github`، من 1 إلى 64 حرفًا من `A-Z` و`a-z` و`0-9` و`_` و`-`) ومالك:

- **التطبيق** (`{ owner: 'app' }`): credential واحد يستخدمه الـagent للجميع، مثل service account أو تثبيت bot.
- **مستخدم** (`{ owner: 'user', principalId, issuer? }`): credential واحد لكل شخص مسجّل دخوله. `principalId` هو معرّف المستخدم، و`issuer` اسم مزوّد الهوية اللي أصدره. يعني `alice` من issuer و`alice` من issuer آخر مالكان مختلفان. مع [مصادقة المسارات](/ar/auth) ينعكس principal الطلب عليه هكذا: `{ owner: 'user', principalId: principal.id,
  issuer: principal.issuer }`. وcredential المستخدم يحتاج هذا الـprincipal، لأن بدونه لا يوجد مستخدم يملكه.

`tokenStoreKey(provider, owner)` هو مفتاح سجل الـcredential: `<provider>|app`، أو `<provider>|user|<issuer>|<principalId>` مع percent-encoding للـissuer والمعرّف (الـissuer الغائب جزء فارغ). الترميز يجعل المفتاح واضحًا: معرّف principal فيه `|` ما يقدر يتصادم مع مالك آخر.

```ts
import { tokenStoreKey } from '@lousho/build-ai-agent';

tokenStoreKey('github', { owner: 'app' }); // 'github|app'
tokenStoreKey('github', { owner: 'user', principalId: 'a|b', issuer: 'https://id.example.com' });
// 'github|user|https%3A%2F%2Fid.example.com|a%7Cb'
```

## تخزين tokens

`AgentStore.tokens` هو `OAuthTokenStore`:

```ts
import { memoryStore } from '@lousho/build-ai-agent';

const { tokens } = memoryStore();
const alice = { owner: 'user', principalId: 'alice', issuer: 'https://id.example.com' } as const;

await tokens.set('github', alice, { accessToken: 'gho_...', refreshToken: 'ghr_...', tokenType: 'Bearer', expiresAt: Date.now() + 3_600_000 });
const token = await tokens.get('github', alice); // { accessToken, refreshToken, ... } or undefined
const connected = await tokens.list({ owner: alice }); // [{ provider: 'github', owner, expiresAt, scope, hasRefreshToken: true, updatedAt }]
await tokens.delete('github', alice); // disconnect
```

- `get` و`set` و`delete` تقرأ وتكتب (تستبدل) وتحذف credential واحد.
- `list({ provider?, owner? })` ترجع metadata فقط: الـprovider والمالك ونوع الـtoken وانتهاء الصلاحية والـscope وهل فيه refresh token مخزَّن ومتى كُتب السجل. ولا ترجع أبدًا access token ولا refresh token.
- `putPending(state, value, ttlMs)` و`takePending(state)` تحفظان تسجيل دخول جاري (الـPKCE verifier ومكان العودة) بين الـredirect والـcallback. `takePending` ترجعه مرة واحدة وتحذفه، وبعد `ttlMs` يختفي. `state` من 16 إلى 128 حرفًا من `A-Z` و`a-z` و`0-9` و`_` و`-`؛ وأي `state` مشوَّه يُمرَّر إلى `takePending` ببساطة لا تجد شيئًا.
- `setClient(provider, client)` و`getClient(provider)` تحفظان client مسجَّل لدى authorization server (dynamic client registration). والسجل يمكن أن يحتوي client secret، لذلك يُشفَّر مثل الـtoken.

كل store جاهز فيه `tokens`:

| Store | أين تُحفظ الـtokens | مشفَّرة |
| --- | --- | --- |
| `memoryStore()` | objects عادية في ذاكرة العملية | لا: لا شيء يغادر العملية |
| `fileStore(dir, { tokenKey })` | `<dir>/oauth/tokens/<sha256 of the key>.json`، `<dir>/oauth/pending/<state>.json` | نعم |
| `new SqliteStore(path, { tokenKey })` | الجدولان `oauth_tokens` و`oauth_pending` | نعم |
| `new KVStore(kv, { tokenKey })` | `<prefix>oauth/tokens/<key>`، `<prefix>oauth/pending/<state>` (مع انتهاء صلاحية) | نعم |

**المفتاح.** الـstores الدائمة تشفّر كل سجل بـAES-256-GCM بمفتاح 32 بايت تمرّره إنت بصيغة base64: إما خيار `tokenKey`، وإلا متغير البيئة `LOUSHO_TOKEN_KEY`. لا يوجد مفتاح افتراضي، ولا شيء يُشتق من كلمة مرور. ولّد واحدًا بـ`generateTokenKey()` أو من الـshell:

```bash
node -e "console.log(Buffer.from(crypto.getRandomValues(new Uint8Array(32))).toString('base64'))"
```

```ts
import { createAgent, fileStore, generateTokenKey } from '@lousho/build-ai-agent';

console.log(generateTokenKey()); // store it as a secret, e.g. LOUSHO_TOKEN_KEY

const agent = createAgent({ provider, store: fileStore('./.lousho', { tokenKey: process.env.LOUSHO_TOKEN_KEY }) });
```

في Cloudflare Workers لا يوجد `process.env`: أضف المفتاح كـsecret (`wrangler secret put LOUSHO_TOKEN_KEY`) ومرّر `env.LOUSHO_TOKEN_KEY` في `tokenKey`. والـWorker اللي يولّده `lousho build --target=cloudflare-worker` يعمل هذا عنك.

- إذا المفتاح ليس 32 بايت base64 بالضبط، يظهر `ConfigurationError` عند بناء الـstore.
- بدون مفتاح، الـagent اللي ما يخزّن token أبدًا يشتغل كالمعتاد: القراءات لا تجد شيئًا. وأول `set` أو `setClient` أو `putPending` يرمي [`LOUSHO_TOKEN_KEY_MISSING`](/ar/errors#lousho_token_key_missing)، وكذلك قراءة سجل موجود.
- كل كتابة تستخدم IV عشوائي جديد من 12 بايت، فنفس الـtoken المكتوب مرتين يعطي ciphertext مختلفين. ومفتاح السجل مُوثَّق مع الـIV: الـciphertext المنسوخ إلى صف مالك آخر لا ينجح فكّ تشفيره. الصيغة المخزَّنة: `v1.<base64 iv>.<base64 ciphertext>`.
- سجل مكتوب بمفتاح آخر، أو تغيّر على القرص، يفشل بـ[`LOUSHO_TOKEN_DECRYPT_FAILED`](/ar/errors#lousho_token_decrypt_failed) — والخطأ يسمّي الـprovider ولا يذكر الـtoken أبدًا.

**تدوير المفتاح.** مرّر أكثر من مفتاح، الأحدث أولًا: `tokenKey: [newKey, oldKey]` أو `LOUSHO_TOKEN_KEY="<new>,<old>"`. الكتابة تستخدم المفتاح الأول، والقراءة تجرّب كل واحد بالترتيب، فالـtokens تنتقل للمفتاح الجديد كلما جُدِّدت. لا يوجد أمر يعيد تشفير كل السجلات؛ وبمجرد ما تُسقط المفتاح القديم، الـtokens اللي ما زالت مكتوبة فيه لم تعد تُقرأ، ومستخدموها يسجّلون الدخول من جديد (احذف تلك السجلات).

**لا شيء يسجّل الـtoken.** الـstores لا تضع أبدًا access token ولا refresh token ولا PKCE verifier ولا client secret في رسالة خطأ ولا سطر log ولا `cause` لخطأ. وقيم الـtokens ليست جزءًا من أحداث الـagent ولا الـtranscripts ولا الـcheckpoints ولا الـtraces ولا الـcassettes المسجَّلة، إلا إذا رجّعتها أداة بنفسها. والأداة اللي تستخدم token ترجع جواب الـAPI، ليس الـtoken.

**الاتساق.** SQLite يأخذ تسجيل الدخول المعلّق في transaction واحدة، والـfile store يحجزه بإنشاء ملف حصري، فيحصل عليه مستدعٍ واحد بالضبط. أما Workers KV فلا transactions فيه: `takePending` تقرأ ثم تحذف، فيمكن أن يقرأ callbackان في موقعَي edge مختلفَين، ضمن تأخير انتشار KV (حتى دقيقة تقريبًا)، نفس الـstate. والـstate قيمة عشوائية 256-bit لا يحملها إلا متصفح المستخدم، فإعادة استخدامها لا تمنح شيئًا لمن لا يملكها أصلًا. و`tokens.list()` في `KVStore` تحتاج `list()` الخاصة بالـbinding (الـKV namespace الحقيقي فيهها؛ نسخة fake مصنوعة يدويًا يمكن ألا تملكها). و`prune()` في `SqliteStore` تحذف أيضًا تسجيلات الدخول المعلّقة المنتهية؛ والـfile store يسقطها عند بدء تسجيل الدخول التالي، وKV ينهيها بنفسه.

## أدوات تحتاج تسجيل دخول

عرّف الـprovider مرة واحدة، على مستوى الـmodule بجانب الأدوات اللي تستخدمه، بـ`defineOAuthProvider()`. والأداة تطلب الـtoken بـ`ctx.getToken(provider)`:

```ts
import { createAgent, defineOAuthProvider, defineTool, memoryStore } from '@lousho/build-ai-agent';
import { z } from 'zod';

export const github = defineOAuthProvider({
  name: 'github', // also the token store key
  displayName: 'GitHub', // shown on the sign-in prompt
  authorizationUrl: 'https://github.com/login/oauth/authorize',
  tokenUrl: 'https://github.com/login/oauth/access_token',
  clientId: process.env.GITHUB_CLIENT_ID ?? 'client-id',
  clientSecret: process.env.GITHUB_CLIENT_SECRET, // omit for a public client
  scopes: ['repo'],
  redirectUri: 'https://agent.example.com/api/agent/oauth/callback', // as registered with GitHub
});

const listRepos = defineTool({
  name: 'list_repos',
  description: "Lists the user's repositories",
  input: z.object({}),
  execute: async (_args, ctx) => {
    const { accessToken } = await ctx.getToken(github); // first, before any side effect
    const res = await fetch('https://api.github.com/user/repos', { headers: { authorization: `Bearer ${accessToken}` } });
    if (res.status === 401) ctx.requireAuth(github); // the token was revoked: sign in again
    const repos = (await res.json()) as Array<{ full_name: string }>;
    return repos.map((repo) => repo.full_name); // the API's answer, never the token
  },
});

const agent = createAgent({ provider, tools: [listRepos], store: memoryStore() });
```

- `getToken()` تقرأ من `store.tokens` الـtoken الخاص بـprincipal الـrun ([principal](/ar/auth)) (`credentialOwner: 'user'`، وهو الافتراضي) أو الخاص بالتطبيق (`credentialOwner: 'app'`). والـtoken اللي تنتهي صلاحيته خلال 60 ثانية وفيه refresh token يُجدَّد أولًا على `tokenUrl` ويُحفظ؛ وإذا رفض الخادم التجديد يُحذف.
- بدون token صالح الـrun **يوقف**، بالضبط مثل [approval](/ar/approvals): `finishReason: 'awaiting-approval'`، وapproval معلّق بـ`kind: 'sign-in'`، durable في مخازن الـagent. وبعد تسجيل المستخدم وقبول الـapproval، يعمل الـtool call من جديد **من البداية**. استدعِ `getToken()` قبل أي شيء له side effect: أي شغل مُنجز قبلها يتكرر مرتين.
- `ctx.requireAuth(provider)` لرمز رفضته الـAPI (استجابة 401): تحذف الـtoken المخزَّن وتوقف لتسجيل دخول جديد.
- credential المستخدم تحتاج principal: في run بدون واحد (لا route auth ولا channel) تُفشل `getToken()` الاستدعاء بـ[`LOUSHO_OAUTH_PRINCIPAL_REQUIRED`](/ar/errors#lousho_oauth_principal_required) ولا يتوقف شيء.
- الـagent يحتاج token store (`store` فيه `tokens`)؛ وبدونه يتوقف الـrun بـ[`LOUSHO_OAUTH_STORE_MISSING`](/ar/errors#lousho_oauth_store_missing).
- الـprovider يُسجَّل باسمه `name` على مستوى الـprocess، فيقدر الـcallback يكمل تسجيل دخول بدأ في request آخر أو قبل restart. وتعريف نفس الاسم مرة أخرى يستبدله.

**credentials التطبيق.** الـprovider اللي له `credentialOwner: 'app'` يحمل token واحد للجميع (تثبيت bot، service account). ومستخدم الدردشة لا يُرسَل له رابط تسجيل الدخول أبدًا، لأن اللي يفتحه سيربط حسابه هو كـcredential للـagent لكل المستخدمين: وبدون الـtoken يفشل الاستدعاء بـ[`LOUSHO_OAUTH_APP_SIGNIN_REQUIRED`](/ar/errors#lousho_oauth_app_signin_required). والمشغّل يسجّل دخول التطبيق مرة واحدة بـ`agent.oauth.signInUrl(provider)`:

```ts
import { createAgent, defineOAuthProvider, fileStore } from '@lousho/build-ai-agent';

const slackBot = defineOAuthProvider({
  name: 'slack_bot',
  displayName: 'Slack',
  credentialOwner: 'app',
  authorizationUrl: 'https://slack.com/oauth/v2/authorize',
  tokenUrl: 'https://slack.com/api/oauth.v2.access',
  clientId: process.env.SLACK_CLIENT_ID ?? 'client-id',
  clientSecret: process.env.SLACK_CLIENT_SECRET,
  scopes: ['chat:write'],
  redirectUri: 'https://agent.example.com/oauth/callback',
});

// connect-slack.ts: run once against the deployed agent's store, open the URL, approve.
const agent = createAgent({ provider, store: fileStore('./.lousho', { tokenKey: process.env.LOUSHO_TOKEN_KEY }) });
console.log('Open this to connect the app:', await agent.oauth.signInUrl(slackBot));
```

الرابط يشتغل 10 دقائق؛ ومسار الـcallback في الـagent المنشور (اللي يشارك نفس الـstore) يخزّن الـtoken، وكل run يستخدمه بعدها، بـprincipal أو بدونه.

## ما يراه المستخدم

الإيقاف يوصل مثل أي approval، ومعه الرابط المطلوب فتحه:

- حدث `approval.requested` (و`run.done` اللي بعده بـ`finishReason: 'awaiting-approval'`) فيه `kind: 'sign-in'` و`signIn: { provider, displayName?, url }`. و`agent.approvals.list()` ترجع نفس السجل. اعرض `url`؛ وحين يرجع المستخدم، وافق على الإيقاف ("I've signed in") بـ`agent.approvals.resolve({ id, approved: true })` أو `POST /chat/:id/approvals/:approvalId { "approved": true }`. الموافقة قبل ما الـcallback يخزّن token ترمي [`LOUSHO_SIGNIN_PENDING`](/ar/errors#lousho_signin_pending) (HTTP 409 على المسار) ويبقى الـrun موقوفًا. أما `approved: false` فتلغي: يستلم الـmodel خطأ أداة بـ`kind: 'denied'` نصه "Sign-in to GitHub was cancelled.".
- الـ`approve` callback لا يُسأل عن تسجيل دخول أبدًا: المستخدم وحده يستطيع تسجيل الدخول.
- تطبيقات React وVue وSvelte تستلمه كـ`pendingApproval.kind === 'sign-in'` مع `pendingApproval.signIn`: اعرض الرابط واستدعِ `approve()` حين يقول المستخدم إنه انتهى (`reject()` تلغي). وجزء `data-lousho-approval` من stream الـAI SDK يحمل `kind` و`signIn` أيضًا.
- [القنوات](/ar/channels) تنشر الرسالة الافتراضية "Sign in to GitHub to continue: &lt;url>" بلا أزرار Approve / Deny. وSlack يرسلها بـ`chat.postEphemeral` للمستخدم اللي بدأ الـturn، وDiscord كرسالة ephemeral متابعة، فلا أحد غيره في الـthread يرى الرابط. أما Teams وTelegram فينشرانها في المحادثة (ليس لديهما رسالة يراها مستخدم واحد فقط)، وGitHub لا ينشرها في thread عام أبدًا. وخلف `createDeployedServer()` و`lousho dev` يكمل الـcallback دورة القناة الموقوفة بنفسه، وتُنشر الإجابة في نفس مكان السؤال.
- صفحة الدردشة في `lousho dev` تعرض الرابط مع "I've signed in" و"Cancel"؛ و`lousho chat` و`lousho acp` يعرضان الرابط ويسألان من جديد إلى أن يسجّل المستخدم الدخول.

## مسار callback

`redirectUri` لازم يشير إلى `GET /oauth/callback` في الـagent المخدَّم، بالضبط كما سُجّل لدى الـprovider:

| Host | Callback |
| --- | --- |
| `lousho dev` وخادم node وصورة Docker والـWorker | `GET /oauth/callback` |
| `createRouteHandler(agent, { basePath })` | `GET <basePath>/oauth/callback` (مثل `/api/agent/oauth/callback`) |

المسار **ليس** خلف route auth ولا bearer token: الـredirect من المتصفح لا يحمل API token. وحمايته هي `state`: 32 بايت عشوائية، استخدام واحد، صالحة 10 دقائق. ينادي `agent.oauth.complete({ state, code, error })` ويرد بصفحة HTML صغيرة ("Signed in to GitHub. You can close this tab."، أو نص الإلغاء إذا أرسل الـprovider `error`)، مع `cache-control: no-store`، وبدون script، وبدون أن يعكس أي قيمة من الـquery. و`state` غير المعروفة أو المستخدمة أو المنتهية يُجاب بـ400؛ ورفض تبادل الـcode يُجاب بـ502 ([`LOUSHO_OAUTH_TOKEN_EXCHANGE_FAILED`](/ar/errors#lousho_oauth_token_exchange_failed)). وإذا اجتاز طلب الـcallback مصادقة المسار (كوكي session تقبلها دالة المصادقة عندك، مثلًا)، يُرفض تسجيل دخول بدأ لمستخدم آخر.

`agent.oauth.complete()` تخزّن الـtoken فقط: الـclient اللي عرض الرابط يكمل الـrun بالموافقة على الإيقاف. وإذا كنت تخدم مسارًا خاصًا بك، افعل الشيء نفسه:

```ts
import { createAgent } from '@lousho/build-ai-agent';

const agent = createAgent({ provider });

export async function GET(request: Request): Promise<Response> {
  const query = new URL(request.url).searchParams;
  const { outcome } = await agent.oauth.complete({
    state: query.get('state') ?? '',
    code: query.get('code') ?? undefined,
    error: query.get('error') ?? undefined,
  });
  return new Response(outcome === 'signed-in' ? 'Signed in. You can close this tab.' : 'Sign-in cancelled.');
}
```

إذا رفض المستخدم عند الـprovider، ترجع `complete()` القيمة `outcome: 'declined'`، والموافقة على الإيقاف وقتها تلغي الاستدعاء مثل `approved: false`.

## approval وتسجيل الدخول معًا

الأداة اللي فيها `needsApproval` تسأل أولًا: بوابة الـapproval تعمل قبل `execute` الخاصة بالأداة. وبعد القبول يبدأ الاستدعاء، فلا تجد `getToken()` token ويوقف الـrun مرة أخرى، هذه المرة لتسجيل الدخول. وبعد تسجيل الدخول، الموافقة على هذا الإيقاف تنفّذ الاستدعاء مرة واحدة؛ ولا يُعرض على المراجع ثانيةً. والاستدعاء اللي يحتاج تسجيل دخول لدى اثنين من الـproviders يتوقف مرة لكل واحد منهما، بالتتابع.

وإذا احتاجت عدة استدعاءات في turn واحد للـmodel إلى تسجيل دخول، يوقف الـrun عند الأول؛ والباقي يعمل بعد ما يُبتّ فيه، مثل بقية turn توقف على approval.

## الأمان

- **PKCE والـstate.** كل تسجيل دخول يستخدم PKCE مع S256 (verifier من 32 بايت) و`state` عشوائية من 32 بايت. الـverifier يُحفظ فقط في السجل المعلّق المشفَّر (`store.tokens.putPending`) — أبدًا في snapshot الـapproval ولا checkpoint ولا حدث. و`state` لاستخدام واحد وتنتهي بعد 10 دقائق. ورابط التفويض يحمل `state` والـchallenge، وكلاهما آمن للعرض؛ أما authorization code فلا يُسجَّل أبدًا.
- **التشفير.** الـtokens وتسجيلات الدخول المعلّقة تُشفَّر في التخزين عبر الـstores الدائمة ([تخزين الـtokens](#تخزين-tokens)).
- **ربط الـprincipal.** token المستخدم يُخزَّن للـprincipal اللي الـrun الموقوف يتصرف نيابةً عنه، من كان اللي يكمّل الـcallback، والـrun لا يقرأ إلا token الـprincipal الخاص به. وtokens مستخدمَين لا تختلط أبدًا؛ ونفس الـid من issuer آخر هو مستخدم آخر. أما credential التطبيق فلا يسجّل دخولها إلا المشغّل.
- **من يرى الرابط.** اللي يفتح رابط تسجيل دخول يربط حسابه هو بالمستخدم اللي طلبه. اعرضه لذلك المستخدم فقط: في stream الـrun نفسه، أو رسالة ephemeral في قناة مشتركة (Slack وDiscord)، ولا في thread عام أبدًا.
- **لا ترجع token من أداة أبدًا.** ارجع جواب الـAPI. وكشبكة أمان: إذا كانت نتيجة أداة فيها token سلّمته `getToken()` أثناء ذلك الاستدعاء، يُستبدل بـ`[REDACTED]` قبل تسجيلها، وتحذير يسمّي الأداة. والـtokens لا تدخل أبدًا في أحداث الـagent ولا transcripts ولا checkpoints ولا سجلات الـapproval ولا trace spans ولا cassettes مسجَّلة.

## خوادم MCP مع OAuth

خوادم MCP المستضافة مثل Linear وGitHub وAtlassian وNotion تتطلب OAuth 2.1 كما تعرّفه مواصفة تفويض MCP. أعطِ مدخل HTTP في `mcpServers` حقل `oauth` والـSDK يتولى البروتوكول: يقرأ metadata المورد المحمي للخادم (RFC 9728) ليجد authorization server الخاص به، ويقرأ metadata ذلك الخادم (RFC 8414)، ويسجّل client إذا ما كان عندك واحد (dynamic client registration، RFC 7591)، ويسجّل الدخول بـPKCE (S256) وresource indicator (RFC 8707). والـtokens تُحفظ في token store الـagent (مشفَّرة في الـstores الدائمة) تحت اسم provider `mcp-<server>`، ويجدّدها MCP SDK حين يرفض الخادم واحدًا منتهيًا.

```ts
import { createAgent } from '@lousho/build-ai-agent';
import { SqliteStore } from '@lousho/build-ai-agent/sqlite';

const agent = createAgent({
  provider,
  mcpServers: {
    linear: {
      url: 'https://mcp.linear.app/mcp',
      oauth: { redirectUri: 'https://agent.example.com/oauth/callback' },
    },
  },
  store: new SqliteStore('./agent.db', { tokenKey: process.env.LOUSHO_TOKEN_KEY }),
});

// connect-linear.ts: run once against the deployed agent's store, open the URL, approve.
console.log('Open this to connect Linear:', await agent.oauth.mcpSignInUrl('linear'));
```

الحقل `oauth` يقبل:

- `redirectUri` (مطلوب): عنوان الـcallback للـagent، أي [مسار الـcallback](#مسار-callback) في الـagent المنشور.
- `clientId`، و`clientSecret` لـconfidential client: client سجّلته بنفسك لدى authorization server. وبدون `clientId`، الـSDK يسجّل واحدًا عند أول تسجيل دخول (باسم `clientName`، والافتراضي `lousho`، و`redirectUri` هو الـredirect URI الوحيد له) ويحتفظ به في الـtoken store.
- `scopes`: تُطلب حين لا تسمّي metadata الخادم أيًّا منها.

**تسجيل الدخول.** الـgrant للتطبيق، مثل [credentials التطبيق](#أدوات-تحتاج-تسجيل-دخول): تسجيل دخول واحد للـagent كله، يجريه المشغّل. `agent.oauth.mcpSignInUrl('<server>')` (آخر سطر في المثال فوق) ترجع رابط التفويض؛ المشغّل يفتحه ويوافق، ومسار الـcallback في الـagent المنشور، اللي يشارك نفس الـstore، يخزّن الـtoken. والرابط يشتغل مرة واحدة، لمدة 10 دقائق. و`mcpSignInUrl()` تصنع رابطًا جديدًا دائمًا، حتى لو فيه token مخزَّن، فهي أيضًا تعيد ربط التطبيق بحساب آخر. وأول `ready()` أو tool call بعدها يتصل بالـtoken الجديد؛ ولا شيء يحتاج restart.

**`needs-auth`.** إلى أن يُسجَّل دخول التطبيق، أو بعد إلغاء الـgrant (الـtoken مرفوض ومعه الـrefresh token)، تكون حالة الخادم `'needs-auth'` والاتصال يفشل بـ[`LOUSHO_MCP_AUTH_REQUIRED`](/ar/errors#lousho_mcp_auth_required): `ready()` وأول `send()` يرفضان به (أو، مع `connectMcp(servers, { onError: 'skip' })`، يُترك الخادم خارجًا). وtool call مرفوض أثناء run يصير نتيجة خطأ للـmodel، بنفس الرمز؛ والـrun لا يتوقف، لأن مستخدم الدردشة لا يسجّل الدخول عن التطبيق أبدًا. والاتصال لا يسجّل client ولا يبدأ تسجيل دخول من نفسه: `mcpSignInUrl()` وحدها تفعل.

**الأمان.**

- `oauth` يحتاج url بـ`https`؛ و`http` العادي مسموح فقط لـ`localhost` و`127.0.0.1` و`[::1]`. و`headers` تظل تشتغل بجانب `oauth` (header بمفتاح API مثلًا) وتُرسَل فقط إلى origin خادم MCP نفسه، ولا تُرسَل إلى authorization server أبدًا؛ وheader `Authorization` مع `oauth` يُرفض.
- الـtoken يُرسَل فقط إلى الـ`url` اللي أُخذ له. وإذا تغيّر `url` المدخل، الـgrant المخزَّن وأي client مسجَّل لا يُستخدمان، والخادم يحتاج تسجيل دخول جديد. والـSDK يرفض أيضًا metadata المورد المحمي إذا `resource` فيها لا يطابق عنوان الخادم.
- الـtokens وauthorization codes وPKCE verifiers وclient secret لا تظهر أبدًا في رسائل الأخطاء ولا أسطر الـlogs ولا `status()` ولا أحداث الـagent ولا نتائج الأدوات؛ وخطأ authorization server يُبلَّغ عنه برمز `error` الخاص بـOAuth فقط.

**الحدود.** grants الـMCP يملكها التطبيق: اتصال واحد وtoken واحد لكل خادم لكل مستخدمي الـagent. أما grants MCP لكل مستخدم (كل مستخدم يسجّل الدخول بحسابه وبقائمة أدوات خاصة به) فغير مدعومة بعد. وOAuth يشمل خوادم HTTP فقط، لا stdio. ووثائق Client ID metadata ومصادقة الـclient بـ`private_key_jwt` غير مدعومة.

لاستخدام `connectMcp()` بدون agent، مرّر الـstore هكذا: `connectMcp(servers, { tokens: store.tokens })`. هي تستخدم الـtoken المخزَّن، وتسجيل الدخول يمر عبر `agent.oauth.mcpSignInUrl()` في agent على نفس الـstore.
