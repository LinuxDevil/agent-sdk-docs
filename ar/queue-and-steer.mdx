أضف input إلى run ما زال شغال، أو غيّر اتجاهه. الاثنين methods على الـ run handle اللي ترجعه `agent.stream()`؛ شوف [Streaming](/ar/streaming).

## Queued input

`run.enqueue(input)` تضيف input من المستخدم (string، أو content parts، أو `Message[]`) إلى run ما زال شغال — مثل متابعة يكتبها المستخدم والـ agent يشتغل. الـ run ما يوقف: الـ input ينضم للـ transcript في أول نقطة آمنة — بعد نتائج tools الخطوة الحالية، وما يدخل أبدًا بين turn فيها tool calls ونتائجها — والـ model call التالية تشوفه كأن المستخدم كتبه بنفسه. والـ input اللي ينضاف للـ queue بينما الـ model يكتب رده الأخير ياخذ خطوة زيادة، فيرد عليه الـ model في نفس الـ run. بادئة `vendor/` في اسم الـ model تحدد الـ provider؛ ومع OpenRouter استخدم `openrouter/<vendor>/<model>` (مثل `openrouter/openai/gpt-4o-mini`).

```ts
import { createAgent } from '@lousho/build-ai-agent';

const agent = createAgent({ model: 'openai/gpt-4o-mini' });
const run = agent.stream('Plan a weekend in Rome.');

const queued = run.enqueue('Keep it under 500 EUR.');
for await (const event of run) {
  if (event.type === 'input.applied') console.log(`applied before step ${event.step}`);
}
if (queued.applied === false || !(await queued.applied)) {
  // The run ended without it: send it as a new turn (e.g. session.send()).
}
```

`enqueue()` ترجع `{ id, applied }`. الـ `id` يطلع في حدثي `input.queued` و`input.applied`. وتكون `applied` بـ`false` لو الـ run كان خلّص أصلًا: الـ input ما اتاخد، فأرسله بنفسك كـ turn جديد (`session.send()`). وإلا فهي promise تتحل إلى `true` أول ما يدخل الـ input الـ transcript، أو إلى `false` لو الـ run وقف قبل الـ model call التالية (انلغى، أو وقف على approval (موافقة)، أو خلصت `maxSteps` أو الـ budget، أو فشل)؛ وحينها الـ input برضه يبقى عليك.

- عدة inputs تنضاف للـ queue قبل نفس الـ model call تتطبق مع بعض، بترتيب ما انضافت.
- مع checkpointing (`sessionId` أو durable session)، الـ input اللي لسه ينتظر ينحفظ على طول في آخر checkpoint الـ run — نفس خانة الـ input المنتظر ورا tool calls بلا نتيجة (شوف [Durable execution](/ar/durable-execution)). لو صار crash أو الـ run فشل، الـ input ما يضيع: `agent.resume()` تطبقه (بس `applied` حق run فشل داخل الـ process تفضل تتحل إلى `false`). أما run خلّص أو وقف أو انلغى فما يحتفظ فيه.
- بدون stream: مرّر `InputQueue` كـ`ExecuteOptions.inputQueue` ونادِ `push()` عليه — هو نفس الـ queue اللي ورا `run.enqueue()`. كل queue يخدم run واحد.
- في الـ session، `agent.session({ turnPolicy: 'queue' })` تخلي أي `send()` أو `stream()` تتنادى وفي turn شغالة (أو مستنية تبدأ) تنضم لنفس الـ turn بنفس الطريقة. شوف [Sessions](/ar/sessions#كائن-الـ-session).

الـ input اللي في الـ queue يستنى الخطوة الشغالة. لو تبغى تغيّر اتجاه الـ run على طول، وجّهه (القسم التالي).

#### متقدم: executor API

بدون stream: مرّر `InputQueue` إلى `AgentExecutor.execute()` (شوف [executor API](/ar/executor-api)):

```ts
import { AgentExecutor } from '@lousho/build-ai-agent/executor';
import { InputQueue } from '@lousho/build-ai-agent';

const inputQueue = new InputQueue();
const pending = AgentExecutor.execute({ agent, provider, input: 'Plan my trip.', inputQueue });
inputQueue.push('Also book a hotel.');
const result = await pending;
```

## Steering

`run.steer(input)` تحوّل run شغال إلى input جديد من المستخدم — مثل لما المستخدم يغيّر رأيه والـ agent لسه يفكّر:

- لو في model call شغالة ولسه ما طلّعت نص ولا tool calls: تنلغى بإشارة abort خاصة فيها، ما هي إشارة الـ run، فالـ run يكمل. ناتجها الجزئي يترمى، و`input` ينضاف كرسالة user، والـ model يتنادى من جديد. تكون `applied` بـ`'immediate'`، وخطوة الـ call الملغية تخلص بـ`step.done` `'steered'`. والـ provider اللي يتجاهل إشارة الـ abort ما نستناه؛ رده المتأخر يترمى.
- لو الـ model طلّع نص أصلًا (أو tool calls)، الـ `input` يستنى النقطة الآمنة التالية مثل [`enqueue()`](#queued-input): وتكون `applied` بـ`'queued'`.
- الـ tool calls اللي شغالة تخلص ونتايجها تنحفظ؛ واللي ما بدأت من نفس الـ turn ما تشتغل وتاخد نتيجة "cancelled before it ran" المعتادة. بعدين يتطبق الـ input.
- `applied` تصير `false` بعد ما الـ run يخلص: أرسل الـ input كـ turn جديد.

```ts
import { createAgent } from '@lousho/build-ai-agent';

const agent = createAgent({ model: 'openai/gpt-4o-mini' });
const run = agent.stream('Plan a weekend in Rome.');

const steered = run.steer('Actually, make it Paris.');
console.log(steered.applied); // 'immediate', 'queued' or false
for await (const event of run) {
  if (event.type === 'input.steered') console.log(`steered (${event.mode})`);
}
console.log(await steered.joined); // true once the input is in the transcript
```

`steer()` ترجع `{ id, applied, joined }`: الـ `id` يطلع في `input.steered` و`input.applied`، و`joined` promise تقول هل الـ input وصل الـ transcript ولا لا (مثل `applied` في `enqueue()`). الـ call الملغية تتحسب خطوة من `maxSteps`. ومع checkpointing، الـ input ينحفظ في آخر الـ checkpoint أول ما يتاخد وقبل ما الـ model يتنادى من جديد — فلو صار crash أثناء التحويل ما يضيع؛ أما الـ turn الجزئي المرموي فما ينحفظ في أي checkpoint أبدًا. وبدون stream، نادِ `steer()` على `ExecuteOptions.inputQueue` حق الـ run. وفي الـ session، `agent.session({ turnPolicy: 'steer' })` تخلي أي `send()` أو `stream()` تتنادى والـ turn شغالة توجّه تلك الـ turn (شوف [Sessions](/ar/sessions#كائن-الـ-session)).
