أغلب الخدمات تنشر مستند OpenAPI وما عندها سيرفر MCP. `openApiTools()`
يحوّل المستند إلى tool واحد typed لكل عملية في الـ API، فيقدر الـ agent
يستدعي الـ API بدون `defineTool()` مكتوبة يدويًا لكل endpoint وبدون
الـ [`http` tool](/ar/tools#tools-مدمجة) الخام. والعمليات التي تغيّر
البيانات تطلب [approval](/ar/approvals) (موافقة) افتراضيًا.

`openApiTools` مُصدَّرة من `@lousho/build-ai-agent` ومن
`@lousho/build-ai-agent/tools`. ما تحتاج أي حزمة إضافية. بادئة الموديل
`vendor/` هي التي تحدد الـ provider؛ ومع OpenRouter استخدم
`openrouter/<vendor>/<model>` (مثل `openrouter/openai/gpt-4o-mini`).

## بداية سريعة

```ts
import { createAgent, openApiTools } from '@lousho/build-ai-agent';

const tools = await openApiTools('https://api.example.com/openapi.json', {
  include: ['getOrder', 'refundOrder'],
  bearerToken: () => process.env.ORDERS_API_TOKEN ?? '',
});

const agent = createAgent({ model: 'openai/gpt-4o-mini', tools });
const paused = await agent.send('Refund order 1042');
// getOrder ran. refundOrder (a POST) is waiting for approval:
// agent.approvals.resolve({ id: paused.approvalId!, approved: true })
```

`openApiTools()` دائمًا async، لأن المستند ممكن يكون URL. ترجع array من
tools تمرّرها إلى `createAgent({ tools })` مثل أي tools أخرى.

`document` ممكن يكون object مُفسَّر لـ OpenAPI 3.0 أو 3.1، أو string بصيغة
JSON أو YAML، أو https URL (string أو `URL`). `openApiTools()` تحلّل
المستند مرة واحدة؛ أما `execute` في الـ tool فلا تفعل إلا بناء الطلب
وإرساله.

## شكل كل tool

| الجزء | القيمة |
| ---- | ----- |
| الاسم | `operationId`، مع استبدال أي حرف خارج `A-Za-z0-9_-` بـ `_`. بدون `operationId`: `<method>_<path>` (`GET /orders/{orderId}` يصير `get_orders_orderId`). مع `prefix`: `<prefix>__<name>`. بحد أقصى 64 حرفًا. وعمليتان بنفس الاسم ترميان `ConfigurationError` يذكر الاثنتين. |
| الوصف | `summary` الخاص بالعملية، ثم `description` (يُقطع عند 1,000 حرف)، ثم الـ method والـ path (`GET /orders/{orderId}`). |
| الـ input | object فيه كل parameter من path وquery وheader وcookie كخاصية top-level (إلزامية كما يصرّح المستند)، إضافة إلى `body` لجسم طلب `application/json`. الـ schemas تتبع إشارات `$ref` داخل `components`، بما فيها `parameters` و`requestBodies`. و`nullable` في OpenAPI 3.0 يعمل. والـ parameter الذي اسمه مأخوذ من موضع آخر يُسمّى `<location>_<name>`. |
| النتيجة | `{ status, statusText, body }` لكل response HTTP، حتى حالات الخطأ، فيقدر الـ model يقرأ 404 ويتصرف بناءً عليه. و`body` يكون JSON مُفسَّر إذا قالت الاستجابة إنها JSON، وإلا text، ويكون `null` إذا كانت فارغة. |
| الأخطاء | فشل الشبكة، والـ timeout، والـ redirect المرفوض — كلها أخطاء tool. |

معاملات الـ header `Accept` و`Content-Type` و`Authorization` تُتجاهل كما
تنص مواصفة OpenAPI؛ استخدم `bearerToken` أو `headers` لبيانات الاعتماد.

## الخيارات

| الخيار | الافتراضي | المعنى |
| ------ | ------- | ------- |
| `baseUrl` | أول مدخل في `servers` | وجهة الطلبات. يتغلّب على المستند. ولمستند جُلب من URL، غياب `servers` يعني الـ origin الخاص بذلك الـ URL. |
| `include` | كل العمليات | أسماء العمليات (`operationId` أو الاسم المشتق)، أو دالة `(op) => boolean`. وتسمية عملية غير موجودة في المستند ترمي خطأً. |
| `exclude` | لا شيء | أسماء العمليات المراد استبعادها. |
| `approval` | `'mutating'` | `'mutating'` أو `'always'` أو `'never'` أو `(op) => boolean`. |
| `prefix` | لا شيء | بادئة لأسماء الـ tools. |
| `headers` | لا شيء | headers تُرسل مع كل طلب، أو دالة تُستدعى لكل طلب. |
| `bearerToken` | لا شيء | اختصار لـ `Authorization: Bearer <token>`؛ وإذا كانت دالة فتُستدعى لكل طلب. |
| `providedArguments` | لا شيء | قيم يزوّدها تطبيقك؛ انظر أدناه. |
| `timeoutMs` | `30000` | لكل طلب. |
| `maxResponseChars` | `50000` | جسم الاستجابة يُقطع عند هذا الطول، مع ملاحظة تقول كم حُذف. |
| `fetch` | `fetch` العامة | تحل محل `fetch` (للاختبارات والـ proxies). ولا يمكن دمجها مع `privateAddresses: 'refuse'`. |
| `privateAddresses` | `'allow'` | `'refuse'` تخلي الطلبات وجلب المستند يفشلان مع عناوين loopback وlink-local والخاصة؛ انظر [قواعد الأمان](#قواعد-الأمان). Node فقط. |
| `allowPrivate` | لا شيء | مع `'refuse'`: hosts (`intranet.example`، `*.corp.example`، أو عنوان IP) يجوز أن تكون عناوين خاصة أو تُحلّ إليها. |

و`op` هو `{ name, operationId?, method, path, summary?, tags }`.

## افتراضيات الـ approval

مع `approval: 'mutating'`، تعمل GET وHEAD وOPTIONS مباشرة، وكل method أخرى
تطلب approval. وكل tool يحمل أيضًا annotations بأسلوب MCP:
`readOnlyHint: true, destructiveHint: false` على GET وHEAD وOPTIONS؛
و`readOnlyHint: false` على الباقي، مع `destructiveHint: true` لـ DELETE.
وأي شيء يقرأ الـ annotations يعامل هذه الـ tools كما يعامل tools الـ MCP.

```ts
import { openApiTools } from '@lousho/build-ai-agent';

declare const spec: object;

// Ask for everything except two reads that are known to be harmless.
const tools = await openApiTools(spec, {
  approval: (op) => !['getOrder', 'listOrders'].includes(op.name),
});
```

## القيم التي يزوّدها تطبيقك

`providedArguments` تملأ الـ parameters التي لا يجب أن يختارها الـ model،
مثل tenant id. المفتاح المزوَّد يُحذف من الـ input schema الخاصة بالـ tool
(فالـ model لا يراه أبدًا) ويُضاف إلى الطلب. والقيمة ممكن تكون دالة،
تُستدعى لكل طلب مع العملية ومعرّف الـ tool call.

```ts
import { openApiTools } from '@lousho/build-ai-agent';

declare const spec: object;
declare const currentTenant: () => string;

const tools = await openApiTools(spec, {
  providedArguments: {
    'X-Tenant-Id': () => currentTenant(),
    accountId: 'acct_123',
  },
});
```

المفتاح هو مفتاح الـ input الخاص بالـ parameter: اسمه، أو `<in>_<name>`
(مثل `query_id`) عندما يتشارك اثنان من الـ parameters في العملية الواحدة
الاسم نفسه؛ ومفتاح جسم الطلب هو `body` (أو `requestBody` عندما يكون
parameter قد أخذ `body` من قبل). والمفتاح الذي لا تمتلكه أي عملية مُختارة
يرمي خطأً، فلا يؤدي خطأ مطبعي إلى كشف الـ parameter للـ model بصمت.

## قواعد الأمان

- **الـ base URL لك أنت، لا للـ model.** الـ model يختار قيم الـ parameters
  والـ body؛ ولا يختار الـ host أبدًا. الـ base URL لازم يكون https. ولا
  يُقبل http العادي إلا لـ `localhost` و`127.0.0.1` و`[::1]`، وأي URL فيه
  اسم مستخدم أو كلمة مرور يُرفض. ونفس القاعدة تنطبق على URL المستند.
- **بيانات الاعتماد لا تصل إلى ما يراه الـ model وسجلاتك.** الـ headers
  والـ tokens لا تدخل أبدًا في الـ input schema الخاصة بالـ tool، ولا في
  حدثي `tool.start` و`tool.done`، ولا في الـ transcript؛ فقط input الـ
  model نفسه والاستجابة. والـ header الذي يزوّده الـ model لـ header
  parameter مُصرَّح به لا يحل محل `headers` أو `bearerToken` أبدًا.
- **الـ redirects تبقى على origin الـ base URL.** الطلبات تستخدم redirects
  يدوية: يُتبَع 3 على الأكثر، وفقط إلى نفس الـ origin الخاص بالـ base URL.
  والـ redirect إلى origin آخر هو خطأ tool، فالـ token لا يغادر الـ origin
  المُعَدّ أبدًا.
- **قيم الـ path تبقى داخل المقطع الخاص فيها.** معاملات الـ path تُرمَّز
  percent-encoded (فلا يقدر `../admin` يطلع خارج مقطعه)، والقيمة
  التي تساوي `.` أو `..` تمامًا تُرفض.
- **العناوين الخاصة: لا فحص افتراضيًا، و`privateAddresses: 'refuse'`
  يفعّله.** افتراضيًا الـ tools تنادي الـ base URL الذي أعددته أنت، أينما
  حُلّ: عناوين الـ base لك وغالبًا داخلية. وعندما لا يكون الـ base URL أو
  URL المستند تحت سيطرتك الكاملة (اسم يجيب عليه DNS شخص آخر، أو مستند
  تجلبه من مكان آخر)، مرّر `privateAddresses: 'refuse'`. عندها يُرفض كل
  طلب operation وجلب المستند، بما فيها كل hop في الـ redirect، إذا كان
  الـ host عنوانًا أو يُحل إلى عنوان loopback أو link-local أو خاص أو
  shared أو multicast أو محجوز (نفس القائمة التي يستخدمها `http_request`،
  بما فيها NAT64 و6to4). أسماء الـ hosts تُفحص بنفس الـ DNS lookup
  المثبَّت الذي يستخدمه `http_request` و`web_fetch`: الـ host يُحل مرة
  واحدة لكل اتصال، وكل عنوان يُفحص، والـ socket يتصل بالعنوان الذي فُحص،
  فاسم DNS-rebinding (عام للفحص، و`127.0.0.1` للاتصال) لا يصل إلى عنوان
  خاص أبدًا. والـ IP literals بأي صيغة يقبلها `URL` (`2130706433`،
  `0x7f000001`، `0177.0.0.1`، `[::ffff:127.0.0.1]`) وأسماء `localhost` /
  `*.localhost` تُرفض عند إنشاء الـ tools، كـ `ConfigurationError`. الـ
  model لا يقدر ينقل طلبًا إلى host آخر: قيم الـ path تُرمَّز
  percent-encoded داخل مقطعها، ومتغيرات server URL تأخذ فقط القيم
  الافتراضية للمستند، والـ redirects تبقى على origin الأساس. ضع الـ hosts
  الداخلية الخاصة بك في `allowPrivate` (`allowPrivate: ['localhost']`
  لواجهة محلية). والطلب المرفوض هو خطأ tool يذكر الـ host، ولا يذكر أبدًا
  العناوين التي حُلّ إليها.
  `'refuse'` لا يمكن دمجه مع `fetch`: الـ `fetch` المخصصة تحل الأسماء
  بنفسها، فلا يقدر الفحص يثبّت العنوان الذي تتصل به، وإنشاء الـ tools يرمي
  خطأً بدل أن يفحص نصف الطريق فقط. ومع `fetch` الخاصة بك (أو proxy)، افحص
  الوجهات هناك. `'refuse'` يحتاج Node.js (`undici` و`node:dns`)؛ وعلى
  runtime بدونهما، إنشاء الـ tools يرمي `ConfigurationError` بدل إرسال
  طلبات غير مفحوصة. وفي Cloudflare Workers لا تتوفّر `openApiTools`.

## الـ APIs الكبيرة

واجهة فيها مئات العمليات تعني مئات الـ tools. أعطِ الـ agent ما يحتاجه
بـ `include` أو `exclude`، أو بـ predicate على `op.tags`:

```ts
import { openApiTools } from '@lousho/build-ai-agent';

declare const spec: object;

const tools = await openApiTools(spec, { include: (op) => op.tags.includes('orders') });
```

## الحدود

- OpenAPI 3.0 و3.1 فقط. ومستند Swagger 2.0 يرمي `ConfigurationError`
  يطلب منك تحويله أولًا.
- أجسام الطلبات لازم تكون JSON (`application/json` أو `+json`). والعملية
  التي ليس لها إلا جسم multipart أو form أو XML تُستبعد؛ وتسميتها في
  `include` ترمي خطأً.
- يُستخدم فقط أول مدخل في `servers`، والمتغيرات بقيمها الافتراضية.
  وتُتجاهل `servers` على مستوى الـ path وعلى مستوى العملية.
- كل `$ref` لازم يكون محليًا (`#/components/...`)؛ والإشارة إلى ملف آخر
  أو URL ترمي خطأً. اعمل bundle للمستند أولًا.
- لا يوجد OAuth flows. و`bearerToken` و`headers` يغطّيان بيانات الاعتماد
  الثابتة والمتغيرة لكل طلب.
- أجسام الاستجابات تُقرأ نصًا، وما في streaming لها.
