## المتطلبات

- Node.js **22.19 أو أحدث** (`engines.node` في `package.json`، والرقم مفروض من الاعتمادية `undici@8`، التي تضع هي نفسها `engines` على `>=22.19.0`. ميزات Node الأخرى المرتبطة بإصدار معيّن والتي تستخدمها الـ SDK هي `node:sqlite` لـ `SqliteStore` (22.13) وإزالة الأنواع المدمجة (native type stripping) لملفات الـ agent بصيغة `.ts` (22.18)، وكلتاهما تحت هذا الحد الأدنى، فخفضه يعني تخفيف قيد اعتمادية `undici` أولًا. و`undici` لا تُحمَّل إلا عندما ترسل الأداة `http_request` أو `web_fetch` طلبًا، راجع [Optional peers](#optional-peers)).
- TypeScript اختيارية لكننا ننصح بها — الـ SDK تأتي مع type definitions كاملة.

## تثبيت الحزمة

```bash
npm install @lousho/build-ai-agent ai zod
# or
pnpm add @lousho/build-ai-agent ai zod
# or
yarn add @lousho/build-ai-agent ai zod
```

`ai` (وهي Vercel AI SDK: `^4.3.19` أو `^6.0.0` أو `^7.0.0`) و`zod` (`^3.25.76 || ^4.0.0`) peer dependencies إجبارية. الإصدار `ai` 5 غير مدعوم.

أي schema من الإصدارين الرئيسيين لـ zod تشتغل في كل مكان تقبل فيه الـ SDK schema: `defineTool({ input })`، و`output` منظَّم، وأدوات MCP. يشمل هذا schemas من zod 4 عبر `zod/v4` مع zod 3.25 مثبت، وschemas من zod 3 عبر `zod/v3` على zod 4. حقل `input` في `defineTool` يمكن أن يكون أيضًا schema من مكتبة [Standard Schema](https://standardschema.dev) أخرى، إذا كانت تكشف الـ JSON Schema الخاصة بها (`~standard.jsonSchema`). الـ model يحتاج JSON Schema، فأي Standard Schema بلا واحدة تُرفض — استخدم zod لتلك الأدوات. حزم الـ providers الخاصة بـ `ai` 4 تعلن zod 3 كـ peer dependency، فاقرن zod 4 مع `ai` 6 أو 7.

### حزم الـ providers

كل provider حقيقي لـ LLM يعتمد على peer dependency اختيارية، بالإصدار الرئيسي الذي يتوافق مع إصدار `ai` لديك. ثبّت الزوج من صف واحد:

| `ai`      | OpenAI وOpenRouter: `@ai-sdk/openai` | Anthropic: `@ai-sdk/anthropic` | Google: `@ai-sdk/google` | Ollama                                 |
| --------- | ------------------------------------ | ------------------------------ | ------------------------ | -------------------------------------- |
| `^4.3.19` | `^0.0.42` (أو `^1.0.0`)              | `^0.0.42` (أو `^1.0.0`)        | `^1.2.0`                 | `ollama-ai-provider@^1.2.0`            |
| `^6.0.0`  | `^3.0.0`                             | `^3.0.0`                       | `^3.0.0`                 | `ollama-ai-provider-v2@^3.0.0` (zod 4) |
| `^7.0.0`  | `^4.0.0`                             | `^4.0.0`                       | `^4.0.0`                 | `ollama-ai-provider-v2@^4.0.0` (zod 4) |

على الإصدار الرئيسي الحالي من `ai` مثلًا:

```bash
npm install @lousho/build-ai-agent ai@^7.0.0 zod @ai-sdk/openai@^4.0.0
```

**Ollama على `ai` 6/7 يحتاج zod 4.** الحزمة `ollama-ai-provider-v2` (حزمة Ollama لـ `ai` 6 و7) تعلن `zod ^4` كـ peer dependency. الـ SDK تقبل zod 4، فثبّتها مع zod 4، مثلًا `npm install ai@^7.0.0 ollama-ai-provider-v2@^4.0.0 zod@^4.0.0`. مع zod 3 استخدم `ai@^4.3.19` مع `ollama-ai-provider@^1.2.0`. و`lousho init --provider ollama` ينشئ المشروع بـ `ai@^7.0.0` و`ollama-ai-provider-v2@^4.0.0` وzod 4.

**ما يختبره CI.** كل تركيبة تقبلها نطاقات الـ peers تُثبَّت فعلًا وتمر على فحص الأنواع والـ build ومجموعة الاختبارات كاملة، مع كل تغيير: `ai` 4 مع zod 3 (هو تثبيت التطوير) ومع zod 4، و`ai` 6 مع zod 3 ومع zod 4، و`ai` 7 مع zod 3 ومع zod 4. حالتا zod 4 على `ai` 6 و7 تثبّتان أيضًا `ollama-ai-provider-v2` (3.x و4.x) وتشغّلان provider الخاص بـ Ollama عليه، فدعم Ollama على `ai` 6/7 مُختبَر فعلًا وليس مفترَضًا.

الـ peers تُحمَّل عند الطلب: استيراد `@lousho/build-ai-agent` (أو أي من مداخلها الفرعية) لا يحمّل أي حزمة provider، فثبّت فقط التي تستخدمها. حزمة كل provider تُحمَّل أول مرة يجري فيها ذلك الـ provider استدعاء. إذا كانت ناقصة، يفشل الاستدعاء بـ `MissingPeerDependencyError` يحمل الأمر الدقيق الذي عليك تشغيله، بما يناسب إصدار `ai` الرئيسي المثبت عندك. بادئة النموذج `vendor/` هي التي تحدد الـ provider؛ مع OpenRouter استخدم `openrouter/<vendor>/<model>` (مثل `openrouter/openai/gpt-4o-mini`). مع `ai` 4:

```bash
npm install @ai-sdk/openai@^0.0.42
```

```ts
import { MissingPeerDependencyError, resolveProvider } from '@lousho/build-ai-agent';

const provider = resolveProvider('openai/gpt-4o-mini'); // needs OPENAI_API_KEY; does not load the peer
try {
  await provider.generate({ messages: [{ role: 'user', content: 'hello' }] });
} catch (error) {
  if (error instanceof MissingPeerDependencyError) {
    console.error(error.packageName, error.installCommand);
  }
}
```

### Optional peers

هذه الحزم أيضًا peer dependencies اختيارية. مشروع لا يستخدم أبدًا Docker sandboxing ولا MCP ولا OpenTelemetry tracing ولا bindings لـ React أو Vue ولا `lousho build` ولا أسئلة `lousho init` ولا code mode، لا يثبّت أيًّا منها:

| الحزمة                      | النطاق    | تتيح                                                                                            | التثبيت                                          |
| --------------------------- | --------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| `dockerode`                 | `^5.0.1`  | Docker sandboxing: `SubprocessSandbox` (وفحص `lousho doctor` للاتصال بـ Docker)                | `npm install dockerode@^5.0.1`                   |
| `@modelcontextprotocol/sdk` | `^1.31.0` | MCP: `createAgent({ mcpServers })` / `connectMcp()`، و`serveMcp()`، و`lousho mcp`              | `npm install @modelcontextprotocol/sdk@^1.31.0`  |
| `@opentelemetry/api`        | `^1.9.1`  | OpenTelemetry tracing: `createOtelTraceExporter()` من `@lousho/build-ai-agent/otel`            | `npm install @opentelemetry/api@^1.9.1`          |
| `react`                     | `^18`، `^19` | React bindings (`@lousho/build-ai-agent/react`)                                             | `npm install react`                              |
| `vue`                       | `^3`      | Vue bindings (`@lousho/build-ai-agent/vue`)                                                    | `npm install vue@^3`                             |
| `tsup`                      | `^8.0.0`  | `lousho build`، الذي يجمّع الـ agent لكل target                                                 | `npm install --save-dev tsup@^8.0.0`             |
| `prompts`                   | `^2.4.2`  | الأسئلة التفاعلية في `lousho init` (`lousho init --yes` والـ flags لا تحتاج شيئًا)             | `npm install prompts@^2.4.2`                     |
| `quickjs-emscripten`        | `^0.32.0` | [Code mode](/ar/code-mode): `createAgent({ codeMode })` يشغّل سكربتات `run_code` داخل isolate من QuickJS | `npm install quickjs-emscripten@^0.32.0` |

مثل حزم الـ providers، كل واحدة تُحمَّل عند أول استخدام وليس وقت الاستيراد. الناقصة منها تفشل ذلك الاستدعاء بـ `MissingPeerDependencyError` يذكر الميزة والأمر الدقيق، مثلًا:

```text
The optional package 'dockerode' is not installed, but Docker sandboxing (SubprocessSandbox) needs it. Run: npm install dockerode@^5.0.1
```

`npm create lousho-agent` يثبّت `prompts` بنفسه، فالـ scaffolding به لا يحتاج شيئًا إضافيًّا. و`lousho doctor` يسرد كل peer dependency اختيارية: ماذا تتيح وهل هي مثبتة (غياب `dockerode` خطأ فقط إذا كان ملف مواصفات الـ agent يستخدم أداة داخل sandbox).

`undici` و`yaml` تبقيان اعتماديتين عاديتين. `yaml` تحلّل ملفات مواصفات الـ agents وملفات `agent.yaml` والـ skills، وليس في Node parser مدمج لـ YAML. أما `undici` فتُحمَّل عند أول طلب تجريه `http_request` أو `web_fetch`: كلتاهما تتصل عبر `Agent` من undici يفحص العنوان في DNS lookup ويثبّت الاتصال عليه، و`http_request` تحصر أيضًا `validateSSL: false` في ذلك `Agent`. الـ `fetch` العامة لا توفّر أيًّا من هذين السلوكين.

### حجم الحزمة

الـ tarball حجمه نحو 4 MB مضغوطًا (15 MB بعد فك الضغط). هذه مقايضة مقصودة ومعلنة، لا مصادفة: المجلد `src/` يُشحن لأن `lousho build` يجمّع `src/deploy/runtime.worker.ts` و`src/index.ts` من الحزمة المثبتة، ولأن source maps في `dist/` تشير إليه (الـ maps لا تحمل الكود المصدري مضمَّنًا فيها؛ وتضمينه بدلًا من ذلك مع حذف `src/` أعطى حجمًا أكبر عند القياس، 5.2 MB مضغوطًا). أما `apps/agent-forge/` فهي لوحة التحكم المبنية مسبقًا التي يقدّمها `lousho studio`. والملف `llms-full.txt` بحجم 1 MB موجود في المستودع، لا في الحزمة.

## نقاط الدخول تتشارك الكود (ESM وCJS)

مداخل الحزمة (`.` و`./hooks` و`./tools` و`./mcp` وغيرها) مبنية بـ code splitting: تستورد chunks مشتركة من `dist/`. لذلك class أو singleton مثل `HookRegistry` أو `SDKError` أو `globalToolRegistry` هو الكائن نفسه أيًّا كان المدخل الذي يصدّره وتستورده أنت منه، ضمن صيغة modules واحدة (`globalToolRegistry` يصدّره `./executor` و`./tools`، لا الجذر). لكن `import` من ESM و`require` من CJS للحزمة في عملية واحدة يحمّلان نسختين منفصلتين (dual-package hazard المعروف في Node)، فالـ class من إحداهما ليس `===` نظيره من الأخرى. `instanceof SDKError`، و`instanceof` لكل subclass من `SDKError` تصدّرها الـ SDK (`ValidationError` و`TimeoutError` و`RateLimitError` و`LLMProviderError` و`MissingPeerDependencyError` وغيرها)، و`instanceof HookRegistry`، كلها آمنة بين النسختين لأنها تفحص علامة `Symbol.for`؛ لبقية الـ classes استخدم صيغة modules واحدة في العملية.

نقاط الدخول التي يصرّح بها `exports`، وماذا تحتوي كل واحدة:

### إعدادات TypeScript

ملفات الـ declarations تجتاز فحص الأنواع مع `skipLibCheck: false` على zod 3 وzod 4، ومع `moduleResolution` بالقيم `bundler` و`nodenext` و`node16` (ESM). تركيبة واحدة فقط تفشل، وسببها من المصدر الأعلى (upstream): مشروع CommonJS (بلا `"type": "module"`) مع `module`/`moduleResolution: "node16"` و`ai` 7. فـ `ai` 7 تُشحن كـ ES modules فقط، ووضع node16 في TypeScript لا يسمح لكود CommonJS باستيراد تلك الأنواع (الخطأ TS1479 داخل declarations الخاصة بالـ SDK). استخدم `"module": "nodenext"` (يحلّها) أو `"moduleResolution": "bundler"`، أو أضف `"type": "module"`، أو أبقِ `skipLibCheck: true` (وهو ما تستخدمه مشاريع `lousho init`).

declarations المدخل الجذر تستخدم أنواع Node (`Buffer`، واستيرادات من `node:crypto` و`node:http` و`node:net`)، فثبّت `@types/node`. TypeScript 6 لم تعد تحمّل كل حزم `@types` افتراضيًّا (القيمة الافتراضية لـ `types` صارت `[]`)، فعلى TypeScript 6 وما بعدها أضفها أيضًا في `tsconfig.json`، وإلا سيُبلغ `skipLibCheck: false` عن `Cannot find name 'Buffer'` و`Cannot find module 'node:http'` داخل declarations الخاصة بالـ SDK:

```json
{
  "compilerOptions": {
    "types": ["node"]
  }
}
```

## التثبيت من build محلي

لتجربة commit غير منشور، اعمل build للـ SDK وحزّمها من checkout محلي لهذا المستودع، ثم ثبّت الـ tarball في مشروعك. هي الطريقة نفسها التي يستخدمها `lousho init --sdk-path` في المشاريع التي ينشئها. الـ CI يتحقق منها عبر `npm run pack-smoke`، الذي يثبّت الـ tarball في مشروع جديد ويحمّل كل نقطة دخول، في ESM وCJS:

```bash
# in the SDK checkout
npm install
npm run build
npm pack --pack-destination /path/to/your-project

# in your project (peers come from the registry)
npm install ./lousho-build-ai-agent-<version>.tgz ai zod
```

ولعمل scaffold لمشروع جديد بالطريقة نفسها، من الـ checkout: `node bin/lousho.js init ../my-agent --sdk-path .`.

على Windows، الأمر `npx C:\abs\path\create-lousho-agent-<version>.tgz` لا يفعل شيئًا بصمت (سلوك غريب في npm مع المسارات المطلقة التي تبدأ بحرف قرص). استخدم بدلًا منه مسارًا نسبيًّا (`npx ./create-lousho-agent-<version>.tgz my-agent`) أو صيغة `file:` (`npx file:C:/abs/path/create-lousho-agent-<version>.tgz my-agent`).

الأمر `npm install github:LinuxDevil/agent-sdk` **لا** يعمل: `dist/` غير موجود في git، وليس في المستودع خطوة `prepare` تعمل build، فينتهي التثبيت بلا نقاط دخول.

## إنشاء مشروع جديد

`lousho init` ينشئ مشروعًا جاهزًا للتشغيل: `package.json` (ESM، ويعتمد على هذه الـ SDK بنطاق إصدار)، و`tsconfig.json` strict، و`src/agent.ts` يستدعي `createAgent({ model, instructions })` مع أداة مثال معرَّفة بـ `defineTool()`، و`src/agent.test.ts` يشتغل offline باستخدام `mockModel`، و`.env.example` يذكر اسم متغير مفتاح الـ provider عندك، و`.gitignore`، وREADME. بعدها يثبّت الاعتماديات ويشغّل `git init`.

```bash
npm create lousho-agent my-agent         # or: npx @lousho/build-ai-agent init my-agent
npx @lousho/build-ai-agent init my-agent --yes --provider anthropic --template tools --no-install
```

| الخيار | المعنى |
| ---- | ------- |
| `--provider openai\|anthropic\|openrouter\|ollama` | الافتراضي: الـ provider الذي متغير مفتاح API الخاص به مضبوط، وإلا `openai`. |
| `--template minimal\|tools\|yaml` | `minimal` (أداة واحدة)، أو `tools` (ثلاث أدوات)، أو `yaml` (ملف مواصفات `agent.yaml` يشغّله `lousho dev`). الافتراضي `minimal`. |
| `--package-manager npm\|pnpm\|yarn\|bun` | الافتراضي: الذي شغّل الأمر (`npm_config_user_agent`)، وإلا `npm`. |
| `--yes`, `-y` | لا يسأل أبدًا؛ يستخدم الافتراضيات لكل ما لم تحدده. الأسئلة تظهر فقط على terminal. |
| `--no-install`, `--no-git` | يتخطى تثبيت الاعتماديات / `git init`. |
| `--force` | يكتب في مجلد غير فارغ (وإلا يرفض `init`). |
| `--sdk-path <dir\|tarball>` | لتطوير الـ SDK: يعتمد على checkout (يُحزَّم بـ `npm pack`) أو على `.tgz` محزَّم بدل الإصدار المنشور. يُقرأ أيضًا من `LOUSHO_SDK_PATH`. |

`create-lousho-agent` (`packages/create-lousho-agent`) مجرد غلاف بسيط يشغّل `lousho init` بنفس الوسائط.

## الـ CLI `lousho`

تثبيت الحزمة يثبّت أيضًا أمر `lousho`: `init` و`doctor` و`dev` و`chat` و`acp` و`add` و`mcp` و`eval` و`traces` و`build` و`studio`. راجع [الـ CLI](/ar/cli) لما يفعله كل واحد وخياراته. الـ build يحتاج `tsup`، وهي peer dependency اختيارية (راجع الجدول أعلاه): `npm install --save-dev tsup`.


ما يفحصه:

1. إصدار Node عندك مقابل `engines.node` في الحزمة.
2. الـ peers الإجبارية `ai` و`zod`: مثبتة وضمن نطاق `peerDependencies` الخاص بالـ SDK (يُحلَّ من المجلد الحالي).
3. حزم الـ providers الاختيارية (`@ai-sdk/openai` و`@ai-sdk/anthropic`، و`ollama-ai-provider` على `ai` 4 أو `ollama-ai-provider-v2` على `ai` 6/7)، مع أمر `npm install` لكل ناقصة. حزمة provider لا تتوافق مع `ai` المثبت (مثلًا `ai` 7 مع `@ai-sdk/openai` 1.x) تُعلَّم مع الإصدار الذي عليك تثبيته بدلًا منها.
4. هل متغير مفتاح API لكل provider مضبوط. يُطبع فقط اسم المتغير و`set` أو `not set`، ولا تُطبع القيمة أبدًا. وعندما يكون `OPENAI_BASE_URL` أو `ANTHROPIC_BASE_URL` مضبوطًا (سيرفر محلي أو متوافق مع OpenAI)، يعرض سطر ذلك الـ provider أيضًا الـ base URL، بلا أي بيانات اعتماد أو query string فيه. ويعرض أيضًا أي provider سيختاره `createAgent()` افتراضيًّا في بيئتك. ويُعرض `OPENAI_BASE_URL` عندما يكون مضبوطًا (بلا أي بيانات اعتماد أو query فيه).
5. مع مسار ملف مواصفات (`lousho doctor agent.yaml`): تُتحقَّق صحة الملف مع مسارات الحقول لكل خطأ، وتُفحص حزمة الـ provider والمفتاح (الناقص منهما يصبح إخفاقًا)، ويجب أن تكون عناصر `tools` أدوات مدمجة، وأن يكون أي أمر في `mcpServers` قابلًا للحل. أما مجلد agent أو module لـ agent بصيغة `.ts`/`.js` (`lousho doctor src/agent.ts`، وهو ما يشغّله `npm run doctor` في مشروع مُنشأ بـ scaffold) فيُحمَّل بالطريقة التي يحمّله بها `lousho dev`، وتُفحص حزمة الـ provider الخاصة بالـ model ومفتاحه بالطريقة نفسها. بدون مسار، غياب المفتاح مجرد تحذير، لأن doctor لا يمكنه معرفة أي provider يستخدمه الـ agent عندك.
6. إمكانية الوصول إلى Ollama — فقط إذا استخدم ملف المواصفات Ollama أو كان `OLLAMA_HOST` مضبوطًا.
7. توفر Docker — تحذير فقط إذا استخدم ملف المواصفات أداة داخل sandbox.
8. مع `--ping`: طلب `GET` لكل provider متغيره مضبوط، بمهلة 5 ثوانٍ، إلى endpoint يتطلب المفتاح: `/models` لـ OpenAI وAnthropic، و`/api/v1/key` لـ OpenRouter (لأن `/models` عنده يجيب بلا مفتاح). المفتاح المرفوض (HTTP 401/403) إخفاق؛ والسيرفر الذي لا يمكن الوصول إليه تحذير. مع ضبط `OPENAI_BASE_URL` يُرسل ping إلى `<base>/models`، ويوضّح السطر أنه يبيّن إمكانية الوصول فقط، لأن السيرفر المحلي قد لا يتحقق من المفاتيح. المفاتيح تُرسل إلى الـ provider الخاص بها فقط ولا تُطبع أبدًا.

على Windows تستخدم أسطر الإصلاح صيغة PowerShell (`$env:OPENAI_API_KEY="<your key>"`) بدلًا من `export`.

رمز الخروج `1` إذا فشل أي فحص و`0` غير ذلك (التحذيرات لا تفشل)، فيصلح بوابة لـ CI. أضف `--json` لمخرجات تقرؤها الآلة. الألوان تُستخدم فقط عندما يكون stdout على terminal و`NO_COLOR` غير مضبوط.

للمشكلات غير المتعلقة بالتثبيت، راجع [استكشاف الأخطاء وإصلاحها](/ar/troubleshooting).
