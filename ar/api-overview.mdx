## بناء الـ agents وتشغيلها

| Export                        | الوصف                                                                 |
| ----------------------------- | --------------------------------------------------------------------------- |
| `createAgent(config)`         | agent بدون إعدادات بواجهة `{ send(message) }`، من string في `model` أو من provider (مع instructions وtools). |
| `AgentBuilder` (من `lousho/executor`) | builder بأسلوب fluent لـ `AgentConfig` (`AgentBuilder.create().setName(...)...build()`). متقدم: راجع [واجهة الـ executor](/ar/executor-api). |
| `AgentExecutor.execute(opts)` (من `lousho/executor`) | executor ساكن (static): يشغّل agent (LLM + حلقة tool calls) ويعيد `ExecutionResult`. متقدم: راجع [واجهة الـ executor](/ar/executor-api). |
| `resumeAfterApproval()` (من `lousho/executor`) | استئناف execution متوقف على approval (موافقة) بشري. متقدم: راجع [واجهة الـ executor](/ar/executor-api). |
| `InMemoryApprovalStore`       | `ApprovalStore` محلي داخل الـ process؛ هو الـ store الافتراضي للـ agents التي تُنشأ بـ `createAgent()`. |
| `StorageServiceApprovalStore`, `LocalStorageCheckpointStore` (من `/utils`) | stores للـ approvals والـ checkpoints مبنية على ملفات فوق `StorageService` (راجع [Approvals](/ar/approvals) و[Durable execution](/ar/durable-execution)). |
| `SqliteStore` (من `/sqlite`) | sessions وcheckpoints وapprovals في ملف SQLite واحد (راجع [Sessions](/ar/sessions#choosing-a-store)). |
| `fileStore(dir)`              | sessions وcheckpoints وapprovals كملفات JSON عادية تحت `dir` (راجع [Sessions](/ar/sessions#choosing-a-store)). |
| `KVStore`, `KVCheckpointStore` (من `/kv`) | stores على binding من Cloudflare Workers KV، لـ Worker تكتبه بنفسك (راجع [النشر](/ar/deployment)). |
| `AgentStore`, `memoryStore()` | خيار `createAgent({ store })`: `{ sessions?, checkpoints?, approvals?, tokens? }`، وواحد يعمل في الذاكرة (راجع [Sessions](/ar/sessions#choosing-a-store)؛ `tokens` يحتوي tokens الـ OAuth، راجع [OAuth](/ar/oauth)). |
| `SessionAwaitingApprovalError` | يرميه `execute()` إذا كان الـ `sessionId` الممرّر متوقفًا على approval (راجع [Durable execution](/ar/durable-execution)). |
| `SDKError`, `ERROR_CODES`    | الكلاس الأساس لأخطاء الـ SDK: `code` ثابت و`hint` ورابط `docs` (راجع [الأخطاء](/ar/errors)). |

### Dynamic config

`model` و`instructions` و`tools` في `createAgent()` كل خيار منها
يقبل القيمة الثابتة أو دالة على الـ run: `(ctx) => value | Promise<value>`
(النوع `PerRun<T>`). الـ `ctx` هو `{ sessionId?, input, metadata?, principal? }` (النوع
`RunConfigContext`): فيه الـ `sessionId` الممرّر لـ `send()` / `stream()` أو معرّف
`agent.session()`، وإدخال المستخدم في الـ run، وخيار الاستدعاء `metadata` في
`send()` و`stream()` و`session.send()` و`session.stream()`، والمتصل الذي قبلته
مصادقة الـ run (`principal`، يغيب إذا لم يمرّر الاستدعاء متصلًا). تُنفَّذ الدوال
مرة واحدة عندما يبدأ الـ run، قبل أول model call، ومرة أخرى في كل turn في الـ
session. وكل شيء آخر ينطبق على ما تعيده: `fallbackModels` و`retry` و
`projectInstructions` والـ memory والـ skills والـ sub-agents وtools الـ MCP
والصلاحيات والـ approvals والـ guardrails. وإذا استخدمت agent ديناميكيًا كـ
sub-agent، يكون الـ `input` هو task prompt، ويأخذ `sessionId` و`metadata` و
`principal` من run الـ agent الرئيسي.

```ts
import { createAgent, defineTool } from 'lousho';
import { mockModel } from 'lousho/testing';
import { z } from 'zod';

const refund = defineTool({ name: 'refund', description: 'Refunds an order', input: z.object({ orderId: z.string() }), execute: async () => 'ok' });

const agent = createAgent({
  provider: mockModel(['Hello!']),
  // A cheaper model for short inputs, tenant instructions, tools by role.
  model: ({ input }) => (typeof input === 'string' && input.length < 200 ? 'small-model' : 'large-model'),
  instructions: ({ metadata }) => `You are the support agent of ${String(metadata?.tenant ?? 'Acme')}.`,
  tools: ({ metadata }) => (metadata?.role === 'admin' ? [refund] : []),
});

await agent.send('Hi', { metadata: { tenant: 'Globex', role: 'admin' } });
```

إذا رمت الدالة خطأً، يفشل الـ run بـ `LOUSHO_CONFIG_RESOLVER_FAILED`
(`error.field` يسمّي الخيار، و`error.cause` هو الخطأ المرمي): `send()` يرفض،
و`stream()` ينتهي بحدث `error`، وتحتفظ الـ session بالـ transcript كما كان.
الـ run المتوقف على approval أو سؤال يحتفظ بالـ `ctx` وبالـ model الذي حسمه في
snapshot التوقف: استئنافه، حتى من process أخرى، يستخدم ذلك الـ model (لا
يتبدّل أبدًا في منتصف الـ turn) ويستدعي دالة `tools` مرة أخرى بالـ `ctx` نفسه.
أما الـ run المستأنف من checkpoint بعد crash (`agent.resume(id)`) فيُحسب من
جديد مع `input: []` ودون `metadata`. وإذا كانت كل القيم ثابتة، لا يتغير شيء: يُبنى
الـ agent مرة واحدة عندما تنشئه.

### UI bindings

`lousho/react` يصدّر `useLoushoAgent(source, options?)`، وهو
React hook يشغّل agent داخل الـ process نفسه (`{ agent, sessionId? }`) أو عبر HTTP
(`{ url }`)، ويعيد `messages` و`status` و`pendingApproval` و
`send()` و`stop()` و`approve()` و`reject()`. أجزاؤه المحايدة عن الـ framework —
`reduceAgentEvents()` و`parseEventStream()` — مُصدّرة أيضًا. راجع
[React](/ar/react). `lousho/vue` يصدّر `useLoushoAgent()` نفسه
كـ composable لـ Vue 3، والحالة فيه refs. راجع [Vue](/ar/vue). و
`lousho/svelte` يصدّر `loushoAgent()`، الحالة والأفعال نفسها كـ
Svelte store (`$agent`). راجع [Svelte](/ar/svelte).

### Sub-agents

مرّر `subagents: { researcher, writer }` (agents من `createAgent()` لكل واحد منها
`description`، أو catalog بصيغة `{ list, resolve }`) إلى `createAgent()` أو
`AgentExecutor.execute()`. الـ agent الرئيسي يحصل على tool باسم `task` للتفويض،
وعلى tools المهام الخلفية الثلاث `agent_status` و`agent_await` و`agent_cancel`،
وعلى قائمة بالـ sub-agents في الـ prompt. كل sub-agent يعمل على task prompt
خاص به، ويرث من run الـ agent الرئيسي: الـ signal والـ hooks (`ctx.subagent`)
والـ tracing وstore الـ approvals وevent listeners (`event.subagent`).
`maxSubagentDepth` (الافتراضي 1) يحدّ عمق التداخل. راجع
[Sub-agents](/ar/sub-agents).

### Approvals

الـ agent الذي تبنيه بـ `createAgent()` يتوقف مؤقتًا عند tool عليها `needsApproval`
بدلًا من أن يفشل: `send()` (و`session.send()`) يعيد `finishReason: 'awaiting-approval'`
مع `approvalId`. `agent.approvals.list()` يعيد الاستدعاءات المعلّقة، و
`agent.approvals.resolve({ id, approved, note? })` ينفّذ الاستدعاء أو يرفضه
ويعيد نتيجة الـ run بعد أن يكتمل (يكمل الـ session نفسها التي توقف فيها).
تُحفظ التوقفات في `InMemoryApprovalStore` خاص بكل agent إلا إذا مرّرت
`approvalStore` (مثل `SqliteStore.approvals`) أو `store`. والخيار
`approve: (request: PendingApproval) => boolean | string | Promise<boolean | string>`
يحسم كل استدعاء من الكود دون توقف (`stream()` يظل ينتهي عند التوقف) —
`request` يحمل الاستدعاء مع `kind` و`principal`. ومع `askQuestion: true` يستطيع
الـ agent أن يسأل المستخدم (`kind: 'question'`)، وتجيب بـ
`agent.approvals.answer({ id, answer })`. راجع [Approvals](/ar/approvals).

### Structured output

مرّر `output: zodSchema` إلى `createAgent()` (أو `AgentExecutor.execute()` /
`stream()`): يجب أن يكون الرد الأخير كائن JSON يطابق الـ schema، و
`send()` / `run.result` يعيده بعد الـ validation كـ `result.object` بالنوع
`z.output<typeof schema>` (`result.text` يحتفظ بـ JSON الخام). الـ tools
تعمل أولًا كالمعتاد. كل model call يحمل hint باسم
`responseFormat: { type: 'json', schema }`، وتحوّله providers الـ `ai` SDK
إلى JSON mode. الرد غير الصالح يحصل على خطوة repair واحدة تسرد المشكلات (تُحسب
من `maxSteps`)؛ وإذا ظل غير صالح، ينتهي الـ run بـ
`finishReason: 'output-invalid'` و`outputError: { message, issues }`. راجع
[Structured output](/ar/structured-output).

### Skills

مرّر `skills: [defineSkill({ name, description, content }), ...(await loadSkills(dir))]`
إلى `createAgent()` أو `AgentExecutor.execute()`: الأسماء والأوصاف فقط تدخل الـ
system prompt، والـ model يحمّل محتوى كل skill عبر tool باسم `load_skill`
تُسجَّل تلقائيًا. راجع [Skills](/ar/skills).

### الذاكرة

مرّر `memory: [defineMemory({ name, scope, provider })]` إلى `createAgent()`
لكي تحتفظ بعناصر عبر المحادثات: كل run يستحضر أحدث عناصر كل slot في الـ
system prompt عند أول model call، والـ model يحصل على tools باسم
`remember_<name>` / `recall_<name>`. الـ `scope` إما `'global'` أو `'session'`
أو دالة على `{ sessionId, metadata }`. `inMemoryMemory()` و
`fileMemory({ dir })` هما الـ providers المدمجة. راجع [الذاكرة](/ar/memory).

### Durable execution

مع `sessionId` + `checkpointStore` يصبح الـ run آمنًا من الـ crash والـ session
متعددة الـ turns: يُوضع للـ run checkpoint بعد كل رد من الـ model وكل نتيجة
tool وكل توقف مؤقت، واستدعاء `execute()` مرة أخرى بالـ `sessionId` نفسه يكمل
run لم ينتهِ (دون أن يعيد الـ model call لـ turn له رد بالفعل)، أو يواصل محادثة
منتهية بالإدخال الجديد، أو يرمي `SessionAwaitingApprovalError` ما دام هناك
approval معلّق. الـ tools تنفّذ at-least-once عبر الـ crash، و`execute`
يستقبل `toolCallId` الخاص بالاستدعاء لتستخدمه كـ idempotency key. راجع
[Durable execution](/ar/durable-execution) للضمانات بالضبط.

كيف ينتهي الـ run (أسباب الإنهاء)، وكيف تلغي run، وكيف تنفّذ الـ tool calls
بالتوازي: راجع [Runs](/ar/runs).

| -------------------------------------------- | --------------------------------------------- |

| `httpTool`, `currentDateTool`, `dayNameTool` | tools مدمجة. |
| `createFsTools(fs, options?)`, `createShellTool(shell, options?)` | tools للـ workspace (`read_file`، `write_file`، `edit_file`، `list_dir`، `glob`، `grep`، `shell`) فوق `FsProvider` / `ShellProvider`. راجع [tools الـ workspace](/ar/workspace-tools). |
| `NodeWorkspace`, `MemoryWorkspace`, `SandboxShell` | providers للـ workspace: مجلد حقيقي (المسارات محصورة داخل `root`، وبيئة shell فيها الحد الأدنى)، وشجرة في الذاكرة مع `exec` سكربتي للاختبارات، و`ShellProvider` فوق `SandboxAdapter` (Docker). |
| `createTodoTools({ store?, onChange? })`     | tools باسم `todo_write` / `todo_read` (مع `getTodos()`) تتيح للـ agents تخطيط العمل متعدد الخطوات ومتابعته؛ راجع [tools الـ todo](/ar/tools#todo-tools). |

| `loadMcpTools(client, connectionName)`       | يحمّل tools سيرفر MCP متصل كـ `ToolDescriptor`. متاحة من جذر الحزمة ومن `lousho/tools` و`lousho/mcp`. |

راجع [Tools](/ar/tools) لدليل تعريف الـ tools وتسجيلها.

```ts
import { defineTool } from 'lousho';
import { z } from 'zod';

const sendEmail = defineTool({
  name: 'send_email', // 1-64 chars: letters, digits, _ and -
  description: 'Send an email',
  input: z.object({ to: z.string().email(), subject: z.string() }),
  needsApproval: ({ to }) => !to.endsWith('@mycompany.com'), // `to` is typed
  async execute({ to, subject }) {
    return { messageId: `${to}:${subject}` };
  },
});
```

الحقول الاختيارية: `displayName` و`needsApproval` (boolean أو predicate)
و`requiresSandbox` و`sandboxExecute`. تعريف الـ tool يتحقق فورًا من اسمها
ووصفها والـ `input` بـ zod، وتسجيل tool بالاسم نفسه مرتين يرمي خطأً يذكر موضع
التعارض.

الـ tool المعرّفة تحمل الـ schema في `inputSchema` (الـ zod schema نفسها في
`input`) ودالة `execute` مباشرة. هذان الحقلان هما المعتمدان في
`ToolDescriptor`. أما كائن `.tool` (`{ description, parameters, execute }` بصيغة
`ai` v4) فهو legacy: يُبنى للتوافق فقط، ولا يُستخدم إلا مع descriptors التي لا
تحدد `inputSchema` / `execute`.

```ts
import { loadMcpTools } from 'lousho/mcp';

const tools = await loadMcpTools(mcpClient, 'my-server');
```

**دعم الـ schema.** `inputSchema` (بصيغة JSON Schema) لكل tool يتحوّل إلى zod
schema، ووسائط الـ model تُفحَص مقابله قبل استدعاء السيرفر. المحوّل يعالج
`type` (منها المصفوفات مثل `["string", "null"]`)، و`enum` بأنواع مختلطة، و`const`،
و`anyOf` / `oneOf` (union؛ `anyOf: [X, { type: "null" }]` تصبح `X.nullable()`)،
و`allOf` (دمج / intersection)، و`$ref` المحلي داخل `$defs` / `definitions`،
و`properties` / `required`، و`additionalProperties` (boolean أو schema)، و`items`،
و`default`، والقيود `minimum` و`maximum` و`exclusiveMinimum`
و`exclusiveMaximum` و`minLength` و`maxLength` و`pattern` و`minItems` و
`maxItems`. وعندما يكون JSON Schema ملتبسًا، يكون التحويل متساهلًا: الكلمات المفتاحية
غير المعروفة والـ schemas الفارغة و`items` بصيغة tuple والـ refs التي لا تُحلّ
تصبح `z.any()`، والـ `$ref` التعاودي يتوسّع مرة واحدة ويُستخدم `z.any()` للموضع
الداخلي، والـ regex غير الصالح في `pattern` يُتخطّى، والكائنات تحتفظ بخصائص إضافية
إلا إذا كان `additionalProperties` هو `false`. لا يرمي المحوّل خطأً أبدًا بسبب
محتوى الـ schema.

**الـ tools المتخطّاة.** إذا تعذّر تحويل tool واحدة، فهي وحدها التي تُتخطّى؛ وتُحمَّل بقية
tools السيرفر. مرّر `logger` لكي يصلك تحذير يذكر السيرفر والـ tool
والسبب، و`onSkip` لكي تجمع ما تُرك:

```ts
import { loadMcpTools, type SkippedMcpTool } from 'lousho/mcp';

const skipped: SkippedMcpTool[] = [];
const tools = await loadMcpTools(mcpClient, 'my-server', {
  logger: console,
  onSkip: (tool) => skipped.push(tool), // { name, reason }
});
```

**النتائج.** نتيجة MCP التي فيها `isError: true` هي فشل tool عادي: الـ model
يستقبل `{ "error": "McpToolError", "toolName": "...", "message": "..." }` و
`message` يحتوي المحتوى النصي الذي أعاده السيرفر. النتائج الناجحة قابلة للتسلسل
كـ JSON: إذا أعاد السيرفر `structuredContent`، فهو كائن النتيجة؛ وإلا تكون النتيجة
`{ text, content }`، بحيث يجمع `text` كل الأجزاء النصية ويحتفظ `content` بكل
جزء بترتيبه (`text`، `image`، `audio`، `resource`، `resource_link`؛ والجزء
الذي نوعه غير معروف يُحتفظ به كـ `{ type: 'unknown', raw }`). وإذا وصل
`structuredContent` مع أجزاء غير نصية، تصبح النتيجة
`{ structuredContent, text, content }` ويحتوي `content` الأجزاء غير النصية فقط،
لكي لا تُرمى الصور والصوت والموارد أبدًا.

tools الـ todo وأخطاء الـ tools: راجع [Tools](/ar/tools#todo-tools).

## Flows وevals وobservability والأمان

- `FlowBuilder` / `FlowExecutor` (`lousho/flows`) - graphs
  لمسارات عمل متعددة الخطوات؛ راجع [Flows](/ar/flows).
- `TriggerAdapter` و`TriggerRegistry` (`lousho/triggers`) -
  نقطة التوسعة لآلية إيقاظ خاصة بك، ومعها `verifySlackSignature()` و
  `parseCronExpression()` وأدوات `WebhookAuth` المساعدة؛ راجع [Triggers](/ar/triggers).
- `jwt()` و`oidc()` و`basic()` و`apiToken()` و`anonymous()` و`routeAuth()`
  (`lousho/auth`) - auth على الـ routes كقائمة مرتبة؛ المتصل
  الذي تقبله يصل إلى الـ run كـ `principal`؛ راجع
  [Route auth and principals](/ar/auth).
- `defineEval()`، وscorers مثل `exactMatch` و`toolCallOrder` و`budget`، وفحوص
  مثل `includes` و`atLeast`، و`llmJudge()` - evals للـ agents تعمل تحت vitest
  أو `lousho eval`؛ راجع [Evals](/ar/evals).
- `withSpan()` و`TraceExporter` - tracing لـ `AgentExecutor.execute()`.
  `TraceExporter` واجهة BYO: لا تُشحن الحزمة مع أي exporter افتراضي. وللحصول على spans
  حقيقية في OpenTelemetry، استورد `createOtelTraceExporter()` من الـ subpath
  `lousho/otel` (يحتاج الـ peer dependency الاختيارية
  `@opentelemetry/api`) بدلًا من أن تكتب جسر OTel بنفسك - راجع
  `examples/tracing/run-otel.ts`. الـ spans تتبع الـ GenAI semantic conventions
  الخاصة بـ OpenTelemetry (والـ flows تتتبّع أيضًا)؛ راجع
  [observability](/ar/observability).
- `NoopSandbox` / `SubprocessSandbox` - sandbox للـ tools التي تختاره عبر
  `requiresSandbox`؛ و`runPatchChecks()` وفحوص الـ patch مثل
  `createCommandCheck()` و`createDiffSizeCheck()` و
  `secretScanCheck`. راجع [Guardrails وsandboxing](/ar/guardrails).
- `HookRegistry` و`AgentHook` و`HookContext` و`ToolCallHookContext` و
  `GenerateHookContext` - hooks تراقب الـ tool calls والـ model calls أو ترفضها
  أو تعيد كتابتها أو تحجب أجزاء منها. راجع [Hooks](/ar/hooks).
- `EncryptionUtils` و`sha256` و`StorageService`
  (`lousho/utils`) - أدوات مساعدة داعمة؛ راجع
  [Utilities](/ar/utilities).
