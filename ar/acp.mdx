[Agent Client Protocol](https://agentclientprotocol.com) بروتوكول يخلّي المحرر
يقود agent للبرمجة يشتغل كعملية فرعية: المحرر يكتب طلبات JSON-RPC 2.0
على stdin الخاص بالـ agent، رسالة JSON واحدة في كل سطر، ويقرأ
ردوده وتحديثاته الـ streamed من stdout. Zed ومحررات
أخرى تتكلم بهذا البروتوكول. `lousho acp` يقدّم أي Lousho agent بهذه الطريقة، فتقدر
تدردش معه وتتابع الـ tool calls وتوافق عليها من لوحة الـ agent في المحرر.

## الأمر

```bash
npx lousho acp agent.yaml                          # a spec file
npx lousho acp ./my-agent --model openai/gpt-4o    # an agent directory, on another model
npx lousho acp src/agent.ts                        # a .ts/.js module (createAgent() options or an agent)
```

```text
lousho acp <spec.yaml|spec.json|agent-dir|agent.ts> [--model provider/model]
```

الـ `<path>` يتحمّل بنفس طريقة [`lousho chat`](/ar/cli#lousho-chat)، و`--model`
يشتغل بنفس الشكل. بادئة `vendor/` في الـ model تختار الـ provider؛
ومع OpenRouter استخدم `openrouter/<vendor>/<model>` (مثلاً
`openrouter/openai/gpt-4o`). المحرر هو الذي يبدأ العملية، وهي تظل شغالة حتى
ينغلق stdin. لا يحمل stdout إلا رسائل البروتوكول: الأخطاء،
وأي شيء يطبعه كود الـ agent بـ `console.log`، تذهب إلى stderr الذي
تعرضه المحررات في سجلاتها. مسار أو خيار خاطئ ينهي العملية برمز خروج 1 مع
الخطأ المرمّز (`LOUSHO_CONFIG_INVALID`، ...) على stderr.

## Zed

أضف الـ agent إلى `settings.json` في Zed، ثم اختره من لوحة الـ agent:

```json
{
  "agent_servers": {
    "My Lousho agent": {
      "type": "custom",
      "command": "npx",
      "args": ["lousho", "acp", "/path/to/my-agent"],
      "env": { "OPENAI_API_KEY": "sk-..." }
    }
  }
}
```

شغّله من المشروع المثبَّت فيه `@lousho/build-ai-agent` (أو استخدم
مسارًا مطلقًا إلى `node_modules/.bin/lousho` كـ `command`). مفاتيح الـ provider
تأتي من `env` أو من البيئة التي شُغِّل Zed فيها.

## المدعوم

الإصدار 1 من البروتوكول. الـ agent يرد على:

| الـ method | ما تفعله |
| ------ | ------------ |
| `initialize` | ترجّع `protocolVersion: 1` و`loadSession: false`، وقدرات prompt نصية فقط، وبدون طرق مصادقة. |
| `session/new` | تفتح session (جلسة) في الـ SDK عبر `agent.session()`: الـ prompts في session واحدة تتشارك سجلّها. ترجّع `{ sessionId }`. `cwd` و`mcpServers` يُتجاهَلان؛ عرّف سيرفرات MCP للـ agent في إعداداته هو. |
| `session/prompt` | تشغّل دورة واحدة. كتل النص هي المدخل؛ وكتلة `resource_link` تصير رابط Markdown إلى URI الخاص بها. تُنجَز بـ `{ stopReason }` عند انتهاء الدورة. |
| `session/cancel` (إشعار) | تلغي الدورة الشغالة في الـ session: `session/prompt` الخاص بها يُنجَز بـ `{ stopReason: 'cancelled' }`، وطلب الصلاحية الذي ما يزال مفتوحًا يُحسب مرفوضًا. |

طوال تنفيذ الدورة يرسل الـ agent إشعارات `session/update`:

- `agent_message_chunk` مع كتلة محتوى `text` لكل قطعة نص يكتبها الـ model؛
- `agent_thought_chunk` مع كتلة محتوى `text` لكل جزء من [استدلال](/ar/reasoning) الـ model؛
- `tool_call` (`status: 'in_progress'`، و`kind: 'other'`، واسم الـ tool في `title`، ومعاملاتها في `rawInput`) عند بدء tool call؛
- `tool_call_update` مع `status: 'completed'` (النتيجة كمحتوى نصي وكـ `rawOutput`) أو `'failed'` (الخطأ) عند انتهائه.

الـ sub-agent runs التي يبدأها الـ tool `task` لا تُمرَّر إلى المحرر؛
الـ `task` نفسه يظهر كـ tool call واحد.

**الصلاحيات.** لما tool تحتاج approval (موافقة) — `needsApproval` أو قواعد `permissions`
التي تطلب ذلك — يرسل الـ agent للمحرر طلب `session/request_permission`
فيه الـ tool call وخيارين: `allow` (Allow، `allow_once`)
و`reject` (Reject، `reject_once`). الإجابة تحسم الـ approval عبر
`agent.approvals.streamResolve()` والدورة المستأنفة تكمل بث
التحديثات؛ والرفض يعلّم الـ tool call بـ `failed` والـ model يكمل شغله.
الدورة الواحدة يمكن تسأل عدة مرات.

**الأسئلة.** التوقف من نوع `ask_question` (`askQuestion: true`) لا يتحوّل إلى
طلب صلاحية، لأن إجابة المستخدم يمكن تكون نصًا حرًا. بدل ذلك ينهي
الدورة بـ `end_turn`، والسؤال مع خياراته المرقّمة يصير رسالة
الـ agent؛ والـ prompt التالي في الـ session هو الإجابة
(`agent.approvals.streamAnswer()`).

**أسباب التوقف.** `end_turn` للانتهاء الطبيعي، و`max_turn_requests` لما
`maxSteps` ينفد، و`max_tokens` لما إحدى ميزانيات `limits` تُستنفد أو الـ model يقف
عند حدّ مخرجاته، و`refusal` لما guardrail يمنع أو فلتر
المحتوى عند الـ provider يوقف الـ model، و`cancelled` بعد
`session/cancel`.

**الأخطاء.** الـ method غير المعروفة يُرَدّ عليها بخطأ JSON-RPC رقم `-32601`، وسطر
ليس JSON بـ `-32700`، و`sessionId` غير معروف أو prompt فارغ بـ `-32602`، وprompt
ثاني بينما واحد يشتغل في نفس الـ session بـ `-32600`. والـ run الذي يفشل
يُرَدّ عليه بـ `-32603` مع رسالة الخطأ، ورمز خطأ الـ SDK الخاص به (مثلاً
`LOUSHO_PROVIDER_RATE_LIMITED`) في `error.data.code`.

## غير المدعوم

- `session/load` (`loadSession: false`) وأوضاع الـ session.
- طرق `fs/*` و`terminal/*` الخاصة بالعميل: الـ agent يقرأ الملفات ويشغّل
  الأوامر بأدواته هو ([أدوات مساحة العمل](/ar/workspace-tools))، وليس
  عبر المحرر.
- كتل الـ prompt من نوع الصور والصوت والموارد المضمَّنة (prompts نصية فقط).
- تحديثات `plan`، وخيارا الصلاحية `allow_always` /
  `reject_always`.
- المصادقة (`authMethods` فارغة): مفاتيح الـ provider تأتي من البيئة.

## في الكود

نواة البروتوكول هي `serveAcp(agent, { input, write })`: تقرأ أسطر JSON-RPC
من أي async iterable وتسلّم كل سطر صادر إلى `write`،
فتقدر تقدّمها على transport آخر أو تشغّلها في الاختبارات بدون عملية.
وتُنجَز لما ينتهي `input`، بعد إلغاء أي دورة شغالة.

```ts
import * as readline from 'node:readline';
import { createAgent, serveAcp } from '@lousho/build-ai-agent';

const agent = createAgent({ model: 'openai/gpt-4o-mini', instructions: 'You are a coding assistant.' });

await serveAcp(agent, {
  input: readline.createInterface({ input: process.stdin }),
  write: (line) => process.stdout.write(`${line}\n`),
});
```

مرّر `store` لتحفظ سجلات محادثات sessions الـ ACP في `AgentStore` (مثل
`SqliteStore`)؛ افتراضيًا تستخدم `store` الخاص بالـ agent أو الذاكرة.
