`agent.send(text)` turn واحد وبس: كل call بتبدأ من سجل فاضي.
الـ **session** (جلسة) هي محادثة فيها أكثر من turn: بتحتفظ بسجل المحادثة
وبتمرّره للـ model مع كل `send()`.

> الأمثلة في الصفحة دي بتسيب لك تعريف بعض الأسماء: `provider` هو أي `LLMProvider` (من غير اتصال: `createMockProvider()`).

```ts
import { createAgent } from 'lousho';

const chat = createAgent({ instructions: 'Be brief.', provider });

const session = chat.session(); // in memory, new generated id
await session.send('My name is Ali.');
const { text } = await session.send('What is my name?'); // sees the first exchange

console.log(session.id, session.messages.length);
```

## كائن الـ session

| العضو | الوصف |
| ------ | ----------- |
| `id` | الـ id بتاع الـ session: بيتولّد (UUID) لو ما مرّرته بنفسك. |
| `send(input, { signal })` | يبعت رسالة user مع المحادثة كلها حتى اللحظة، ويرجع `ExecutionResult` المعتاد. |
| `stream(input, { signal })` | زي `send()`، بس يرجع `AgentRun` بيعمل stream للـ turn كـ typed events - شوف [Streaming a session turn](#streaming-a-session-turn). |
| `messages` | snapshot للقراءة بس من سجل المحادثة (رسائل الـ user والـ assistant والـ tool؛ من غير الـ system prompt). تعديل الـ snapshot ما يغيّر الـ session. |
| `load()` | يقرأ سجل المحادثة المحفوظ من الـ store. `send()` بيعملها عنك؛ استدعِها عشان تعرض السجل قبل أول `send()` في session مستأنفة. كل call (`load()` و`send()` و`history()`، ...) بيقرأ الـ store من جديد، فالـ turns اللي كائن session تاني عملها commit لنفس الـ id بتبان. |
| `compact(options?)` | يعمل compaction لسجل المحادثة على طول - شوف [ضغط سياق جلسة](/ar/compaction#الـcompaction-على-session). |
| `clear()` | يفرّغ سجل المحادثة ويحفظه فاضي (الـ store ما يفضل فيه رسائل للـ id). يحافظ على id الـ session والـ store والـ options؛ يمسح checkpoint كل turn والـ checkpoint history بتاعتها (`<id>.turn-<n>`، واللي فيها نسخ من سجل المحادثة)، فـ `agent.fork('<id>.turn-<n>')` ما يقدر يرجّع المحادثة؛ وخانات الـ memory مشتركة بين الـ sessions وما بتتأثر. يبعت `context.cleared` للـ listeners على `on()`. يرمي `LOUSHO_SESSION_BUSY` لو في turn شغالة، و`LOUSHO_SESSION_AWAITING_APPROVAL` لو turn durable مستنية approval. |
| `on(listener)` | يسمع events الـ session: events كل turn أول ما تحصل (turns بتاع `send()` و`stream()`، وturn متوقفة `agent.approvals.resolve()` بيكمّلها)، زيادة على events بتاع `compact()` / `clear()` (`compaction.start` و`compaction.done` و`context.cleared`)؛ ويرجع function بتشيل الـ listener. events الـ turn هي `AgentEvent` اللي `stream()` بتاعها بيطلّعها. |
| `pending()` | في [durable session](#durable-sessions): الـ turn اللي لسه ما خلصت (`{ status, approvalId?, approvalKind?, idempotencyKey? }`؛ `approvalKind` بتكون `'question'` لما الـ turn مستنية `ask_question`؛ و`idempotencyKey` هو الـ `Idempotency-Key` بتاع HTTP للـ turn، شوف [إعادة إرسال turn](/ar/deployment#إعادة-إرسال-turn))، أو `null`. |
| `resume({ signal })` | في durable session: يخلّص turn منقطعة ويرجع بنتيجتها، أو `null` لو ما فيه turn pending. |
| `discardPending()` | في durable session: يرمي turn ما خلصت من غير ما يشغّلها، ويسحب الـ approvals اللي كانت مستنياها (ما بتتسرد تاني، وأي محاولة تقرّر واحدة منها بتفشل بـ `LOUSHO_APPROVAL_NOT_FOUND`). وكمان بيرمي checkpoint بتاع turn ما ينفعش يتقري (`LOUSHO_CHECKPOINT_CORRUPT`). |
| `history()` | خطوات سجل المحادثة (خطوة لكل رد من الـ model، مع الـ tool calls بتاعته ونتائجها) - شوف [Forking a session](#forking-a-session). |
| `fork({ fromStep, id?, patch? })` | session جديدة بتبدأ من سجل محادثة الـ session دي لحد خطوة معينة؛ والـ session دي ما بتتغير - شوف [Forking a session](#forking-a-session). |

calls `send()` اللي تجي مع بعض على نفس الـ session بتتصف وتتنفذ
واحدة ورا التانية بترتيب الاستدعاء، فسجل المحادثة ما بيتداخل أبد.

`agent.session({ id, turnPolicy })` يحدد تصرّف `send()` أو `stream()`
لما يكون في turn شغالة أو مستنية تبدأ:

- `'wait'` (الافتراضي): يستنى ويتنفذ كـ turn لوحدها، زي ما فوق.
- `'queue'`: الـ input بتاعها ينضم للـ turn دي، زي
  [`run.enqueue()`](/ar/queue-and-steer#queued-input): بيتضاف بعد
  نتائج الـ tools بتاع الخطوة الحالية، وcall الـ model التالي في الـ turn
  بيشوفه. الـ call بيرجع بنتيجة الـ turn دي (والـ `signal` بتاعته ما
  بتسري على الـ turn)، وسجل المحادثة اللي بيتحفظ لما الـ turn تخلص
  بيمسك رسالة الـ user اللي دخلت الـ queue بترتيبها. `stream()` اللي بتنضم
  ما بتطلّع غير `run.done` بتاع الـ turn؛ أما events الـ turn،
  ومنها `input.queued` و`input.applied`، فبتتعمل stream على
  الـ run اللي بدأها. لو الـ turn خلصت قبل ما تقدر تاخد الـ input
  (خلصت، اتوقفت، أو اتلغت)، الـ call بيتنفذ كـ turn تالية في
  الآخر على أي حال — إلا في durable session الـ turn المتوقفة بتاعتها لسه
  pending: هنا الـ call بيعملها resume الأول، ويرمي
  `SessionAwaitingApprovalError` لو لسه مستنية الـ approval
  (قرّرها بـ `agent.approvals.resolve()`). ولو الـ turn فشلت، الـ call
  بيرمي نفس الـ error؛ وفي durable session الـ input بيفضل في
  checkpoint بتاع الـ turn و`resume()` بيطبّقه.
- `'steer'`: زي `'queue'`، بس الـ input بينضم عن طريق
  [`run.steer()`](/ar/queue-and-steer#steering): لو call الـ model بتاع الـ turn
  ما طلّعت أي حاجة لسه، بتتلغي وبتتعمل من الأول مع الرسالة الجديدة،
  والـ tool calls بتاع الـ turn اللي لسه ما بدأت ما بتتنفذ.
  غير كده بتستنى النقطة الآمنة التالية، زي `'queue'`. الـ call بيرجع
  بنتيجة الـ turn، ونفس الـ fallbacks بتسري.

بادئة `vendor/` في اسم الـ model هي اللي بتحدد الـ provider؛ ومع OpenRouter استخدم
`openrouter/<vendor>/<model>` (مثال `openrouter/openai/gpt-4o-mini`).

```ts
import { createAgent } from 'lousho';

const agent = createAgent({ model: 'openai/gpt-4o-mini' });
const session = agent.session({ id: 'user-42', turnPolicy: 'queue' });

const first = session.send('Find flights to Rome.');
const second = session.send('Only direct ones, please.'); // joins the first turn
console.log((await second) === (await first)); // true: one turn, one result
```

`send()` و`stream()` بياخدو string، أو content parts (`[{ type: 'text', ... }, { type: 'image', ... }]`، رسالة user واحدة)، أو `Message[]`؛ والـ stores بتحتفظ بالـ parts، شوف [المدخلات متعددة الوسائط](/ar/providers#إدخال-multimodal).

`send()` اللي بيرمي (error من الـ provider، أو tool بترمي
`PropagatingToolError`) بيسيب سجل المحادثة زي ما كان بالظبط قبل الـ call.
أما `send()` اللي بيتلغي بـ `signal` (زرار Stop مثلًا) فبيحتفظ باللي قاله
الـ user والـ model لحد اللحظة، عشان `GET /chat/:id` والـ turn الجاية
يفضل عندهم السياق:

- رسالة الـ user، بشرط إن الـ model اتنادى (signal ملغي من قبل أول
  call للـ model بيرمي الـ turn كلها)؛
- الـ turn لحد آخر tool call اتنفذت (الـ tool calls بتاعة الـ assistant
  ونتائجها؛ والـ calls اللي في نفس الدفعة وما بدأتش بياخدو نتيجة
  "cancelled")، فـ side effect زي refund مستحيل يضيع من السجل؛
- الرد اللي الـ model كان عمله stream لحد ما اتوقف، كرسالة assistant
  فيها `metadata: { interrupted: true }` (`stream()` بس هو اللي بيعمل stream؛
  `send()` العادي ما عندوش رد جزئي).

والـ `send()` الملغي بيرجع بـ `finishReason: 'aborted'`، زي `agent.send()`.
والـ `usage` بتاعه بيحسب call الـ model اللي اتوقف، بتقدير من الـ request
والنص اللي اتعمله stream لو الـ provider ما بلّغش بحاجة، عشان
`limits.maxCostUsd` بتاع الـ session ما يتحسبش أقل من الحقيقة. وسجل المحادثة المحفوظ
مستحيل يكون فيه turn للـ assistant فيه tool calls من غير نتائج الـ tools المقابلة.

`send()` اللي بيتوقف عند tool فيها `needsApproval` بيرجع بـ
`finishReason: 'awaiting-approval'`. بعدها `agent.approvals.resolve({ id, approved })`
بيكمّل الـ run كـ turn تالية في الـ session، فالـ tool call ونتيجته
والإجابة النهائية بينضموا لسجل المحادثة (شوف
[approvals](/ar/approvals)).

`agent.session({ id, limits })` يحط budgets على كل turns الـ session
(مثال `{ maxCostUsd: 1 }`)، وبتتحسب من الـ usage المحفوظ مع
سجل المحادثة؛ أما `createAgent({ limits })` فبيقيّد كل turn لوحدها. شوف
[الميزانيات](/ar/configuration#الميزانيات).

## Streaming a session turn

`session.stream(input, { signal })` هو `agent.stream()` بس لمحادثة:
بيرجع نفس الـ `AgentRun` (typed events مع promise اسمه `result`، شوف
[streaming](/ar/streaming))، بس الـ turn بتشوف سجل المحادثة حتى اللحظة
وبتنضم له.

```ts
import { createAgent } from 'lousho';

const chat = createAgent({ instructions: 'Be brief.', provider });
const session = chat.session();

for await (const event of session.stream('My name is Ali.')) {
  if (event.type === 'text.delta') process.stdout.write(event.text);
}
// The turn is already saved: this call sees it.
const { text } = await session.send('What is my name?');
```

- بيبني نفس قائمة الرسائل بتاع `send()` ويتصف ورا الـ calls السابقة
  على الـ session (ممكن تخلط `send()` و`stream()`).
- لما الـ run يخلص، رسالة الـ user الجديدة ومخرجات الـ run بيتحفظوا
  بالظبط زي ما `send()` بيحفظهم، وبس بعدها `run.done` يتسلّم. يعني لما
  حلقة `for await` تخلص، أو `run.result` يرجع، سجل المحادثة
  يكون كامل. والـ events شايلة `runId` بتاع الـ handle المُرجَع.
- الـ run الفاشل بيسيب سجل المحادثة زي ما كان قبل الـ call، زي `send()`.
  أما الـ run الملغي (بـ `signal`، أو لما تطلع من الحلقة بدري) فبيحتفظ برسالة
  الـ user والـ tool calls اللي اتنفذت والرد اللي اتعمله stream لحد اللحظة
  (متعلّم بـ `metadata.interrupted`)، زي `send()` الملغي. والـ run اللي
  كان خلص أصلًا لما الحلقة اتسابت بيتحفظ. والـ run الفاشل بيقفل
  الـ stream بـ `error` و`run.done` (`finishReason: 'error'`)،
  و`run.result` بيرمي. وده بيشمل store بيفشل في الـ load أو الـ save:
  ساعتها الـ turn ما يكون لها `run.start`.
- run بيتوقف عند tool فيها `needsApproval` بينتهي بـ `approval.requested`
  و`run.done` (`'awaiting-approval'`)، بالظبط زي ما `send()` بيرجع، وسجل
  المحادثة بيمسك الـ turn لحد موضع التوقف. و`agent.approvals.resolve()`
  بيكمّلها كـ turn تالية في الـ session. وcallback بتاع `approve` ما بيسري
  على الـ streams، زي `agent.stream()`.

الـ sessions طبقة رفيعة: الـ session ماسكة سجل المحادثة وبتسلّمه للـ
executor في كل turn. ومن غير checkpoint store، الـ turn بتتحفظ بس لما
تخلص، فـ crash في نص turn بيضيّعها؛ شوف القسم اللي بعده.

## Two kinds of conversation id

`agent.session({ id })` و`agent.send(msg, { sessionId })` محادثتين مختلفتين.
الـ SDK عنده طريقتين يحفظ بيهم محادثة تحت id، وما بيتشاركوش
نفس التخزين:

| | `agent.session({ id }).send(msg)` | `agent.send(msg, { sessionId })` |
| --- | --- | --- |
| هو إيه | session: سجل محادثة، و`send()` واحد لكل turn | run واحد durable (شوف [durable execution](/ar/durable-execution))؛ لو ناديته تاني بنفس الـ id بيكمّله |
| المحادثة محفوظة فين | `store.sessions` تحت `id` (كل turn بيتعملها checkpoint كـ `<id>.turn-<n>` وهي شغالة) | `store.checkpoints` تحت `sessionId` (الـ `messages` بتاعة الـ checkpoint) |
| محتاج إيه | ولا حاجة (في الـ memory افتراضيًا) | `store.checkpoints` (ومن غيره `LOUSHO_CONFIG_MISSING_CHECKPOINT_STORE`) |
| تقراها تاني بـ | `session.load()`، `GET /chat/:id` | `store.checkpoints.load(sessionId)` (الـ `messages` بتاعته)، `agent.fork(sessionId)` |
| تكمّلها بعد crash بـ | `agent.session({ id }).resume()` | `agent.resume(sessionId)` |

استخدم طريقة واحدة لكل id. الـ id اللي بيتستخدم بالطريقتين بيمسك محادثتين ما لهمش علاقة ببعض:
الـ turn اللي اتبعتت بطريقة ما بتشوفش الـ turns اللي اتبعتت بالطريقة التانية، و
`GET /chat/:id` بيعرض سجل محادثة الـ session بس. `agent.resume(id)` بيدوّر
على run بتاع `send({ sessionId })` الأول، ولو مش لاقي، ساعتها بس بيعمل resume
للـ turn الـ pending بتاعة الـ session، فلو الاتنين موجودين بيخلّص الـ run ويسيب
turn الـ session pending (خلّصها بـ `agent.session({ id }).resume()`).
والـ prompt schedules بتشتغل كـ runs بتاع `send({ sessionId })` (شوف
[الجداول الزمنية](/ar/schedules#الـ-prompt-schedules-والـ-sessions))، فاقرا تقارير الـ schedule
من `store.checkpoints`، مش من `GET /chat/:id`.

## Durable sessions

ادِّ الـ agent `store` فيه checkpoints وكل turn في الـ session بيتعملها
checkpoint بعد كل رد من الـ model وكل نتيجة tool، باستخدام
ميكانيزم [durable execution](/ar/durable-execution). والـ turn اللي قطعها
crash، أو فشل في كتابة checkpoint، أو `PropagatingToolError`، ممكن
تتخلّص بعدين، في process تانية:

```ts
import { createAgent } from 'lousho';
import { SqliteStore } from 'lousho/sqlite';

const agent = createAgent({ provider, store: new SqliteStore('./.lousho/agent.db') });

// After a restart: finish the turn that was running, if any.
const finished = await agent.resume('user-42'); // ExecutionResult, or null when nothing was pending
console.log(finished?.text, await agent.session({ id: 'user-42' }).pending()); // pending() is null now
```

- `createAgent({ store })` ياخد أي `AgentStore`
  (`{ sessions?, checkpoints?, approvals? }`، شوف [Choosing a store](#choosing-a-store)):
  `agent.session({ id })` بيحط سجل محادثته في `store.sessions`
  وcheckpoints بتاعته في `store.checkpoints`، و`store.approvals` بيمسك
  توقفات الـ approval. والـ `store` الخاص بالـ session (يعني `SessionStore`، أو
  كائن `{ sessions, checkpoints }`) و`checkpointStore` بيغلبوا store
  الـ agent، جزء بجزء.
- `agent.resume(id)` هو نفسه `agent.session({ id }).resume()`، الفرق إنه
  بيخلّص الأول run بدأت بـ `agent.send(message, { sessionId: id })` (شوف
  [durable execution](/ar/durable-execution) و
  [نوعين الـ id](#two-kinds-of-conversation-id)).
- كل turn بتشتغل بـ `sessionId: '<session id>.turn-<n>'` (و`n` هو طول
  سجل المحادثة وقت ما الـ turn بدأت)، فالـ process الجديدة تلاقي
  الـ turn المنقطعة من غير أي شغل تتبّع زيادة. والـ turn اللي خلصت بتنضم
  لسجل المحادثة، بالظبط زي `send()` العادية، وcheckpoint بتاعتها بتتمسح.
  id الـ turn ده مجرد مفتاح للـ checkpoint: الـ tools و`needsApproval` وقواعد
  الـ permissions والـ hooks بتاعة الـ tool calls لسه بياخدو id الـ session نفسه كـ `ctx.sessionId`.
  الـ checkpoint history بتاعة الـ turn بتفضل محفوظة لآخر `turnHistoryLimit`
  turns اتعملها commit (الافتراضي 10، `agent.session({ id, turnHistoryLimit })`)، عشان
  `agent.fork('<id>.turn-<n>', { fromStep })` يقدر يعمل fork منهم؛ والـ histories بتاعة
  الـ turns الأقدم بتتمسح مع commit الـ turns الجديدة (كل entry في الـ history فيها نسخة من
  سجل المحادثة كله، فلو احتفظت بـ history كل الـ turns الـ store هيكبر بمربع
  طول المحادثة)، حتى لو كل turn بتستخدم كائن store أو process جديدة.
  والـ history اللي برا النافذة وموجودة أصلًا في الـ store -
  من إصدار أقدم، أو تحت `turnHistoryLimit` أكبر - بتتمسح هي كمان
  على مدار الـ commits الجاية، لحد 32 turn في كل commit، الأقدم الأول؛ والـ process
  اللي بتعمل commit لـ turn واحدة بس بتخلّص أقدم 32، و
  `fileStore(dir).prune()` / `SqliteStore.prune()` بيمسحوا الباقي.
  أما `session.fork()` فبيشتغل من سجل المحادثة ومش مقيّد بالحد ده.
- وهي شغالة، الـ turn بتمسك run lease على الـ checkpoint بتاعتها (شوف
  [durable execution](/ar/durable-execution#run-leases)): أي `send()` على نفس
  الـ session من process أو replica أو كائن store تاني بيفشل بـ
  `LOUSHO_SESSION_BUSY` قبل ما يشغّل أي حاجة، بدل ما يعمل resume للـ turn
  الشغالة ويشغّل الـ tool calls بتاعتها مرة تانية.
- `resume()` بيكمّل الـ turn عن طريق مسار الـ resume في الـ executor
  (`input: []`): الـ tool calls اللي نتائجها اتسجلت ما بتتنفذش تاني،
  ورد الـ model المسجّل ما بيتطلبش تاني. بس tool كانت شغالة
  لما الـ process ماتت بتتنفذ تاني (at-least-once، شوف
  [durable execution](/ar/durable-execution#at-least-once-tools-خلّي-الـ-side-effects-idempotent)).
- `send()` و`stream()` بيعملوا resume للـ turn الـ pending الأول، وبعدين
  بيبعتوا الرسالة الجديدة، فالـ model بيشوف الـ turn خلصت (events بتاع
  الـ turn اللي اتعملها resume ما بتتعمل stream). استخدم `pending()` تشيك
  الأول، أو `discardPending()` عشان ترمي الـ turn اللي ما خلصت.
- الـ turn اللي بتفشل بتسجّل الـ error وعدد المحاولات على الـ checkpoint بتاعتها
  (`lastError` و`attempts`). لو الـ error مش هيروح بإعادة المحاولة (400 من
  الـ provider زي تجاوز طول السياق، أو فشل في الـ auth)، الـ
  `send()` / `stream()` الجاي ما بيعيدش الـ turn: بيفشل بـ
  `LOUSHO_SESSION_TURN_FAILED`. استدعِ `discardPending()` عشان ترمي الـ turn، أو
  `resume()` عشان تعيد المحاولة بعد ما تصلّح السبب. والفشل التاني (crash، أو
  5xx، أو error في الشبكة) لسه الـ `send()` الجاي بيعمله resume. وده بيسري
  كمان على turn أول call للـ model فيها فشل: الـ run لسه ما حفظش أي
  checkpoint، فالـ session بتحتفظ بالـ input بتاع الـ turn كـ turn pending
  (`pending()` بيبلّغ إنها `in-progress`) وبتشغّلها تاني من الـ input ده.
- turn بتتوقف عند tool فيها `needsApproval` بتفضل في checkpoint بتاعتها، مش في
  سجل المحادثة، لحد ما تخلص. وهي مستنية، `resume()` و`send()`
  و`stream()` بيرموا `SessionAwaitingApprovalError` (ومعه `approvalId`)،
  و`agent.approvals.resolve({ id, approved })` بيكمّل الـ turn في الـ
  session دي. بعد restart، `agent.approvals.resolve()` أو `streamResolve()`
  من الـ process الجديدة بيكمّلوها برضه: الـ agent بيلاقي الـ session من
  سجل التوقف (للـ session ids اللي فيها حروف وأرقام و`_` و`-`)، فما فيه
  داعي تفتح الـ session أو تستدعي `resume()` الأول. وادِّ الاتنين agents
  نفس الـ `store` الدائم (أو `approvalStore`).
- `resume()` بيرجع نتيجة الـ turn اللي خلصت؛ ما بيعملش stream، و
  `stream()` برضه ما بيعملش stream للـ turn الـ pending اللي بيخلّصها الأول. وعشان
  تعرض تقدّم turn اتعملها resume، سجّل `session.on(listener)` قبل
  الـ call (أو مرّر `createAgent({ onEvent })`): بيوصله الـ `AgentEvent` بتاع الـ turn
  أول ما تحصل.
- الـ turn المتوقفة بتقفل id الـ session: الـ session بتسجّلها تحت
  `<id>.paused` في الـ checkpoint store، فـ `agent.send(message, { sessionId: id })`،
  و`agent.stream()` بنفس الـ `sessionId`، وأي كائن session على سجل محادثة
  مختلف (store تاني، أو سجل بطول مختلف) بيترفضوا بـ
  `SessionAwaitingApprovalError` (`LOUSHO_SESSION_AWAITING_APPROVAL`) هم كمان، و
  `pending()` بتاعهم بيبلّغ عن التوقف. قرّر الـ approval، أو ارمِ الـ turn بـ
  `agent.session({ id }).discardPending()`، عشان الـ session تقبل turns جديدة تاني.
- الـ turn الملغية الـ checkpoint بتاعتها بتتمسح؛ واللي احتفظت بيه (رسالة الـ user،
  والـ tool calls اللي اتنفذت، والرد المنقطع) بينضم لسجل المحادثة، زي
  من غير checkpoint store. و`clear()` بيمسح الـ turn الـ pending كمان، والـ checkpoint
  history بتاعة كل turn، فالـ turns اللي اتمسحت ما بقاش ينفع يتعملها fork.

## Stores

`SessionStore` بيمسك سجلات المحادثات بين الـ calls:

```ts
import type { Message } from 'lousho';

interface SessionStore {
  load(id: string): Promise<Message[] | undefined>;
  save(id: string, messages: readonly Message[]): Promise<void>;
  delete(id: string): Promise<void>;
  // Optional compare-and-swap: save only if the stored transcript still has this revision.
  saveIf?(id: string, expectedRevision: string, messages: readonly Message[]): Promise<boolean>;
}
```

كل turn بتعمل commit عن طريق `saveIf` لو الـ store عنده، مع
`transcriptRevision(<the transcript the turn started from>)`. فلو عمليتين (أو
كائنين store على نفس البيانات) خلّصوا turn على نفس الـ session في نفس
اللحظة، ما ينفعش الاتنين يعملوا commit: واحدة بتكسب، والـ `send()` بتاع التانية بيرمي
`LOUSHO_SESSION_BUSY`. `MemorySessionStore` و`FileSessionStore` (ملف
`<id>.json.lock` بيتنشأ بشكل حصري؛ والـ lock اللي أقدم من `staleLockMs`،
الافتراضي 10 ثواني، بيتاخد منه) و`SqliteStore.sessions` (transaction واحدة
`BEGIN IMMEDIATE`) بيعملوا implement ليها. والـ store اللي ما عندوش، زي `KVStore.sessions` (الـ KV
ما فيه compare-and-swap)، بياخد load ومقارنة وsave بأحسن مجهود، وممكن
writer في process تانية يدخل بينهم، فتضيع turn واحدة.

- `MemorySessionStore` (الافتراضي، store جديد لكل session) بيعيش طول ما
  الـ process عايشة. شارك نفس الـ instance بين الـ sessions عشان تلاقيها بالـ id.
- `FileSessionStore(dir)` بيكتب ملف JSON واحد لكل session (`<dir>/<id>.json`)،
  كتابة atomic (ملف مؤقت وبعدين rename)، وبينشئ `dir` أول save. وكل
  حرف uppercase في الـ id بيتكتب كـ `^` وبعده الحرف lowercase
  (`Alice` -> `^alice.json`)، فالـ ids اللي بتختلف في حالة الحروف بس بياخدو ملفات
  مختلفة على Windows وmacOS كمان.

```ts
import { createAgent, FileSessionStore } from 'lousho';

const agent = createAgent({ provider });
const store = new FileSessionStore('./.lousho/sessions');

const first = agent.session({ id: 'user-42', store });
await first.send('My name is Ali.');

// Later, even in another process or another createAgent() instance:
const again = agent.session({ id: 'user-42', store });
await again.send('What is my name?'); // "Ali"
```

ids بتاع الـ sessions لازم تطابق `^[A-Za-z0-9_-]{1,128}$` (بتبقى أسماء ملفات، عشان كده
`../x` و`a/b` بيترفضوا بـ error بيوضّح السبب). اعمل implement
لـ `SessionStore` بنفسك عشان تحط سجلات المحادثات في database أو Redis.

الـ `AgentStore` فيه جزء رابع اختياري جنب `sessions` و`checkpoints`
و`approvals`: `tokens`، يعني access وrefresh tokens بتاع OAuth للـ tools
والاتصالات، والـ file وSQLite وKV stores بيخزّنوها مشفرة (شوف
[OAuth](/ar/oauth#تخزين-tokens)).

## Choosing a store

الـ sessions وcheckpoints بتاع durable execution والـ approvals كل واحدة
لها واجهة store (`SessionStore` و`CheckpointStore` و`ApprovalStore`). اختار
الـ implementation على حسب وين الـ process شغالة:

| Store | Sessions | Checkpoints | Approvals | استخدمه لما |
| --- | --- | --- | --- | --- |
| In memory (`memoryStore()`) | `MemorySessionStore` | in memory | `InMemoryApprovalStore` | tests وscripts، process واحدة ما بيتعملها restart أبد |
| Files (`fileStore(dir)`) | `<dir>/sessions/<id>.json` | `<dir>/checkpoints/` و`<dir>/checkpoint-history/` | `<dir>/approvals/<id>.json` | جهاز واحد، وتبي ملفات عادية تقدر تفحصها |
| SQLite | `store.sessions` | `store.checkpoints` | `store.approvals` | سيرفر Node: ملف واحد durable بيدعم transactions، وعدة processes تتشاركه بأمان |
| Cloudflare KV (`KVStore` من `lousho/kv`) | `store.sessions` | `store.checkpoints` | `store.approvals` | deployments على Workers (شوف [النشر](/ar/deployment)) |

كل واحدة فيهم جزء من `AgentStore`: مرّرهم مع بعض كده
`createAgent({ store: { sessions, checkpoints, approvals } })`. و`memoryStore()`
و`fileStore(dir)` و`SqliteStore` و`KVStore` `AgentStore`s جاهزة. وللملفات
العادية، `fileStore(dir)` بتكتب ملف JSON واحد لكل session وcheckpoint وapproval
pending تحت `dir`، وكل واحد بيتكتب في ملف مؤقت، وبيتعمله flush على الديسك، وبعدين بيتعمله rename
لمكانه (فلا crash ولا انقطاع كهربا بيسيب نص ملف أبد). على Windows، الـ rename فوق ملف، أو قراية ملف،
مفتوح عند writer أو reader تاني بيفشل للحظة بـ `EPERM` أو `EACCES` أو
`EBUSY`؛ و`fileStore()` و`FileSessionStore` بيعيدوا المحاولة مع backoff قصير (حوالي
1.3 ثانية في المجموع) وبعدين بيفشلوا بـ `LOUSHO_STORAGE_FAILED`. والـ saves المتزامنة على نفس
الملف لسه بتنتهي بواحد منهم بس (آخر rename هو اللي بيكسب):

```ts
import { createAgent, fileStore } from 'lousho';

const agent = createAgent({ provider, store: fileStore('./.lousho') });
// ./.lousho/sessions/user-42.json, ./.lousho/checkpoints/..., ./.lousho/approvals/...
await agent.session({ id: 'user-42' }).send('Hello');
```

في كل اسم ملف، الحرف الـ uppercase في الـ id بيتكتب كـ `^` وبعده
الحرف lowercase (`Alice` -> `sessions/^alice.json`): أنظمة الملفات الافتراضية
في Windows وmacOS ما بتفرّقش بين حالة الحروف، و`alice` و`Alice` لازم ما يتشاركوش
نفس سجل المحادثة. والـ id اللي ما فيهوش حروف uppercase بيفضل باسمه العادي. والملف
اللي اتحفظ بإصدار أقدم تحت اسم فيه حروف مختلطة (`Alice.json`) لسه بيتقري
لنفس الـ id ده بالظبط، وبيتنقل لاسمه الجديد في الـ save الجاي. والـ id اللي
هيعمل اسم ملف طويل زيادة بعد الـ encoding (session id كله uppercase طوله 128 حرف
زائد `.turn-<n>`)، أو اسم جهاز في Windows (`nul`، `com1`)، بيتخزن
كـ `~<prefix>~<hash>.json` بدل كده.

كل ملف `checkpoints/<id>.json` جنبه ملف `checkpoint-history/<id>.json`: الـ history المحدودة بتاع الـ checkpoint، الأقدم الأول. والمجلدات بتتنشأ عند أول كتابة، فـ `approvals/` (و`oauth/`) ما بيظهروا إلا بعد أول approval pending (أو sign-in).

تقرير approval من `fileStore` آمن عبر الـ processes (caller واحد بس
اللي بياخد السجل، والـ claim اللي سابه resolver وقع بيتاخد منه بعد
دقيقة)؛ والـ session بتعمل commit للـ turns بتاعتها بـ compare-and-swap تحت ملف lock
(`sessions/<id>.json.lock`)، والـ run الشغال اللي بيتعمله checkpoint بيمسك الـ run lease بتاعه
في `leases/<id>.json` (شوف [durable execution](/ar/durable-execution#run-leases)).
ولو عندك processes كتير بتتشارك store، `SqliteStore` هو الاختيار الأمتن.

`fileStore(dir).prune({ olderThanMs })` بيمسح اللي آخر كتابة ليه كانت من أكتر من
`olderThanMs`، زي `SqliteStore.prune()`: سجلات المحادثات والـ checkpoints وملفات
الـ checkpoint history، زائد sign-ins بتاع OAuth الـ pending المنتهية. والـ run المتوقف على
approval pending بيفضل، مهما كان قديم (الـ checkpoint بتاعته والـ history بتاعته وسجل محادثة
الـ session بتاعته)، وكمان الـ approvals الـ pending وOAuth tokens بيفضلوا. وبيرجع
بالأعداد، `{ sessions, checkpoints, checkpointHistory, oauthPending }`:

```ts
import { fileStore } from 'lousho';

const store = fileStore('./.lousho');
await store.prune({ olderThanMs: 30 * 24 * 60 * 60 * 1000 }); // a month
```

وأي object عنده الدوال التلاتة بتاع جزء معين بيشتغل مكانه كمان: `SessionStore`
على Redis، أو `CheckpointStore` مبني على KV على Cloudflare Workers (الـ
Worker المولّد بيستخدم `KVCheckpointStore`، شوف [النشر](/ar/deployment)).

`SqliteStore` بيخزن التلاتة في ملف database واحد، باستخدام
`node:sqlite` المدمج في Node (من غير native dependency؛ محتاج Node 22.13 أو أحدث، ومش
متعمله re-export من الـ root entry، فاستيراد الـ SDK ما بيحمّله أبد):

```ts
import { createAgent } from 'lousho';
import { SqliteStore } from 'lousho/sqlite';

const store = new SqliteStore('./.lousho/agent.db'); // or ':memory:'
const agent = createAgent({ provider, store }); // transcripts, per-step checkpoints and approvals
await agent.session({ id: 'user-42' }).send('Hello');

store.prune({ olderThanMs: 7 * 24 * 60 * 60 * 1000 }); // { sessions, checkpoints, approvals, oauthPending } deleted
store.close();
```

مع الـ executor مباشرة، مرّر `store.checkpoints` كـ `checkpointStore` و
`store.approvals` كـ `approvalStore`؛ شوف [executor API](/ar/executor-api).

- المجلد بيتنشأ لو مش موجود. والـ schema متعملها versioning بـ
  `PRAGMA user_version` وبتتعملها migration عند الفتح؛ وdatabase مكتوبة
  بإصدار أحدث بتترفض.
- وضع WAL وbusy timeout مدته 5 ثواني بيخلّوا عمليتين يتشاركوا الملف. وبس
  واحدة فيهم تقدر تقرر الـ approval.
- الـ checkpoints وsnapshots بتاع الـ approval بيتخزّنوا كـ JSON معتم ما بيتفسّرش محتواه، فالحقول
  الجديدة بتعدي round-trip من غير ما تتغير.
- `prune()` بيشيل الـ sessions والـ checkpoints اللي ما اتحدثت خلال `olderThanMs`،
  والـ approvals اللي اتحسمت قبل المدة دي وsign-ins بتاع OAuth الـ pending المنتهية؛
  أما الـ approvals اللي لسه ما اتحسمت وOAuth tokens فبيفضلوا، وكمان الـ turn المتوقفة على
  approval لسه ما اتحسمت (الـ checkpoint بتاعتها وسجل محادثة الـ session)،
  مهما كانت قديمة. وتقرير approval الـ turn المتوقفة بتاعتها اتمسحت على أي حال
  بيفشل بـ [`LOUSHO_APPROVAL_ORPHANED`](/ar/errors#lousho_approval_orphaned)
  من غير ما يشغّل الـ tool.
- ملف مش database بتاع SQLite بيفشل بـ error بيذكر المسار؛
  واستخدام الـ store بعد `close()` بيرمي error واضح.

## Forking a session

`session.history()` بتسرد خطوات الـ session، و`session.fork({ fromStep })` بيبدأ session جديدة من أي خطوة فيهم، فتقدر تجرب اتجاه تاني
من غير ما تضيّع المحادثة الأصلية:

```ts
import { createAgent, defineTool } from 'lousho';
import { mockModel } from 'lousho/testing';
import { z } from 'zod';

const searchFlights = defineTool({
  name: 'search_flights',
  description: 'Find flights to a city',
  input: z.object({ to: z.string() }),
  execute: async ({ to }) => `2 flights to ${to}`,
});
const agent = createAgent({
  tools: [searchFlights],
  provider: mockModel([
    { toolCalls: [{ name: 'search_flights', args: { to: 'Lisbon' } }] },
    'Two flights to Lisbon on Friday.',
    'Porto has a direct flight at 9:00.',
  ]),
});
const session = agent.session({ id: 'trip' });
await session.send('Find me a flight to Lisbon on Friday.');

for (const { step, turn, text, toolCalls } of await session.history()) {
  console.log(step, turn, text, toolCalls.map((call) => `${call.name} -> ${call.result}`));
}

// Keep everything up to and including step 1, then go another way.
const fork = await session.fork({ fromStep: 1 }); // saved in the same store
const reply = await fork.send('Look at Porto instead.');
console.log(fork.id, reply.text); // 'trip-fork-1', 'Porto has a direct flight at 9:00.'
```

- الـ **step** رد واحد من الـ model في سجل المحادثة: رسالة assistant،
  مع رسائل الـ tools اللي بترد على الـ tool calls بتاعته. و`history()`
  بترجع `{ step, turn, messageIndex, text, toolCalls }` لكل خطوة، الأقدم الأول:
  `step` مرقّمة من 1 على الـ session كلها (مش لكل turn)، و`turn`
  مرقّمة من 0، و`messageIndex` هو index رسالة الـ assistant في
  `session.messages`، وكل tool call معاه `id` و`name` و`args` متعملها parse
  (الـ string الخام لو مش JSON) و`result` (محتوى رسالة الـ tool
  كنص، متكوّد JSON زي ما الـ model شافه). والخطوات copies.
- الـ **turn** بتبدأ عند كل رسالة user، فـ `turn` بتاع الخطوة هو الـ index المبدوء من 0
  لرسالة الـ user اللي بيرد عليها، نفس الترقيم اللي
  workspace rewind بيستخدمه. والـ input اللي اتعمله queue أو steer جوه turn شغالة
  (`turnPolicy: 'queue'` أو `'steer'`) رسالة user برضه، فبيبدأ
  turn جديدة في `history()`.
- `history()` هو تاريخ سجل المحادثة الحالي: بعد
  `session.compact()` الخطوات بتترقّم من جديد من السجل اللي اتعمله compaction.
  وturn الـ durable اللي لسه ما خلصت مش في السجل لسه، فما
  بتتسرد.
- `fork({ fromStep })` بيمسك السجل لحد آخر رسالة tool في الخطوة
  ومعاها؛ و`fromStep: 0` ما بيمسك حاجة. وخطوة برا
  `0..history().length` بتترفض بـ
  [`LOUSHO_SESSION_STEP_NOT_FOUND`](/ar/errors#lousho_session_step_not_found)،
  ورسالته بتسرد النطاق الصحيح.
- `patch: { toolResult: { toolCallId, result } }` بيبدّل نتيجة tool call
  واحدة في السجل المحتفَظ فيه ("ماذا لو البحث ما كان لقى ولا حاجة؟")،
  بنفس طريقة `patch` في `agent.fork()`.
- الـ fork بيتحفظ في نفس store بتاع الـ session، وهو session لنفس الـ agent بنفس
  الـ options (`store` وcheckpoints و`limits` و`turnPolicy` و`compaction`، و[وضع الصلاحيات](/ar/permission-modes)
  اللي الـ session عليه وقت الـ fork)، فالـ streaming والـ approvals والـ turns المعمولها checkpoint بيشتغلوا زي أي
  `agent.session()`، و`agent.session({ id: fork.id, store })` بيكمّلها
  بعدين، حتى في process تانية. والـ id بتاعته هو `id` لو
  مرّرته، وإلا `<id>-fork-<n>` لأول `n` من 1 ما لها سجل محادثة (ولو الـ id
  طويل زيادة على اللاحقة دي، `<start of id>-<8 hex of its hash>-fork-<n>`، ويفضل
  في حدود 128 حرف). و`id`
  إله سجل محادثة أصلًا (أو نفس id الـ session) بيترفض بـ
  [`LOUSHO_SESSION_EXISTS`](/ar/errors#lousho_session_exists).
- الـ `messages` بتاعة الـ fork بتمسك سجل محادثته أول ما `fork()` يرجع.
- سجل محادثة الـ session الأصلية وcheckpoints بتاعتها ما بيتغيروا.
- الـ budgets: الـ spend المسجَّل لـ `limits` بيفضل على الرسائل المحتفَظ فيها، فـ
  `limits` بتاع الـ fork بيبدأ من اللي الـ session صرفته عند نهاية آخر
  turn محتفَظ فيها (الـ turn بتسجّل صرفها على آخر رسالة فيها).
- `fork()` بيستنى الـ calls اللي في الـ queue، وبيرمي `LOUSHO_SESSION_BUSY` لما
  يكون في turn شغالة.
- ممكن تعمل fork لـ session متوقفة. والـ turn المتوقفة وapproval بتاعتها أو
  `ask_question` والـ turn المنقطعة في durable session بيفضلوا مع
  الـ session المصدر: الـ fork مالوش turn pending، و`agent.approvals.resolve()`
  بيكمّل المصدر بس، مرة واحدة.
- بس المحادثة هي اللي بتتعملها fork. الملفات اللي الـ agent كتبها والـ side
  effects التانية بتاع الخطوات بعد نقطة الـ fork ما بترجعش؛ وعشان ترجع
  ملفات مساحة العمل، شوف جزء الـ rewind في [أدوات مساحة العمل](/ar/workspace-tools).

وعشان تعمل fork لـ run واحدة بدأت بـ `agent.send(message, { sessionId })`، من
history بتاع checkpoints، استخدم `agent.fork()` بدل كده (شوف
[fork and replay](/ar/durable-execution#fork-و-replay)).
