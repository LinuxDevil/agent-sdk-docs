`agent.send(text)` هو turn واحد فقط: كل call يبدأ من سجل فارغ.
أما الـ **session** (جلسة) فهي محادثة من أكثر من turn: تحتفظ بسجل المحادثة
وتمرّره إلى الـ model مع كل `send()`.

انظر أيضًا: [إيقاف وإعادة تشغيل واستئناف](/ar/pause-and-resume)، وهو دليل قصير من البداية إلى النهاية.

> تترك لك الأمثلة في هذه الصفحة تعريف بعض الأسماء: `provider` هو أي `LLMProvider` (ودون اتصال: `createMockProvider()`).

```ts
import { createAgent } from 'lousho';

const chat = createAgent({ instructions: 'Be brief.', provider });

const session = chat.session(); // in memory, new generated id
await session.send('My name is Ali.');
const { text } = await session.send('What is my name?'); // sees the first exchange

console.log(session.id, session.messages.length);
```

## كائن الـ session

| العضو | الوصف |
| ------ | ----------- |
| `id` | معرّف الـ session: يُولَّد (UUID) إذا لم تمرّره بنفسك. |
| `send(input, { signal })` | يرسل رسالة user مع المحادثة كلها حتى الآن، ويُرجع `ExecutionResult` المعتاد. |
| `stream(input, { signal })` | مثل `send()`، لكنه يُرجع `AgentRun` يبث الـ turn على هيئة typed events - انظر [Streaming a session turn](#streaming-a-session-turn). |
| `messages` | snapshot للقراءة فقط من سجل المحادثة (رسائل الـ user والـ assistant والـ tool؛ دون الـ system prompt). تعديل الـ snapshot لا يغيّر الـ session. |
| `load()` | يقرأ سجل المحادثة المحفوظ من الـ store. يستدعيها `send()` نيابةً عنك؛ استدعِها لكي تعرض السجل قبل أول `send()` في session مستأنفة. كل call (`load()` و`send()` و`history()`، ...) يقرأ الـ store من جديد، لذا تظهر الـ turns التي أجرى لها كائن session آخر commit على المعرّف نفسه. |
| `compact(options?)` | يُجري compaction لسجل المحادثة فورًا - انظر [ضغط سياق جلسة](/ar/compaction#الـcompaction-على-session). |
| `clear()` | يفرّغ سجل المحادثة ويحفظه فارغًا (فلا تبقى في الـ store رسائل لهذا المعرّف). يحتفظ بمعرّف الـ session والـ store والـ options؛ ويحذف checkpoint كل turn والـ checkpoint history الخاص بها (`<id>.turn-<n>`، وهي تحتوي على نسخ من سجل المحادثة)، لذا لا يستطيع `agent.fork('<id>.turn-<n>')` استعادة المحادثة؛ أما خانات الـ memory فمشتركة بين الـ sessions ولا تتأثر. يرسل `context.cleared` إلى الـ listeners المسجّلة عبر `on()`. يرمي `LOUSHO_SESSION_BUSY` إذا كانت هناك turn قيد التشغيل، و`LOUSHO_SESSION_AWAITING_APPROVAL` إذا كانت هناك turn durable تنتظر approval. |
| `on(listener)` | يستمع إلى events الـ session: events كل turn فور حدوثها (turns الخاصة بـ `send()` و`stream()`، والـ turn المتوقفة التي يكملها `agent.approvals.resolve()`)، بالإضافة إلى events الخاصة بـ `compact()` / `clear()` (`compaction.start` و`compaction.done` و`context.cleared`)؛ ويُرجع function تزيل الـ listener. events الـ turn هي أحداث `AgentEvent` التي يُصدرها `stream()` الخاص بها. |
| `pending()` | في [durable session](#durable-sessions): الـ turn التي لم تكتمل بعد (`{ status, approvalId?, approvalKind?, idempotencyKey? }`؛ تكون `approvalKind` هي `'question'` عندما تنتظر الـ turn `ask_question`؛ و`idempotencyKey` هو `Idempotency-Key` الخاص بـ HTTP للـ turn، انظر [إعادة إرسال turn](/ar/deployment#إعادة-إرسال-turn))، أو `null`. |
| `resume({ signal })` | في durable session: يُكمل turn منقطعة ويُرجع نتيجتها، أو `null` إذا لم تكن هناك turn pending. |
| `discardPending()` | في durable session: يتخلّص من turn غير مكتملة دون تشغيلها، ويسحب الـ approvals التي كانت تنتظرها (فلا تُسرَد مرة أخرى، وتفشل أي محاولة للبتّ في إحداها بـ `LOUSHO_APPROVAL_NOT_FOUND`). ويتخلّص أيضًا من checkpoint turn لا يمكن قراءته (`LOUSHO_CHECKPOINT_CORRUPT`). |
| `history()` | خطوات سجل المحادثة (خطوة لكل رد من الـ model، مع الـ tool calls الخاصة به ونتائجها) - انظر [Forking a session](#forking-a-session). |
| `fork({ fromStep, id?, patch? })` | session جديدة تبدأ من سجل محادثة هذه الـ session حتى خطوة معيّنة؛ ولا تتغير هذه الـ session - انظر [Forking a session](#forking-a-session). |

استدعاءات `send()` المتزامنة على الـ session نفسها تُصَفّ وتُنفَّذ
واحدًا تلو الآخر بترتيب الاستدعاء، فلا يتداخل سجل المحادثة أبدًا.

يحدد `agent.session({ id, turnPolicy })` سلوك `send()` أو `stream()`
عندما تكون هناك turn قيد التشغيل أو تنتظر البدء:

- `'wait'` (الافتراضي): ينتظر ويُنفَّذ كـ turn مستقلة، كما سبق.
- `'queue'`: ينضم الـ input الخاص به إلى تلك الـ turn، مثل
  [`run.enqueue()`](/ar/queue-and-steer#queued-input): يُضاف بعد
  نتائج الـ tools في الخطوة الحالية، ويراه call الـ model التالي في الـ turn.
  يُرجع الـ call نتيجة تلك الـ turn (ولا يسري الـ `signal` الخاص به
  على الـ turn)، ويحتوي سجل المحادثة المحفوظ عند انتهاء الـ turn
  على رسالة الـ user التي دخلت الـ queue في موضعها. أما `stream()` المنضم
  فلا يُصدر إلا `run.done` الخاص بالـ turn؛ وتُبَث events الـ turn،
  ومنها `input.queued` و`input.applied`، على
  الـ run الذي بدأها. إذا انتهت الـ turn قبل أن تتمكن من أخذ الـ input
  (اكتملت، أو توقفت، أو أُلغيت)، يُنفَّذ الـ call كـ turn تالية في
  النهاية على أي حال — إلا في durable session لا تزال الـ turn المتوقفة فيها
  pending: هنا يستأنفها الـ call أولًا، ويرمي
  `SessionAwaitingApprovalError` إذا كانت لا تزال تنتظر الـ approval
  (بُتّ فيها بـ `agent.approvals.resolve()`). وإذا فشلت الـ turn، يرمي الـ call
  الـ error نفسه؛ وفي durable session يبقى الـ input في
  checkpoint الـ turn ويطبّقه `resume()`.
- `'steer'`: مثل `'queue'`، لكن الـ input ينضم عبر
  [`run.steer()`](/ar/queue-and-steer#steering): إذا لم يكن call الـ model في الـ turn
  قد أصدر أي شيء بعد، فإنه يُلغى ويُعاد من البداية مع الرسالة الجديدة،
  ولا تُنفَّذ الـ tool calls الخاصة بالـ turn التي لم تبدأ بعد.
  وفيما عدا ذلك ينتظر نقطة الأمان التالية، مثل `'queue'`. يُرجع الـ call
  نتيجة الـ turn، وتسري الـ fallbacks نفسها.

البادئة `vendor/` في اسم الـ model هي التي تحدد الـ provider؛ ومع OpenRouter استخدم
`openrouter/<vendor>/<model>` (مثلًا `openrouter/openai/gpt-4o-mini`).

```ts
import { createAgent } from 'lousho';

const agent = createAgent({ model: 'openai/gpt-4o-mini' });
const session = agent.session({ id: 'user-42', turnPolicy: 'queue' });

const first = session.send('Find flights to Rome.');
const second = session.send('Only direct ones, please.'); // joins the first turn
console.log((await second) === (await first)); // true: one turn, one result
```

يقبل `send()` و`stream()` نصًا (string)، أو content parts (`[{ type: 'text', ... }, { type: 'image', ... }]`، وهي رسالة user واحدة)، أو `Message[]`؛ وتحتفظ الـ stores بالـ parts، انظر [المدخلات متعددة الوسائط](/ar/providers#إدخال-multimodal).

إذا رمى `send()` (error من الـ provider، أو tool ترمي
`PropagatingToolError`) فإنه يترك سجل المحادثة كما كان تمامًا قبل الـ call.
أما `send()` الذي يُلغى بـ `signal` (زر Stop مثلًا) فيحتفظ بما قاله
الـ user والـ model حتى تلك اللحظة، لكي يبقى السياق متاحًا لـ `GET /chat/:id`
وللـ turn التالية:

- رسالة الـ user، بشرط أن يكون الـ model قد استُدعي (الـ signal الملغى قبل أول
  call للـ model يتخلّص من الـ turn كلها)؛
- الـ turn حتى آخر tool call نُفِّذ (الـ tool calls الخاصة بالـ assistant
  ونتائجها؛ وتأخذ الـ calls التي في الدفعة نفسها ولم تبدأ نتيجة
  "cancelled")، لذا يستحيل أن يضيع side effect مثل refund من السجل؛
- الرد الذي بثّه الـ model حتى توقفه، كرسالة assistant
  تحمل `metadata: { interrupted: true }` (`stream()` وحده هو الذي يبث؛
  أما `send()` العادي فليس له رد جزئي).

ويُرجع `send()` الملغى `finishReason: 'aborted'`، مثل `agent.send()`.
ويحتسب الـ `usage` الخاص به call الـ model الذي توقف، بتقدير من الـ request
والنص المبثوث إذا لم يُبلغ الـ provider بشيء، لكي
لا يُحتسب `limits.maxCostUsd` الخاص بالـ session أقل من الحقيقة. ويستحيل أن يحتوي سجل المحادثة المحفوظ
على turn للـ assistant فيها tool calls دون نتائج الـ tools المقابلة.

إذا توقف `send()` عند tool فيها `needsApproval` فإنه يُرجع
`finishReason: 'awaiting-approval'`. بعد ذلك يُكمل `agent.approvals.resolve({ id, approved })`
الـ run كـ turn تالية في الـ session، فينضم الـ tool call ونتيجته
والإجابة النهائية إلى سجل المحادثة (انظر
[approvals](/ar/approvals)).

يضع `agent.session({ id, limits })` budgets على جميع turns الـ session
(مثلًا `{ maxCostUsd: 1 }`)، وتُحتسب من الـ usage المحفوظ مع
سجل المحادثة؛ أما `createAgent({ limits })` فيقيّد كل turn على حدة. انظر
[الميزانيات](/ar/configuration#الميزانيات).

## Streaming a session turn

`session.stream(input, { signal })` هو `agent.stream()` لكن لمحادثة:
يُرجع الـ `AgentRun` نفسه (typed events مع promise اسمه `result`، انظر
[streaming](/ar/streaming))، لكن الـ turn ترى سجل المحادثة حتى تلك اللحظة
وتنضم إليه.

```ts
import { createAgent } from 'lousho';

const chat = createAgent({ instructions: 'Be brief.', provider });
const session = chat.session();

for await (const event of session.stream('My name is Ali.')) {
  if (event.type === 'text.delta') process.stdout.write(event.text);
}
// The turn is already saved: this call sees it.
const { text } = await session.send('What is my name?');
```

- يبني قائمة الرسائل نفسها التي يبنيها `send()` ويُصَفّ خلف الـ calls السابقة
  على الـ session (يمكنك الخلط بين `send()` و`stream()`).
- عندما ينتهي الـ run، تُحفظ رسالة الـ user الجديدة ومخرجات الـ run
  تمامًا كما يحفظها `send()`، وبعد ذلك فقط يُسلَّم `run.done`. أي أنه عندما
  تنتهي حلقة `for await`، أو يُرجع `run.result`، يكون سجل المحادثة
  مكتملًا. وتحمل الـ events الـ `runId` الخاص بالـ handle المُرجَع.
- الـ run الفاشل يترك سجل المحادثة كما كان قبل الـ call، مثل `send()`.
  أما الـ run الملغى (بـ `signal`، أو عندما تخرج من الحلقة مبكرًا) فيحتفظ برسالة
  الـ user والـ tool calls التي نُفِّذت والرد المبثوث حتى تلك اللحظة
  (مُعلَّمًا بـ `metadata.interrupted`)، مثل `send()` الملغى. والـ run الذي
  كان قد انتهى أصلًا عند مغادرة الحلقة يُحفظ. والـ run الفاشل يُغلق
  الـ stream بـ `error` و`run.done` (`finishReason: 'error'`)،
  ويرمي `run.result`. ويشمل ذلك الـ store الذي يفشل في الـ load أو الـ save:
  وعندئذ لا يكون للـ turn حدث `run.start`.
- الـ run الذي يتوقف عند tool فيها `needsApproval` ينتهي بـ `approval.requested`
  و`run.done` (`'awaiting-approval'`)، تمامًا كما يُرجع `send()`، ويحتوي سجل
  المحادثة على الـ turn حتى موضع التوقف. ويُكملها `agent.approvals.resolve()`
  كـ turn تالية في الـ session. ولا يسري callback الخاص بـ `approve`
  على الـ streams، مثل `agent.stream()`.

الـ sessions طبقة رقيقة: تحتفظ الـ session بسجل المحادثة وتسلّمه إلى الـ
executor في كل turn. ودون checkpoint store، لا تُحفظ الـ turn إلا عند
اكتمالها، لذا يُضيّعها crash في منتصفها؛ انظر القسم التالي.

## Two kinds of conversation id

`agent.session({ id })` و`agent.send(msg, { sessionId })` محادثتان مختلفتان.
لدى الـ SDK طريقتان لحفظ محادثة تحت معرّف، ولا تتشاركان
التخزين نفسه:

| | `agent.session({ id }).send(msg)` | `agent.send(msg, { sessionId })` |
| --- | --- | --- |
| ما هي | session: سجل محادثة، و`send()` واحد لكل turn | run واحد durable (انظر [durable execution](/ar/durable-execution))؛ استدعاؤه مرة أخرى بالمعرّف نفسه يُكمله |
| أين تُحفظ المحادثة | `store.sessions` تحت `id` (يُحفظ checkpoint لكل turn باسم `<id>.turn-<n>` أثناء تشغيلها) | `store.checkpoints` تحت `sessionId` (الـ `messages` الخاصة بالـ checkpoint) |
| ما الذي تحتاجه | لا شيء (في الـ memory افتراضيًا) | `store.checkpoints` (وبدونه `LOUSHO_CONFIG_MISSING_CHECKPOINT_STORE`) |
| تقرؤها مرة أخرى بـ | `session.load()`، `GET /chat/:id` | `store.checkpoints.load(sessionId)` (الـ `messages` الخاصة به)، `agent.fork(sessionId)` |
| تُكملها بعد crash بـ | `agent.session({ id }).resume()` | `agent.resume(sessionId)` |

استخدم طريقة واحدة لكل معرّف. المعرّف المستخدم بالطريقتين يحتوي على محادثتين لا علاقة بينهما:
الـ turn المرسلة بإحدى الطريقتين لا ترى الـ turns المرسلة بالطريقة الأخرى، و
`GET /chat/:id` يعرض سجل محادثة الـ session فقط. يبحث `agent.resume(id)`
أولًا عن run خاص بـ `send({ sessionId })`، وإذا لم يجده، يستأنف عندئذ فقط
الـ turn الـ pending الخاصة بالـ session، لذا إذا وُجد الاثنان فإنه يُكمل الـ run ويترك
turn الـ session في حالة pending (أكملها بـ `agent.session({ id }).resume()`).
وتعمل الـ prompt schedules كـ runs من نوع `send({ sessionId })` (انظر
[الجداول الزمنية](/ar/schedules#الـ-prompt-schedules-والـ-sessions))، لذا اقرأ تقارير الـ schedule
من `store.checkpoints`، لا من `GET /chat/:id`.

## Durable sessions

أعطِ الـ agent `store` يحتوي على checkpoints، فيُحفظ checkpoint لكل turn في الـ session
بعد كل رد من الـ model وكل نتيجة tool، باستخدام
آلية [durable execution](/ar/durable-execution). والـ turn التي يقطعها
crash، أو فشل في كتابة checkpoint، أو `PropagatingToolError`، يمكن
إكمالها لاحقًا، في process أخرى:

```ts
import { createAgent } from 'lousho';
import { SqliteStore } from 'lousho/sqlite';

const agent = createAgent({ provider, store: new SqliteStore('./.lousho/agent.db') });

// After a restart: finish the turn that was running, if any.
const finished = await agent.resume('user-42'); // ExecutionResult, or null when nothing was pending
console.log(finished?.text, await agent.session({ id: 'user-42' }).pending()); // pending() is null now
```

- يقبل `createAgent({ store })` أي `AgentStore`
  (`{ sessions?, checkpoints?, approvals? }`، انظر [Choosing a store](#choosing-a-store)):
  يضع `agent.session({ id })` سجل محادثته في `store.sessions`
  والـ checkpoints الخاصة به في `store.checkpoints`، ويحتفظ `store.approvals`
  بتوقفات الـ approval. ويتقدّم الـ `store` الخاص بالـ session (أي `SessionStore`، أو
  كائن `{ sessions, checkpoints }`) و`checkpointStore` على store
  الـ agent، جزءًا بجزء.
- `agent.resume(id)` هو نفسه `agent.session({ id }).resume()`، والفرق أنه
  يُكمل أولًا الـ run الذي بدأ بـ `agent.send(message, { sessionId: id })` (انظر
  [durable execution](/ar/durable-execution) و
  [نوعا الـ id](#two-kinds-of-conversation-id)).
- تعمل كل turn بـ `sessionId: '<session id>.turn-<n>'` (حيث `n` هو طول
  سجل المحادثة لحظة بدء الـ turn)، لذا تجد الـ process الجديدة
  الـ turn المنقطعة دون أي عمل تتبّع إضافي. والـ turn المكتملة تنضم
  إلى سجل المحادثة، تمامًا مثل `send()` العادي، ويُحذف الـ checkpoint الخاص بها.
  معرّف الـ turn هذا مجرد مفتاح للـ checkpoint: لا تزال الـ tools و`needsApproval` وقواعد
  الـ permissions والـ hooks الخاصة بالـ tool calls تأخذ معرّف الـ session نفسه كـ `ctx.sessionId`.
  يبقى الـ checkpoint history الخاص بالـ turn محفوظًا لآخر `turnHistoryLimit`
  turns أُجري لها commit (الافتراضي 10، `agent.session({ id, turnHistoryLimit })`)، لكي
  يستطيع `agent.fork('<id>.turn-<n>', { fromStep })` إجراء fork منها؛ وتُحذف histories
  الـ turns الأقدم مع commit الـ turns الجديدة (كل entry في الـ history يحتوي على نسخة من
  سجل المحادثة كله، فلو احتُفظ بـ history كل الـ turns لنما الـ store بمربع
  طول المحادثة)، حتى لو استخدمت كل turn كائن store أو process جديدة.
  والـ history الموجود خارج النافذة أصلًا في الـ store -
  من إصدار أقدم، أو تحت `turnHistoryLimit` أكبر - يُحذف هو أيضًا
  على مدار الـ commits التالية، بحدّ 32 turn في كل commit، الأقدم أولًا؛ والـ process
  التي تُجري commit لـ turn واحدة فقط تُنظّف أقدم 32، و
  `fileStore(dir).prune()` / `SqliteStore.prune()` يحذفان الباقي.
  أما `session.fork()` فيعمل من سجل المحادثة ولا يتقيّد بهذا الحد.
- أثناء التشغيل، تحتفظ الـ turn بـ run lease على الـ checkpoint الخاص بها (انظر
  [durable execution](/ar/durable-execution#run-leases)): أي `send()` على
  الـ session نفسها من process أو replica أو كائن store آخر يفشل بـ
  `LOUSHO_SESSION_BUSY` قبل أن يشغّل أي شيء، بدلًا من أن يستأنف الـ turn
  الجارية ويشغّل الـ tool calls الخاصة بها مرة ثانية.
- يُكمل `resume()` الـ turn عبر مسار الـ resume في الـ executor
  (`input: []`): لا تُنفَّذ مرة أخرى الـ tool calls التي سُجِّلت نتائجها،
  ولا يُطلب رد الـ model المسجَّل مرة أخرى. لكن الـ tool التي كانت قيد التشغيل
  عندما توقفت الـ process تُنفَّذ مرة أخرى (at-least-once، انظر
  [durable execution](/ar/durable-execution#at-least-once-tools-اجعل-الـ-side-effects-idempotent)).
- يستأنف `send()` و`stream()` الـ turn الـ pending أولًا، ثم
  يرسلان الرسالة الجديدة، فيرى الـ model الـ turn مكتملة (لا تُبَث events
  الـ turn المستأنفة). استخدم `pending()` للتحقق
  أولًا، أو `discardPending()` لكي تتخلّص من الـ turn غير المكتملة.
- الـ turn التي تفشل تسجّل الـ error وعدد المحاولات على الـ checkpoint الخاص بها
  (`lastError` و`attempts`). إذا كان الـ error لن يزول بإعادة المحاولة (400 من
  الـ provider مثل تجاوز طول السياق، أو فشل في الـ auth)، فإن
  `send()` / `stream()` التالي لا يعيد الـ turn: بل يفشل بـ
  `LOUSHO_SESSION_TURN_FAILED`. استدعِ `discardPending()` لكي تتخلّص من الـ turn، أو
  `resume()` لكي تعيد المحاولة بعد إصلاح السبب. أما أنواع الفشل الأخرى (crash، أو
  5xx، أو error في الشبكة) فلا يزال `send()` التالي يستأنفها. وينطبق ذلك
  أيضًا على turn فشل فيها أول call للـ model: لم يحفظ الـ run أي
  checkpoint بعد، لذا تحتفظ الـ session بالـ input الخاص بالـ turn كـ turn pending
  (يُبلغ `pending()` أنها `in-progress`) وتعيد تشغيلها من هذا الـ input.
- الـ turn التي تتوقف عند tool فيها `needsApproval` تبقى في الـ checkpoint الخاص بها، لا في
  سجل المحادثة، حتى تكتمل. وأثناء انتظارها، يرمي `resume()` و`send()`
  و`stream()` الخطأ `SessionAwaitingApprovalError` (ومعه `approvalId`)،
  ويُكمل `agent.approvals.resolve({ id, approved })` الـ turn في هذه الـ
  session. وبعد restart، يُكملها أيضًا `agent.approvals.resolve()` أو `streamResolve()`
  من الـ process الجديدة: يجد الـ agent الـ session من
  سجل التوقف (لمعرّفات الـ session التي تحتوي على حروف وأرقام و`_` و`-`)، فلا
  داعي لفتح الـ session أو استدعاء `resume()` أولًا. وأعطِ كلا الـ agents
  الـ `store` الدائم نفسه (أو `approvalStore`).
- يُرجع `resume()` نتيجة الـ turn المكتملة؛ ولا يبث، و
  `stream()` أيضًا لا يبث الـ turn الـ pending التي يُكملها أولًا. ولكي
  تعرض تقدّم turn مستأنفة، سجّل `session.on(listener)` قبل
  الـ call (أو مرّر `createAgent({ onEvent })`): تصله أحداث `AgentEvent` الخاصة بالـ turn
  فور حدوثها.
- الـ turn المتوقفة تقفل معرّف الـ session: تسجّلها الـ session تحت
  `<id>.paused` في الـ checkpoint store، لذا يُرفض `agent.send(message, { sessionId: id })`،
  و`agent.stream()` بالـ `sessionId` نفسه، وأي كائن session على سجل محادثة
  مختلف (store آخر، أو سجل بطول مختلف) بالخطأ
  `SessionAwaitingApprovalError` (`LOUSHO_SESSION_AWAITING_APPROVAL`) أيضًا، و
  يُبلغ `pending()` الخاص بها عن التوقف. بُتّ في الـ approval، أو تخلّص من الـ turn بـ
  `agent.session({ id }).discardPending()`، لكي تقبل الـ session turns جديدة مرة أخرى.
- الـ turn الملغاة يُحذف الـ checkpoint الخاص بها؛ وما احتفظت به (رسالة الـ user،
  والـ tool calls التي نُفِّذت، والرد المنقطع) ينضم إلى سجل المحادثة، كما يحدث
  دون checkpoint store. ويحذف `clear()` الـ turn الـ pending أيضًا، والـ checkpoint
  history الخاص بكل turn، لذا لم يعد ممكنًا إجراء fork للـ turns المحذوفة.

## Stores

يحتفظ `SessionStore` بسجلات المحادثات بين الـ calls:

```ts
import type { Message } from 'lousho';

interface SessionStore {
  load(id: string): Promise<Message[] | undefined>;
  save(id: string, messages: readonly Message[]): Promise<void>;
  delete(id: string): Promise<void>;
  // Optional compare-and-swap: save only if the stored transcript still has this revision.
  saveIf?(id: string, expectedRevision: string, messages: readonly Message[]): Promise<boolean>;
}
```

تُجري كل turn الـ commit عبر `saveIf` إذا كان الـ store يوفّرها، مع
`transcriptRevision(<the transcript the turn started from>)`. فإذا أنهت عمليتان (أو
كائنا store على البيانات نفسها) turn على الـ session نفسها في اللحظة
نفسها، لا يمكن أن تُجري الاثنتان commit: تنجح إحداهما، ويرمي `send()` الخاص بالأخرى
`LOUSHO_SESSION_BUSY`. وتطبّقها `MemorySessionStore` و`FileSessionStore` (ملف
`<id>.json.lock` يُنشأ بشكل حصري؛ والـ lock الأقدم من `staleLockMs`،
الافتراضي 10 ثوانٍ، يُستولى عليه) و`SqliteStore.sessions` (transaction واحدة
`BEGIN IMMEDIATE`). أما الـ store الذي لا يوفّرها، مثل `KVStore.sessions` (فالـ KV
لا يدعم compare-and-swap)، فيُجري load ومقارنة وsave بأفضل جهد، وقد
يتدخّل بينها writer في process أخرى، فتضيع turn واحدة.

- `MemorySessionStore` (الافتراضي، store جديد لكل session) يبقى طالما
  الـ process تعمل. شارك الـ instance نفسه بين الـ sessions لكي تجدها بالمعرّف.
- يكتب `FileSessionStore(dir)` ملف JSON واحدًا لكل session (`<dir>/<id>.json`)،
  كتابةً atomic (ملف مؤقت ثم rename)، وينشئ `dir` عند أول save. وكل
  حرف uppercase في المعرّف يُكتب كـ `^` يليه الحرف lowercase
  (`Alice` -> `^alice.json`)، لذا تأخذ المعرّفات التي تختلف في حالة الحروف فقط ملفات
  مختلفة على Windows وmacOS أيضًا.

```ts
import { createAgent, FileSessionStore } from 'lousho';

const agent = createAgent({ provider });
const store = new FileSessionStore('./.lousho/sessions');

const first = agent.session({ id: 'user-42', store });
await first.send('My name is Ali.');

// Later, even in another process or another createAgent() instance:
const again = agent.session({ id: 'user-42', store });
await again.send('What is my name?'); // "Ali"
```

يجب أن تطابق معرّفات الـ sessions النمط `^[A-Za-z0-9_-]{1,128}$` (فهي تصبح أسماء ملفات، ولذلك
يُرفض `../x` و`a/b` بـ error يوضّح السبب). طبّق
`SessionStore` بنفسك لكي تضع سجلات المحادثات في database أو Redis.

يحتوي `AgentStore` على جزء رابع اختياري إلى جانب `sessions` و`checkpoints`
و`approvals`: وهو `tokens`، أي access وrefresh tokens الخاصة بـ OAuth للـ tools
والاتصالات، وتخزّنها الـ stores من نوع file وSQLite وKV مشفّرة (انظر
[OAuth](/ar/oauth#تخزين-tokens)).

## Choosing a store

لكلٍّ من الـ sessions وcheckpoints الخاصة بـ durable execution والـ approvals
واجهة store (`SessionStore` و`CheckpointStore` و`ApprovalStore`). اختر
الـ implementation بحسب مكان تشغيل الـ process:

| Store | Sessions | Checkpoints | Approvals | استخدمه عندما |
| --- | --- | --- | --- | --- |
| In memory (`memoryStore()`) | `MemorySessionStore` | in memory | `InMemoryApprovalStore` | الـ tests والـ scripts، وprocess واحدة لا يُعاد تشغيلها أبدًا |
| Files (`fileStore(dir)`) | `<dir>/sessions/<id>.json` | `<dir>/checkpoints/` و`<dir>/checkpoint-history/` | `<dir>/approvals/<id>.json` | جهاز واحد، وتريد ملفات عادية يمكنك فحصها |
| SQLite | `store.sessions` | `store.checkpoints` | `store.approvals` | سيرفر Node: ملف واحد durable يدعم الـ transactions، وتتشاركه عدة processes على host واحد (انظر [مشاركة ملف SQLite](#مشاركة-ملف-sqlite)) |
| Cloudflare KV (`KVStore` من `lousho/kv`) | `store.sessions` | `store.checkpoints` | `store.approvals` | الـ deployments على Workers (انظر [النشر](/ar/deployment)) |

كلٌّ منها جزء من `AgentStore`: مرّرها معًا هكذا
`createAgent({ store: { sessions, checkpoints, approvals } })`. و`memoryStore()`
و`fileStore(dir)` و`SqliteStore` و`KVStore` هي `AgentStore`s جاهزة. وللملفات
العادية، يكتب `fileStore(dir)` ملف JSON واحدًا لكل session وcheckpoint وapproval
pending تحت `dir`، ويُكتب كلٌّ منها في ملف مؤقت، ثم يُجرى له flush على القرص، ثم rename
إلى مكانه (فلا يترك crash أو انقطاع كهرباء نصف ملف أبدًا). على Windows، يفشل الـ rename فوق ملف، أو قراءة ملف،
مفتوح لدى writer أو reader آخر لحظيًا بـ `EPERM` أو `EACCES` أو
`EBUSY`؛ ويعيد `fileStore()` و`FileSessionStore` المحاولة مع backoff قصير (نحو
1.3 ثانية إجمالًا) ثم يفشلان بـ `LOUSHO_STORAGE_FAILED`. ولا تزال الـ saves المتزامنة على
الملف نفسه تنتهي بواحد منها فقط (آخر rename هو الذي ينجح):

```ts
import { createAgent, fileStore } from 'lousho';

const agent = createAgent({ provider, store: fileStore('./.lousho') });
// ./.lousho/sessions/user-42.json, ./.lousho/checkpoints/..., ./.lousho/approvals/...
await agent.session({ id: 'user-42' }).send('Hello');
```

في كل اسم ملف، يُكتب الحرف الـ uppercase في المعرّف كـ `^` يليه
الحرف lowercase (`Alice` -> `sessions/^alice.json`): فأنظمة الملفات الافتراضية
في Windows وmacOS لا تفرّق بين حالة الحروف، ويجب ألا يتشارك `alice` و`Alice`
سجل المحادثة نفسه. والمعرّف الذي لا يحتوي على حروف uppercase يبقى باسمه العادي. والملف
الذي حُفظ بإصدار أقدم تحت اسم بحروف مختلطة (`Alice.json`) لا يزال يُقرأ
للمعرّف نفسه تمامًا، ويُنقل إلى اسمه الجديد في الـ save التالي. والمعرّف الذي
سينتج اسم ملف طويلًا جدًا بعد الـ encoding (session id كله uppercase بطول 128 حرفًا
مضافًا إليه `.turn-<n>`)، أو اسم جهاز في Windows (`nul`، `com1`)، يُخزَّن
باسم `~<prefix>~<hash>.json` بدلًا من ذلك.

بجانب كل ملف `checkpoints/<id>.json` ملف `checkpoint-history/<id>.json`: وهو الـ history المحدود للـ checkpoint، الأقدم أولًا. وتُنشأ المجلدات عند أول كتابة، لذا لا يظهر `approvals/` (و`oauth/`) إلا بعد أول approval pending (أو sign-in).

البتّ في approval من `fileStore` آمن عبر الـ processes (caller واحد فقط
يأخذ السجل، والـ claim الذي تركه resolver متعطّل يُستولى عليه بعد
دقيقة)؛ وتُجري الـ session الـ commit للـ turns الخاصة بها بـ compare-and-swap تحت ملف lock
(`sessions/<id>.json.lock`)، والـ run الجاري الذي يُحفظ له checkpoint يحتفظ بالـ run lease الخاص به
في `leases/<id>.json` (انظر [durable execution](/ar/durable-execution#run-leases)).
وإذا كانت لديك processes كثيرة تتشارك store، فإن `SqliteStore` هو الخيار الأمتن.

يحذف `fileStore(dir).prune({ olderThanMs })` ما كانت آخر كتابة له قبل أكثر من
`olderThanMs`، مثل `SqliteStore.prune()`: سجلات المحادثات والـ checkpoints وملفات
الـ checkpoint history، بالإضافة إلى sign-ins الخاصة بـ OAuth الـ pending المنتهية. ويبقى الـ run المتوقف على
approval pending، مهما كان قديمًا (الـ checkpoint الخاص به والـ history الخاص به وسجل محادثة
الـ session الخاصة به)، وتبقى أيضًا الـ approvals الـ pending وOAuth tokens. ويُرجع
الأعداد، `{ sessions, checkpoints, checkpointHistory, oauthPending }`:

```ts
import { fileStore } from 'lousho';

const store = fileStore('./.lousho');
await store.prune({ olderThanMs: 30 * 24 * 60 * 60 * 1000 }); // a month
```

وأي object يملك الدوال الثلاث لجزء معيّن يعمل مكانه أيضًا: `SessionStore`
على Redis، أو `CheckpointStore` مبني على KV في Cloudflare Workers (يستخدم الـ
Worker المولَّد `KVCheckpointStore`، انظر [النشر](/ar/deployment)).

يخزّن `SqliteStore` الثلاثة في ملف database واحد، باستخدام
`node:sqlite` المدمج في Node (دون native dependency؛ يتطلب Node 22.13 أو أحدث، ولا
يُعاد تصديره من الـ root entry، لذا لا يحمّله استيراد الـ SDK أبدًا):

```ts
import { createAgent } from 'lousho';
import { SqliteStore } from 'lousho/sqlite';

const store = new SqliteStore('./.lousho/agent.db'); // or ':memory:'
const agent = createAgent({ provider, store }); // transcripts, per-step checkpoints and approvals
await agent.session({ id: 'user-42' }).send('Hello');

store.prune({ olderThanMs: 7 * 24 * 60 * 60 * 1000 }); // { sessions, checkpoints, approvals, oauthPending } deleted
store.close();
```

مع الـ executor مباشرةً، مرّر `store.checkpoints` كـ `checkpointStore` و
`store.approvals` كـ `approvalStore`؛ انظر [executor API](/ar/executor-api).

- يُنشأ المجلد إذا لم يكن موجودًا. والـ schema لها versioning عبر
  `PRAGMA user_version` وتُجرى لها migration عند الفتح؛ وتُرفض الـ database المكتوبة
  بإصدار أحدث.
- وضع WAL وانتظار قصير للـ lock مع إعادة المحاولة (نحو 5 ثوانٍ إجمالًا، ثم
  `LOUSHO_STORAGE_BUSY`) يتيحان لعدة processes أن تتشارك الملف. ولا يستطيع إلا واحد منها
  البتّ في الـ approval. انظر [مشاركة ملف SQLite](#مشاركة-ملف-sqlite).
- تُخزَّن الـ checkpoints وsnapshots الخاصة بالـ approval كـ JSON معتم لا يُفسَّر محتواه، لذا
  تمرّ الحقول الجديدة في round-trip دون تغيير.
- يزيل `prune()` الـ sessions والـ checkpoints التي لم تُحدَّث خلال `olderThanMs`،
  والـ approvals التي حُسمت قبل تلك المدة وsign-ins الخاصة بـ OAuth الـ pending المنتهية؛
  أما الـ approvals التي لم تُحسم بعد وOAuth tokens فتبقى، وكذلك الـ turn المتوقفة على
  approval لم تُحسم بعد (الـ checkpoint الخاص بها وسجل محادثة الـ session)،
  مهما كانت قديمة. والبتّ في approval حُذفت الـ turn المتوقفة الخاصة بها على أي حال
  يفشل بـ [`LOUSHO_APPROVAL_ORPHANED`](/ar/errors#lousho_approval_orphaned)
  دون تشغيل الـ tool.
- الملف الذي ليس database خاصة بـ SQLite يفشل بـ error يذكر المسار؛
  واستخدام الـ store بعد `close()` يرمي error واضحًا.

### مشاركة ملف SQLite

هذا هو القسم الوحيد الذي تربط إليه الصفحات الأخرى.

- **مدعوم:** عدة processes (مثلًا نسختا replica من Docker على named volume واحد، أو
  سيرفر وCLI) على **host واحد**، تتشارك ملف SQLite واحدًا على **قرص محلي**.
  يعمل الملف بوضع WAL، وكل turn في session تحتفظ بـ
  [run lease](/ar/durable-execution#run-leases)، لذا يمكن للـ replicas أن تتبادل
  الرسائل على الـ session نفسها. والكتابة على session تشغّلها process أخرى
  تفشل بـ `LOUSHO_SESSION_BUSY`؛ ويردّ عليها `POST /chat` والـ channels
  بـ `409` وهيدر `Retry-After`، فأعد المحاولة.
- **غير مدعوم:** ملف SQLite على filesystem شبكي (NFS، EFS، SMB)، لأن SQLite
  لا تستطيع الاعتماد على الـ locking الخاص به، ولا عدة hosts. لعدة hosts،
  طبّق `SessionStore` و`CheckpointStore` و`ApprovalStore` على
  database مشتركة مثل Postgres أو Redis. لا يتضمن الـ SDK أي store شبكي.
- **الساعات والـ PIDs:** تُحتسب الـ leases بساعة كل process على حدة، لذا اجعل
  ساعات الـ replicas متزامنة (NTP). ولا يُستولى على الـ run المتعطّل مبكرًا إلا عندما يثبت
  أن الـ process الخاصة به غير موجودة على الـ host نفسه (يُفحص الـ boot id
  والـ PID namespace ووقت بدء الـ process)؛ وفيما عدا ذلك ينتظر من 30 إلى 60 ثانية
  حتى تنتهي الـ lease. انظر [Run leases](/ar/durable-execution#run-leases).

## Forking a session

تسرد `session.history()` خطوات الـ session، ويبدأ `session.fork({ fromStep })` session جديدة من أي خطوة منها، فتستطيع تجربة اتجاه آخر
دون أن تفقد المحادثة الأصلية:

```ts
import { createAgent, defineTool } from 'lousho';
import { mockModel } from 'lousho/testing';
import { z } from 'zod';

const searchFlights = defineTool({
  name: 'search_flights',
  description: 'Find flights to a city',
  input: z.object({ to: z.string() }),
  execute: async ({ to }) => `2 flights to ${to}`,
});
const agent = createAgent({
  tools: [searchFlights],
  provider: mockModel([
    { toolCalls: [{ name: 'search_flights', args: { to: 'Lisbon' } }] },
    'Two flights to Lisbon on Friday.',
    'Porto has a direct flight at 9:00.',
  ]),
});
const session = agent.session({ id: 'trip' });
await session.send('Find me a flight to Lisbon on Friday.');

for (const { step, turn, text, toolCalls } of await session.history()) {
  console.log(step, turn, text, toolCalls.map((call) => `${call.name} -> ${call.result}`));
}

// Keep everything up to and including step 1, then go another way.
const fork = await session.fork({ fromStep: 1 }); // saved in the same store
const reply = await fork.send('Look at Porto instead.');
console.log(fork.id, reply.text); // 'trip-fork-1', 'Porto has a direct flight at 9:00.'
```

- الـ **step** رد واحد من الـ model في سجل المحادثة: رسالة assistant،
  مع رسائل الـ tools التي تردّ على الـ tool calls الخاصة به. وتُرجع `history()`
  `{ step, turn, messageIndex, text, toolCalls }` لكل خطوة، الأقدم أولًا:
  `step` مرقّمة من 1 على مستوى الـ session كلها (لا لكل turn)، و`turn`
  مرقّمة من 0، و`messageIndex` هو index رسالة الـ assistant في
  `session.messages`، وكل tool call معه `id` و`name` و`args` بعد الـ parse
  (أو الـ string الخام إذا لم يكن JSON) و`result` (محتوى رسالة الـ tool
  كنص، مُرمَّزًا بـ JSON كما رآه الـ model). والخطوات نسخ (copies).
- تبدأ الـ **turn** عند كل رسالة user، لذا فإن `turn` الخاص بالخطوة هو الـ index المبدوء من 0
  لرسالة الـ user التي تردّ عليها، وهو الترقيم نفسه الذي
  يستخدمه workspace rewind. والـ input الذي أُضيف عبر queue أو steer داخل turn جارية
  (`turnPolicy: 'queue'` أو `'steer'`) هو رسالة user أيضًا، لذا يبدأ
  turn جديدة في `history()`.
- `history()` هو تاريخ سجل المحادثة الحالي: بعد
  `session.compact()` تُرقَّم الخطوات من جديد بناءً على السجل بعد الـ compaction.
  وturn الـ durable التي لم تكتمل بعد ليست في السجل حتى الآن، لذا لا
  تُسرَد.
- يحتفظ `fork({ fromStep })` بالسجل حتى آخر رسالة tool في الخطوة
  شاملةً إياها؛ ولا يحتفظ `fromStep: 0` بشيء. والخطوة الواقعة خارج
  `0..history().length` تُرفض بـ
  [`LOUSHO_SESSION_STEP_NOT_FOUND`](/ar/errors#lousho_session_step_not_found)،
  وتسرد رسالته النطاق الصحيح.
- يستبدل `patch: { toolResult: { toolCallId, result } }` نتيجة tool call
  واحد في السجل المحتفَظ به ("ماذا لو لم يجد البحث شيئًا؟")،
  بالطريقة نفسها التي يعمل بها `patch` في `agent.fork()`.
- يُحفظ الـ fork في store الـ session نفسه، وهو session للـ agent نفسه بالـ
  options نفسها (`store` والـ checkpoints و`limits` و`turnPolicy` و`compaction`، و[وضع الصلاحيات](/ar/permission-modes)
  الذي كانت عليه الـ session وقت الـ fork)، لذا يعمل الـ streaming والـ approvals والـ turns ذات الـ checkpoints كما في أي
  `agent.session()`، ويُكملها `agent.session({ id: fork.id, store })`
  لاحقًا، حتى في process أخرى. ومعرّفه هو `id` إذا
  مرّرته، وإلا `<id>-fork-<n>` لأول `n` بدءًا من 1 ليس له سجل محادثة (وإذا كان المعرّف
  أطول من أن تُضاف إليه هذه اللاحقة، `<start of id>-<8 hex of its hash>-fork-<n>`، ويبقى
  في حدود 128 حرفًا). والـ `id`
  الذي له سجل محادثة أصلًا (أو هو معرّف الـ session نفسه) يُرفض بـ
  [`LOUSHO_SESSION_EXISTS`](/ar/errors#lousho_session_exists).
- تحتوي `messages` الخاصة بالـ fork على سجل محادثته فور عودة `fork()`.
- لا يتغير سجل محادثة الـ session الأصلية ولا الـ checkpoints الخاصة بها.
- الـ budgets: يبقى الـ spend المسجَّل لـ `limits` على الرسائل المحتفَظ بها، لذا
  يبدأ `limits` الخاص بالـ fork مما أنفقته الـ session عند نهاية آخر
  turn محتفَظ بها (تسجّل الـ turn إنفاقها على آخر رسالة فيها).
- ينتظر `fork()` الـ calls الموجودة في الـ queue، ويرمي `LOUSHO_SESSION_BUSY` عندما
  تكون هناك turn قيد التشغيل.
- يمكنك إجراء fork لـ session متوقفة. وتبقى الـ turn المتوقفة والـ approval الخاصة بها أو
  `ask_question` والـ turn المنقطعة في durable session مع
  الـ session المصدر: لا تكون للـ fork أي turn pending، ولا يُكمل `agent.approvals.resolve()`
  إلا المصدر، مرة واحدة.
- المحادثة وحدها هي التي يُجرى لها fork. فالملفات التي كتبها الـ agent والـ side
  effects الأخرى للخطوات بعد نقطة الـ fork لا تُستعاد؛ ولكي تستعيد
  ملفات مساحة العمل، انظر قسم الـ rewind في [أدوات مساحة العمل](/ar/workspace-tools).

ولكي تُجري fork لـ run واحد بدأ بـ `agent.send(message, { sessionId })`، من
الـ history الخاص بالـ checkpoints، استخدم `agent.fork()` بدلًا من ذلك (انظر
[fork and replay](/ar/durable-execution#fork-و-replay)).
