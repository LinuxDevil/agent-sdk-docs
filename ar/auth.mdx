أي agent يشتغل على HTTP يحتاج يعرف شغلتين عن كل request: هل مسموح له يمرّ أصلًا، ومين المتصل. `lousho/auth` تجاوب على الاثنين. إنت تعطي الـ route قائمة مرتبة من مدخلات auth: `jwt()` أو `oidc()` أو `basic()` أو `apiToken()` أو `anonymous()`، أو function تكتبها بنفسك. أول entry يقبل الـ request يرجع **principal** (هوية المتصل بعد ما auth تحققت منه)، وهذا الـ principal يدخل الـ run، وهناك تقدر دوال `model` و`instructions` و`tools` ونطاقات الـ memory تقرأه.

```ts
import { createAgent, createRouteHandler } from 'lousho';
import { apiToken, jwt } from 'lousho/auth';
import { mockModel } from 'lousho/testing';

const agent = createAgent({
  provider: mockModel(['Hello!']),
  instructions: ({ principal }) => `You are helping ${principal?.id ?? 'a guest'}.`,
});

export const { GET, POST } = createRouteHandler(agent, {
  auth: [
    jwt({ secret: process.env.JWT_SECRET ?? 'a-development-secret-of-32-bytes!!', issuer: 'https://auth.example.com', audience: 'agent-api' }),
    apiToken(process.env.CI_TOKEN ?? 'ci-token', { id: 'ci' }),
  ],
});
```

## قائمة الـ auth

المدخلات تشتغل بالترتيب، وكل واحد منها يسوي واحدة من ثلاثة:

| الـ entry ... | يصير إيه |
| --- | --- |
| يرجع `Principal` | الـ request ينقبل، والمدخلات اللي بعده ما تدخل الصورة |
| يرجع `null` أو `undefined` | يتخطّى: السؤال ينتقل للـ entry اللي بعده |
| يرمي `AuthError(401)` أو `AuthError(403)` | الـ request ينرفض بهذا الـ status، والمدخلات اللي بعده ما تدخل الصورة |

لو كل المدخلات عملت skip، الـ request ياخذ `401`. والقائمة الفاضية ترفض كل request. أما الـ entry اللي يرمي أي خطأ آخر فهذا bug: الـ request ياخذ `500` بـ body عام، والخطأ يتسجّل بـ `console.error` (وما ينبعت للمتصل أبدًا).

الـ helpers الجاهزة ما ترمي أبدًا على credential غلط: كلمة مرور غلط، أو token منتهي، أو token مصدر لـ audience آخر — كلها تعمل skip. يعني الـ entry اللي بعده ياخذ فرصته (يعني عادي يكون عندك مدخلين `jwt()` لـ issuerين مختلفين)، والـ request اللي ما قبله أحد ينتهي بنفس الـ `401`.

الـ `Principal` هو:

```ts
interface Principal {
  id: string;                                 // JWT `sub`, Basic user name, 'api-token', ...
  type: 'user' | 'service';
  authenticator: string;                      // 'jwt' | 'oidc' | 'basic' | 'api-token' | 'anonymous' | your name
  issuer?: string;                            // JWT `iss`: the same id from another issuer is another caller
  claims?: Readonly<Record<string, unknown>>; // verified claims; never the raw token or a password
}
```

## الـ helpers

كل الـ helpers تتعمل مرة واحدة عند التشغيل، وتفحص خياراتها وقتها: الـ helper اللي ما يقدر يشتغل يرمي [`LOUSHO_AUTH_CONFIG_INVALID`](/ar/errors#lousho_auth_config_invalid) بدل ما يرفض كل request بعدين.

### `jwt()`

تقبل `Authorization: Bearer <JWT>` الموقّع بالمفتاح اللي إنت تضبطه. مرّر مصدر مفتاح واحد بالضبط:

| الخيار | المفتاح | الخوارزميات (الافتراضي: كل عائلة المفتاح) |
| --- | --- | --- |
| `secret` | سر HMAC بطول 32 بايت على الأقل | `HS256` و`HS384` و`HS512` |
| `publicKey` | مفتاح PEM بصيغة `-----BEGIN PUBLIC KEY-----` أو JWK | `RS256` و`RS384` و`RS512` (RSA بطول 2048 بت أو أكثر)، `ES256` (P-256)، `ES384` (P-384) |
| `jwksUrl` | JWKS endpoint (https، أو http على localhost) | `RS256` و`ES256` افتراضيًا؛ مفاتيح RSA وEC فقط |

```ts
import { jwt } from 'lousho/auth';

const fromOurAuthServer = jwt({
  jwksUrl: 'https://auth.example.com/.well-known/jwks.json',
  issuer: 'https://auth.example.com',
  audience: 'agent-api',
  // Map the verified claims to the principal; return null to skip.
  principal: (claims) => (typeof claims.sub === 'string' ? { id: claims.sub, type: 'user', authenticator: 'jwt', issuer: claims.iss, claims } : null),
});
```

اللي ينفحص:

- قيمة `alg` في الـ header لازم تكون من `algorithms`. `none` مرفوضة دائمًا، وكذلك الـ token اللي هيدره معلّم extension بـ `crit`.
- الخوارزمية لازم تناسب المفتاح: الـ public key ما ينستخدم أبدًا كسر HMAC مهما يقول هيدر الـ token، ومجموعة المفاتيح ما تعطي مفتاح HMAC أبدًا.
- `exp` مطلوب، و`nbf` و`iat` محترمين. الثلاثة تسمح بفرق ساعة قدره `clockToleranceSec` (الافتراضي 60، والحد الأقصى 300).
- لما تضبط `issuer`، لازم `iss` يساوي وحدة من قيم `issuer` بالضبط. ما في تسامح مع سلاش زيادة في الآخر.
- `aud` (string أو قائمة) لازم يحتوي وحدة من `audience`. و`audience` مطلوبة؛ مرّر `allowAnyAudience: true` لو قاصد تتخطّى هذا الفحص.
- مجموعة المفاتيح تتجلب بمهلة 5 ثوانٍ، وتعيش في الكاش 10 دقائق، ويُعاد جلبها مرة واحدة كل 30 ثانية كحد أقصى لما يجي token بـ `kid` ما تعرفه (والجلب الفاشل يتعاد بنفس حد الـ 30 ثانية). عنوانها إعداد فقط: هيدرات `jku` و`x5u` و`jwk` في الـ token تتجاهل.

الـ principal الافتراضي هو `{ id: sub, type: 'user', authenticator: 'jwt', issuer: iss, claims }`؛ والـ token اللي ما فيه `sub` يتخطّى.

### `oidc()`

هي `jwt()` بس مفاتيحها تجي من OpenID Connect provider. تجلب `<issuer>/.well-known/openid-configuration` مرة واحدة (أو `discoveryUrl` لو مررته)، وتشترط إن `issuer` في الوثيقة يساوي قيمتك بالضبط، وتستخدم `jwks_uri` منها (https، أو http على `localhost` / `127.0.0.1` / `[::1]` — نفس قاعدة `jwksUrl` في `jwt()`). الخوارزميات الافتراضية `RS256` و`ES256`؛ وHMAC ممنوع.

```ts
import { oidc } from 'lousho/auth';

const google = oidc({ issuer: 'https://accounts.google.com', audience: process.env.GOOGLE_CLIENT_ID ?? 'client-id' });
```

الـ principal يكون `authenticator: 'oidc'`، و`issuer` فيه `iss` اللي رجّعه الـ provider.

### `basic()`

credentials بتاع HTTP Basic. أسماء المستخدمين وكلمات المرور تتطبّع NFC وتتقارن في زمن ثابت، وكل user مضبوط يتقارن مع كل request، فالـ user المجهول ياخذ نفس وقت كلمة المرور الغلط. والـ `401` يحمل الهيدر `WWW-Authenticate: Basic realm="<realm>", charset="UTF-8"` عشان المتصفحات تعرض نافذة تسجيل الدخول.

```ts
import { basic } from 'lousho/auth';

const operators = basic({ users: { ops: process.env.OPS_PASSWORD ?? 'change-me' }, realm: 'agent' });
// Or check against your own store (compare in constant time there):
const fromDatabase = basic({ users: async (user, password) => user === 'svc' && password === (process.env.SVC_PASSWORD ?? '') });
```

**ما تستخدم `basic()` إلا على HTTPS**: كلمة المرور تسافر مع كل request.

### `apiToken()` و`anonymous()`

`apiToken(token, { id })` تقبل `Authorization: Bearer <token>` (يتقارن في زمن ثابت) كـ service principal `{ id: id ?? 'api-token', type: 'service', authenticator: 'api-token' }`. وهذا من زمان هو معنى الـ token كـ string: `createRouteHandler({ auth: '<token>' })` و`LOUSHO_API_TOKEN` الاثنين `apiToken()`. والـ string الفاضي (`auth: ''`، مثلًا env var مضبوط بس قيمته فاضية) ينرفض بـ `LOUSHO_AUTH_CONFIG_INVALID`: من `createRouteHandler()` لحظة إنشائه، ومن `serveFetch()` مع كل request. يعني ما يقفل الـ routes ولا يفتحها بصمت.

`anonymous()` تقبل الكل كـ `{ id: 'anonymous', type: 'user', authenticator: 'anonymous' }`: حطها آخر وحدة في الـ routes اللي تخدم المتصلين المسجلين والمجهولين مع بعض، واقرأ `principal.authenticator` في الـ run.

### entry من عندك

أي function تاخذ `Request` تشتغل كـ entry. صرّح بالـ challenges اللي ترد بها على `401`، وإلا تعلن `Bearer`:

```ts
import { AuthError, type AuthFn } from 'lousho/auth';

const tenantKey: AuthFn = async (request) => {
  const key = request.headers.get('x-tenant-key');
  if (!key) return null; // not ours: ask the next entry
  if (key === 'suspended-tenant') throw new AuthError(403); // stop here
  return { id: key, type: 'service', authenticator: 'tenant-key' };
};
tenantKey.challenges = [{ scheme: 'Bearer', realm: 'tenants' }];
```

## `401` و`403` و`WWW-Authenticate`

- ما حد قبل الـ request (أو entry رمى `AuthError(401)`): `401` مع `{ "error": "Unauthorized" }` وهيدر `WWW-Authenticate` واحد لكل challenge مختلف في القائمة، بالترتيب (`Bearer` لـ `jwt` و`oidc` و`apiToken`؛ و`Basic realm="..."` لـ `basic`).
- entry رمى `AuthError(403)`: `403` مع `{ "error": "Forbidden" }`.
- entry فشل بطريقة أخرى: `500` مع `{ "error": "Internal Server Error" }`.

الـ body ما يقول أبدًا أي فحص فشل: الـ token المنتهي والتوقيع الغلط والـ audience الغلط كلها تاخذ نفس الـ `401`. وكل رد auth يحمل `Cache-Control: no-store`. والـ tokens وكلمات المرور ما تتسجّل أبدًا.

## أين يشتغل

| الـ helper أو السيرفر | Node 22+ | Cloudflare Workers وVercel Edge وBun وDeno |
| --- | --- | --- |
| `jwt()` و`oidc()` و`basic()` و`apiToken()` و`anonymous()` و`routeAuth()` | نعم | نعم: Web Crypto و`fetch` فقط، وما في استيراد `node:` |
| `createRouteHandler({ auth })` | نعم | نعم |
| الـ targetين `node-server` و`docker` | نعم | لا (Node `http`) |
| ملف `auth.ts` في مجلد الـ agent | نعم (`node-server` و`docker`) | لا |
| الـ build target `cloudflare-worker` | | `LOUSHO_API_TOKEN` فقط؛ ما في قائمة auth حتى الآن |

`oidc()` و`jwt({ jwksUrl })` تحتاج `fetch` خارجي لمجموعة المفاتيح، وكل الـ runtimes المذكورة عندها. وفي Worker مكتوب يدويًا، نادِ `createRouteHandler` أو `routeAuth()` بنفسك مع أي helper.

## `createRouteHandler`

`auth` ياخذ القائمة، أو entry واحد، أو token string، أو (زي قبل) function ترجع boolean. `true` تقبل بالـ principal `{ id: 'anonymous', type: 'user', authenticator: 'custom' }`، و`false` تعني `401`. من دون `auth` يكون الـ route مفتوح، وفي الإنتاج (`NODE_ENV=production`) يسجّل تحذير واحد. `GET <basePath>/health` ما يكون ورا `auth` أبدًا. والـ principal المقبول يوصل لكل route: `POST <basePath>` و`/chat` والـ approvals (الموافقات) وendpoint `useChat`. شوف [Next.js](/ar/nextjs#المسارات).

## سيرفر Node و`auth.ts`

السيرفر المولَّد (يستخدم `createDeployedServer()` الداخلية في الـ bundle) ياخذ نفس القائمة (أو entry واحد). ولما `LOUSHO_API_TOKEN` يكون مضبوط، `apiToken(LOUSHO_API_TOKEN)` تتلحق ورا مدخلاتك، فيظل token المشغّل شغّال. الـ channels تحت `/channels/<name>` ما هي ورا القائمة: هي تتحقق من طلباتها بنفسها.

في [مجلد الـ agent](/ar/agent-directories)، حط القائمة في `auth.ts` (أو `auth.js`) جنب `agent.ts`:

```ts
// my-agent/auth.ts
import { apiToken, oidc } from 'lousho/auth';

export default [
  oidc({ issuer: 'https://login.example.com', audience: 'agent-api' }),
  apiToken(process.env.CI_TOKEN!, { id: 'ci' }),
];
```

`lousho build --target=node-server` (أو `docker`) يجمّعها، والسيرفر المبني يستخدمها (`resolveAgentDir()` ترجعها كـ `auth`، والـ manifest يقول `auth: true`). ومع وجود `auth.ts`، الـ token المخبوز عبر `adapter.scaffold(..., { auth: { token } })` ما ينستخدم؛ أما `LOUSHO_API_TOKEN` فيظل شغّال. والـ target `cloudflare-worker` يقدّم ملفات الـ spec فقط ويحتفظ بـ token `LOUSHO_API_TOKEN`؛ شوف [النشر](/ar/deployment#المصادقة).

وممكن `auth.ts` كمان يصدّر دوال اسمها `authorizeSession` و`authorizeApproval` جنب الـ default export. السيرفر المبني يستخدمها كقواعد [من يقدر يستخدم الـ session](#من-يقدر-يستخدم-الـ-session) و[من يقدر يحسم الـ approval](#من-يقدر-يحسم-الـ-approval)، و`resolveAgentDir()` ترجعها بنفس الأسماء. وأي قيمة ثانية تحت هذه الأسماء تفشّل التحميل (`LOUSHO_AGENT_DIR_INVALID`). و`lousho dev` ما فيه route auth، فلا القائمة ولا هذه القواعد تنطبق هناك.

## قراءة الـ principal في الـ run

الـ principal موجود على سياق الـ run جنب `sessionId` و`metadata`. بادئة `vendor/` في الـ model هي اللي تختار الـ provider؛ ومع OpenRouter استخدم `openrouter/<vendor>/<model>` (مثل `openrouter/openai/gpt-4o-mini`).

```ts
import { createAgent, defineMemory, inMemoryMemory, type Principal } from 'lousho';
import { mockModel } from 'lousho/testing';

const notes = defineMemory({
  name: 'notes',
  // One memory per caller. Key on the issuer too: ids from different issuers can collide.
  scope: ({ principal }) => principal && `user:${principal.issuer ?? ''}:${principal.id}`,
  provider: inMemoryMemory(),
});

const agent = createAgent({
  provider: mockModel(['Hi!', 'Hi again!']), // one scripted reply per turn below
  model: ({ principal }) => (principal?.claims?.plan === 'pro' ? 'openai/gpt-4o' : 'openai/gpt-4o-mini'),
  instructions: ({ principal }) => (principal?.type === 'service' ? 'Answer in JSON.' : 'Be friendly.'),
  memory: [notes],
});

// Outside a route, pass the principal yourself:
const caller: Principal = { id: 'u-42', type: 'user', authenticator: 'jwt', issuer: 'https://auth.example.com' };
await agent.send('Hello', { principal: caller });
await agent.session({ id: 'chat-1' }).send('Hello again', { principal: caller });
```

`principal` منفصل عن `metadata` عن قصد: `metadata` هو اللي المتصل أرسله، و`principal` هو اللي auth تحققت منه. والـ run اللي يتستأنف من checkpoint أو بعد approval يحتفظ بالـ principal اللي بدأ فيه. والـ channels (Slack وDiscord وTeams وGitHub وTelegram) تحط الـ sender كـ principal (`authenticator: 'slack'`، `'discord'`، إلخ). والـ tools وسياسات الـ approval وقواعد الـ permissions والـ sub-agents يشوفوه كمان: شوف [Principals in tools and approvals](#principals-in-tools-and-approvals).

## ملاحظات أمنية

- **الـ session (الجلسة) افتراضيًا ملك المتصل اللي بدأها.** بعد ما الـ route auth يقبل متصل، الـ session id ينربط بأول principal يرسل له turn (قراءة الـ id ما تحجز شي)، وأي principal ثاني ياخذ `403` (`LOUSHO_SESSION_FORBIDDEN`). وهذا السجل يعيش في الذاكرة، لكل agent، لآخر 100,000 session انستخدمت. والـ session المخزّنة اللي مالكها مو مسجّل (بعد restart، أو على replica ثانية، أو بعد تجاوز هذا الحد) تنرفض لكل principal، حتى مالكها. ولو عندك أكثر من instance، أو store يعيش أطول من الـ process، مرّر `authorizeSession` يفحص الملكية مقابل بياناتك أنت. شوف [من يقدر يستخدم الـ session](#من-يقدر-يستخدم-الـ-session).
- **الـ cookies تحتاج حماية من CSRF، والـ routes تعطيها افتراضيًا.** الـ POST لازم يكون JSON (وإلا `415`) وما يجي من صفحة موقع ثاني (`403`، `LOUSHO_REQUEST_FORBIDDEN`). وخلّي cookie الـ session كمان `SameSite=Lax` أو `Strict`. شوف [الطلبات بين المواقع](#الطلبات-بين-المواقع).
- **الـ approvals.** القرار يوصل بس لـ approval تابع للـ session اللي في الـ URL (approval session ثانية يعطي `404`). وافتراضيًا ما يحسمه إلا المتصل اللي الـ run يشتغل لصالحه. ولو الـ approval لازم يجي من شخص ثاني، مثل مشرف يوافق على استرداد مبلغ لعميل، اضبط `authorizeApproval`. وإلا العميل يقدر يوافق على الـ call حقه بنفسه: الـ approval id موجود في الـ stream حقه. شوف [من يقدر يحسم الـ approval](#من-يقدر-يحسم-الـ-approval).
- **الأخطاء.** routes الـ session ترسل `name` و`code` الخطأ مع رسالة عامة. والخطأ الكامل (body رد الـ provider، أو chat template) يروح لسجل السيرفر (`console.error`) ولـ `onEvent`. مرّر `exposeErrors: true` عشان ترسل الرسالة الخام، زي ما يسوي `lousho dev`. وحزمة الـ provider الناقصة (`LOUSHO_PEER_MISSING`) ترسل رسالتها دائمًا: وهي أمر `npm install` من الـ SDK نفسه.
- `basic()` بس على HTTPS؛ والـ bearer token كمان كلمة مرور، فأنهِ TLS قدّام أي سيرفر ما هو على localhost.
- خلّي `issuer` و`audience` مضبوطين في `jwt()`: وإلا token صادر لخدمة أخرى من خدماتك ينقبل هنا.

## Principals in tools and approvals

كل حاجة تقرّر أو تتصرف نيابة عن المتصل تاخذ principal الـ run، وهو frozen (أي tool أو policy تحاول تسنّد له قيمة ترمي خطأ):

| أين | كيف |
| --- | --- |
| `execute(args, ctx)` في الـ tool | `ctx.principal` |
| function `needsApproval` | `ctx.principal` (الوسيط الثاني) |
| `when(args, ctx)` في قاعدة permission | `ctx.principal` |
| الـ hooks `preToolCall` و`postToolCall` | `ctx.principal` |
| `onPermissionDecision(entry, { principal })` | الوسيط الثاني؛ والـ entry نفسه ما يحمل principal |
| approval معلّق (`agent.approvals.list()` و`approve` وfunction `approvers` في الـ channel) | `request.principal`: مين المتصل |
| الـ sub-agents داخل الـ process (`task` والمهام الخلفية) | principal الـ lead، في كل اللي فوق |

والـ run اللي ما فيه principal (ما في route auth، أو `send()` من دون `principal`) ما يكون له principal في أي موضع من اللي فوق.

### في tool

```ts
import { defineTool } from 'lousho';
import { z } from 'zod';

export const myOrders = defineTool({
  name: 'my_orders',
  description: "Lists the caller's orders",
  input: z.object({}),
  execute: async (_args, ctx) => {
    if (!ctx.principal) return { error: 'Sign in first.' };
    // Key on the issuer too: the same id from another issuer is another caller.
    return { owner: `${ctx.principal.issuer ?? ''}:${ctx.principal.id}`, orders: [] };
  },
});
```

الـ principal يجي بس من route auth أو من sender تحققت منه الـ channel، وما يجي أبدًا من body الـ request ولا من الـ model، والـ tool ما تقدر تغيّره.

### سياسات الـ approval وقواعد الـ permissions

```ts
import { createAgent, defineTool } from 'lousho';
import { mockModel } from 'lousho/testing';
import { z } from 'zod';

const deploy = defineTool({
  name: 'deploy',
  description: 'Deploys a service',
  input: z.object({ service: z.string() }),
  // Ask a human only when the caller has no `admin` claim.
  needsApproval: (_args, ctx) => ctx.principal?.claims?.admin !== true,
  execute: async ({ service }) => `deployed ${service}`,
});

const agent = createAgent({
  provider: mockModel(['Ready.']),
  tools: [deploy],
  // Service accounts (CI tokens) may not deploy at all.
  permissions: [{ tool: 'deploy', when: (_args, ctx) => ctx.principal?.type === 'service', action: 'deny', reason: 'Not for service accounts' }],
});

await agent.send('Deploy the API', { principal: { id: 'ci', type: 'service', authenticator: 'api-token' } });
```

### من وافق

القرار يقدر يسمّي مين اتخذه. والـ tool الموافَق عليه يشوف صاحب القرار في `ctx.approval.by`، جنب `ctx.approval.note`:

```ts
import { createAgent, defineTool, type Principal } from 'lousho';
import { mockModel } from 'lousho/testing';
import { z } from 'zod';

const sendEmail = defineTool({
  name: 'send_email',
  description: 'Sends an email',
  input: z.object({ to: z.string() }),
  needsApproval: true,
  execute: async ({ to }, ctx) => `sent to ${to} for ${ctx.principal?.id}, approved by ${ctx.approval?.by?.id}`,
});

const agent = createAgent({
  provider: mockModel([{ toolCalls: [{ name: 'send_email', args: { to: 'sam@example.com' } }] }, 'Sent.']),
  tools: [sendEmail],
});
const alice: Principal = { id: 'alice', type: 'user', authenticator: 'jwt' };
const lead: Principal = { id: 'lead', type: 'user', authenticator: 'jwt' };

const paused = await agent.send('Email Sam', { principal: alice });
// The tool runs for alice; lead is recorded as the approver.
await agent.approvals.resolve({ id: paused.approvalId!, approved: true }, { principal: lead });
```

`resolve()` و`answer()` و`streamResolve()` و`streamAnswer()` تاخذ `{ principal }`. والـ approvals route (`POST /chat/:sessionId/approvals/:id`) يمرّر المتصل اللي قبلته قائمة الـ auth؛ حقول الـ body ما تقدر تضبطه. و`mountChannels()` تمرّر الـ user اللي ضغط كـ `{ id, type: 'user', authenticator: <channel name> }`، أو، لو السؤال اتجاوب برسالة، مُرسل الرسالة. أما القرارات اللي تعملها callback `approve` أو اللي تنرسل لـ `/channels/<name>/approvals/:id` فما فيها approver.

الـ approver ما يصير principal الـ run أبدًا: الـ call الموافَق عليه وباقي الـ run يشتغل لصالح المتصل اللي وقّفه. وأي credential أو grant تخص هذا المتصل تُستخدم بس لاتصالاته هو، مهما كان مين اللي وافق.

### من يقدر يستخدم الـ session

افتراضيًا، بعد ما الـ route auth يقبل متصل، الـ session تصير ملك أول principal يرسل لها turn (والـ principals تتقارن بـ `id` و`type` و`authenticator` و`issuer`). وأي principal ثاني ياخذ `403` (`LOUSHO_SESSION_FORBIDDEN`) على `GET /chat/:id` و`POST /chat` و`POST <basePath>` وendpoint `useChat`؛ أما القرارات على الـ approvals حقها فمتروكة لـ `authorizeApproval` (تحت). وقراءة id ما أحد أرسل له turn لسا ما تحجز شي، فالمتصل ما يقدر يقفل id متوقّع (`user-42`) على صاحبه بإنه يقرأه أول. والـ turn اللي `input` حقه فاضي ياخذ `400` وما يحجز شي، والـ turn اللي ما يخزّن شي (فشل قبل الحفظ) يتخلّى عن حجزه. والـ route اللي بدون auth ما يفحص شي. وكل اللي يتصلون بنفس `apiToken()` هم principal واحد، فيتشاركون كل الـ sessions؛ والـ route المحمي بـ bearer token واحد (`auth: '<token>'`، أو سيرفر Node أو الـ Worker مع `LOUSHO_API_TOKEN` بس) ما يفحص أي مالك أصلًا.

المالك ينحفظ في الذاكرة، لكل agent object، لآخر 100,000 session انستخدمت. والـ restart، أو replica ثانية، أو session ما انستخدمت مدة أطول، أو host يبني الـ agent مع كل request، كلها تنسّيه. وقتها الافتراضي يفشل مقفول: الـ session المخزّنة أصلًا (فيها transcript أو turn ما خلص) وما لها مالك مسجّل تنرفض لكل principal، حتى اللي بدأها، عشان ما أحد يستولي على session بإنه يخلّي النظام ينسى مالكها. وبس الـ session اللي ما انخزنت أبدًا ممكن تنحجز من جديد. فلأي شي يشتغل على أكثر من instance، أو يحتفظ بالـ sessions بين الـ restarts، افحص الملكية بنفسك بـ `authorizeSession`.

`createRouteHandler()` وسيرفر Node المولَّد ياخذون `authorizeSession`، وهو يستبدل هذا الافتراضي (في مجلد الـ agent، صدّره من `auth.ts`: شوف المثال تحت [من يقدر يحسم الـ approval](#من-يقدر-يحسم-الـ-approval)). ينسأل قبل ما المتصل يقرأ session (`action: 'read'`)، أو يرسل لها turn (`'chat'`، ويشمل `POST <basePath>` وendpoint `useChat`)، أو يحسم واحد من الـ approvals حقها (`'approve'`). رجّع `false` عشان `403` (`LOUSHO_SESSION_FORBIDDEN`). واشتقاق الـ id من المتصل يخلّي الفحص stateless:

```ts
import { createAgent, createRouteHandler, memoryStore } from 'lousho';
import { jwt } from 'lousho/auth';

const agent = createAgent({ model: 'openai/gpt-4o-mini', store: memoryStore() });
// The user id a session id starts with: everything before its last `-`. A prefix match would let
// `alice` reach `alice-x`'s sessions, so the suffix has no `-` (e.g. `crypto.randomUUID().replaceAll('-', '')`).
const ownerOf = (sessionId: string) => sessionId.slice(0, Math.max(sessionId.lastIndexOf('-'), 0));

export const { GET, POST } = createRouteHandler(agent, {
  auth: jwt({ secret: process.env.JWT_SECRET!, issuer: 'https://auth.example.com', audience: 'agent-api' }),
  // Session ids are `<user id>-<suffix without '-'>`: a user can only reach their own.
  authorizeSession: ({ principal, sessionId }) => principal !== undefined && ownerOf(sessionId) === principal.id,
});
```

`authorizeSession: () => true` يخلّي كل متصل مصادَق عليه يستخدم كل session (السلوك اللي كان قبل هذا الافتراضي).

### الطلبات بين المواقع

المتصفح يرسل الـ cookies مع الطلبات اللي تسويها صفحة موقع ثاني، فمع auth مبني على cookies، صفحة على `evil.example` كان ممكن تبدأ turn أو توافق على call باسم المستخدم حقك. routes الـ session ترفض هذا افتراضيًا:

- الـ POST اللي `Origin` حقه مو origin السيرفر نفسه (الـ `Host` حقه، أو الـ host اللي يبلّغ عنه proxy قدّامه في `X-Forwarded-Host` أو `Forwarded: host=`) ومو موجود في `allowedOrigins`، أو اللي المتصفح علّمه بـ `Sec-Fetch-Site: cross-site`، ياخذ `403` (`LOUSHO_REQUEST_FORBIDDEN`). والطلبات اللي بدون `Origin` (curl، أو سيرفر، أو agent ثاني) ما تتأثر؛
- body الـ POST لازم يكون `Content-Type: application/json` (وإلا `415`، `LOUSHO_UNSUPPORTED_MEDIA_TYPE`): لأن الـ forms و`text/plain` هي اللي يقدر موقع ثاني يرسلها بدون CORS preflight.

الـ front end اللي على origin ثاني تحطه في `allowedOrigins` (ويحتاج كمان CORS headers، يضيفها الـ host حقك)؛ و`allowedOrigins: ['*']` يطفّي فحص الـ origin، و`requireJsonBody: false` يطفّي فحص الـ content-type. والقيم تتقارن كـ origins: حالة الأحرف، والسلاش في الآخر، والـ port الافتراضي (`https://app.example:443`) ما تفرق. و`allowedHosts` (مطفّي افتراضيًا) يرفض أي request الـ `Host` حقه مو في القائمة، للحماية من DNS rebinding لسيرفر على عنوان خاص. الثلاثة تشتغل على `createRouteHandler()` وسيرفر Node المولَّد؛ وهذا السيرفر والـ Cloudflare Worker يقرأونها من `LOUSHO_ALLOWED_ORIGINS` و`LOUSHO_ALLOWED_HOSTS` (مفصولة بفواصل) و`LOUSHO_REQUIRE_JSON_BODY=false`.

ورا reverse proxy:

- الـ proxy لازم يبلّغ السيرفر بالـ host العام، وإلا الـ POST من نفس الموقع في المتصفح ياخذ `403`: خلّ الـ `Host` الأصلي (في nginx: `proxy_set_header Host $host;`)، أو اضبط `X-Forwarded-Host` (`proxy_set_header X-Forwarded-Host $host;`) أو `Forwarded: host=...`. والـ port الافتراضي فيه (`agent.example:443`) يطابق صفحة `https://agent.example`. وإلا حط الـ origin العام في `allowedOrigins`.
- `allowedHosts` يفحص بس هيدر `Host` اللي يوصل للسيرفر، وما يفحص الهيدرات المحوَّلة أبدًا (لأن الصفحة اللي تسوي DNS rebinding تقدر تضبطها). ورا proxy يعيد كتابة `Host`، حط الاسم الـ upstream اللي يرسله الـ proxy، مو الاسم العام.

```ts
import { createAgent, createRouteHandler } from 'lousho';

const agent = createAgent({ model: 'openai/gpt-4o-mini' });

export const { GET, POST } = createRouteHandler(agent, {
  auth: process.env.AGENT_TOKEN,
  allowedOrigins: ['https://app.example.com'],
});
```

### من يقدر يحسم الـ approval

القرار المرسَل لـ `POST /chat/:sessionId/approvals/:id` لازم يسمّي الـ session اللي يتبع لها الـ approval؛ وأي session ثانية ترد بـ `404`، زي الـ approval اللي انحسم من قبل. أما `POST <basePath>/approvals/:id` (الـ route اللي يرسل له `useLoushoAgent`) فما يسمّي session، فينفحص مقابل الـ session الخاصة بالـ approval نفسه.

بعدها `authorizeApproval({ principal, sessionId, approval })` يقرر؛ و`false` تعني `403` (`LOUSHO_APPROVAL_FORBIDDEN`). والافتراضي، `callerOwnsApproval`، ما يخلّي أحد يحسم إلا المتصل اللي الـ run الموقوف يشتغل لصالحه (`approval.principal`، يتقارن بـ `id` و`type` و`authenticator` و`issuer`). يعني المستخدم يقدر يأكد الـ call حقه، وما يقدر يحسم call مستخدم ثاني. والـ run اللي بدون principal، أو الـ route اللي بدون auth، يقبل أي متصل.

لما `needsApproval` يعني إن شخص ثاني لازم يوافق، قل مين. هنا العميل ما عاد يقدر يوافق على استرداد مبلغه بنفسه، والمشرف يقدر يقرأ أي session (عشان يشوف على إيش يوافق) ويحسم فيها:

```ts
import { createAgent, createRouteHandler, memoryStore } from 'lousho';
import { jwt } from 'lousho/auth';

const agent = createAgent({ model: 'openai/gpt-4o-mini', store: memoryStore() });
const isSupervisor = (principal?: { claims?: Readonly<Record<string, unknown>> }) => principal?.claims?.role === 'supervisor';
// Session ids are `<user id>-<suffix without '-'>`; the owner is everything before the last `-`.
const ownerOf = (sessionId: string) => sessionId.slice(0, Math.max(sessionId.lastIndexOf('-'), 0));

export const { GET, POST } = createRouteHandler(agent, {
  auth: jwt({ secret: process.env.JWT_SECRET!, issuer: 'https://auth.example.com', audience: 'agent-api' }),
  // Customers use their own sessions; supervisors may read and decide in any session.
  authorizeSession: ({ principal, sessionId, action }) =>
    (principal !== undefined && ownerOf(sessionId) === principal.id) || (action !== 'chat' && isSupervisor(principal)),
  authorizeApproval: ({ principal }) => isSupervisor(principal),
});
```

في مجلد agent مبني بـ `lousho build --target=node-server` (أو `docker`)، صدّر نفس القواعد من `auth.ts`. هنا المستخدمين يقدّمون طلبات مصاريف، والمدير يحسمها، وما أحد يوافق على طلبه بنفسه:

```ts
// my-agent/auth.ts
import { apiToken } from 'lousho/auth';
import type { ApprovalAccessRequest, SessionAccessRequest } from 'lousho';

export default [
  apiToken(process.env.ALICE_TOKEN!, { id: 'alice' }),
  apiToken(process.env.BOB_TOKEN!, { id: 'bob' }),
  apiToken(process.env.MANAGER_TOKEN!, { id: 'manager' }),
];

// Session ids are `<user id>-<suffix without '-'>`.
const ownerOf = (sessionId: string) => sessionId.slice(0, Math.max(sessionId.lastIndexOf('-'), 0));

// Users use their own sessions; the manager may open any session to review a claim.
export function authorizeSession({ principal, sessionId }: SessionAccessRequest): boolean {
  return principal?.id === 'manager' || (principal !== undefined && ownerOf(sessionId) === principal.id);
}

// Only the manager decides, and never on a claim of their own.
export function authorizeApproval({ principal, approval }: ApprovalAccessRequest): boolean {
  return principal?.id === 'manager' && approval.principal?.id !== 'manager';
}
```

وقتها طلب alice الموقوف في الـ session `alice-1` يتحسم بـ `POST /chat/alice-1/approvals/:id` مع token المدير (`200`)؛ ومع token alice نفسها ياخذ `403` (`LOUSHO_APPROVAL_FORBIDDEN`). وبدون هذه الـ exports السيرفر المبني يحتفظ بالافتراضيات، فما يقدر يحسمه إلا alice.

لما طلبين يحسمون نفس الـ approval، ياخذون continuation واحد: طول ما continuation القرار الفائز شغّال (على نفس process السيرفر)، أي قرار ثاني لهذا الـ approval ياخذ `409` (`LOUSHO_APPROVAL_CONFLICT`)، سواء وصل في نفس اللحظة أو والـ tool المحسوم شغّال؛ وبعد ما ينتهي هذا الـ continuation، القرار ياخذ `404` (`LOUSHO_APPROVAL_NOT_FOUND`). والقرار اللي عالجته replica ثانية ياخذ `404` هناك.

### الوقف والكراش والـ fork

الـ principal ينحفظ مع checkpoints الـ run وsnapshots الـ approvals، فالـ run اللي يتستأنف في process أخرى (بعد restart، أو `agent.approvals.resolve()`، أو `agent.resume()`، أو turn معلّق في session) يشتغل لصالح نفس المتصل. والـ call اللي يكمّل run غير مكتمل له checkpoint لازم ما يمرّر principal (فيكمّل بالمحفوظ) أو يمرّر نفسه؛ أما `send(message, { sessionId, principal })` من متصل آخر فيرمي `LOUSHO_CONFIG_INVALID`، عشان مدخله ما يشتغل بهوية غيره. والـ checkpoints والـ snapshots المحفوظة قبل هذا الإصدار ما فيها principal وتستأنف بدونه.

`agent.fork()` و`AgentExecutor.fork()` تنسخ checkpoint الـ run مع الـ principal: يعني الـ fork هو run لنفس المتصل. والـ approval المعلّق ما ينسخ؛ الـ fork يطلبه من جديد. أما `session.fork()` فتنسخ المحادثة فقط: الـ fork ما فيه principal خاص، وكل turn فيه يشتغل بالـ principal اللي `send()` تمرّره، والـ approval المعلّق يظل مع الـ session الأصلية.

### الـ sub-agents

الـ sub-agents داخل الـ process (الـ tool `task` والمهام الخلفية) تشتغل لصالح متصل الـ lead، وحتى عند استئناف الـ approval الخاص بها. أما الـ [remote sub-agent](/ar/sub-agents) (`remoteAgent()`) فما يعرف مين المتصل: الـ route auth على السيرفر البعيد هو اللي يقرر الـ principal (مثلًا الـ service principal اللي يطلع من `apiToken()` على token الـ lead).

### اللي يتخزن واللي يتسجّل

الـ principal، ومعه الـ claims، يتخزن في الـ checkpoints وسجلات الـ approvals اللي أصلًا فيها transcript المحادثة؛ فعامل هذه الـ stores كبيانات شخصية. وما يتضاف لأحداث `AgentEvent` (حتى `permission.decision`)، ولا لـ spans في OpenTelemetry، ولا ملفات الـ trace، ورسائل الأخطاء ما تسمّي المتصلين.
