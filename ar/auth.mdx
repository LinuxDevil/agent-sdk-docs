أي agent يعمل عبر HTTP يحتاج إلى معرفة أمرين عن كل request: هل يُسمح له بالمرور أصلًا، ومن المتصل. تجيب `lousho/auth` عن السؤالين. أنت تعطي الـ route قائمة مرتبة من مدخلات auth: `jwt()` أو `oidc()` أو `basic()` أو `apiToken()` أو `anonymous()`، أو function تكتبها بنفسك. أول entry يقبل الـ request يُرجع **principal** (هوية المتصل بعد أن تحققت منها auth)، وهذا الـ principal يدخل الـ run، وهناك تستطيع دوال `model` و`instructions` و`tools` ونطاقات الـ memory قراءته.

```ts
import { createAgent, createRouteHandler } from 'lousho';
import { apiToken, jwt } from 'lousho/auth';
import { mockModel } from 'lousho/testing';

const agent = createAgent({
  provider: mockModel(['Hello!']),
  instructions: ({ principal }) => `You are helping ${principal?.id ?? 'a guest'}.`,
});

// Read secrets from the environment and fail at startup when one is missing.
// Never fall back to a literal: a default in your source is a secret everyone can read.
function requireEnv(name: string): string {
  const value = process.env[name];
  if (!value) throw new Error(`${name} is not set`);
  return value;
}

export const { GET, POST } = createRouteHandler(agent, {
  auth: [
    jwt({ secret: requireEnv('JWT_SECRET'), issuer: 'https://auth.example.com', audience: 'agent-api' }),
    apiToken(requireEnv('CI_TOKEN'), { id: 'ci' }),
  ],
});
```

## قائمة الـ auth

تعمل المدخلات بالترتيب، وكل واحد منها يفعل واحدًا من ثلاثة أشياء:

| الـ entry ... | ماذا يحدث |
| --- | --- |
| يُرجع `Principal` | يُقبل الـ request، ولا تُستشار المدخلات التي بعده |
| يُرجع `null` أو `undefined` | يتخطّى: ينتقل السؤال إلى الـ entry التالي |
| يرمي `AuthError(401)` أو `AuthError(403)` | يُرفض الـ request بهذا الـ status، ولا تُستشار المدخلات التي بعده |

إذا تخطّت كل المدخلات، يحصل الـ request على `401`. والقائمة الفارغة ترفض كل request. أما الـ entry الذي يرمي أي خطأ آخر فهذا bug: يحصل الـ request على `500` مع body عام، ويُسجَّل الخطأ عبر `console.error` (ولا يُرسل إلى المتصل أبدًا).

الـ helpers الجاهزة لا ترمي أبدًا عند credential خاطئ: كلمة مرور خاطئة، أو token منتهٍ، أو token صادر لـ audience آخر — كلها تتخطّى. أي أن الـ entry التالي يأخذ فرصته (فمن الطبيعي أن يكون لديك مدخلان `jwt()` لـ issuerين مختلفين)، والـ request الذي لم يقبله أحد ينتهي بالـ `401` نفسه.

الـ `Principal` هو:

```ts
interface Principal {
  id: string;                                 // JWT `sub`, Basic user name, 'api-token', ...
  type: 'user' | 'service';
  authenticator: string;                      // 'jwt' | 'oidc' | 'basic' | 'api-token' | 'anonymous' | your name
  issuer?: string;                            // JWT `iss`: the same id from another issuer is another caller
  claims?: Readonly<Record<string, unknown>>; // verified claims; never the raw token or a password
}
```

## الـ helpers

تُنشأ كل الـ helpers مرة واحدة عند التشغيل، وتفحص خياراتها حينها: الـ helper الذي لا يستطيع العمل يرمي [`LOUSHO_AUTH_CONFIG_INVALID`](/ar/errors#lousho_auth_config_invalid) بدلًا من أن يرفض كل request لاحقًا.

### `jwt()`

تقبل `Authorization: Bearer <JWT>` الموقّع بالمفتاح الذي تضبطه أنت. مرّر مصدر مفتاح واحدًا بالضبط:

| الخيار | المفتاح | الخوارزميات (الافتراضي: كل عائلة المفتاح) |
| --- | --- | --- |
| `secret` | سر HMAC بطول 32 بايت على الأقل | `HS256` و`HS384` و`HS512` |
| `publicKey` | مفتاح PEM بصيغة `-----BEGIN PUBLIC KEY-----` أو JWK | `RS256` و`RS384` و`RS512` (RSA بطول 2048 بت أو أكثر)، `ES256` (P-256)، `ES384` (P-384) |
| `jwksUrl` | JWKS endpoint (https، أو http على localhost) | `RS256` و`ES256` افتراضيًا؛ مفاتيح RSA وEC فقط |

```ts
import { jwt } from 'lousho/auth';

const fromOurAuthServer = jwt({
  jwksUrl: 'https://auth.example.com/.well-known/jwks.json',
  issuer: 'https://auth.example.com',
  audience: 'agent-api',
  // Map the verified claims to the principal; return null to skip.
  principal: (claims) => (typeof claims.sub === 'string' ? { id: claims.sub, type: 'user', authenticator: 'jwt', issuer: claims.iss, claims } : null),
});
```

ما يُفحص:

- يجب أن تكون قيمة `alg` في الـ header من `algorithms`. وتُرفض `none` دائمًا، وكذلك الـ token الذي يعلّم الـ header فيه extension عبر `crit`.
- يجب أن تناسب الخوارزمية المفتاح: لا يُستخدم الـ public key أبدًا كسر HMAC مهما قال header الـ token، ولا تُعطي مجموعة المفاتيح مفتاح HMAC أبدًا.
- `exp` مطلوب، و`nbf` و`iat` محترَمان. والثلاثة تسمح بفارق في الساعة قدره `clockToleranceSec` (الافتراضي 60، والحد الأقصى 300).
- عندما تضبط `issuer`، يجب أن يساوي `iss` إحدى قيم `issuer` بالضبط. ولا تسامح مع شرطة مائلة زائدة في النهاية.
- يجب أن يحتوي `aud` (string أو قائمة) على إحدى قيم `audience`. و`audience` مطلوبة؛ مرّر `allowAnyAudience: true` إذا كنت تقصد تخطّي هذا الفحص.
- تُجلب مجموعة المفاتيح بمهلة 5 ثوانٍ، وتبقى في الكاش 10 دقائق، ويُعاد جلبها مرة واحدة كل 30 ثانية كحد أقصى عندما يصل token بـ `kid` غير معروف (ويُعاد الجلب الفاشل بحد الـ 30 ثانية نفسه). عنوانها يأتي من الإعداد فقط: تُتجاهل headers `jku` و`x5u` و`jwk` في الـ token.

الـ principal الافتراضي هو `{ id: sub, type: 'user', authenticator: 'jwt', issuer: iss, claims }`؛ والـ token الذي لا يحتوي `sub` يُتخطّى.

### `oidc()`

هي `jwt()` لكن مفاتيحها تأتي من OpenID Connect provider. تجلب `<issuer>/.well-known/openid-configuration` مرة واحدة (أو `discoveryUrl` إذا مررته)، وتشترط أن يساوي `issuer` في الوثيقة قيمتك بالضبط، وتستخدم `jwks_uri` منها (https، أو http على `localhost` / `127.0.0.1` / `[::1]` — القاعدة نفسها الخاصة بـ `jwksUrl` في `jwt()`). الخوارزميات الافتراضية `RS256` و`ES256`؛ وHMAC ممنوع.

```ts
import { oidc } from 'lousho/auth';

const google = oidc({ issuer: 'https://accounts.google.com', audience: process.env.GOOGLE_CLIENT_ID ?? 'client-id' });
```

يكون الـ principal بـ `authenticator: 'oidc'`، ويحمل `issuer` فيه قيمة `iss` التي أرجعها الـ provider.

### `basic()`

credentials الخاصة بـ HTTP Basic. تُطبَّع أسماء المستخدمين وكلمات المرور بـ NFC وتُقارَن في زمن ثابت، ويُقارَن كل user مضبوط مع كل request، فيستغرق الـ user المجهول الوقت نفسه الذي تستغرقه كلمة المرور الخاطئة. ويحمل الـ `401` الـ header `WWW-Authenticate: Basic realm="<realm>", charset="UTF-8"` لكي تعرض المتصفحات نافذة تسجيل الدخول.

```ts
import { basic } from 'lousho/auth';

const operators = basic({ users: { ops: process.env.OPS_PASSWORD! }, realm: 'agent' });
// Or check against your own store (compare in constant time there):
const fromDatabase = basic({ users: async (user, password) => user === 'svc' && password === process.env.SVC_PASSWORD });
```

**لا تستخدم `basic()` إلا عبر HTTPS**: كلمة المرور تُرسل مع كل request.

### `apiToken()` و`anonymous()`

`apiToken(token, { id })` تقبل `Authorization: Bearer <token>` (يُقارَن في زمن ثابت) كـ service principal `{ id: id ?? 'api-token', type: 'service', authenticator: 'api-token' }`. وهذا منذ زمن هو معنى الـ token المكتوب كـ string: `createRouteHandler({ auth: '<token>' })` و`LOUSHO_API_TOKEN` كلاهما `apiToken()`. والـ string الفارغ (`auth: ''`، مثلًا env var مضبوط لكن قيمته فارغة) يُرفض بـ `LOUSHO_AUTH_CONFIG_INVALID`: من `createRouteHandler()` لحظة إنشائه، ومن `serveFetch()` مع كل request. أي أنه لا يقفل الـ routes ولا يفتحها بصمت.

`anonymous()` تقبل الجميع كـ `{ id: 'anonymous', type: 'user', authenticator: 'anonymous' }`: ضعها في آخر القائمة في الـ routes التي تخدم المتصلين المسجلين والمجهولين معًا، واقرأ `principal.authenticator` في الـ run.

### entry من عندك

أي function تأخذ `Request` تعمل كـ entry. صرّح بالـ challenges التي ترد بها مع `401`، وإلا فإنها تعلن `Bearer`:

```ts
import { AuthError, type AuthFn } from 'lousho/auth';

const tenantKey: AuthFn = async (request) => {
  const key = request.headers.get('x-tenant-key');
  if (!key) return null; // not ours: ask the next entry
  if (key === 'suspended-tenant') throw new AuthError(403); // stop here
  return { id: key, type: 'service', authenticator: 'tenant-key' };
};
tenantKey.challenges = [{ scheme: 'Bearer', realm: 'tenants' }];
```

## `401` و`403` و`WWW-Authenticate`

- لم يقبل أحد الـ request (أو رمى entry `AuthError(401)`): `401` مع `{ "error": "Unauthorized" }` وheader `WWW-Authenticate` واحد لكل challenge مختلف في القائمة، بالترتيب (`Bearer` لـ `jwt` و`oidc` و`apiToken`؛ و`Basic realm="..."` لـ `basic`).
- رمى entry `AuthError(403)`: `403` مع `{ "error": "Forbidden" }`.
- فشل entry بطريقة أخرى: `500` مع `{ "error": "Internal Server Error" }`.

لا يذكر الـ body أبدًا أي فحص فشل: الـ token المنتهي والتوقيع الخاطئ والـ audience الخاطئ كلها تحصل على الـ `401` نفسه. وكل رد auth يحمل `Cache-Control: no-store`. ولا تُسجَّل الـ tokens وكلمات المرور أبدًا.

## أين يعمل

| الـ helper أو السيرفر | Node 22+ | Cloudflare Workers وVercel Edge وBun وDeno |
| --- | --- | --- |
| `jwt()` و`oidc()` و`basic()` و`apiToken()` و`anonymous()` و`routeAuth()` | نعم | نعم: Web Crypto و`fetch` فقط، ولا يوجد استيراد `node:` |
| `createRouteHandler({ auth })` | نعم | نعم |
| الـ targetان `node-server` و`docker` | نعم | لا (Node `http`) |
| ملف `auth.ts` في مجلد الـ agent | نعم (`node-server` و`docker`) | لا |
| الـ build target `cloudflare-worker` | | `LOUSHO_API_TOKEN` فقط؛ لا توجد قائمة auth حتى الآن |

تحتاج `oidc()` و`jwt({ jwksUrl })` إلى `fetch` خارجي لمجموعة المفاتيح، وكل الـ runtimes المذكورة توفّره. وفي Worker مكتوب يدويًا، استدعِ `createRouteHandler` أو `routeAuth()` بنفسك مع أي helper.

## `createRouteHandler`

يأخذ `auth` القائمة، أو entry واحدًا، أو token string، أو (كما كان سابقًا) function تُرجع boolean. تقبل `true` بالـ principal `{ id: 'anonymous', type: 'user', authenticator: 'custom' }`، و`false` تعني `401`. ومن دون `auth` يكون الـ route مفتوحًا، وفي الإنتاج (`NODE_ENV=production`) يُسجَّل تحذير واحد. ولا يكون `GET <basePath>/health` خلف `auth` أبدًا. ويصل الـ principal المقبول إلى كل route: `POST <basePath>` و`/chat` والـ approvals (الموافقات) وendpoint `useChat`. راجع [Next.js](/ar/nextjs#المسارات).

## سيرفر Node و`auth.ts`

يأخذ السيرفر المولَّد (يستخدم `createDeployedServer()` الداخلية في الـ bundle) القائمة نفسها (أو entry واحدًا). وعندما يكون `LOUSHO_API_TOKEN` مضبوطًا، تُلحق `apiToken(LOUSHO_API_TOKEN)` بعد مدخلاتك، فيبقى token المشغّل فعّالًا. الـ channels تحت `/channels/<name>` ليست خلف القائمة: فهي تتحقق من طلباتها بنفسها.

في [مجلد الـ agent](/ar/agent-directories)، ضع القائمة في `auth.ts` (أو `auth.js`) بجانب `agent.ts`:

```ts
// my-agent/auth.ts
import { apiToken, oidc } from 'lousho/auth';

export default [
  oidc({ issuer: 'https://login.example.com', audience: 'agent-api' }),
  apiToken(process.env.CI_TOKEN!, { id: 'ci' }),
];
```

يجمّعها `lousho build --target=node-server` (أو `docker`)، ويستخدمها السيرفر المبني (تُرجعها `resolveAgentDir()` كـ `auth`، ويذكر الـ manifest `auth: true`). ومع وجود `auth.ts`، لا يُستخدم الـ token المضمَّن عبر `adapter.scaffold(..., { auth: { token } })`؛ أما `LOUSHO_API_TOKEN` فيبقى فعّالًا. والـ target `cloudflare-worker` يقدّم ملفات الـ spec فقط ويحتفظ بـ token `LOUSHO_API_TOKEN`؛ راجع [النشر](/ar/deployment#المصادقة).

ويمكن أن يصدّر `auth.ts` أيضًا دوالّ اسمها `authorizeSession` و`authorizeApproval` بجانب الـ default export. يستخدمها السيرفر المبني كقواعد [من يستطيع استخدام الـ session](#من-يستطيع-استخدام-الـ-session) و[من يستطيع حسم الـ approval](#من-يستطيع-حسم-الـ-approval)، وتُرجعها `resolveAgentDir()` بالأسماء نفسها. وأي قيمة أخرى تحت هذه الأسماء تُفشل التحميل (`LOUSHO_AGENT_DIR_INVALID`). ولا يوجد route auth في `lousho dev`، فلا القائمة ولا هذه القواعد تنطبق هناك.

## قراءة الـ principal في الـ run

يوجد الـ principal في سياق الـ run بجانب `sessionId` و`metadata`. بادئة `vendor/` في الـ model هي التي تختار الـ provider؛ ومع OpenRouter استخدم `openrouter/<vendor>/<model>` (مثل `openrouter/openai/gpt-4o-mini`).

```ts
import { createAgent, defineMemory, inMemoryMemory, type Principal } from 'lousho';
import { mockModel } from 'lousho/testing';

const notes = defineMemory({
  name: 'notes',
  // One memory per caller. Key on the issuer too: ids from different issuers can collide.
  scope: ({ principal }) => principal && `user:${principal.issuer ?? ''}:${principal.id}`,
  provider: inMemoryMemory(),
});

const agent = createAgent({
  provider: mockModel(['Hi!', 'Hi again!']), // one scripted reply per turn below
  model: ({ principal }) => (principal?.claims?.plan === 'pro' ? 'openai/gpt-4o' : 'openai/gpt-4o-mini'),
  instructions: ({ principal }) => (principal?.type === 'service' ? 'Answer in JSON.' : 'Be friendly.'),
  memory: [notes],
});

// Outside a route, pass the principal yourself:
const caller: Principal = { id: 'u-42', type: 'user', authenticator: 'jwt', issuer: 'https://auth.example.com' };
await agent.send('Hello', { principal: caller });
await agent.session({ id: 'chat-1' }).send('Hello again', { principal: caller });
```

`principal` منفصل عن `metadata` عن قصد: `metadata` هو ما أرسله المتصل، و`principal` هو ما تحققت منه auth. والـ run الذي يُستأنف من checkpoint أو بعد approval يحتفظ بالـ principal الذي بدأ به. والـ channels (Slack وDiscord وTeams وGitHub وTelegram) تضع الـ sender كـ principal (`authenticator: 'slack'`، `'discord'`، إلخ). وتراه أيضًا الـ tools وسياسات الـ approval وقواعد الـ permissions والـ sub-agents: راجع [Principals in tools and approvals](#principals-in-tools-and-approvals).

## ملاحظات أمنية

- **الـ session (الجلسة) افتراضيًا ملك المتصل الذي بدأها.** بعد أن يقبل الـ route auth متصلًا، يرتبط الـ session id بأول principal يرسل إليه turn (قراءة الـ id لا تحجز شيئًا)، وأي principal آخر يحصل على `403` (`LOUSHO_SESSION_FORBIDDEN`). ويعيش هذا السجل في الذاكرة، لكل agent، لآخر 100,000 session استُخدمت. والـ session المخزّنة التي لم يُسجَّل مالكها (بعد restart، أو على replica أخرى، أو بعد تجاوز هذا الحد) تُرفض لكل principal، حتى لمالكها. وإذا كان لديك أكثر من instance، أو store يعيش أطول من الـ process، فمرّر `authorizeSession` يفحص الملكية مقابل بياناتك أنت. راجع [من يستطيع استخدام الـ session](#من-يستطيع-استخدام-الـ-session).
- **الـ cookies تحتاج إلى حماية من CSRF، والـ routes توفّرها افتراضيًا.** يجب أن يكون الـ POST بصيغة JSON (وإلا `415`) وألّا يأتي من صفحة موقع آخر (`403`، `LOUSHO_REQUEST_FORBIDDEN`). واجعل cookie الـ session أيضًا `SameSite=Lax` أو `Strict`. راجع [الطلبات بين المواقع](#الطلبات-بين-المواقع).
- **الـ approvals.** لا يصل القرار إلا إلى approval تابع للـ session الموجودة في الـ URL (الـ approval الخاص بـ session أخرى يعطي `404`). وافتراضيًا لا يحسمه إلا المتصل الذي يعمل الـ run لصالحه. وإذا كان يجب أن يأتي الـ approval من شخص آخر، مثل مشرف يوافق على استرداد مبلغ لعميل، فاضبط `authorizeApproval`. وإلا يستطيع العميل الموافقة على الـ call الخاص به بنفسه: فالـ approval id موجود في الـ stream الخاص به. راجع [من يستطيع حسم الـ approval](#من-يستطيع-حسم-الـ-approval).
- **الأخطاء.** ترسل routes الـ session قيمتي `name` و`code` للخطأ مع رسالة عامة. ويذهب الخطأ الكامل (body رد الـ provider، أو chat template) إلى سجل السيرفر (`console.error`) وإلى `onEvent`. مرّر `exposeErrors: true` لكي ترسل الرسالة الخام، كما يفعل `lousho dev`. وحزمة الـ provider الناقصة (`LOUSHO_PEER_MISSING`) ترسل رسالتها دائمًا: وهي أمر `npm install` من الـ SDK نفسه.
- `basic()` عبر HTTPS فقط؛ والـ bearer token هو أيضًا كلمة مرور، فأنهِ TLS أمام أي سيرفر ليس على localhost.
- أبقِ `issuer` و`audience` مضبوطين في `jwt()`: وإلا فإن token صادرًا لخدمة أخرى من خدماتك سيُقبل هنا.

## Principals in tools and approvals

كل ما يقرّر أو يتصرف نيابة عن المتصل يحصل على principal الـ run، وهو frozen (أي tool أو policy تحاول إسناد قيمة إليه ترمي خطأ):

| أين | كيف |
| --- | --- |
| `execute(args, ctx)` في الـ tool | `ctx.principal` |
| function `needsApproval` | `ctx.principal` (الوسيط الثاني) |
| `when(args, ctx)` في قاعدة permission | `ctx.principal` |
| الـ hooks `preToolCall` و`postToolCall` | `ctx.principal` |
| `onPermissionDecision(entry, { principal })` | الوسيط الثاني؛ والـ entry نفسه لا يحمل principal |
| approval معلّق (`agent.approvals.list()` و`approve` وfunction `approvers` في الـ channel) | `request.principal`: من المتصل |
| الـ sub-agents داخل الـ process (`task` والمهام الخلفية) | principal الـ lead، في كل ما سبق |

والـ run الذي ليس له principal (لا يوجد route auth، أو `send()` من دون `principal`) لا يكون له principal في أي موضع مما سبق.

### في tool

```ts
import { defineTool } from 'lousho';
import { z } from 'zod';

export const myOrders = defineTool({
  name: 'my_orders',
  description: "Lists the caller's orders",
  input: z.object({}),
  execute: async (_args, ctx) => {
    if (!ctx.principal) return { error: 'Sign in first.' };
    // Key on the issuer too: the same id from another issuer is another caller.
    return { owner: `${ctx.principal.issuer ?? ''}:${ctx.principal.id}`, orders: [] };
  },
});
```

لا يأتي الـ principal إلا من route auth أو من sender تحققت منه الـ channel، ولا يأتي أبدًا من body الـ request ولا من الـ model، ولا تستطيع الـ tool تغييره.

### سياسات الـ approval وقواعد الـ permissions

```ts
import { createAgent, defineTool } from 'lousho';
import { mockModel } from 'lousho/testing';
import { z } from 'zod';

const deploy = defineTool({
  name: 'deploy',
  description: 'Deploys a service',
  input: z.object({ service: z.string() }),
  // Ask a human only when the caller has no `admin` claim.
  needsApproval: (_args, ctx) => ctx.principal?.claims?.admin !== true,
  execute: async ({ service }) => `deployed ${service}`,
});

const agent = createAgent({
  provider: mockModel(['Ready.']),
  tools: [deploy],
  // Service accounts (CI tokens) may not deploy at all.
  permissions: [{ tool: 'deploy', when: (_args, ctx) => ctx.principal?.type === 'service', action: 'deny', reason: 'Not for service accounts' }],
});

await agent.send('Deploy the API', { principal: { id: 'ci', type: 'service', authenticator: 'api-token' } });
```

### من وافق

يستطيع القرار أن يسمّي من اتخذه. وترى الـ tool الموافَق عليها صاحب القرار في `ctx.approval.by`، بجانب `ctx.approval.note`:

```ts
import { createAgent, defineTool, type Principal } from 'lousho';
import { mockModel } from 'lousho/testing';
import { z } from 'zod';

const sendEmail = defineTool({
  name: 'send_email',
  description: 'Sends an email',
  input: z.object({ to: z.string() }),
  needsApproval: true,
  execute: async ({ to }, ctx) => `sent to ${to} for ${ctx.principal?.id}, approved by ${ctx.approval?.by?.id}`,
});

const agent = createAgent({
  provider: mockModel([{ toolCalls: [{ name: 'send_email', args: { to: 'sam@example.com' } }] }, 'Sent.']),
  tools: [sendEmail],
});
const alice: Principal = { id: 'alice', type: 'user', authenticator: 'jwt' };
const lead: Principal = { id: 'lead', type: 'user', authenticator: 'jwt' };

const paused = await agent.send('Email Sam', { principal: alice });
// The tool runs for alice; lead is recorded as the approver.
await agent.approvals.resolve({ id: paused.approvalId!, approved: true }, { principal: lead });
```

تأخذ `resolve()` و`answer()` و`streamResolve()` و`streamAnswer()` القيمة `{ principal }`. ويمرّر الـ approvals route (`POST /chat/:sessionId/approvals/:id`) المتصل الذي قبلته قائمة الـ auth؛ ولا تستطيع حقول الـ body ضبطه. وتمرّر `mountChannels()` الـ user الذي ضغط كـ `{ id, type: 'user', authenticator: <channel name> }`، أو، إذا أُجيب عن السؤال برسالة، مُرسل الرسالة. أما القرارات التي يتخذها callback `approve` أو التي تُرسل إلى `/channels/<name>/approvals/:id` فليس فيها approver.

لا يصبح الـ approver أبدًا principal الـ run: فالـ call الموافَق عليه وبقية الـ run يعملان لصالح المتصل الذي أوقفه. وأي credential أو grant تخص هذا المتصل لا تُستخدم إلا لاستدعاءاته هو، بغض النظر عمّن وافق.

### من يستطيع استخدام الـ session

افتراضيًا، بعد أن يقبل الـ route auth متصلًا، تصبح الـ session ملكًا لأول principal يرسل إليها turn (وتُقارَن الـ principals بـ `id` و`type` و`authenticator` و`issuer`). وأي principal آخر يحصل على `403` (`LOUSHO_SESSION_FORBIDDEN`) على `GET /chat/:id` و`POST /chat` و`POST <basePath>` وendpoint `useChat`؛ أما القرارات على الـ approvals الخاصة بها فمتروكة لـ `authorizeApproval` (أدناه). وقراءة id لم يرسل إليه أحد turn بعد لا تحجز شيئًا، فلا يستطيع المتصل أن يقفل id متوقعًا (`user-42`) على صاحبه بقراءته أولًا. والـ turn الذي يكون `input` فيه فارغًا يحصل على `400` ولا يحجز شيئًا، والـ turn الذي لا يخزّن شيئًا (فشل قبل الحفظ) يتخلّى عن حجزه. والـ route الذي ليس عليه auth لا يفحص شيئًا. وكل من يتصلون بالـ `apiToken()` نفسه هم principal واحد، فيتشاركون كل الـ sessions؛ والـ route المحمي بـ bearer token واحد (`auth: '<token>'`، أو سيرفر Node أو الـ Worker مع `LOUSHO_API_TOKEN` فقط) لا يفحص أي مالك أصلًا.

يُحفظ المالك في الذاكرة، لكل agent object، لآخر 100,000 session استُخدمت. والـ restart، أو replica أخرى، أو session لم تُستخدم لمدة أطول، أو host يبني الـ agent مع كل request، كلها تُنسيه. حينها يفشل الافتراضي مغلقًا: الـ session المخزّنة مسبقًا (فيها transcript أو turn لم يكتمل) والتي ليس لها مالك مسجّل تُرفض لكل principal، حتى من بدأها، لكي لا يستولي أحد على session بجعل النظام ينسى مالكها. ولا يمكن حجز session من جديد إلا إذا لم تُخزَّن أبدًا. لذا لأي شيء يعمل على أكثر من instance، أو يحتفظ بالـ sessions بين مرات الـ restart، افحص الملكية بنفسك عبر `authorizeSession`.

يأخذ `createRouteHandler()` وسيرفر Node المولَّد `authorizeSession`، وهو يستبدل هذا الافتراضي (في مجلد الـ agent، صدّره من `auth.ts`: راجع المثال أدناه في [من يستطيع حسم الـ approval](#من-يستطيع-حسم-الـ-approval)). يُستدعى قبل أن يقرأ المتصل session (`action: 'read'`)، أو يرسل إليها turn (`'chat'`، ويشمل `POST <basePath>` وendpoint `useChat`)، أو يحسم أحد الـ approvals الخاصة بها (`'approve'`). أرجِع `false` للحصول على `403` (`LOUSHO_SESSION_FORBIDDEN`). واشتقاق الـ id من المتصل يجعل الفحص stateless:

```ts
import { createAgent, createRouteHandler, memoryStore } from 'lousho';
import { jwt } from 'lousho/auth';

const agent = createAgent({ model: 'openai/gpt-4o-mini', store: memoryStore() });
// The user id a session id starts with: everything before its last `-`. A prefix match would let
// `alice` reach `alice-x`'s sessions, so the suffix has no `-` (e.g. `crypto.randomUUID().replaceAll('-', '')`).
const ownerOf = (sessionId: string) => sessionId.slice(0, Math.max(sessionId.lastIndexOf('-'), 0));

export const { GET, POST } = createRouteHandler(agent, {
  auth: jwt({ secret: process.env.JWT_SECRET!, issuer: 'https://auth.example.com', audience: 'agent-api' }),
  // Session ids are `<user id>-<suffix without '-'>`: a user can only reach their own.
  authorizeSession: ({ principal, sessionId }) => principal !== undefined && ownerOf(sessionId) === principal.id,
});
```

`authorizeSession: () => true` تسمح لكل متصل مصادَق عليه باستخدام كل session (السلوك الذي كان قبل هذا الافتراضي).

### الطلبات بين المواقع

يرسل المتصفح الـ cookies مع الطلبات التي تنشئها صفحة موقع آخر، فمع auth مبني على الـ cookies، كان يمكن لصفحة على `evil.example` أن تبدأ turn أو توافق على call باسم المستخدم الخاص بك. ترفض routes الـ session هذا افتراضيًا:

- الـ POST الذي لا يكون `Origin` الخاص به origin السيرفر نفسه (أي الـ `Host` الخاص به، أو الـ host الذي يبلّغ عنه proxy أمامه في `X-Forwarded-Host` أو `Forwarded: host=`) وليس موجودًا في `allowedOrigins`، أو الذي علّمه المتصفح بـ `Sec-Fetch-Site: cross-site`، يحصل على `403` (`LOUSHO_REQUEST_FORBIDDEN`). ولا تتأثر الطلبات التي ليس فيها `Origin` (curl، أو سيرفر، أو agent آخر)؛
- يجب أن يكون body الـ POST بـ `Content-Type: application/json` (وإلا `415`، `LOUSHO_UNSUPPORTED_MEDIA_TYPE`): لأن الـ forms و`text/plain` هي ما يستطيع موقع آخر إرساله من دون CORS preflight.

ضع الـ front end الموجود على origin آخر في `allowedOrigins` (ويحتاج أيضًا إلى CORS headers يضيفها الـ host الخاص بك)؛ و`allowedOrigins: ['*']` تعطّل فحص الـ origin، و`requireJsonBody: false` تعطّل فحص الـ content-type. وتُقارَن القيم كـ origins: حالة الأحرف، والشرطة المائلة في النهاية، والـ port الافتراضي (`https://app.example:443`) لا تُحدث فرقًا. و`allowedHosts` (معطّل افتراضيًا) يرفض أي request لا يكون الـ `Host` الخاص به في القائمة، للحماية من DNS rebinding لسيرفر على عنوان خاص. تعمل الثلاثة على `createRouteHandler()` وسيرفر Node المولَّد؛ ويقرأها هذا السيرفر والـ Cloudflare Worker من `LOUSHO_ALLOWED_ORIGINS` و`LOUSHO_ALLOWED_HOSTS` (مفصولة بفواصل) و`LOUSHO_REQUIRE_JSON_BODY=false`.

خلف reverse proxy:

- يجب أن يبلّغ الـ proxy السيرفر بالـ host العام، وإلا يحصل الـ POST القادم من الموقع نفسه في المتصفح على `403`: أبقِ الـ `Host` الأصلي (في nginx: `proxy_set_header Host $host;`)، أو اضبط `X-Forwarded-Host` (`proxy_set_header X-Forwarded-Host $host;`) أو `Forwarded: host=...`. والـ port الافتراضي فيه (`agent.example:443`) يطابق صفحة `https://agent.example`. وإلا فضع الـ origin العام في `allowedOrigins`.
- لا يفحص `allowedHosts` إلا header الـ `Host` الذي يصل إلى السيرفر، ولا يفحص الـ headers المحوَّلة أبدًا (لأن الصفحة التي تنفّذ DNS rebinding تستطيع ضبطها). وخلف proxy يعيد كتابة `Host`، ضع اسم الـ upstream الذي يرسله الـ proxy، لا الاسم العام.

```ts
import { createAgent, createRouteHandler } from 'lousho';

const agent = createAgent({ model: 'openai/gpt-4o-mini' });

export const { GET, POST } = createRouteHandler(agent, {
  auth: process.env.AGENT_TOKEN,
  allowedOrigins: ['https://app.example.com'],
});
```

### من يستطيع حسم الـ approval

يجب أن يسمّي القرار المرسَل إلى `POST /chat/:sessionId/approvals/:id` الـ session التي يتبع لها الـ approval؛ وأي session أخرى ترد بـ `404`، مثل الـ approval الذي حُسم من قبل. أما `POST <basePath>/approvals/:id` (الـ route الذي يرسل إليه `useLoushoAgent`) فلا يسمّي session، فيُفحص مقابل الـ session الخاصة بالـ approval نفسه.

بعدها تقرر `authorizeApproval({ principal, sessionId, approval })`؛ و`false` تعني `403` (`LOUSHO_APPROVAL_FORBIDDEN`). والافتراضي، `callerOwnsApproval`، لا يسمح لأحد بالحسم إلا للمتصل الذي يعمل الـ run الموقوف لصالحه (`approval.principal`، ويُقارَن بـ `id` و`type` و`authenticator` و`issuer`). أي أن المستخدم يستطيع تأكيد الـ call الخاص به، ولا يستطيع حسم call مستخدم آخر. والـ run الذي ليس له principal، أو الـ route الذي ليس عليه auth، يقبل أي متصل.

عندما يعني `needsApproval` أن شخصًا آخر يجب أن يوافق، فحدّد من هو. هنا لم يعد العميل يستطيع الموافقة على استرداد مبلغه بنفسه، ويستطيع المشرف قراءة أي session (ليرى ما الذي يوافق عليه) والحسم فيها:

```ts
import { createAgent, createRouteHandler, memoryStore } from 'lousho';
import { jwt } from 'lousho/auth';

const agent = createAgent({ model: 'openai/gpt-4o-mini', store: memoryStore() });
const isSupervisor = (principal?: { claims?: Readonly<Record<string, unknown>> }) => principal?.claims?.role === 'supervisor';
// Session ids are `<user id>-<suffix without '-'>`; the owner is everything before the last `-`.
const ownerOf = (sessionId: string) => sessionId.slice(0, Math.max(sessionId.lastIndexOf('-'), 0));

export const { GET, POST } = createRouteHandler(agent, {
  auth: jwt({ secret: process.env.JWT_SECRET!, issuer: 'https://auth.example.com', audience: 'agent-api' }),
  // Customers use their own sessions; supervisors may read and decide in any session.
  authorizeSession: ({ principal, sessionId, action }) =>
    (principal !== undefined && ownerOf(sessionId) === principal.id) || (action !== 'chat' && isSupervisor(principal)),
  authorizeApproval: ({ principal }) => isSupervisor(principal),
});
```

في مجلد agent مبني بـ `lousho build --target=node-server` (أو `docker`)، صدّر القواعد نفسها من `auth.ts`. هنا يقدّم المستخدمون طلبات مصاريف، ويحسمها المدير، ولا يوافق أحد على طلبه بنفسه:

```ts
// my-agent/auth.ts
import { apiToken } from 'lousho/auth';
import type { ApprovalAccessRequest, SessionAccessRequest } from 'lousho';

export default [
  apiToken(process.env.ALICE_TOKEN!, { id: 'alice' }),
  apiToken(process.env.BOB_TOKEN!, { id: 'bob' }),
  apiToken(process.env.MANAGER_TOKEN!, { id: 'manager' }),
];

// Session ids are `<user id>-<suffix without '-'>`.
const ownerOf = (sessionId: string) => sessionId.slice(0, Math.max(sessionId.lastIndexOf('-'), 0));

// Users use their own sessions; the manager may open any session to review a claim.
export function authorizeSession({ principal, sessionId }: SessionAccessRequest): boolean {
  return principal?.id === 'manager' || (principal !== undefined && ownerOf(sessionId) === principal.id);
}

// Only the manager decides, and never on a claim of their own.
export function authorizeApproval({ principal, approval }: ApprovalAccessRequest): boolean {
  return principal?.id === 'manager' && approval.principal?.id !== 'manager';
}
```

حينها يُحسم طلب alice الموقوف في الـ session `alice-1` عبر `POST /chat/alice-1/approvals/:id` مع token المدير (`200`)؛ ومع token alice نفسها يحصل على `403` (`LOUSHO_APPROVAL_FORBIDDEN`). ومن دون هذه الـ exports يحتفظ السيرفر المبني بالافتراضيات، فلا يستطيع حسمه إلا alice.

عندما يحسم طلبان الـ approval نفسه، يحصلان على continuation واحد: ما دام continuation القرار الفائز يعمل (على process السيرفر نفسها)، يحصل أي قرار آخر لهذا الـ approval على `409` (`LOUSHO_APPROVAL_CONFLICT`)، سواء وصل في اللحظة نفسها أو أثناء عمل الـ tool المحسومة؛ وبعد انتهاء هذا الـ continuation، يحصل القرار على `404` (`LOUSHO_APPROVAL_NOT_FOUND`). والقرار الذي عالجته replica أخرى يحصل على `404` هناك.

### الإيقاف والتعطّل والـ fork

يُحفظ الـ principal مع checkpoints الـ run وsnapshots الـ approvals، فالـ run الذي يُستأنف في process أخرى (بعد restart، أو `agent.approvals.resolve()`، أو `agent.resume()`، أو turn معلّق في session) يعمل لصالح المتصل نفسه. والـ call الذي يكمل run غير مكتمل له checkpoint يجب ألّا يمرّر principal (فيكمل بالمحفوظ) أو أن يمرّر الـ principal نفسه؛ أما `send(message, { sessionId, principal })` من متصل آخر فيرمي `LOUSHO_CONFIG_INVALID`، لكي لا يعمل مدخله بهوية غيره. والـ checkpoints والـ snapshots المحفوظة قبل هذا الإصدار ليس فيها principal وتُستأنف من دونه.

تنسخ `agent.fork()` و`AgentExecutor.fork()` checkpoint الـ run مع الـ principal: أي أن الـ fork هو run للمتصل نفسه. ولا يُنسخ الـ approval المعلّق؛ بل يطلبه الـ fork من جديد. أما `session.fork()` فتنسخ المحادثة فقط: ليس للـ fork principal خاص، وكل turn فيه يعمل بالـ principal الذي تمرّره `send()`، ويبقى الـ approval المعلّق مع الـ session الأصلية.

### الـ sub-agents

تعمل الـ sub-agents داخل الـ process (الـ tool `task` والمهام الخلفية) لصالح متصل الـ lead، حتى عند استئناف الـ approval الخاص بها. أما الـ [remote sub-agent](/ar/sub-agents) (`remoteAgent()`) فلا يعرف من المتصل: الـ route auth على السيرفر البعيد هو الذي يقرر الـ principal (مثلًا الـ service principal الناتج عن `apiToken()` على token الـ lead).

### ما يُخزَّن وما يُسجَّل

يُخزَّن الـ principal، ومعه الـ claims، في الـ checkpoints وسجلات الـ approvals التي تحتوي أصلًا على transcript المحادثة؛ فعامل هذه الـ stores كبيانات شخصية. ولا يُضاف إلى أحداث `AgentEvent` (حتى `permission.decision`)، ولا إلى spans في OpenTelemetry، ولا إلى ملفات الـ trace، ولا تذكر رسائل الأخطاء أسماء المتصلين.
