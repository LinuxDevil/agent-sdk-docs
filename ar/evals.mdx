الـ evals هي regression tests لسلوك الـ *agent*: أي tools نادى،
بأي ترتيب، بأي arguments، كم خطوة أخذ، وما قال.
تكتبها بـ `defineEval()`، وتعيش في ملفات `*.eval.ts`، وتشتغل على
[vitest](https://vitest.dev). أفضل مكان تشغّلها فيه هو CI عبر `lousho eval`،
الذي يطبع ملخصًا ويكتب تقارير JUnit وJSON.

```bash
npm install --save-dev vitest
npx lousho eval
```

## كتابة trajectory eval

مرّر لـ `defineEval()` agent (من `createAgent()`) ودالة `test`. أرسل
الرسائل بـ `t.send()`، وبعدها اعمل assert على الـ run. لو خلّيت `mockModel`
هو الـ provider، يصير الـ eval deterministic: لا شبكة، لا API key، لا
flakiness. **هذه هي الطريقة الافتراضية لكتابة eval**؛ استخدم model حقيقي
فقط في [judge evals](#judge-evals) بالأسفل.

```ts
// refund.eval.ts
import { z } from 'zod';
import { createAgent, defineEval, defineTool, includes } from '@lousho/build-ai-agent';
import { mockModel } from '@lousho/build-ai-agent/testing';

const lookupOrder = defineTool({
  name: 'lookup_order',
  description: 'Look up an order by id',
  input: z.object({ orderId: z.string() }),
  execute: ({ orderId }) => ({ orderId, status: 'delivered' }),
});

defineEval({
  name: 'refund flow',
  tags: ['smoke'],
  // A factory builds a fresh agent (and a fresh script) for every case.
  agent: () =>
    createAgent({
      prompt: 'You handle refund requests.',
      tools: [lookupOrder],
      provider: mockModel([
        { toolCalls: [{ name: 'lookup_order', args: { orderId: '42' } }] },
        { text: 'Order 42 can be refunded within 30 days.' },
      ]),
    }),
  async test(t) {
    await t.send('Refund order 42');
    t.completed();
    t.calledTool('lookup_order', { args: { orderId: '42' } });
    t.notCalledTool('issue_refund');
    t.check('mentions policy', t.reply, includes('30 days'));
    t.maxSteps(4);
  },
});
```

`defineEval()` تقبل أيضًا الصيغة الأصلية
(`{ name, agent, input, provider, score, threshold }`): تشتغل كما هي
بدون تغيير، ونتيجتها تظهر في `lousho eval` كـ assertion واحدة على `score`.

### Assertions

كل assertion يتسجّل. الـ case تفشل في النهاية وتعدّ **كل** gate فاشلة،
فتشوف كل المشاكل من run واحد.

| Call | Kind | تنجح حين |
| --- | --- | --- |
| `t.completed()` | gate | آخر run انتهى بـ `stop` عادي: لا error، ولا abort، ولا approval معلّق، ولا قطع عند `maxSteps` |
| `t.calledTool(name, { args?, times? })` | gate | الـ agent نادى الـ tool؛ `args` هي partial deep match (لازم تحتوي arguments الـ call هذه المفاتيح بقيم متساوية)؛ `times` عدد دقيق للـ calls المطابقة |
| `t.notCalledTool(name)` | gate | الـ tool ما اتنادت أبدًا |
| `t.toolOrder([a, b])` | gate | الـ tools اتنادت بهذا الترتيب (ممكن calls أخرى بينهم) |
| `t.maxSteps(n)` | gate | الـ agent أخذ `n` خطوات model كحد أقصى |
| `t.maxTokens(n)` | gate | الـ agent استهلك `n` tokens كحد أقصى |
| `t.maxCostUsd(n)` | gate | تكلفة الـ run المُبلَّغ عنها `n` دولار كحد أقصى. تتخطى (تنحسب ناجحة، بعلامة `skipped`) إذا الـ SDK ما بلّغ عن تكلفة |
| `t.check(name, value, check)` | gate | الـ `check` ينجح على `value` |
| `t.soft(name, value, check)` | soft | ما تفشل الـ run أبدًا (إلا مع `--strict`)؛ الدرجة تتسجّل وتظهر في التقرير |
| `await t.judge(rubric)` | n/a | ترجع درجة من 0 إلى 1 من judge هو LLM (شوف [Judge evals](#judge-evals)) |

الـ checks المتاحة لـ `t.check()` و`t.soft()`: `includes(text)` و`matches(regex)`
و`equals(value)` (نعم/لا، درجة 1 أو 0)، و`atLeast(n)` و`atMost(n)`
(الرقم نفسه هو الدرجة).

رسائل الفشل تقول لك بالضبط ما ظهر:

```text
calledTool('lookup_order') failed: tools called were [search_docs, issue_refund]
calledTool('lookup_order', {"args":{"orderId":"41"}}) failed: 'lookup_order' was called 1 time(s) but no call matched the expected args; closest call differs in orderId: expected "41", got "42"
completed() failed: finishReason was 'max-steps' (the run hit maxSteps while still calling tools)
```

باقي أعضاء الـ context: `t.reply` (نص آخر رد)، و`t.result` (آخر
`ExecutionResult`)، و`t.toolCalls` (كل الـ calls حتى الآن، مع arguments محلّلة).
تقدر تستدعي `send()` أكثر من مرة؛ الخطوات والـ tokens والـ tool calls تتراكم.

### Datasets

مرّر `cases` و`test` تشتغل مرة لكل case، وكل case تظهر في التقرير لحالها.
الـ case أي object؛ `label` حقها (أو `name`، أو `input`) هو الذي يسمّيها.

```ts
import { z } from 'zod';
import { createAgent, defineEval, defineTool } from '@lousho/build-ai-agent';
import { mockModel } from '@lousho/build-ai-agent/testing';

const lookupOrder = defineTool({
  name: 'lookup_order',
  description: 'Look up an order by id',
  input: z.object({ orderId: z.string() }),
  execute: ({ orderId }) => ({ orderId }),
});

defineEval({
  name: 'order lookups',
  agent: () =>
    createAgent({
      tools: [lookupOrder],
      provider: mockModel([
        { toolCalls: [{ name: 'lookup_order', args: { orderId: '7' } }] },
        { text: 'Found it.' },
      ]),
    }),
  cases: [
    { input: 'Where is order 7?', orderId: '7' },
    { input: 'Status of #7', orderId: '7', label: 'hash syntax' },
  ],
  async test(t, c) {
    await t.send(c.input);
    t.calledTool('lookup_order', { args: { orderId: c.orderId } });
  },
});
```

مرّر **factory** (`agent: () => createAgent(...)`) حتى كل case تأخذ agent
جديد وسكربت `mockModel` جديد. مع agent واحدة مشتركة، الـ scripted model
تخلص عنده الـ turns عند ثاني case.

## Judge evals

`t.judge(rubric)` يقيّم آخر رد بـ LLM ويرجع درجة من
0 إلى 1. يحتاج provider للـ judge، وlousho ما ينادي أي LLM حقيقي إلا لو
ضبطت واحد: بدون `judge`، `t.judge()` يرمي خطأ يشرح لك كيف تصلحه.

```ts
// tone.judge.eval.ts: run with `lousho eval --judge`
import { createAgent, defineEval, atLeast } from '@lousho/build-ai-agent';
import { mockModel } from '@lousho/build-ai-agent/testing';

defineEval({
  name: 'tone',
  agent: createAgent({ provider: mockModel(['Happy to help with that refund!']) }),
  // A real provider in practice; mockModel keeps this example offline.
  judge: { provider: mockModel(['0.9']), model: 'judge-model' },
  async test(t) {
    await t.send('I want my money back');
    t.soft('polite', await t.judge('Is the reply polite?'), atLeast(0.7));
  },
});
```

ملفات `*.judge.eval.ts` ما يلتقطها الـ run العادي أبدًا (ولا
`npm test`)؛ ما يشغّلها إلا `lousho eval --judge` (أو `npm run test:evals:judge`
في هذا الـ repo).

## `lousho eval`

```text
lousho eval [globs...] [--tag t] [--junit path] [--json path] [--strict] [--judge] [--record | --replay | --drift [--drift-usage]] [--url <base> [--token <bearer>]]
```

| الخيار | المعنى |
| --- | --- |
| `globs...` | ملفات الـ eval المطلوب تشغيلها (الافتراضي: كل `**/*.eval.ts`، أو `**/*.judge.eval.ts` مع `--judge`) |
| `--tag t` | يشغّل فقط الـ evals التي `tags` فيها تتضمن `t` (كرّره أو افصل بفواصل لأكثر من tag) |
| `--junit path` | يكتب تقرير JUnit XML |
| `--json path` | يكتب الملخص وكل نتيجة structured كـ JSON |
| `--strict` | إخفاقات الـ soft تفشل الـ run |
| `--judge` | يشغّل ملفات `*.judge.eval.ts` بدل الملفات العادية |
| `--url base` | يشغّل كل case على الـ agent المنشور عند `base` بدل داخل العملية؛ `--token` (أو `LOUSHO_EVAL_TOKEN`) هو الـ bearer token. شوف [تشغيل evals على deployment](#تشغيل-evals-على-deployment) |
| `--config path` | يستخدم vitest config الخاص بك بدل المولَّد |
| `--record` | يشغّل على الـ provider الحقيقي ويكتب cassette (ملف تسجيل) واحد لكل case ([بالأسفل](#record-replay-and-drift)) |
| `--replay` | يشغّل كل case من الـ cassette الخاص بها، بدون شبكة؛ cassette مفقودة تفشل الـ case |
| `--drift` | يعيد التسجيل في مجلد مؤقت ويبلّغ كيف تغيّرت trajectory كل case (`--drift-usage` يقارن الـ tokens أيضًا) |

الأمر يشغّل نسخة vitest المثبّتة في مشروعك (vitest dependency *تخصك أنت*؛
لو مفقودة، يطبع الأمر `npm install --save-dev vitest` ويخرج بـ 2)،
ثم يطبع سطر لكل case بدرجاتها ومدتها، ثم المجاميع، ثم إخفاقات الـ gate
وإخفاقات الـ soft كل وحدة لحالها.

**رمز الخروج:** `1` عند أي إخفاق gate (أو إخفاق soft مع `--strict`، أو حين
يفشل vitest نفسه، مثل ملف ما يتحمّل)، و`2` حين ما يقدر يشتغل أصلًا
(arguments غلط، vitest مفقود)، و`0` فيما عدا ذلك.

كيف تُجمَع النتائج: كل case تضيف سطر JSON واحد لملف اسمه محدّد في
env var `LOUSHO_EVAL_RESULTS`، التي يضبطها `lousho eval` ثم يرجع يقراها.
هذا أثبت من reporter مخصص لـ vitest: يشتغل عبر إصدارات vitest المختلفة
وworker pools، وما يحتاج تحميل أي module من مشروعك.

### JUnit

التقرير JUnit قياسي: `testsuite` واحد لكل eval، و`testcase` واحد لكل case.
الـ gate الفاشلة تصير `<failure message="...">` تحمل رسالة التشخيص؛
والـ case التي رمت خطأ تصير `<error>`؛ وإخفاقات الـ soft تكون ملاحظات
`<system-out>` (أو failures مع `--strict`).

### في CI

```yaml
# .github/workflows/evals.yml
name: evals
on: [pull_request]
jobs:
  evals:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm ci
      - run: npx lousho eval --junit reports/evals.xml --json reports/evals.json
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: eval-reports
          path: reports/
      - uses: mikepenz/action-junit-report@v4
        if: always()
        with:
          report_paths: reports/evals.xml
```

شغّل `--tag smoke` على كل pull request والمجموعة الكاملة كل ليلة؛
و`--judge` شغّله فقط حيث تقبل calls حقيقية لـ LLM وتكلفتها.

## Record, replay and drift

الـ eval على model حقيقي بطيء ويكلّف ويحتاج مفتاح؛ ونفس الـ eval على
`mockModel` ما يختبر إلا السكربت الذي كتبته أنت. `lousho eval` يقف في النص:
يسجّل كل case مرة واحدة على الـ provider الحقيقي عبر
[`recordReplay`](/ar/testing#record-و-replay) ويعيد تشغيل التسجيل في CI.
ملفات الـ eval عندك ما تتغير.

```bash
npx lousho eval --record        # real provider: writes the cassettes, commit them
npx lousho eval --replay        # every case from its cassette, no network, no key
npx lousho eval --drift         # re-record and diff each case's trajectory
```

- **`--record`** يشغّل كل case بالـ provider الحقيقي لـ agentها ويكتب
  cassette واحد لكل case جنب ملف الـ eval:
  `__cassettes__/<eval-name>/<case>.json` (الأسماء تتحول لـ slug، مثل
  `refund-flow/polite.json`؛ والـ eval بدون `cases` يكتب `default.json`).
  أعط كل case `label` فريد حتى تبقى الأسماء ثابتة. والـ case التي agentها
  يستخدم أكثر من provider (مثل sub-agent على model ثاني) تأخذ
  `<case>.2.json` وهكذا. الملفات تستخدم صيغة الـ cassette العادية، مع
  إخفاء مفاتيح الـ API؛ راجعها واعمل لها commit.
- **`--replay`** ما ينادي الـ model أبدًا. الـ case بدون cassette تفشل بـ
  `no cassette for "<eval> [<case>]" at ...` مع أمر `--record` المطلوب تشغيله؛
  ولو طلبات الـ agent تغيّرت، الـ model call المعاد يفشل بـ
  `CassetteMismatchError` يسمّي أول اختلاف. أما `lousho eval` العادي مع `CI`
  مضبوطة فيعيد تشغيل كل case عندها cassette ويشغّل الباقي live؛ وبدون `CI`
  يشتغل live كالمعتاد.
- **`--drift`** يعيد تسجيل كل case في مجلد مؤقت (الـ cassettes المُعمّل لها
  commit ما تنمسّ) ويقارن كل واحدة بالـ cassette المودعة:
  أسماء الـ tools بترتيبها، وarguments كل call (بعد تطبيع JSON، فترتيب
  المفاتيح ما يُعتدّ به)، وعدد الخطوات، وسبب الانتهاء. استهلاك الـ tokens
  يتغير في كل run حقيقي، فما ينقارن إلا مع `--drift-usage`. الملخص يأخذ
  جدول `Drift:` (eval، case، field، committed، current)؛ وكل case انحرفت
  تأخذ assertion soft اسمها `drift`، فتظهر كـ `PASS (soft fail)` وكملاحظة
  `<system-out>` في تقرير JUnit. مع `--strict` يصير الـ drift إخفاق gate:
  الـ case تفشل، JUnit فيه `<failure>`، والـ run يخرج بـ 1.

```text
Drift:
EVAL         CASE    FIELD  COMMITTED                     CURRENT
refund flow  polite  args   lookup_order {"orderId":"42"}  lookup_order {"orderId":"43"}
```

شغّل `--drift` كل ليلة أو قبل ترقية الـ model، و`--replay` (أو
`lousho eval` العادي في CI) على كل pull request. الـ judges ما يتسجّلون:
قيّم بـ judge حقيقي فقط في ملفات `*.judge.eval.ts`.

كيف تشتغل: الـ run loop يمرّر كل model call (`generate` أو `stream`، سواء من
run عادي، أو run مبثوث، أو sub-agent، أو استئناف بعد approval) عبر seam
واحدة لاعتراض الـ provider: `setProviderInterceptor()` (مُصدَّرة من
`@lousho/build-ai-agent/testing`؛ و`src/providers/interception.ts` في
المصدر). ما في شي مثبّت فيها افتراضيًا، فهي بلا كلفة. وطالما الـ case شغالة
في أحد هذه الأوضاع، `lousho eval` يجاوبها بالـ provider مغلّف بـ
`recordReplay()` لـ cassette تلك الـ case. وتقدر تستخدم الـ seam بنفسك لتحط
أي wrapper عند حدود الـ model: الـ interceptor يستقبل provider الـ run
ويرجع الـ provider المطلوب نداؤه (لازم يرجع نفس الـ wrapper لنفس الـ
provider، وما يمس provider سبق وغلّفه). وأي فشل cassette يطلعه —
mismatch في الـ replay أو cassette مفقودة — يوصل لـ `send()` بشكل typed
(`CassetteMismatchError`، `LOUSHO_CASSETTE_INVALID`)، وليس كخطأ provider
مضغوط.

## تشغيل evals على deployment

نفس ملف الـ eval الذي يحرس CI داخل العملية يقدر يعمل smoke test لـ agent
منشور ([سيرفر node أو Cloudflare Worker](/ar/deployment#http-api)). وجّه
`lousho eval` على الـ base URL الخاص به وكل case تشتغل على الـ deployment
بدل الـ agent داخل العملية:

```bash
npx lousho eval --url https://agent.example.com --token "$DEPLOY_TOKEN"   # or LOUSHO_EVAL_TOKEN
```

كل case تأخذ session بعيدة خاصة فيها (`POST /chat { sessionId, input }`،
session واحدة لكل case، تتشاركها كل استدعاءات `t.send()` فيها) ويُقرأ
الـ SSE stream حتى `run.done`. الأحداث تتحول لنفس النتيجة التي ينتجها الـ
run داخل العملية: الـ tool calls، الرد النهائي، سبب الانتهاء، الخطوات،
والاستهلاك. فتشتغل `t.calledTool()` و`t.completed()` والـ scorers
و`t.judge()` والملخص و`--junit` بدون تغيير. الـ `agent` في الملف ما
يُستخدم؛ خلّي model الـ deployment وtoolsه على السلوك الذي تريد فحصه.

- الـ check الذي يحتاج بيانات الـ stream ما يحملها يفشل ويقول ذلك (مثل
  `maxTokens` حين `run.done` ما فيه usage)؛ و`maxCostUsd` يُبلَّغ عنه
  `skipped` حين ما في تكلفة.
- `--url` ما يجتمع مع `--record` أو `--replay` أو `--drift`
  (`LOUSHO_CONFIG_CONFLICTING_OPTIONS`): الـ cassettes تسجّل provider داخل
  العملية. وevals صيغة `score:`/`threshold` تحتاج أيضًا provider داخل
  العملية وتفشل بنفس الكود؛ استخدم trajectory evals.
- الـ deployment الذي ما يوصل، أو رد غير 2xx، أو stream منقطع يفشل تلك
  الـ case بـ `LOUSHO_REMOTE_REQUEST_FAILED`، و`401` بـ
  `LOUSHO_REMOTE_UNAUTHORIZED`؛ والـ run يكمل. الـ token ما يُطبع أبدًا
  ولا يُكتب في أي تقرير.

في الكود، مرّر `target` (يغلّب `agent`؛ و`--url` يغلّب الاثنين):

```ts
import { defineEval, remoteTarget } from '@lousho/build-ai-agent';

defineEval({
  name: 'deployed refund flow',
  target: remoteTarget({ url: 'https://agent.example.com', auth: process.env.LOUSHO_EVAL_TOKEN }),
  async test(t) {
    await t.send('Refund order 42');
    t.completed();
    t.calledTool('lookup_order');
  },
});
```

`remoteTarget({ url, auth?, fetch? })` تقبل `fetch` تحقنها بنفسك، وبهذه
الطريقة اختبارات الـ SDK نفسها تشغّل الـ routes الحقيقية داخل العملية بدون
socket.
