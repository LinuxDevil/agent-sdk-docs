تثبيت الحزمة يثبّت معها أمر `lousho`. ينشئ مشاريع جديدة، ويفحص الإعداد عندك، ويشغّل agent محليًا، ويقدّمه عبر MCP، ويشغّل evals، ويعرض traces محفوظة، ويبني artifact جاهزًا للنشر، ويفتح لوحة Agent Forge. شغّله بـ `npx lousho <command>` داخل مشروع مثبّت فيه الـ SDK.

| الأمر | ما يفعله | التفاصيل |
| ------- | ------------ | ------- |
| `lousho init [dir]` | ينشئ مشروعًا جديدًا: agent مع tool مثال، واختبار يشتغل offline، و`.env.example`؛ ويثبّت الـ dependencies ويشغّل `git init`. | [التثبيت](/ar/installation#إنشاء-مشروع-جديد) |
| `lousho doctor [spec] [--json]` | يفحص Node وpeer packages ومفاتيح الـ providers، وملف spec اختياريًا؛ ويطبع fix لكل مشكلة. | [التثبيت](/ar/installation#استكشاف-الأخطاء-lousho-doctor) |
| `lousho dev <path>` | سيرفر تطوير محلي لملف spec أو مجلد agent أو agent مكتوب بـ TS: واجهة chat فيها session (جلسة) لكل تبويب وأحداث تصل streaming، مع hot reload عند الحفظ. | [أدناه](#lousho-dev) |
| `lousho chat <path>` | REPL في الـ terminal لملف spec أو مجلد agent أو agent مكتوب بـ TS: يعرض الردود streaming، ويبيّن الـ tool calls، ويطلب approvals (موافقات) ويطرح الأسئلة. | [أدناه](#lousho-chat) |
| `lousho acp <path>` | يقدّم ملف spec أو مجلد agent أو agent مكتوب بـ TS لمحرر (Zed وغيره من ACP clients) عبر Agent Client Protocol على stdio. | [ACP](/ar/acp) |
| `lousho add <name>` | يثبّت tool أو skill أو channel أو schedule أو memory slot من JSON registry داخل مجلد agent، بعد ما يعرض الـ permission manifest ويفحص الكود مقابله. | [Registry](/ar/registry) |
| `lousho mcp <spec>` | يقدّم الـ agent كسيرفر MCP (stdio، أو HTTP مع `--http`). | [MCP](/ar/mcp-integration#تشغيل-agent-كسيرفر-mcp) |
| `lousho eval [globs...]` | يشغّل ملفات `*.eval.ts` تحت vitest؛ ويطبع ملخصًا ويكتب تقارير JUnit/JSON. | [Evals](/ar/evals#lousho-eval) |
| `lousho traces [id]` | يعرض آخر runs حفظها `fileTraceExporter()` (المدة، والـ model والـ tool calls، والـ tokens، والتكلفة)، أو يطبع run واحد كشجرة spans. | [Observability](/ar/observability#local-traces) |
| `lousho build --target=<t> --agent=<spec>` | يبني سيرفر Node أو Docker image أو Cloudflare Worker جاهزًا للنشر. | [النشر](/ar/deployment) |
| `lousho studio` | يفتح Agent Forge، الـ dashboard المرئية، على port محلي واحد. | [Agent Forge](/ar/agent-forge) |

أي أمر يستقبل `<spec>` يقرأ ملف spec للـ agent (`.yaml` أو `.yml` أو `.json`، انظر [الإعداد](/ar/configuration#ملفات-تعريف-الـ-agent-agentspec)).

## الاستخدام

```text
lousho init [dir] [--provider P] [--template T] [--yes] [--no-install] [--no-git] [--package-manager PM] [--force] [--sdk-path <dir|tgz>]
lousho dev <spec.yaml|spec.json|agent-dir|agent.ts> [--port N] [--host H] [--no-schedules] [--traces[=dir]]
lousho chat <spec.yaml|spec.json|agent-dir|agent.ts> [--model provider/model] [--session id] [--store sqlite:<file>] [--traces[=dir]]
lousho acp <spec.yaml|spec.json|agent-dir|agent.ts> [--model provider/model]
lousho add <name> [--registry <url-or-path>] [--dir <agent-dir>] [--yes] [--allow <list>] [--overwrite] [--dry-run]    (or --list)
lousho build <agent-dir|spec> --target=<name> [--out=<dir>]    (or --agent=<path>)
lousho studio [--port N] [--host H] [--prod|--dev]
lousho mcp <agent.yaml|json> [--http --port N --host H]
lousho doctor [agent.yaml|json] [--json]
lousho eval [globs...] [--tag t] [--junit path] [--json path] [--strict] [--judge] [--record | --replay | --drift [--drift-usage]] [--url <base> [--token <bearer>]] [--config vitest.config.ts]
lousho traces [traceId|prefix] [--dir D] [--limit N] [--json] [--content]
```

كل الأوامر تحلّل الـ flags بنفس الطريقة (`parseArgs` في Node، بالوضع strict): الصيغتان `--flag value` و`--flag=value` تعملان، وإذا تكرّر flag تُعتمد آخر قيمة (`--tag` يجمع القيم بدل ذلك)، و`--` تنهي الـ flags، و`-h` / `--help` يطبع الـ usage الخاص بالأمر ويخرج بـ 0. الـ flag غير المعروف، أو الـ flag بدون قيمته (لا يأخذ الـ flag التالي قيمةً له أبدًا)، أو الـ argument الزائد، يفشل بـ `LOUSHO_CONFIG_INVALID` مع سطر الـ usage. القيمة التي تبدأ بـ `-` تحتاج صيغة `=`: `--model=-x`. `--traces` هو الـ flag الوحيد الذي قيمته اختيارية: يأخذها فقط بصيغة `=` (`--traces=./t`)، فـ`--traces agent.yaml` يبقى flag متبوعًا بمسار.

`lousho init` هو الاستثناء: يحلّل flags بنفسه، وأي flag أو قيمة غير صالحة يفشل بـ `InitUsageError` — تُطبع رسالته كما هي ويكون exit code هو 1 — لا بمسار `LOUSHO_CONFIG_INVALID` المشترك. الـ flags القصيرة الوحيدة غير `-h` هي `-y` بدل `--yes`، في `init` وفي `add`.

و`lousho eval` يقبل أيضًا `--config <file>` ليشتغل على ملف إعداد vitest الخاص بك بدل المولَّد؛ وعندها تعمل الـ globs كـ filters لـ vitest على ملفات ذلك الإعداد.

`npm create lousho-agent my-agent` يشغّل `lousho init` بنفس الـ arguments. ولإنشاء مشروع على build غير منشور من الـ SDK، مرّر `--sdk-path` (انظر [التثبيت من build محلي](/ar/installation#التثبيت-من-build-محلي)).

## `lousho dev`

```bash
npx lousho dev agent.yaml                  # a spec file
npx lousho dev ./my-agent                  # an agent directory
npx lousho dev src/agent.ts                # a TypeScript (or JavaScript) module
npx lousho dev agent.yaml --port 4000 --host 0.0.0.0
npx lousho dev ./my-agent --no-schedules   # do not fire the directory's cron schedules
```

في مجلد الـ agent، تُركَّب `channels/` تحت `/channels` وتشتغل `schedules/` (وكلاهما يُستبدل عند الـ reload، بعد إيقاف الـ schedules القديمة أولًا)؛ ومع `--no-schedules` لا يشتغل أي schedule. انظر [Agent directories](/ar/agent-directories#شغّله-بـ-lousho-dev).

يقدّم chat UI على `GET /`، و`GET /health`، و`GET /dev/status`، وendpoints الـ chat أدناه (حد حجم الـ body هو 1MB). ومعنى `<path>` يُستنتج من المسار نفسه:

| المسار | يُحمَّل بواسطة |
| ---- | ----------- |
| `.yaml`, `.yml`, `.json` | `loadSpec()` + `specToAgent()` ([الإعداد](/ar/configuration)) |
| مجلد | `loadAgentDir()` ([Agent directories](/ar/agent-directories)) |
| `.ts`, `.mts`, `.cts`, `.js`, `.mjs`, `.cjs` | الـ default export للـ module، أو export اسمه `agent`: كائن `SimpleAgent` (ما يرجعه `createAgent()`) أو object بخيارات `createAgent()` |

أي امتداد آخر، أو مسار غير موجود، أو module بلا export للـ agent، يفشل بخطأ له كود (`LOUSHO_SPEC_UNSUPPORTED_FORMAT` أو `LOUSHO_CONFIG_INVALID`) مع الـ fix. ملف `.ts` يستورده Node نفسه وقت التشغيل (الإصدار 22.19 أو أحدث يشيل الـ types، فالـ imports النسبية لازم تذكر امتداد الملف)؛ استخدم `.js` للكود الذي يحتاج transpiler.

**Chat sessions.** واجهة الـ chat تحتفظ بـ session واحدة لكل تبويب في المتصفح (المعرّف في `sessionStorage`؛ وزر "New session" يبدأ واحدة أخرى) وتعرض الـ turn أثناء الـ streaming: النص فور وصوله، والـ tool calls مع arguments ونتائجها، والأخطاء، والـ tokens والتكلفة من `run.done`. الـ tool call الذي يحتاج approval يعرض زرّي Approve / Reject؛ والـ `ask_question` call يعرض خياراته كأزرار مع حقل نص حر. نفس الـ endpoints تشتغل من `curl` أو من صفحتك:

| Endpoint | ما يفعله |
| -------- | ------------ |
| `POST /chat` `{ "sessionId", "input" }` | يشغّل `agent.session({ id: sessionId }).stream(input)` ويرسل الـ turn كـ SSE: سطر `data: <AgentEvent JSON>` لكل event ([Streaming](/ar/streaming))، ثم `event: done`. الـ history يُحفظ لكل `sessionId` (من 1 إلى 128 حرف من `A-Za-z0-9_-`). |
| `GET /chat/:sessionId` | الـ transcript الخاص بالـ session: `{ sessionId, messages, pending }`؛ و`pending` تكون `{ status, approvalId? }` ما دام فيه turn ينتظر approval، وإلا `null`. |
| `POST /chat/:sessionId/approvals/:id` `{ "approved", "note"? }` أو `{ "answer" }` | يبتّ في الـ approval المعلّق (`agent.approvals.streamResolve()`)، أو يجيب على سؤال (`agent.approvals.streamAnswer()`)، ويرسل تكملة الـ turn كـ SSE. ويمكن أن يتوقف مرة أخرى بـ `approval.requested` جديد. يعيد `404` إذا لم يكن `id` معلّقًا. |
| `POST /chat` `{ "message" }` | Deprecated: بلا session وبلا streaming. يعيد `ExecutionResult` الخاص بالـ agent كـ JSON، مع header `Deprecation: true`. |

`--traces` (أو `--traces=<dir>`) يكتب كل run في ملفات traces محلية عبر `fileTraceExporter()`، في `.lousho/traces` إلا إذا سمّيت مجلدًا، فيعرض `npx lousho traces` ماذا فعل الـ agent. هو معطّل افتراضيًا لأن الملفات تحتوي محتوى الـ prompts وarguments ونتائج الـ tools، والـ flag يطبع المجلد الذي يكتب فيه. ينطبق على ملفات spec ومجلدات الـ agents والـ modules بالتساوي (الـ `exporter` الخاص بالـ module يُستبدل ما دام الـ flag مضبوطًا). انظر [Local traces](/ar/observability#local-traces).

الـ sessions تعيش في `memoryStore()` داخل العملية (تختفي إذا وقّفت `lousho dev`)، أو في الـ `store` الخاص بالـ agent إذا ضبطته خيارات `createAgent()` في الـ module. تكملة الـ approval تُرسل streaming هي الأخرى: الـ endpoint يشغّلها بـ `agent.approvals.streamResolve()` (أو `streamAnswer()` إذا كان سؤالًا) ويرسل events الـ turn المكمّل — الـ tool call المبتوت فيه، والـ text deltas، وتوقفًا آخر محتملًا، و`run.done` — فور حدوثها.

سيرفرات `lousho build` (`node-server` و`docker`) تقدّم نفس الـ endpoints من نفس الكود، مع sessions في store تحدده `LOUSHO_STORE` وbearer auth اختيارية: انظر [Deployment: HTTP API](/ar/deployment#http-api).

**Hot reload.** يُعاد بناء الـ agent بعد لحظة (100 ms) من تغيّر ملف، بدون إعادة تشغيل السيرفر وبدون خسارة الـ port:

- في حالة spec: ملف الـ spec نفسه؛
- في حالة مجلد: كل ما تحته (`instructions.md`، وملف الإعداد، و`tools/`، و`skills/`، و`subagents/`)، ما عدا `node_modules` و`.git`؛
- في حالة module: الملف والملفات المحلية التي يستوردها (الـ specifiers النسبية في `import` / `require`، تُكتشف مرة واحدة عند بدء التشغيل؛ بلا bundler).

ملفات المجلدات والـ modules تُستورد مع query `?t=<time>` يكسر الـ cache، فأي ملف tool أو agent عدّلته يُعاد تقييمه. أما الملف الذي *يستورده* ذلك الملف (helper مشترك مثلًا) فيبقى في الـ cache عند Node: أعد تشغيل `lousho dev` بعد تعديل ملف كهذا. الـ console يسجّل ما أُعيد تحميله. الـ agent الجديد يُبنى (وينتظر `ready()`، فتتصل سيرفرات MCP) قبل أن يحل محل القديم، ثم يُستدعى `close()` على القديم. إذا فشلت إعادة البناء، يظل آخر agent سليم يرد، والخطأ يُسجَّل ويظهر في banner على صفحة الـ chat (وفي `error` ضمن `GET /dev/status`)؛ وأول تعديل ناجح يزيله. الـ sessions تنجو من الـ reload: الـ store يعيش أكثر من تبديل الـ agent، فالرسالة التالية تكمل المحادثة على الـ agent الجديد. الـ approval الذي كان معلّقًا على الـ agent القديم لا يعرفه الجديد (`404`)؛ ابدأ session جديدة.

المجلدات والـ modules هي كودك وتشتغل بصلاحياتك؛ لا تشغّل `lousho dev` إلا على ما تثق فيه.

- `--port` - الافتراضي `3737`.
- `--host` - الافتراضي `127.0.0.1` (localhost فقط). مرّر مثلًا `--host=0.0.0.0` لتفعّل الوصول من الـ LAN.

## `lousho chat`

```bash
npx lousho chat agent.yaml                          # a spec file
npx lousho chat ./my-agent --model openai/gpt-4o    # an agent directory, on another model
npx lousho chat src/agent.ts --store sqlite:.lousho/chat.db --session support
```

REPL في الـ terminal: كل سطر تكتبه هو turn واحد في الـ session. `<path>` يُحمَّل كما يحمّله `lousho dev` (ملف spec، أو مجلد agent، أو module `.ts`/`.js`، انظر [`lousho dev`](#lousho-dev))؛ والمسار غير الموجود أو الامتداد غير الصالح يفشل بنفس الخطأ الذي له كود (`LOUSHO_CONFIG_INVALID` أو `LOUSHO_SPEC_UNSUPPORTED_FORMAT`)، وكذلك معرّف `--session` غير الصالح (`LOUSHO_SESSION_ID_INVALID`).

```text
> look up cats
[lookup] {"q":"cats"}
  -> found cats
Cats are great.
[usage] 20 in / 6 out tokens, $0.0004
> email the report to sam
Approve send_email({"to":"sam@example.com"})? [y/N] y
  -> sent
Done, the report is on its way.
```

- النص يُكتب فور ما ينتجه الـ model. كل tool call سطر واحد باهت، `[tool_name] {args}`، يتبعه `  -> result` (أو `  -> error: ...`).
- الـ tool call الذي يحتاج approval يسأل `Approve <tool>(args)? [y/N]`: `y` أو `yes` تشغّله، وغيرهما يرفضه والـ model يكمل. الـ `ask_question` call (`askQuestion: true`) يطبع السؤال مع خيارات مرقّمة؛ أجب بالرقم أو بنص حر.
- بعد كل turn يعرض `[usage]` الـ tokens، والتكلفة أيضًا إذا كانت أسعار كل الـ models المستخدمة معروفة (`~` تعني أن الـ tokens مقدّرة).
- أخطاء الـ SDK تُطبع مع الكود `[LOUSHO_...]` والـ fix، والـ session تكمل.
- `--traces` أو `--traces=<dir>` يكتب runs الـ session في ملفات traces محلية، كما في `lousho dev`؛ وسطر على stderr يوضح المكان.

| الأمر | ما يفعله |
| ------- | ------------ |
| `/new` | يبدأ session جديدة (القديمة تبقى في الـ store). |
| `/model <provider/model>` | يعيد بناء الـ agent على model آخر؛ والـ session تكمل. عند الفشل يبقى الـ model الحالي. |
| `/compact` | يعمل compaction للـ transcript الآن (نتائج الـ tools القديمة تُزال) ويطبع الحجم قبل وبعد. |
| `/clear` | يفرّغ الـ transcript؛ ومعرّف الـ session يبقى. |
| `/history` | يطبع الـ transcript. |
| `/quit` | يخرج (Ctrl-D يعمل أيضًا). |

| الخيار | المعنى |
| ------ | ------- |
| `--model provider/model` | يستخدم هذا الـ model بدل الذي يسمّيه الهدف. ينطبق على ملفات spec ومجلدات الـ agents وexports خيارات `createAgent()`؛ أما الـ module الذي يصدّر agent مبنيًا مسبقًا فيحتفظ بالـ model الخاص به. بادئة `vendor/` في الـ model تختار الـ provider؛ ومع OpenRouter استخدم `openrouter/<vendor>/<model>` (مثل `openrouter/openai/gpt-4o`). |
| `--session id` | يفتح هذه الـ session (من 1 إلى 128 حرف من `A-Za-z0-9_-`)؛ الافتراضي `chat-<id>` جديدة. |
| `--store sqlite:<file>` | يحفظ الـ sessions في ملف SQLite ([`SqliteStore`](/ar/durable-execution))، فـ`--session id` يكمل محادثة بعد إعادة التشغيل. الافتراضي: في الذاكرة. الـ approvals المعلّقة لا تُستعاد بعد إعادة التشغيل. |

الـ REPL نفسه هو `runChatRepl()` في `src/cli/chatRepl.ts`؛ يأخذ أسطر الإدخال وoutput stream وfactory للـ agent، فيمكن اختباره بأسطر scripted وagent مبني على `mockModel` وبدون terminal.

## `lousho build`

```bash
npx lousho build --target=node-server --agent=agent.yaml        # or docker / cloudflare-worker
npx lousho build ./my-agent --target=node-server                # an agent directory (node-server, docker)
```

يكتب الـ artifact في `--out` (الافتراضي `.lousho/build/<target>`) ويطبع أمر تشغيله أو نشره. البناء يحتاج `tsup` (`npm install --save-dev tsup`). الـ targets والـ HTTP API الذي تقدّمه وحدود Workers كلها في [النشر](/ar/deployment).

## `lousho studio`

```bash
npx lousho studio            # http://127.0.0.1:4750
npx lousho studio --port 5000
```

يشغّل سيرفر محلي واحد للـ API والـ UI الخاصين بـ Agent Forge. الـ agents وحالة الـ run تُخزَّن تحت `.lousho/` في المجلد الحالي. انظر [Agent Forge](/ar/agent-forge) للـ walkthrough.
