run طويل لـagent يملأ الـcontext window غالبًا بنتائج الـtools: محتويات ملفات، نتائج بحث، ردود API قرأها الـmodel مرة ولم يعد يحتاجها كاملة. الـcompaction (ضغط سياق المحادثة) يُبقي run كهذا تحت حد الـmodel على مرحلتين: أولاً يستبدل بنتائج الـtools القديمة علامة قصيرة، وإذا لم يكفِ ذلك يستبدل بأقدم الدورات ملخصًا يكتبه model (أرخص).

## تفعيل الـcompaction على agent

مع `createAgent()`، فعّل الـcompaction بخيار `compaction`. القيمة `true` تثبّت الـhook بإعداداته الافتراضية: تقليم نتائج الـtools القديمة فوق 90% من window الـmodel. وإذا مررت object فإنك تضبطه بنفسك، وفيه `summarizer` يختار `twoPhaseStrategy()` مع الـmodel الذي تعطيه — سلسلة `"provider/model"` أو `LLMProvider`. بادئة `vendor/` في اسم الـmodel هي التي تحدد الـprovider. مع OpenRouter استخدم `openrouter/<vendor>/<model>` (مثلاً `openrouter/openai/gpt-4o-mini`).

```ts
import { createAgent } from 'lousho';

const simple = createAgent({ model: 'openai/gpt-4o', compaction: true });

const agent = createAgent({
  model: 'openai/gpt-4o',
  compaction: {
    thresholdPercent: 0.8, // compact above 80% of the context window (default 0.9)
    protectedTokens: 20_000, // never change the newest 20K tokens (default 40_000)
    summarizer: 'openai/gpt-4o-mini', // prune, then summarize if still too big
  },
});

for await (const event of agent.stream('Audit the repository.')) {
  if (event.type === 'compaction.done') console.log(`${event.tokensBefore} -> ${event.tokensAfter} tokens`);
}
```

الـobject يقبل `strategy` و`thresholdPercent` و`contextWindow` و`protectedTokens` و`reserveOutputTokens` و`onCompaction` (كما في الجدول أدناه) و`summarizer`. الجمع بين `summarizer` و`strategy` خطأ في الإعداد — مرّر `twoPhaseStrategy({ model })` كقيمة لـ`strategy` بدلًا منه. `createAgent({ hooks })` يقبل أي `AgentHook` أخرى، وهي تعمل قبل hook الـcompaction، فيرى الـcompaction ما أضافته. الـhooks والـcompaction ينطبقان على `send()` و`stream()` والـsessions.

### أحداث الـstream

`agent.stream()` و`session.stream()` و`AgentExecutor.stream()` يبلّغون عن كل عملية compaction بحدثين، داخل الخطوة وقبل استدعاء الـmodel الذي أثارها (انظر [Streaming](/ar/stream-events#event-schema-version-1)):

| `type` | الحقول |
| --- | --- |
| `compaction.start` | `strategy`, `tokensBefore`, `contextWindow`, `thresholdTokens`, `trigger?: 'manual'` |
| `compaction.done` | `strategy`, `appliedStrategy?`, `tokensBefore`, `tokensAfter`, `prunedToolCallIds`, `summary?: boolean`, `error?: { message }`, `unchanged?: true`, `trigger?: 'manual'` |

كل `compaction.start` يتبعه `compaction.done` واحد بالضبط. إذا لم تستطع الاستراتيجية تصغير شيء، يساوي `tokensAfter` قيمة `tokensBefore` وتكون `unchanged` هي `true`. بعد ذلك يواصل الـhook الـcompaction على هذا الـtranscript بهدوء: الخطوات اللاحقة التي لا تزال لا تغيّر شيئًا لا تطلق أحداثًا، وأول محاولة تغيّر شيئًا فعلاً تطلق زوج `compaction.start` / `compaction.done` الخاص بها كالمعتاد، فلا يبلّغ الـrun العالق فوق العتبة عن زوج أحداث في كل خطوة. وإذا فشلت (أو فشل الـsummarizer فعاد الـhook إلى التقليم)، يُضبط `error` ويستمر الـrun. الملخص الذي لا يُنزل المحادثة تحت العتبة — أو الذي يكبّرها — مرفوض بالطريقة نفسها: يُضبط `error`، ويحتفظ الـrun بالنتيجة المقلّمة بدلًا من الملخص، وتكون `appliedStrategy` هي `'prune-tool-results'`. بعد ذلك يكتفي الـhook بتقليم هذا الـtranscript حتى يصبح عدد رسائله ضعف ما كان عليه وقت الرفض، ثم يسمح للـsummarizer بالمحاولة من جديد. فالـsummarizer الذي لا يستطيع المساعدة يكلّف بضعة استدعاءات في الـrun كله، لا استدعاءً في كل خطوة، والـsummarizer الذي رُفض لأنه لم يكن لديه ما يكفي لتلخيصه يحصل على فرصة ثانية. `strategy` هي الاستراتيجية التي عملت، وهي نفسها على `compaction.start` و`compaction.done` (`'prune-tool-results'` ما دامت الملخصات متوقفة مؤقتًا). تكون `summary` هي `true` عندما تُستبدل الدورات القديمة بملخص (النص نفسه لا يُرسَل؛ استخدم `onCompaction`، الذي يقبله الـobject أيضًا). `send()` دون listener لا يطلق أحداثًا. الـhooks تضيف أحداثها بـ `ctx.emit?.(...)` على سياق `preGenerate`، وهو موجود عندما يكون للـrun listeners (`createAgent({ onEvent })` أو `onAgentEvent`) أو عندما يعمل بـstream.

## الـcompaction على run

`createCompactionHook()` يعيد `AgentHook` اسمه `compaction`. مرّره في `createAgent({ hooks })`. الإعداد الموصى به: استراتيجية المرحلتين مع model تلخيص رخيص:

```ts
import { createAgent, createCompactionHook, twoPhaseStrategy } from 'lousho';

const agent = createAgent({
  provider,
  hooks: [
    createCompactionHook({
      strategy: twoPhaseStrategy({ model: 'openai/gpt-4o-mini' }), // prune, then summarize if still too big
      thresholdPercent: 0.9, // compact above 90% of the context window (the default)
      protectedTokens: 40_000, // never change the newest 40K tokens (the default)
      onCompaction: ({ tokensBefore, tokensAfter, prunedToolCallIds, summary, error }) => {
        console.log(`compacted ${tokensBefore} -> ${tokensAfter} tokens (${prunedToolCallIds.length} results pruned)`);
        if (summary) console.log('summary:', summary);
        if (error) console.warn('summarizer failed, kept the pruned conversation:', error.message);
      },
    }),
  ],
});
```

قبل كل استدعاء للـmodel، يقدّر الـhook حجم الطلب بـ `estimateTokens` (انظر [Models, tokens and cost](/ar/models-and-cost#الـ-models-وجدول-الأسعار)): الرسائل (ومنها الـsystem prompt)، وتعريفات الـtools، و schema المخرجات. وبعد أي استدعاء أبلغ فيه الـprovider عن عدد tokens الـprompt، يضيف الـhook الفرق الذي تجاوز به هذا الرقمُ التقديرَ إلى التقدير التالي في الـrun نفسه، فحتى الـframing المخفي الذي يضيفه الـprovider يُحسب. تعريفات الـtools لا تُضغط، لذا يجب أن تتسع المحادثة لما تتركه هذه التعريفات من العتبة. أعداد الـtokens في `compaction.start` / `compaction.done` هي أحجام الطلب هذه. إذا كان الحجم فوق `thresholdPercent` من الـcontext window، يشغّل الـhook استراتيجيته (وينتظرها إذا كانت async) ويستدعي `onCompaction` مع أعداد الـtokens، والـ`toolCallId`s التي قُلّمت، والملخص إن وجد، واسم الاستراتيجية.

| الخيار | الافتراضي | المعنى |
| --- | --- | --- |
| `thresholdPercent` | `0.9` | نفّذ الـcompaction عندما يتجاوز الطلب المقدَّر هذه النسبة من الـcontext window. يجب أن تكون القيمة في (0, 1]. |
| `contextWindow` | من الـregistry، وإلا `128_000` | الـcontext window بالـtokens. افتراضيًا تُجلب لـ `request.model` بـ `getModelInfo()`؛ سجّل الـmodels الخاصة بك بـ `registerModel()`. القيمة الاحتياطية `128_000` تطبع `console.warn` مرة واحدة (انظر [Local and unknown models](#الـmodels-المحلية-وغير-المعروفة)). |
| `reserveOutputTokens` | لا شيء | tokens تبقى فارغة للرد: تصبح العتبة على الأكثر `contextWindow - reserveOutputTokens`. ولا ترفع أبدًا العتبة التي يحددها `thresholdPercent`. |
| `protectedTokens` | `40_000`، وعلى الأكثر نصف العتبة | أحدث الرسائل التي تتسع لها هذه الكمية من الـtokens لا تتغير أبدًا. القيمة الافتراضية محدودة بنصف العتبة (حوالي 3,700 token على window حجمه 8K)، فحتى الـwindow الصغير يحدث فيه compaction. والقيمة التي تضبطها أنت عند العتبة أو فوقها كانت ستحمي كل شيء؛ لذا تُحدّ بالطريقة نفسها، مع `console.warn` مرة واحدة. |
| `strategy` | `pruneToolResultsStrategy()` | طريقة الـcompaction (انظر أدناه). `twoPhaseStrategy()` هي الموصى بها؛ لكنها تحتاج model تلخيص، فهي ليست الافتراضية. |
| `onCompaction` | لا شيء | تُستدعى بعد كل compaction غيّر المحادثة أو أبلغ عن `error`، مع أعداد الـtokens، والـ`toolCallId`s المقلّمة، و`strategy`، و`appliedStrategy`، ونص الملخص، والـ`error`. |

الـcompaction لا يُفشل الـrun أبدًا. إذا رمت الاستراتيجية استثناءً، أو فشل استدعاء الـsummarizer، يستمر الـrun (بالمحادثة المقلّمة، أو دون تغيير) وتستلم `onCompaction` الـ`error`.

داخل الـrun، استدعاء الـmodel الخاص بالـsummarizer جزء من الـrun: الـtokens الخاصة به موجودة في `result.usage` (تحت model الـsummarizer في `byModel`، وفي `modelCalls`)، ويأخذ span من نوع `chat` مع `lousho.call.purpose: 'compaction'` تحت الـspan الخاص بالـrun، ويُحسب ضمن ميزانيات `limits` للـrun. (`session.compact()` و`compactMessages()` يعملان خارج أي run، فلا تُحسب استدعاءات التلخيص فيهما في أي مكان.)

يعيد الـhook كتابة transcript الـrun نفسه، لا نسخة منه: مصفوفة `messages` في الطلب هي قائمة رسائل الـrun، والـhook يغيّرها في مكانها. فتبقى النتيجة المقلّمة أو الملخص في الخطوات اللاحقة، وفي الـcheckpoints (الـsession المستأنفة لا تستعيد السجل الكامل) وفي `result.messages`، ولا تُضغط مرة أخرى في الخطوة التالية. الـcompaction يُفقد معلومات: إذا احتاج الـmodel نتيجة مقلّمة مرة أخرى، فعليه أن يستدعي الـtool من جديد.

### الـmodels المحلية وغير المعروفة

العتبة نسبة من الـcontext window الخاص بالـmodel، فالـcompaction يحتاج الـwindow الحقيقي. لأي model لا يعرفه [سجل الـmodels](/ar/models-and-cost#الـ-models-وجدول-الأسعار) (أغلب الـmodels المحلية)، يفترض الـhook `128_000` token ويطبع `console.warn` مرة واحدة فيه اسم الـmodel. الخادم المحلي يعمل عادةً بـwindow أصغر بكثير، وعندئذٍ لا يعمل الـcompaction أبدًا قبل أن يرفض الخادم الطلب. اضبط الـwindow الذي حمّلت به الـmodel: في LM Studio هو طول السياق المحمّل للـmodel (`loaded_context_length` من `GET /api/v0/models/<id>`)، وفي Ollama هو خيار `num_ctx` (`ollama show <model>` يطبع القيمة الافتراضية للـmodel).

```ts
import { createAgent, registerModel } from 'lousho';

// Either on the agent...
const agent = createAgent({
  model: 'ollama/qwen3:8b',
  compaction: { contextWindow: 8_192, reserveOutputTokens: 1_024 },
});

// ...or once for every feature that reads the window (compaction, tool search).
registerModel({ id: 'qwen3:8b', provider: 'ollama', contextWindow: 8_192 });
```

على window صغير، القيمة الافتراضية لـ `protectedTokens` (40,000) تُحدّ بنصف العتبة، فتبقى أحدث ~3,700 token من window حجمه 8K سليمة، ويمكن تقليم نتائج الـtools الأقدم. اضبط `protectedTokens` بنفسك إذا أردت حماية أكثر أو أقل؛ واجعلها تحت العتبة.

[Tool search](/ar/tool-search) يقرأ الـwindow بالطريقة نفسها ويحذّر بالطريقة نفسها؛ والإعداد الخاص به هو `toolSearch.contextWindow`.

#### متقدم: executor API

تسجيل الـhook في `HookRegistry` للكود الذي يستدعي الـexecutor مباشرة (انظر [executor API](/ar/executor-api)):

```ts
import { AgentExecutor } from 'lousho/executor';
import { HookRegistry, createCompactionHook, twoPhaseStrategy } from 'lousho';

const hooks = new HookRegistry();
hooks.register(
  createCompactionHook({
    strategy: twoPhaseStrategy({ model: 'openai/gpt-4o-mini' }),
    thresholdPercent: 0.9,
    protectedTokens: 40_000,
  })
);

const result = await AgentExecutor.execute({ agent, input, provider, toolRegistry, hooks });
```

## الاستراتيجيات

| الاستراتيجية | وظيفتها |
| --- | --- |
| `pruneToolResultsStrategy()` | تستبدل بنتائج الـtools القديمة علامة. دون استدعاء model. |
| `summarizeStrategy({ model, ... })` | تستبدل بالدورات القديمة رسالة ملخص واحدة يكتبها `model`. |
| `twoPhaseStrategy({ model, ... })` | تقلّم أولاً؛ ولا تلخّص إلا إذا بقيت المحادثة فوق العتبة. موصى بها. |

### تقليم نتائج الـtools

`pruneToolResultsStrategy()` تستبدل بـ `content` كل نتيجة tool أقدم من الذيل المحمي علامة قصيرة تسمّي الاستدعاء، مثل `[pruned: search({"query":"deploy"}) result, 18234 chars; already read]` (المعاملات الأطول من 120 حرفًا تُقتطع)، فيعرف الـmodel ما الذي جلبه من قبل، ولا يستدعي الـtool نفسه مرة أخرى لمجرد أن يرى النتيجة. والعلامات بالصيغة القديمة `[pruned: search result, 18234 chars]` يُتعرَّف عليها وتُترك كما هي. ولا تغيّر أبدًا:

- رسائل system، ولا رسائل user (ومنها الأولى)، ولا دورات assistant — فكل tool call يحتفظ برسالة نتيجته، ويبقى الـtranscript صالحًا لكل provider؛
- نتائج آخر دورة assistant، التي لم يقرأها الـmodel بعد، حتى لو كانت أكبر من `protectedTokens`؛
- النتائج المثبتة، ولا النتائج التي هي أصلاً علامة، ولا النتائج الأقصر من العلامة.

### تلخيص الدورات القديمة

`summarizeStrategy()` ترسل الرسائل التي تسبق الذيل المحمي إلى الـsummarizer مع تعليمة مركّزة، وتستبدل بها رسالة `user` واحدة:

```text
[Conversation summary]
<the summary>
```

| الخيار | الافتراضي | المعنى |
| --- | --- | --- |
| `model` | مطلوب | الـsummarizer: `LLMProvider`، أو spec بصيغة `"provider/model"` يُحلّ بـ `resolveProvider()`. يكفي عادةً model صغير ورخيص. |
| `protectedTokens` | قيمة الـhook | الـtokens الحديثة التي تبقى كما هي. |
| `prompt` | `DEFAULT_SUMMARY_PROMPT` | التعليمة التي تُرسل كرسالة system إلى الـsummarizer. المحادثة التي تُلخَّص هي رسالة الـuser. |
| `maxSummaryTokens` | افتراضي الـprovider | قيمة `maxTokens` لاستدعاء التلخيص. |

الملخص يُبقي الـtranscript صالحًا لكل provider:

- رسائل system والرسائل المثبتة تبقى في أماكنها، والملخص يحل محل أول رسالة مُلخّصة؛
- دورة assistant تُلخَّص أو تبقى مع كل نتائج الـtools الخاصة بها معًا، فلا يفقد أي tool call نتيجته (ولا تفقد أي نتيجة الـcall الخاص بها)؛
- الرسالة الأخيرة ونتائج آخر دورة assistant تبقى دائمًا.

إذا فشل استدعاء التلخيص (أو أعاد نتيجة فارغة)، تعود الاستراتيجية إلى التقليم وتعيد الفشل في `error`.

### المرحلتان

`twoPhaseStrategy()` تأخذ الخيارات نفسها. تقلّم نتائج الـtools أولاً — وهذا مجاني — ولا تستدعي الـsummarizer إلا إذا كانت المحادثة المقلّمة لا تزال فوق `thresholdPercent` من الـcontext window. عندئذٍ يقرأ الـsummarizer المحادثة المقلّمة. وإذا فشل، تبقى المحادثة المقلّمة ويُبلَّغ عن `error`.

## تثبيت الرسائل

`pinMessage(message)` تعيد نسخة من الرسالة موسومة بأنها مثبتة (تضبط `metadata.pinned: true`؛ و`Message.metadata` بيانات للتطبيق لا تُرسل إلى الـmodel أبدًا). الاستراتيجيات المدمجة لا تقلّم رسالة مثبتة ولا تلخّصها أبدًا؛ ونتيجة tool مثبتة تحفظ دورة الـassistant التابعة لها كاملة. ثبّت ما يجب أن يراه الـagent كاملًا دائمًا، مثل نص المهمة أو مستند أساسي:

```ts
import { pinMessage, isPinned, type Message } from 'lousho';

const messages: Message[] = [
  { role: 'system', content: 'You are a research assistant.' },
  pinMessage({ role: 'user', content: 'Goal: compare the three vendors on price and support.' }),
];
console.log(isPinned(messages[1])); // true
```

يجب على الاستراتيجيات المخصصة أن تراعي `isPinned()` أيضًا.

## الـcompaction يدويًا

`compactMessages(messages, options)` تشغّل استراتيجية مرة واحدة، مهما كان حجم المحادثة، وتعيد promise نتيجته مصفوفة جديدة (لا يُعدَّل المدخل). استخدمها لتصغير transcript مخزّن قبل أن تكمله:

```ts
import { compactMessages, summarizeStrategy, type Message } from 'lousho';

declare const history: Message[];

const { messages, tokensBefore, tokensAfter, prunedToolCallIds } = await compactMessages(history, {
  protectedTokens: 8_000,
  model: 'gpt-4o-mini', // for the context-window lookup and the token estimator
});
console.log(`${tokensBefore} -> ${tokensAfter} tokens, pruned ${prunedToolCallIds.length} results`);

const summarized = await compactMessages(history, {
  protectedTokens: 8_000,
  strategy: summarizeStrategy({ model: 'openai/gpt-4o-mini' }),
});
console.log(summarized.summary ?? summarized.error?.message);
```

## الـcompaction على session

`session.compact(options?)` تعمل compaction لسجل [session](/ar/sessions) فورًا، مهما كان حجمه، وتحفظه في الـstore الخاص بالـsession (الذاكرة أو ملف أو SQLite أو KV) وتعيد `{ messagesBefore, messagesAfter, tokensBefore, tokensAfter, strategy, error? }`. تشغّل `options.strategy` إن وُجدت، وإلا استراتيجية `agent.session({ compaction })` — وهي القيمة نفسها التي يأخذها `createAgent({ compaction })`، و`compaction` الخاص بالـagent إذا لم تضبط الـsession واحدة — وإلا تقلّم نتائج الـtools القديمة. الرسائل المثبتة تبقى. والـsession التي لا رسائل فيها تنتهي دون أن تفعل شيئًا. يُرفض الاستدعاء بـ `LOUSHO_SESSION_BUSY` إذا كانت هناك turn قيد التشغيل، وبـ `LOUSHO_SESSION_TURN_PENDING` / `LOUSHO_SESSION_AWAITING_APPROVAL` إذا كانت هناك durable turn لم تنتهِ. الـlisteners التي أُضيفت بـ `session.on()` تستلم `compaction.start` و`compaction.done` مع `trigger: 'manual'`. أما `session.clear()` فتفرّغ الـtranscript، وتحذف الـcheckpoint الخاص بكل turn وسجل الـcheckpoints، وتطلق `context.cleared`.

```ts
import { createAgent, twoPhaseStrategy } from 'lousho';
import { mockModel } from 'lousho/testing';

const agent = createAgent({ provider: mockModel(['ok']) });
const session = agent.session({ compaction: { strategy: twoPhaseStrategy({ model: 'openai/gpt-4o-mini' }) } });
session.on((event) => {
  if (event.type === 'compaction.done') console.log(event.trigger, event.tokensBefore, '->', event.tokensAfter);
});
await session.send('hello');
const { tokensBefore, tokensAfter } = await session.compact({ protectedTokens: 2_000 });
console.log(`${tokensBefore} -> ${tokensAfter} tokens`);
await session.clear();
console.log(session.messages.length); // 0
```

## كتابة strategy

الاستراتيجية اسم ودالة `compact()`، ويمكن أن تكون async. تستلم الرسائل، وعدّاد tokens لـmodel الطلب، والـcontext window، و`protectedTokens`، و`thresholdTokens` (الحجم الذي يجب أن تنزل تحته)، و`signal` الإلغاء الخاصة بالـrun، وتعيد الرسائل الجديدة مع عدد الـtokens قبل وبعد (واختياريًا `summary` أو `error`). أعِد مصفوفة الإدخال دون تغيير عندما لا يكون هناك ما تفعله: عندئذٍ يترك الـhook الـrun على حاله ولا يستدعي `onCompaction`.

```ts
import { createCompactionHook, isPinned, type CompactionStrategy } from 'lousho';

// Keep the system prompt, pinned messages and the last 20 messages.
const keepRecent: CompactionStrategy = {
  name: 'keep-recent',
  compact({ messages, estimateTokens }) {
    const tokensBefore = estimateTokens(messages);
    if (messages.length <= 22) return { messages, tokensBefore, tokensAfter: tokensBefore, prunedToolCallIds: [] };
    // A real strategy must not split a tool call from its result.
    const older = messages.slice(0, -20).filter((m) => m.role === 'system' || isPinned(m));
    const kept = [...older, ...messages.slice(-20)];
    return { messages: kept, tokensBefore, tokensAfter: estimateTokens(kept), prunedToolCallIds: [] };
  },
};

const hook = createCompactionHook({ strategy: keepRecent });
```

الاستراتيجية المخصصة تستلم الحدثين نفسيهما `compaction.start` و`compaction.done` مثل الاستراتيجيات المدمجة. و`onCompaction` (على `createCompactionHook()`) تظل تستلم نص الملخص وكائن `Error`.
