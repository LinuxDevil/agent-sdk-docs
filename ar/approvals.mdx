علّم الـ tool بـ `needsApproval` فيتوقف الـ run قبل تنفيذ الاستدعاء،
حتى يوافق إنسان (أو الكود الخاص بك) على الـ call أو يرفضه. التوقف محفوظ
في `ApprovalStore`، أي أن القرار يمكن أن يصل بعد دقائق أو أيام، من request
آخر أو من process أخرى، ويكمل الـ run من حيث توقف.

انظر أيضًا: [الإيقاف وإعادة التشغيل والاستئناف](/ar/pause-and-resume)، شرح قصير من البداية إلى النهاية.

> الأمثلة في هذه الصفحة تترك بعض الأسماء لك: `provider` هو أي `LLMProvider` (بدون اتصال: `createMockProvider()`)؛ `agent` هو نتيجة `createAgent()`؛ `input` هو نص المستخدم، من نوع `string`؛ `emailTool` هو tool مبني بـ `defineTool()`؛ `storage` هو `StorageService`؛ `toolRegistry` هو `ToolRegistry`.

```ts
import { createAgent, defineTool } from 'lousho';
import { z } from 'zod';

const sendEmail = defineTool({
  name: 'send_email',
  description: 'Send an email',
  input: z.object({ to: z.string() }),
  needsApproval: true,
  execute: async ({ to }) => `sent to ${to}`,
});
const agent = createAgent({ provider, instructions: 'You send emails.', tools: [sendEmail] });

const paused = await agent.send('Email the report to sam@example.com');
if (paused.finishReason === 'awaiting-approval') {
  console.log(await agent.approvals.list()); // [{ id, toolName: 'send_email', args: { to: '...' }, ... }]
  const result = await agent.approvals.resolve({ id: paused.approvalId!, approved: true }); // or approved: false, note: 'why'
  console.log(result.text);
}
```

## أي الـ calls توقف

تكون `needsApproval` إما `true`، أو دالة تستقبل الـ args بعد الـ validation،
typed من `input` الـ zod الخاص بالـ tool:

```ts
import { defineTool } from 'lousho';
import { z } from 'zod';

const sendEmail = defineTool({
  name: 'send_email',
  description: 'Send an email',
  input: z.object({ to: z.string().email(), subject: z.string(), body: z.string() }),
  needsApproval: ({ to }) => !to.endsWith('@mycompany.com'), // only external recipients pause
  async execute({ to, subject, body }) {
    return { messageId: '...' };
  },
});
```

تستطيع الدالة أيضًا منع الـ call أو الموافقة عليه مرة واحدة فقط في الـ session؛
راجع [الموافقة أو المنع أو السؤال](#الموافقة-أو-المنع-أو-السؤال).

عندما يطلب الـ model عدة أدوات في turn واحد، تُنفَّذ الـ calls التي لا تحتاج approval
(موافقة)، ويتوقف الـ run مرة واحدة على **كل** call يحتاج approval:
يحصل كل واحد على approval id خاص به، وتُنفَّذ معًا بعد حسمها كلها
(راجع [عدة calls في خطوة واحدة](#عدة-calls-في-خطوة-واحدة)).

أدوات MCP تطلب approval افتراضيًا (`approval: 'always'`). ومع
`approval: 'annotations'`، تحسم الـ annotations الخاصة بالـ tool على السيرفر بدلًا من ذلك:
`readOnlyHint: true` يُنفَّذ، و`destructiveHint` بقيمة true أو غير الموجود
(افتراضي MCP) يسأل. اختر السلوك لكل سيرفر بـ `approval: 'always' | 'annotations' |
'never'` أو دالة؛ راجع [موافقة أدوات MCP](/ar/mcp-integration#الـ-approval-على-tools-mcp).

## سياسات الصلاحيات

يضع `permissions` قواعد للـ agent كله بدلًا من التحديد tool بـ tool: قائمة
قواعد `{ tool, when?, action, reason? }` تُفحص بالترتيب عند كل tool call،
قبل `needsApproval` الخاص بالـ tool نفسه. أول قاعدة تنطبق هي التي تحسم:

- `allow` ينفّذ الـ call بدون approval، حتى لو كان `needsApproval` سيسأل.
  لكن `needsApproval` الذي يمنع الـ call يبقى مانعًا له.
- `deny` لا ينفّذه. يستلم الـ model خطأ tool فيه `kind: 'denied'`
  و`reason` الخاص بالقاعدة (راجع [أخطاء الأدوات](/ar/tools))، وترى الـ streams
  `tool.error`.
- `ask` يوقف الـ run بانتظار approval، تمامًا مثل `needsApproval` (أو يسأل
  الـ `approve` callback).

وإذا لم تنطبق أي قاعدة، يحسم `needsApproval` الخاص بالـ tool، كما كان سابقًا.
يكون `tool` اسمًا، أو قائمة أسماء، أو `RegExp` يُختبر على الاسم، أو
`'*'` لكل الأدوات. ويحصر `when` القاعدة في بعض الـ calls: يستقبل
الـ args بعد الـ validation (بعد `preToolCall` hooks) و`{ toolName, toolCallId,
sessionId, principal }` (`principal`: من يعمل الـ run نيابة عنه، ثابت؛
ويغيب إذا لم يوجد — راجع [الهويات في الأدوات والموافقات](/ar/auth#principals-in-tools-and-approvals))،
ويمكن أن يكون async؛ وإذا رمى خطأ، يفشل الـ call بالـ error نفسه.
تبني `allow(tools)` و`deny(tools, reason?)` و`ask(tools)` القواعد الشائعة.

```ts
import { allow, ask, createAgent, defineTool, deny, type PermissionRule } from 'lousho';
import { z } from 'zod';

const shell = defineTool({
  name: 'shell',
  description: 'Run a shell command',
  input: z.object({ command: z.string() }),
  execute: async ({ command }) => `ran ${command}`,
});

const noDeletes: PermissionRule = {
  tool: 'shell',
  when: (args) => /\brm\b/.test(String(args.command)),
  action: 'deny',
  reason: 'Deleting files is not allowed',
};

const agent = createAgent({
  provider,
  instructions: 'You are a coding assistant.',
  tools: [shell],
  permissions: [
    noDeletes, // first match wins: this beats the `ask` below
    allow(/^read_/), // read-only tools never pause
    deny('delete_file', 'Use the trash tool instead'),
    ask(['shell', 'write_file']),
  ],
  onPermissionDecision: (entry) => console.log(entry.at, entry.toolName, entry.decision, entry.rule?.reason),
});
```

`onPermissionDecision` هو الـ audit log: يُستدعى مرة لكل tool call
(ما عدا الـ calls المرفوضة أصلًا لأن الـ args غير صالحة) مع
`{ toolName, toolCallId, decision, rule?, args?, at }`. الـ `decision` هو
الـ `action` الخاص بالقاعدة المنطبقة، أو `'default'` عندما لا تنطبق أي قاعدة،
و`rule` هو `{ index, reason? }` الخاص بها، و`at` طابع وقت ISO، ويُحذف `args`
عندما يضبط الـ run `redactContent`. وتستلم الـ streams الإدخال نفسه كحدث
`permission.decision` (راجع [البث](/ar/streaming)). ولا يُنتَج الاثنان إلا عندما
يضبط الـ agent `permissions` أو `onPermissionDecision`، أو permission mode
غير `'default'`.

وفوق هذه القواعد توجد presets جاهزة — `plan` (انظر ولا تلمس)، `acceptEdits`
أو `dontAsk` — ويمكن تبديلها في منتصف الـ session. راجع
[أوضاع الصلاحيات](/ar/permission-modes).

الخياران نفسهما موجودان على `AgentExecutor.execute()` / `stream()` و
`resumeAfterApproval()`. ترث الـ sub-agents قواعد الـ lead agent، وتُفحص
قبل قواعد الـ sub-agent نفسه، وتبلّغ قراراتها إلى `onPermissionDecision`
الخاص بالـ lead.

## الموافقة أو المنع أو السؤال

تستطيع دالة `needsApproval` إرجاع أكثر من boolean. تستقبل الـ args بعد
الـ validation و`{ toolName, toolCallId, sessionId, messages, principal }`
(`principal`: من يعمل الـ run نيابة عنه، راجع
[الهويات في الأدوات والموافقات](/ar/auth#principals-in-tools-and-approvals))،
وتُرجع (أو تُحلّ إلى):

- `'ask'` أو `true`: توقف بانتظار approval، كما كان سابقًا.
- `'approve'` أو `false`: نفّذ الـ call.
- `'deny'` أو `{ deny: reason }`: لا تنفّذه ولا تتوقف. يستلم الـ model
  خطأ tool فيه `kind: 'denied'` والـ `reason`، فيستطيع تجربة شيء آخر؛
  وترى الـ streams `tool.error`، ويسجّل `onPermissionDecision`
  `decision: 'deny'` مع الـ `reason` (وبدون `rule`).

توجد ثلاث helpers تغطي السياسات الشائعة: `always()` (مثل `true`)،
و`never()` (`false`)، و`once()`. تسأل `once()` أول مرة يُستدعى فيها الـ tool
في الـ session؛ وبعد أن يوافق إنسان على call، تُنفَّذ الـ calls اللاحقة للـ tool نفسه
في الـ session نفسها بدون سؤال. لا يُحفظ الرفض، ولا الموافقة التي تأتي من
callback `createAgent({ approve })` (هذا الـ callback يُسأل من جديد عند كل
call)، والـ session الجديدة تسأل من جديد. تحفظ `once({ per: 'args' })` الـ approvals لكل tool مع
الـ args الخاصة به بدلًا من ذلك، فالـ call بـ args مختلفة يسأل من جديد. وهذه الذاكرة
تعيش في الـ transcript (رسالة `tool` الخاصة بالـ call الموافَق عليه تحمل
`metadata.approval`)، فتُحفظ حيثما حُفظت الـ session أو الـ checkpoint أو
الـ approval snapshot، وتبقى فعّالة بعد resume في process أخرى. وبدون
session، يكون كل `send()` transcript مستقلًا بذاته. وإذا أزال الـ compaction
هذه الرسالة، يعود الـ tool إلى السؤال.

```ts
import { createAgent, defineTool, once } from 'lousho';
import { z } from 'zod';

const askOnce = once();
const deploy = defineTool({
  name: 'deploy',
  description: 'Deploy a service',
  input: z.object({ service: z.string(), env: z.enum(['staging', 'prod']) }),
  needsApproval: (args, ctx) => (args.env === 'prod' ? { deny: 'Production deploys go through CI' } : askOnce(args, ctx)),
  execute: async ({ service, env }) => `deployed ${service} to ${env}`,
});
const agent = createAgent({ provider, instructions: 'You deploy services.', tools: [deploy] });
const chat = agent.session(); // the first staging deploy asks, later ones in this session run
```

مع `permissions`، تغلب قاعدة `deny` دائمًا، ولا يُستدعى `needsApproval` الخاص بالـ tool.
وفي غير ذلك، يمنع `'deny'` (أو `{ deny }`) الصادر من الـ tool نفسه
دائمًا، مهما كانت القاعدة المنطبقة. تأخذ قاعدة `allow` مكان سؤال الـ tool
(فتتخطى `'ask'` و`true` و`once()`)، وتوقف قاعدة `ask` حتى لو كان الـ tool
سيوافق. وبدون قاعدة منطبقة، تسري نتيجة `needsApproval` الخاص بالـ tool.
يعمل `preToolCall` hook قبل هذا كله ويستطيع منع الـ call أولًا
(راجع [نتائج الـ hooks](/ar/hooks#hook-outcomes)). تحتفظ أدوات MCP بـ
`needsApproval` المشتق من الـ annotations الخاصة بها (boolean). وتقيّم الـ sub-agents
`needsApproval` لأدواتها بالطريقة نفسها، وموافقة `once()`
المعطاة عن طريق الـ lead agent تبقى محفوظة لبقية مهمة الـ sub-agent.

## وكلاء `createAgent()`

- يُنجَز الـ `send()` الموقوف (لا يرمي error) بـ
  `finishReason: 'awaiting-approval'` ومعه `approvalId` و`approvalIds`: كل
  call تنتظره الخطوة، بترتيب الاستدعاء (`approvalId` هو الأول؛ وفيها إدخال
  واحد عندما يتوقف call واحد).
- تُرجع `agent.approvals.list()` الـ calls المعلّقة، الأقدم أولًا: تلك التي توقف
  عليها هذا الـ agent في هذه الـ process، ومع `approvalStore` يطبّق
  `list()` (مخازن الملفات وSQLite والـ KV والذاكرة كلها تطبّقها)، تلك التي
  يحتفظ بها الـ store من process أخرى أو من قبل restart. والتوقف الذي
  حسمته process أخرى مسبقًا لا يُعرض. كل إدخال هو
  `{ id, toolCallId, toolName, args, createdAt }`،
  إضافةً إلى `subagentPath` عندما يتبع الـ call لـ sub-agent و`expiresAt` عندما
  يكون للتوقف deadline (راجع [انتهاء مهلة الموافقة](#انتهاء-مهلة-الموافقة)). والإدخال الذي
  تجاوز `expiresAt` يبقى مدرجًا حتى يُحسم — فالـ run لا يزال متوقفًا — لكن اتخاذ
  القرار فيه يرفض الـ call.
- تُرجع `agent.approvals.get(id)` call معلّقًا واحدًا بدون حسمه.
  ومع `approvalStore` يطبّق `load()`، يجيب الـ store أولًا، فيُعثر على التوقف
  الذي حُفظ قبل restart، ولا يُعثر على التوقف الذي حسمته process أخرى؛
  وتُرجع `undefined` إذا كان الـ id مجهولًا (بما في ذلك الـ ids المشوّهة) أو
  حُسم من قبل.
- تنفّذ `agent.approvals.resolve({ id, approved, note? })` الـ call (approved)
  أو تعطي الـ model رفضًا مع الـ `note` الخاصة بك (rejected)، وتكمل الـ run،
  وتُنجَز بنتيجة الـ run المكمِّل، الذي قد يتوقف مرة أخرى. وترمي error إذا كان
  الـ `id` مجهولًا أو حُسم من قبل. ويوجد خياران إضافيان ينطبقان على الموافقة (راجع
  [لا تسأل مرة ثانية، والموافقة مع تعديلات](#لا-تسأل-مرة-ثانية،-والموافقة-مع-تعديلات)):
  `remember: 'session'` و`args`.
- الـ run الذي توقف داخل `agent.session()` يكمل في الـ session نفسها: ينضم الـ
  tool call ونتيجته والرد النهائي إلى transcript الـ session.
- ينتهي `agent.stream()` و`session.stream()` عند التوقف بحدث
  `approval.requested` لكل call موقوف و`run.done`
  (`'awaiting-approval'`)؛ احسمها بالطريقة نفسها.

تُحفظ حالات التوقف في `InMemoryApprovalStore` لكل agent، إلا إذا مرّرت
`approvalStore` أو `store` يحتوي على `approvals`. ولكي تحسم توقفًا بعد restart،
أعطِ الـ agent durable store، مثل SQLite (راجع
[اختيار المخزن](/ar/sessions#choosing-a-store)):

```ts
import { createAgent } from 'lousho';
import { SqliteStore } from 'lousho/sqlite';

const store = new SqliteStore('./.lousho/agent.db');
const agent = createAgent({ provider, tools: [emailTool], store }); // or approvalStore: store.approvals
```

مع durable store، تقرأ `list()` و`get(id)` من الـ store، فبعد restart
(أو من process أخرى) تعرضان كل توقف لا يزال محفوظًا، وتتوقفان عن عرض
التوقف بمجرد أن تحسمه أي process. والتوقف المحفوظ الذي لم تشغّله أي session
في هذه الـ process لا يزال يُعرض بدون `sessionId` الخاص به. ومع `ApprovalStore`
مخصص لا يحتوي على `list()`، لا تعرف `list()` إلا حالات التوقف التي أنشأها كائن الـ agent
هذا.

### عدة calls في خطوة واحدة

عندما تحتوي خطوة واحدة من الـ model على عدة calls تحتاج approval، يتوقف الـ run
مرة واحدة عليها كلها. يسردها `result.approvalIds` بترتيب الاستدعاء، وكل
واحد منها إدخال مستقل في `agent.approvals.list()`، ويبلّغ الـ stream بحدث
`approval.requested` واحد لكل call. احسمها بأي ترتيب:

- حسم call بينما لم تُحسم calls أخرى من الخطوة نفسها بعد لا ينفّذ شيئًا:
  تُنجَز `resolve()` بـ `finishReason: 'awaiting-approval'` والـ ids التي
  لا تزال تنتظر قرارًا في `approvalIds` (و`approvalId`، أولها).
- القرار الذي يكمل الخطوة هو الذي يشغّلها: تُنفَّذ الـ calls الموافَق عليها
  بترتيب الاستدعاء، ويعطي كل call مرفوض الـ model الرفض الخاص به، ويكمل
  الـ run. ولا يُنفَّذ أي call قبل أن يراها الإنسان كلها.
- تحسم `agent.approvals.resolveAll([{ id, approved, args?, remember?, note? }, ...])`
  عدة calls دفعة واحدة (واحدًا تلو الآخر، بالترتيب المعطى) وتُنجَز
  بنتيجة آخر قرار.

الـ calls في الخطوة التي لا تحتاج approval لا تنتظر: تُنفَّذ عند تنفيذ
الخطوة، قبل التوقف.

```ts
import { createAgent } from 'lousho';

const agent = createAgent({ model: 'openai/gpt-4o-mini' /* , tools: [payInvoice, archiveThread] */ });
const paused = await agent.send('Pay the invoice and archive the thread');
// paused.approvalIds: ['…pay', '…archive']
const result = await agent.approvals.resolveAll([
  { id: paused.approvalIds![0], approved: true, args: { amount: 120 } },
  { id: paused.approvalIds![1], approved: false, note: 'keep it for now' },
]);
```

يُحفظ كل قرار مع بقية الـ calls المعلّقة في الخطوة، فتستطيع حسمها من
requests أو processes أو channels مختلفة، وبعد restart، مع durable store.
احسم calls الخطوة الواحدة من process واحدة في الوقت نفسه: قراران على الخطوة
نفسها يتسابقان في processين مختلفتين قد يفشلان بـ
`LOUSHO_APPROVAL_CONFLICT` (لا يُنفَّذ شيء؛ احسم من جديد). وتبلّغ الـ session
الموقوفة عن الـ ids التي لا تزال تنتظر قرارًا في `session.pending()`
(`approvalIds`). يُسأل الـ `approve` callback عن كل call في الخطوة؛ والـ
call الذي يؤجّله ينتظر إنسانًا بينما يحسم الـ callback الباقي.

الـ sub-agent الذي تتوقف خطوته على عدة calls يوقف الـ lead عليها كلها
(كل واحد مدرج مع `subagentPath`)، وتُحسم بالطريقة نفسها. والـ sub-agent
الذي بدأته خطوة تتوقف هي أيضًا على calls خاصة بها يُنفَّذ مع الخطوة؛ وإذا
توقف هو أيضًا، يتوقف الـ run عليه بعد حسم calls الخطوة.

### لا تسأل مرة ثانية، والموافقة مع تعديلات

- يوافق `remember: 'session'` على هذا الـ call وعلى كل call لاحق للـ
  tool نفسه **بالـ args نفسها** في الـ session نفسها، بدون توقف (لا يُسأل `needsApproval` الخاص
  بالـ tool مرة أخرى؛ لكن `ask` من قاعدة صلاحيات يبقى يوقف).
  والـ calls بـ args أخرى تسأل كما كان سابقًا. ومثل `once()`، الذاكرة هي الـ
  transcript، فتبقى بعد restart وتزول في session جديدة.
- يوافق `args` مع args معدّلة ("الموافقة مع تعديلات"). تُفحص مقابل الـ
  input schema الخاص بالـ tool؛ والـ args غير الصالحة ترمي
  `LOUSHO_TOOL_ARGS_INVALID` وتُبقي الـ approval معلّقة، فتستطيع الحسم من
  جديد. ويُعاد كتابة الـ tool call الخاص بالـ model في الـ transcript بالـ
  args المعدّلة، فيرى الـ model ما نُفِّذ فعلًا. ينطبق `args` على tool
  call، لا على سؤال أو تسجيل دخول أو handoff، ويُتجاهل مع
  `approved: false`.

```ts
import { createAgent } from 'lousho';

const agent = createAgent({ model: 'openai/gpt-4o-mini', tools: [emailTool] });
const support = agent.session({ id: 'support-42' });
const paused = await support.send('Email the report to sam@example.com');
// Send it to the team list instead, and stop asking for that exact email in this session.
await agent.approvals.resolve({ id: paused.approvalId!, approved: true, args: { to: 'team@example.com' }, remember: 'session' });
```

`remember` و`args` مخصّصان للقرارات التي يتخذها البشر. يحسم الـ `approve` callback
كل call يُسأل عنه، ولا تحتسب `once()` موافقته.

### إنهاء الـ run بعد الرفض

الرفض نتيجة tool، وليس توقّفًا: يستلم الـ model خطأ فيه `kind: 'rejected'`
(مع الـ `note` الخاصة بك) ويكمل الـ run، فالـ model الذي لا يزال يريد إنجاز المهمة
قد يستدعي الـ tool مرة أخرى، بـ args جديدة، ويتوقف على approval جديدة.
لا يوجد خيار على `resolve()` ينهي الـ run. لكي تمنع هذا:

- اذكره في `description` الخاص بالـ tool أو في `instructions` الخاصة بالـ agent: "إذا
  رفض المراجع الاستدعاء، لا تستدعه مرة أخرى؛ أخبر المستخدم أنه لم
  يُنفَّذ."
- افرضه بـ `preToolCall` hook يمنع الـ tool بمجرد أن يوجد له رفض في الـ
  transcript. المنع ليس توقف approval، فيستلم الـ model السبب
  ويرد:

```ts
import { createAgent, type AgentHook } from 'lousho';

const noRefile: AgentHook = {
  name: 'no-refile',
  preToolCall(ctx) {
    const rejected = ctx.messages.some((m) => m.role === 'tool' && m.toolName === ctx.toolName && String(m.content).includes('"kind":"rejected"'));
    return rejected ? { deny: 'A reviewer rejected this call. Do not call it again; tell the user it was not done.' } : undefined;
  },
};

const agent = createAgent({ provider, instructions: 'You file claims.', tools: [emailTool], hooks: [noRefile] });
```

تعتمد هذه القاعدة على تاريخ الـ run: في session طويلة، يمنع رفض حدث سابقًا في الـ
transcript أيضًا calls لاحقة للـ tool نفسه لا علاقة لها به، فضيّق الفحص
(مثلًا على الرسائل التي تلي آخر رسالة من المستخدم) إذا كان واسعًا أكثر من اللازم.

### انتهاء مهلة الموافقة

يضع `createAgent({ approvalTtlMs })` deadline على كل توقف يُنشئه الـ agent:
يحفظ سجل الـ approval المعلّق `expiresAt` (طابع وقت ISO-8601، مثل
`createdAt`)، ويحمله أيضًا حدث `approval.requested` في الـ stream، فتستطيع
الـ UI عرض الـ deadline. وبعده، لا يمكن الموافقة على التوقف — فاتخاذ القرار فيه،
أينما ومتى حدث، يرفض الـ call: يستلم الـ model خطأ tool فيه
`kind: 'denied'` (`Approval of 'send_email' expired before it was
decided`، بدون حقل `reason` منفصل) ويكمل الـ run، كما في الرفض.
ونص السبب `'approval expired'` (الـ export `APPROVAL_EXPIRED_REASON`)
موجود فقط في إدخال التدقيق (`onPermissionDecision`). والتوقف المنتهي الذي
حُسم بـ `approved: true` لا يشغّل الـ tool.

```ts
import { createAgent, defineTool } from 'lousho';
import { z } from 'zod';

const sendEmail = defineTool({
  name: 'send_email',
  description: 'Send an email',
  input: z.object({ to: z.string() }),
  needsApproval: true,
  execute: async ({ to }) => `sent to ${to}`,
});
const agent = createAgent({
  provider,
  tools: [sendEmail],
  approvalTtlMs: 5 * 60_000, // pauses die after five minutes unanswered
});
```

- يُفحص انتهاء المهلة عند حسم التوقف، فيبقى فعّالًا عبر `approvalStore` دائم
  (الـ run المستأنَف في process أخرى أو بعد restart يرى الرفض، لا approval
  قديمة) وعبر `agent.approvals.resolve()` و`streamResolve()` على حد سواء.
- إذا كان `approve` callback لا يزال منتظرًا عند الـ deadline، يُقطع: ويُستأنف
  الـ `send()` / الـ turn في الـ session مع الرفض.
- يتجاوزه `send(message, { approvalTtlMs })` لـ run واحد.
- يجب أن يكون الـ deadline عددًا موجبًا من الـ milliseconds، أقصاه 100 سنة؛
  وأي قيمة أخرى، بما فيها `1e20`، ترمي
  `LOUSHO_CONFIG_INVALID`. اتركه إذا كنت تريد حالات توقف لا تنتهي.
- يحدّد `ttlMs` في قاعدة صلاحيات حالات التوقف الخاصة بهذه القاعدة فقط ويغلب افتراضي
  الـ agent: `{ tool: 'deploy', action: 'ask', ttlMs: 30_000 }`، أو
  `ask('deploy', { ttlMs: 30_000 })`.
- الـ run الذي يحتفظ بـ audit log يسجّل انتهاء المهلة كقرار `deny` مع
  `reason: 'approval expired'` (راجع `onPermissionDecision` أعلاه).
- وبدونه، لا تنتهي حالات التوقف أبدًا — كما كان سابقًا.

### الاستئناف بـ agent تغيّر

تحمل الـ approval snapshot بصمة الـ agent الموقوف، واتخاذ القرار فيها بـ
agent يختلف الـ model أو الـ tools أو الـ instructions الخاصة به يُصدر تحذيرًا
(`'warn'`، الافتراضي)، أو يُرفض بـ `LOUSHO_AGENT_DRIFT` (`onAgentDrift: 'error'`،
وتبقى الـ approval معلّقة)، أو يكمل (`'ignore'`). والـ call الموافَق عليه الذي
لم يعد الـ tool الخاص به موجودًا يُرفض دائمًا بـ `LOUSHO_RESUME_TOOL_MISSING`.
راجع [الاستئناف بوكيل تغيّر](/ar/durable-execution#استئناف-run-بعد-تغيّر-الـ-agent).

عند استئناف call موافَق عليه، تعمل الـ pre-tool hooks مرة أخرى، والـ args
التي تُبقيها (سواء عبر `{ input }` أو بتغيير `ctx.args` في مكانه) يجب أن تساوي
ما وُوفق عليه، ما عدا ترتيب المفاتيح؛ وإلا يُرفض الـ call بخطأ tool
فيه `kind: 'validation'`. والـ hook الذي يحجب أجزاء من مدخلاته أو يوحّدها
يجب أن يعمل على الـ run الموقوف أيضًا، لكي يوافق الإنسان على المدخلات بعد
الحجب. وإعادة التشغيل هذه تضبط `ctx.resumedAfterApproval: true`، فيستطيع
الـ hook الذي يجب أن يعمل مرة واحدة فقط لكل call (loop guard، عداد تدقيق)
تخطيها.

### اتخاذ القرار في الكود

مرّر `approve` لكي تحسم كل call عند ظهوره بدلًا من التوقف: `true` تشغّل الـ
tool، و`false` ترسل إلى الـ model رفضًا، والنص يوافق مع النص كـ note (ردّ على
`ask_question`). أما القيمة الحرفية `'defer'` فلا تحسم: يبقى الـ call معلّقًا —
مدرجًا في `agent.approvals.list()` ويُحسم بـ `agent.approvals.resolve()` —
ويُصدر الـ run التوقف (تُنجَز `send()` بـ `finishReason: 'awaiting-approval'`)،
تمامًا كأن الـ callback لم يُسأل أصلًا. أي أن الـ approver يستطيع أن يحسم
تلقائيًا الـ calls التي يثق بها ويسلّم الباقي لإنسان. يسري هذا على `send()`
والـ sessions و`agent.approvals.resolve()`؛ أما `stream()` فلا يزال ينتهي عند
التوقف. والـ `principal` في وسيطها هو صاحب الـ call، و
تسجّل `agent.approvals.resolve(decision, { principal })` من حسم كـ
`ctx.approval.by` للـ tool (راجع [auth](/ar/auth#من-وافق)).

```ts
import { createAgent } from 'lousho';

const trusted = createAgent({
  provider,
  tools: [emailTool],
  approve: ({ toolName, args }) => toolName !== 'send_email' || String(args.to).endsWith('@example.com'),
});
```

### Streaming للـ run المكمَّل

تكمل `agent.approvals.streamResolve(decision, { signal })` و
`agent.approvals.streamAnswer({ id, answer }, { signal })` الـ run
مثل `resolve()` و`answer()`، لكنها تُرجع الـ `AgentRun` نفسه الذي تُرجعه
`agent.stream()` (راجع [البث](/ar/streaming#الـ-streaming-بعد-الـ-approval)):
`run.start`، ثم `tool.resume` و`tool.done` للـ call المحسوم
(`tool.error` عند الرفض؛ `tool.resume` وليس `tool.start` ثانيًا، لأن الـ run
الموقوف أبلغ مسبقًا عن بدء الـ call)، ثم أحداث الاستكمال حتى `run.done`.
و`run.result` هو ما تُنجَز به `resolve()`. والاستكمال الذي يتوقف مرة أخرى
ينتهي بـ `approval.requested` و`run.done` (`'awaiting-approval'`)، حتى مع
`approve` callback، مثل `stream()`. والتوقف الذي حدث داخل session يكمل في
الـ session نفسها، ويأتي `run.done` بعد حفظ الـ transcript.

```ts
import { createAgent } from 'lousho';

const agent = createAgent({ provider, tools: [emailTool] });
const paused = await agent.send('Email Sam the report');

if (paused.approvalId) {
  const run = agent.approvals.streamResolve({ id: paused.approvalId, approved: true });
  for await (const event of run) {
    if (event.type === 'text.delta') process.stdout.write(event.text);
  }
}
```

## سؤال المستخدم

يعطي `createAgent({ askQuestion: true })` الـ agent الـ tool المدمج
`ask_question` (مُعطّل افتراضيًا؛ تُرجع `askQuestionTool()` الـ tool نفسه لكي
تمرّره في `tools` بنفسك). الـ input الخاص به هو
`{ question: string; options?: string[]; allowFreeText?: boolean }`. ويوقف الـ call
الـ run عبر آلية الـ approvals، فينتظر تمامًا مثل الـ approval: في الـ
sessions، وفي الـ durable stores، وعبر الـ restart.

- يحتوي السجل المعلّق على `kind: 'question'` و
  `question: { text, options?, allowFreeText? }`، في `agent.approvals.list()`
  وفي الـ `approve` callback وعلى حدث `approval.requested`، فتستطيع الـ UI
  عرض سؤال بدلًا من زر موافقة.
- يكمل `agent.approvals.answer({ id, answer })` (مثل
  `resolve({ id, approved: true, note: answer })`) الـ run. يستلم الـ model
  `{ answer, option? }`، و`option` هو index العنصر المطابق في
  `options` (بدون حساسية لحالة الأحرف). ومع `allowFreeText: false`، يصل الرد
  الذي يقع خارج الخيارات إلى الـ model كخطأ tool.
- تمتنع `resolve({ id, approved: false, note? })`: يستلم الـ model
  خطأ tool فيه `kind: 'rejected'` يذكر أن المستخدم امتنع عن الإجابة.
- يستطيع `approve` callback إرجاع نص لكي يجيب من الكود، وهذا مفيد في
  الاختبارات والـ agents التي تعمل بسكربت.

```ts
import { createAgent } from 'lousho';

const agent = createAgent({ instructions: 'Plan the trip with the user.', provider, askQuestion: true });

const paused = await agent.send('Book me a weekend away');
const [pending] = await agent.approvals.list();
if (paused.approvalId && pending?.kind === 'question') {
  console.log(pending.question?.text, pending.question?.options);
  const result = await agent.approvals.answer({ id: paused.approvalId, answer: 'Lisbon' });
  console.log(result.text);
}

// Scripted: answer every question in code.
const scripted = createAgent({
  provider,
  askQuestion: true,
  approve: (request) => (request.kind === 'question' ? 'Lisbon' : false),
});
```

قاعدة `permissions` التي تعطي `allow` لـ `ask_question` تتخطى التوقف،
فيفشل الـ call بـ "No answer"؛ أبقِ الـ tool على الافتراضي.

الـ tool الذي يحتاج أن يسجّل المستخدم دخوله إلى OAuth provider يتوقف بالطريقة
نفسها، مع `kind: 'sign-in'` والرابط في `signIn`؛ راجع
[الأدوات التي تحتاج إلى تسجيل دخول](/ar/oauth#أدوات-تحتاج-تسجيل-دخول).

## متقدم: الـ executor API

تستخدم وكلاء `createAgent()` الـ `agent.approvals` (راجع
[وكلاء `createAgent()`](#وكلاء-createagent)). وعندما تستخدم
`AgentExecutor.execute()` مباشرة (راجع [الـ executor API](/ar/executor-api))،
مرّر `approvalStore`. عند call يحتاج approval، يحفظ الـ executor
`ExecutionSnapshot` بدلًا من استدعاء الـ tool. استأنف لاحقًا، حتى بعد restart
حقيقي إذا أردت، بـ `resumeAfterApproval()`:

```ts
import { AgentExecutor, resumeAfterApproval } from 'lousho/executor';
import { StorageServiceApprovalStore } from 'lousho/utils';

const approvalStore = new StorageServiceApprovalStore(storage);

const paused = await AgentExecutor.execute({
  agent, input, provider, toolRegistry, approvalStore,
});
// paused.finishReason === 'awaiting-approval', paused.approvalId is set

// ...later, from any process, after a human approves...
const result = await resumeAfterApproval(
  { id: paused.approvalId!, approved: true },
  approvalStore,
  toolRegistry,
  provider,
);
```

تأخذ `resumeAfterApproval(decision, store, registry, provider, options?, checkpointStore?)`
أغلب خيارات التنفيذ الخاصة بـ `execute()` (مثل `signal` و`onAgentEvent`
و`exporter`). ومع `sessionId` + `checkpointStore`، يُسجَّل التوقف أيضًا كـ
checkpoint، ويرمي `execute()` بالـ `sessionId` نفسه
`SessionAwaitingApprovalError` حتى يُحسم الـ approval، فلا تستطيع تخطي
approval معلّق (راجع [Durable execution](/ar/durable-execution)).
وتأخذ `streamResumeAfterApproval()` الوسائط نفسها وتعمل stream للـ run
المكمَّل كـ `AgentRun` (راجع [البث بعد الموافقة](/ar/streaming#الـ-streaming-بعد-الـ-approval)).

| الـ store | أين يعيش التوقف |
| ----- | --------------------- |
| `InMemoryApprovalStore` | هذه الـ process فقط؛ الافتراضي لـ `createAgent()`. |
| `StorageServiceApprovalStore(storage)` | ملفات JSON عبر `StorageService`. |
| `fileStore(dir)` | ملف JSON لكل توقف، `<dir>/approvals/<id>.json`، على جهاز واحد؛ ولا يُحسم الـ approval إلا من process واحدة (راجع [اختيار المخزن](/ar/sessions#choosing-a-store)). |
| `SqliteStore.approvals` | ملف SQLite واحد، تتشاركه عدة processes على host واحد ([التفاصيل](/ar/sessions#مشاركة-ملف-sqlite))؛ ولا يُحسم الـ approval إلا من واحدة منها. |

يحتاج الـ `ApprovalStore` إلى `save()` و`resolve()`. أما `load(id)` (يقرأ توقفًا
بدون حجزه) و`list()` (كل توقف لم يُحسم بعد، الأقدم أولًا) فاختياريتان؛
وتستخدمهما `agent.approvals.get()` و`list()` لكي ترى حالات التوقف التي حفظتها
أو حسمتها processes أخرى. تطبّق المخازن المدمجة الاثنتين (لا يسرد `KVStore`
إلا عندما يحتوي الـ namespace binding الخاص به على `list`، مثل أي binding حقيقي).
ولا يطبّق `StorageServiceApprovalStore` إلا `load()`.

## في مواضع أخرى

- **Sub-agents.** الـ tool الذي يحتاج approval داخل sub-agent يوقف run الـ
  lead؛ ويحسمه `agent.approvals` الخاص بالـ lead. راجع
  [الموافقات داخل وكيل فرعي](/ar/sub-agents#approvals-inside-a-sub-agent).
- **أدوات مساحة العمل.** الـ shell tool عليه approval افتراضيًا. راجع
  [أدوات مساحة العمل](/ar/workspace-tools).
- **MCP.** لا يمكن الموافقة عبر MCP على الأدوات التي عليها approval؛ راجع
  [تقديم وكيل عبر MCP](/ar/mcp-integration#تشغيل-agent-كسيرفر-mcp).
- **Agent Forge** يعرض الـ approvals المعلّقة كبطاقات داخل الشات الخاص به؛
  راجع [Agent Forge](/ar/agent-forge).
