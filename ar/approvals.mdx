علّم الـ tool بـ `needsApproval` والـ run يوقف قبل ما ينفّذ الاستدعاء،
حتى يوافق إنسان (أو الكود تبعك) على الـ call أو يرفضه. الوقفة محفوظة
في `ApprovalStore`، يعني القرار يقدر يوصل بعد دقائق أو أيام، من request
ثاني أو من process ثانية، والـ run يكمل من حيث وقف.

```ts
import { createAgent, defineTool } from '@lousho/build-ai-agent';
import { z } from 'zod';

const sendEmail = defineTool({
  name: 'send_email',
  description: 'Send an email',
  input: z.object({ to: z.string() }),
  needsApproval: true,
  execute: async ({ to }) => `sent to ${to}`,
});
const agent = createAgent({ provider, instructions: 'You send emails.', tools: [sendEmail] });

const paused = await agent.send('Email the report to sam@example.com');
if (paused.finishReason === 'awaiting-approval') {
  console.log(await agent.approvals.list()); // [{ id, toolName: 'send_email', args: { to: '...' }, ... }]
  const result = await agent.approvals.resolve({ id: paused.approvalId!, approved: true }); // or approved: false, note: 'why'
  console.log(result.text);
}
```

## أي الـ calls توقف

`needsApproval` تكون `true`، أو دالة تستقبل الـ args بعد الـ validation،
typed من `input` الـ zod تبع الـ tool:

```ts
import { defineTool } from '@lousho/build-ai-agent';
import { z } from 'zod';

const sendEmail = defineTool({
  name: 'send_email',
  description: 'Send an email',
  input: z.object({ to: z.string().email(), subject: z.string(), body: z.string() }),
  needsApproval: ({ to }) => !to.endsWith('@mycompany.com'), // only external recipients pause
  async execute({ to, subject, body }) {
    return { messageId: '...' };
  },
});
```

الدالة تقدر كمان تمنع الـ call أو توافق عليه مرة وحدة بس في الـ session؛
شوف [الموافقة أو المنع أو السؤال](#الموافقة-أو-المنع-أو-السؤال).

لما الـ model يطلب عدة أدوات في turn واحد، أول call يحتاج approval (موافقة)
يوقف الدفعة: الـ calls اللي قبله تنفّذ، والـ run يوقف عليه، واللي بعده
ينفّذ بعد ما ينحسم (شوف
[الموافقات في منتصف دفعة أدوات](/ar/durable-execution#approval-في-منتصف-batch-من-tool-calls)).

أدوات MCP تاخذ `needsApproval` من الـ annotations تبع الـ tool على السيرفر:
`readOnlyHint: true` ينفّذ، و`destructiveHint` بقيمة true أو غير موجود
(افتراضي MCP) يسأل. اختر السلوك لكل سيرفر بـ `approval: 'annotations' | 'always' | 'never'`
أو دالة؛ شوف [موافقة أدوات MCP](/ar/mcp-integration#الـ-approval-على-tools-mcp).

## سياسات الصلاحيات

`permissions` يحط قواعد للـ agent كله بدل ما تحدد tool بـ tool: قائمة
قواعد `{ tool, when?, action, reason? }` تنفحص بالترتيب عند كل tool call،
قبل `needsApproval` تبع الـ tool نفسه. أول قاعدة تنطبق هي اللي تحسم:

- `allow` ينفّذ الـ call بدون approval، حتى لو `needsApproval` كان سيسأل.
  بس `needsApproval` اللي يمنع الـ call يظل يمنعه.
- `deny` ما ينفّذه. الـ model يستلم tool error فيه `kind: 'denied'`
  و`reason` تبع القاعدة (شوف [أخطاء الأدوات](/ar/tools))، والـ streams
  تشوف `tool.error`.
- `ask` يوقف الـ run بانتظار approval، تمامًا مثل `needsApproval` (أو يسأل
  الـ `approve` callback).

وإذا ما انطبقت أي قاعدة، `needsApproval` تبع الـ tool يحسم، مثل قبل.
`tool` يكون اسم، أو قائمة أسماء، أو `RegExp` يُختبر على الاسم، أو
`'*'` لكل الأدوات. و`when` يحصر القاعدة في بعض الـ calls: يستقبل
الـ args بعد الـ validation (بعد `preToolCall` hooks) و`{ toolName, toolCallId,
sessionId, principal }` (`principal`: اللي الـ run يشتغل بالنيابة عنه، ثابت؛
ويغيب إذا ما فيه واحد — شوف [الهويات في الأدوات والموافقات](/ar/auth#principals-in-tools-and-approvals))،
ويقدر يكون async؛ وإذا رمى، الـ call يفشل بنفس الـ error.
`allow(tools)` و`deny(tools, reason?)` و`ask(tools)` تبني القواعد الشائعة.

```ts
import { allow, ask, createAgent, defineTool, deny, type PermissionRule } from '@lousho/build-ai-agent';
import { z } from 'zod';

const shell = defineTool({
  name: 'shell',
  description: 'Run a shell command',
  input: z.object({ command: z.string() }),
  execute: async ({ command }) => `ran ${command}`,
});

const noDeletes: PermissionRule = {
  tool: 'shell',
  when: (args) => /\brm\b/.test(String(args.command)),
  action: 'deny',
  reason: 'Deleting files is not allowed',
};

const agent = createAgent({
  provider,
  instructions: 'You are a coding assistant.',
  tools: [shell],
  permissions: [
    noDeletes, // first match wins: this beats the `ask` below
    allow(/^read_/), // read-only tools never pause
    deny('delete_file', 'Use the trash tool instead'),
    ask(['shell', 'write_file']),
  ],
  onPermissionDecision: (entry) => console.log(entry.at, entry.toolName, entry.decision, entry.rule?.reason),
});
```

`onPermissionDecision` هو الـ audit log: يُستدعى مرة لكل tool call
(ما عدا الـ calls المرفوضة أصلًا لأن الـ args غير صالحة) مع
`{ toolName, toolCallId, decision, rule?, args?, at }`. الـ `decision` هو
الـ `action` تبع القاعدة المنطبقة، أو `'default'` لما ما تنطبق أي قاعدة،
و`rule` هو `{ index, reason? }` تبعها، و`at` طابع وقت ISO، و`args` يُترك
لما الـ run يضبط `redactContent`. الـ streams تستلم نفس الإدخال كحدث
`permission.decision` (شوف [البث](/ar/streaming)). والاثنين يُنتَجون بس لما
الـ agent يضبط `permissions` أو `onPermissionDecision`، أو permission mode
غير `'default'`.

فوق القواعد هذي في presets جاهزة — `plan` (انظر ولا تلمس)، `acceptEdits`
أو `dontAsk` — وتتبدل في نص الـ session. شوف
[أوضاع الصلاحيات](/ar/permission-modes).

نفس الخيارين موجودين على `AgentExecutor.execute()` / `stream()` و
`resumeAfterApproval()`. الـ sub-agents يرثون قواعد الـ lead agent، وتنفحص
قبل قواعد الـ sub-agent نفسه، ويبلّغون قراراتهم لـ `onPermissionDecision`
تبع الـ lead.

## الموافقة أو المنع أو السؤال

دالة `needsApproval` تقدر ترجع أكثر من boolean. تستقبل الـ args بعد
الـ validation و`{ toolName, toolCallId, sessionId, messages, principal }`
(`principal`: اللي الـ run يشتغل بالنيابة عنه، شوف
[الهويات في الأدوات والموافقات](/ar/auth#principals-in-tools-and-approvals))،
وترجع (أو resolve إلى):

- `'ask'` أو `true`: وقفة بانتظار approval، مثل قبل.
- `'approve'` أو `false`: نفّذ الـ call.
- `'deny'` أو `{ deny: reason }`: لا تنفّذه ولا توقف. الـ model يستلم
  tool error فيه `kind: 'denied'` والـ `reason`، فيقدر يجرب شيء ثاني؛
  والـ streams تشوف `tool.error`، و`onPermissionDecision` يسجّل
  `decision: 'deny'` مع الـ `reason` (وبدون `rule`).

في ثلاث helpers يغطون السياسات الشائعة: `always()` (نفس `true`)،
و`never()` (`false`)، و`once()`. `once()` تسأل أول مرة يُستدعى فيها الـ tool
في الـ session؛ بعد ما إنسان يوافق على call، الـ calls اللي بعدها لنفس الـ tool
في نفس الـ session تنفّذ بدون سؤال. الرفض ما ينحفظ، والـ session الجديدة
تسأل من جديد. `once({ per: 'args' })` تحفظ الـ approvals لكل tool مع
الـ args تبعه بدل ذلك، فالـ call بـ args مختلفة يسأل من جديد. الذاكرة هذي
تعيش في الـ transcript (رسالة `tool` تبع الـ call الموافَق عليه تحمل
`metadata.approval`)، فتنحفظ أينما انحفظت الـ session أو الـ checkpoint أو
الـ approval snapshot، وتظل شغالة بعد resume في process ثانية. بدون
session، كل `send()` هو transcript قائم بحاله. وإذا الـ compaction شال
الرسالة هذي، الـ tool يرجع يسأل.

```ts
import { createAgent, defineTool, once } from '@lousho/build-ai-agent';
import { z } from 'zod';

const askOnce = once();
const deploy = defineTool({
  name: 'deploy',
  description: 'Deploy a service',
  input: z.object({ service: z.string(), env: z.enum(['staging', 'prod']) }),
  needsApproval: (args, ctx) => (args.env === 'prod' ? { deny: 'Production deploys go through CI' } : askOnce(args, ctx)),
  execute: async ({ service, env }) => `deployed ${service} to ${env}`,
});
const agent = createAgent({ provider, instructions: 'You deploy services.', tools: [deploy] });
const chat = agent.session(); // the first staging deploy asks, later ones in this session run
```

مع `permissions`، قاعدة `deny` تغلب دائمًا، و`needsApproval` تبع الـ tool
ما يُستدعى. غير ذلك، الـ `'deny'` (أو `{ deny }`) من الـ tool نفسه يمنع
دائمًا، مهما كانت القاعدة المنطبقة. قاعدة `allow` تاخذ مكان سؤال الـ tool
(فتتخطى `'ask'` و`true` و`once()`)، وقاعدة `ask` توقف حتى لو الـ tool
كان سيوافق. بدون قاعدة منطبقة، نتيجة `needsApproval` تبع الـ tool هي اللي
تسري. `preToolCall` hook يشتغل قبل هذا كله ويقدر يمنع الـ call أولًا
(شوف [نتائج الـ hooks](/ar/hooks#hook-outcomes)). أدوات MCP تحتفظ بـ
`needsApproval` المشتق من الـ annotations تبعتها (boolean). والـ sub-agents
يقيّمون `needsApproval` لأدواتهم بنفس الطريقة، والـ `once()` approval
المعطاة عن طريق الـ lead agent تنحفظ لباقي مهمة الـ sub-agent.

## وكلاء `createAgent()`

- الـ `send()` الموقوف يُنجَز (ما يرمي error) بـ
  `finishReason: 'awaiting-approval'` ومعه `approvalId`.
- `agent.approvals.list()` ترجع الـ calls المعلّقة اللي وقف عليها هذا الـ agent
  في الـ process هذي، الأقدم أول: `{ id, toolCallId, toolName, args, createdAt }`،
  زائد `subagentPath` لما الـ call تابع لـ sub-agent و`expiresAt` لما
  للوقفة deadline (شوف [Approval expiry](#approval-expiry)). الإدخال اللي عدّى
  `expiresAt` يظل مدرج حتى ينحسم — الـ run لا يزال واقف — بس اتخاذ القرار
  فيه يرفض الـ call.
- `agent.approvals.get(id)` ترجع call معلّق واحد بدون ما تحسمه:
  إدخالات `list()` أول، بعدين — مع `approvalStore` يطبّق `load()` — وقفة
  انحفظت قبل restart، و`undefined` إذا الـ id مجهول أو انحسم قبل.
- `agent.approvals.resolve({ id, approved, note? })` تنفّذ الـ call (approved)
  أو تعطي الـ model رفض مع الـ `note` تبعك (rejected)، وتكمل الـ run،
  وتُنجَز بنتيجة الـ run المكمِّل، اللي ممكن يوقف مرة ثانية. وترمي error إذا
  الـ `id` مجهول أو انحسم قبل.
- الـ run اللي وقف داخل `agent.session()` يكمل في نفس الـ session: الـ
  tool call ونتيجته والرد النهائي ينضمون لـ transcript الـ session.
- `agent.stream()` و`session.stream()` ينتهون عند الوقفة بحدث
  `approval.requested` و`run.done` (`'awaiting-approval'`)؛ احسمها بنفس
  الطريقة.

الوقفات تنحفظ في `InMemoryApprovalStore` لكل agent، إلا إذا مرّرت
`approvalStore` أو `store` فيه `approvals`. عشان تحسم وقفة بعد restart،
أعط الـ agent durable store، مثل SQLite (شوف
[اختيار المخزن](/ar/sessions#choosing-a-store)):

```ts
import { createAgent } from '@lousho/build-ai-agent';
import { SqliteStore } from '@lousho/build-ai-agent/sqlite';

const store = new SqliteStore('./.lousho/agent.db');
const agent = createAgent({ provider, tools: [emailTool], store }); // or approvalStore: store.approvals
```

`list()` تعرف بس الوقفات اللي عملها كائن الـ agent هذا؛ `get(id)` تلاقي
كمان وقفة لا يزال الـ durable store محتفظ فيها (مثل وحدة انحفظت قبل
restart). خلّي الـ `approvalId` (أو اقرأ الـ store) عشان تحسم وقفة من مكان
ثاني. والـ run المكمَّل ينضم لـ session بس إذا انحسم عن طريق الـ agent
اللي يملك كائن الـ session.

### Approval expiry

`createAgent({ approvalTtlMs })` يحط deadline على كل وقفة يعملها الـ agent:
سجل الـ approval المعلّق يحفظ `expiresAt` (طابع وقت ISO-8601، مثل
`createdAt`)، وحدث `approval.requested` في الـ stream يحمله كمان، فيقدر
الـ UI يعرض الـ deadline. بعده، الوقفة ما تقدر تتوافَق — اتخاذ القرار فيها،
متى وأين ما صار، يرفض الـ call: الـ model يستلم tool error بـ
`kind: 'denied'` والسبب `'approval expired'` (الـ export
`APPROVAL_EXPIRED_REASON`) والـ run يكمل، مثل الرفض. وقفة منتهية انحسمت
بـ `approved: true` ما تشغّل الـ tool.

```ts
import { createAgent, defineTool } from '@lousho/build-ai-agent';
import { z } from 'zod';

const sendEmail = defineTool({
  name: 'send_email',
  description: 'Send an email',
  input: z.object({ to: z.string() }),
  needsApproval: true,
  execute: async ({ to }) => `sent to ${to}`,
});
const agent = createAgent({
  provider,
  tools: [sendEmail],
  approvalTtlMs: 5 * 60_000, // pauses die after five minutes unanswered
});
```

- الـ expiry ينفحص لما تنحسم الوقفة، فيظل شغال عبر `approvalStore` دائم
  (run مستأنَف في process ثانية أو بعد restart يشوف الرفض، مو approval
  قديمة) وعبر `agent.approvals.resolve()` و`streamResolve()` على حد سواء.
- إذا `approve` callback لا يزال منتظر عند الـ deadline، ينقطع: الـ
  `send()` / turn في الـ session يستأنف مع الرفض.
- `send(message, { approvalTtlMs })` يتجاوزه لـ run واحد.
- `ttlMs` في قاعدة صلاحيات يحدّد بس وقفات القاعدة هذي ويغلب على افتراضي
  الـ agent: `{ tool: 'deploy', action: 'ask', ttlMs: 30_000 }`، أو
  `ask('deploy', { ttlMs: 30_000 })`.
- الـ run اللي يحتفظ audit log يسجّل الـ expiry كقرار `deny` مع
  `reason: 'approval expired'` (شوف `onPermissionDecision` فوق).
- بدونه، الوقفات ما تنتهي أبدًا — نفس قبل.

### الاستئناف بـ agent تغيّر

الـ approval snapshot تحمل بصمة الـ agent الموقوف، واتخاذ القرار فيها بـ
agent يختلف الـ model أو الـ tools أو الـ instructions تبعه يطلع تحذير
(`'warn'`، الافتراضي)، أو يُرفض بـ `LOUSHO_AGENT_DRIFT` (`onAgentDrift: 'error'`،
والـ approval تظل معلّقة)، أو يكمل (`'ignore'`). الـ call الموافَق عليه اللي
ما عاد الـ tool تبعه موجود يُرفض دائمًا بـ `LOUSHO_RESUME_TOOL_MISSING`.
شوف [الاستئناف بوكيل تغيّر](/ar/durable-execution#استئناف-run-بعد-ما-يتغير-الـ-agent).

عند استئناف call موافَق عليه، الـ pre-tool hooks تشتغل مرة ثانية، والـ args
اللي تخليها (سواء عبر `{ input }` أو بتغيير `ctx.args` في مكانه) يجب تساوي
اللي انوافق عليه، ما عدا ترتيب المفاتيح؛ وإلا يُرفض الـ call بـ tool error
فيه `kind: 'validation'`. الـ hook اللي يحجب أجزاء من مدخلاته أو يوحّدها
يجب يشتغل على الـ run الموقوف كمان، عشان الإنسان يوافق على المدخلات بعد
الحجب. إعادة التشغيل هذي تضبط `ctx.resumedAfterApproval: true`، فيقدر
الـ hook اللي يجب يشتغل مرة وحدة بس لكل call (loop guard، عداد تدقيق)
يتخطاه.

### اتخاذ القرار في الكود

مرّر `approve` عشان تحسم كل call لما يطلع بدل الوقفة: `true` تشغّل الـ
tool، `false` ترسل للـ model رفض، ونص يوافق مع النص كـ note (رد على
`ask_question`). القيمة الحرفية `'defer'` ما تحسم: الـ call يظل معلّق —
مدرج في `agent.approvals.list()` وينحسم بـ `agent.approvals.resolve()` —
والـ run يطلع الوقفة (`send()` تُنجَز بـ `finishReason: 'awaiting-approval'`)،
تمامًا كأن الـ callback ما انسأل أصلًا. يعني الـ approver يقدر يحسم
تلقائيًا الـ calls اللي يثق فيها ويسلّم الباقي لإنسان. يسري على `send()`
والـ sessions و`agent.approvals.resolve()`؛ `stream()` لا يزال ينتهي عند
الوقفة. والـ `principal` في وسيطها هو صاحب الـ call، و
`agent.approvals.resolve(decision, { principal })` تسجّل من حسم كـ
`ctx.approval.by` للـ tool (شوف [auth](/ar/auth#من-وافق)).

```ts
import { createAgent } from '@lousho/build-ai-agent';

const trusted = createAgent({
  provider,
  tools: [emailTool],
  approve: ({ toolName, args }) => toolName !== 'send_email' || String(args.to).endsWith('@example.com'),
});
```

### Streaming للـ run المكمَّل

`agent.approvals.streamResolve(decision, { signal })` و
`agent.approvals.streamAnswer({ id, answer }, { signal })` يكملون الـ run
مثل `resolve()` و`answer()`، بس يرجعون نفس الـ `AgentRun` اللي ترجعه
`agent.stream()` (شوف [البث](/ar/streaming#الـ-streaming-بعد-الـ-approval)):
`run.start`، بعدين `tool.resume` و`tool.done` للـ call المحسوم
(`tool.error` عند الرفض؛ `tool.resume` وليس `tool.start` ثاني، لأن الـ run
الموقوف أصلًا بلّغ عن بدء الـ call)، بعدين أحداث الاستكمال حتى `run.done`.
و`run.result` هو اللي تُنجَز به `resolve()`. الاستكمال اللي يوقف مرة ثانية
ينتهي بـ `approval.requested` و`run.done` (`'awaiting-approval'`)، حتى مع
`approve` callback، مثل `stream()`. والوقفة اللي صارت داخل session تكمل في
نفس الـ session، و`run.done` يجي بعد ما الـ transcript ينحفظ.

```ts
import { createAgent } from '@lousho/build-ai-agent';

const agent = createAgent({ provider, tools: [emailTool] });
const paused = await agent.send('Email Sam the report');

if (paused.approvalId) {
  const run = agent.approvals.streamResolve({ id: paused.approvalId, approved: true });
  for await (const event of run) {
    if (event.type === 'text.delta') process.stdout.write(event.text);
  }
}
```

## سؤال المستخدم

`createAgent({ askQuestion: true })` يعطي الـ agent الـ tool المدمج
`ask_question` (مُعطّل افتراضيًا؛ `askQuestionTool()` ترجع نفس الـ tool عشان
تمرّره في `tools` بنفسك). الـ input تبعه
`{ question: string; options?: string[]; allowFreeText?: boolean }`. والـ call
يوقف الـ run عبر آلية الـ approvals، فينتظر تمامًا مثل الـ approval: في الـ
sessions، وفي الـ durable stores، وعبر الـ restart.

- السجل المعلّق فيه `kind: 'question'` و
  `question: { text, options?, allowFreeText? }`، في `agent.approvals.list()`
  وفي الـ `approve` callback وعلى حدث `approval.requested`، فيقدر الـ UI
  يعرض سؤال بدل زر موافقة.
- `agent.approvals.answer({ id, answer })` (نفس
  `resolve({ id, approved: true, note: answer })`) يكمل الـ run. الـ model
  يستلم `{ answer, option? }`، و`option` هو index العنصر المطابق في
  `options` (بدون حساسية لحالة الأحرف). مع `allowFreeText: false`، الرد
  اللي خارج الخيارات يوصل للـ model كـ tool error.
- `resolve({ id, approved: false, note? })` تمتنع: الـ model يستلم
  tool error فيه `kind: 'rejected'` يقول إن المستخدم امتنع عن الإجابة.
- `approve` callback يقدر يرجع نص عشان يجاوب من الكود، وهذا مفيد في
  الاختبارات والـ agents اللي تشتغل بسكربت.

```ts
import { createAgent } from '@lousho/build-ai-agent';

const agent = createAgent({ prompt: 'Plan the trip with the user.', provider, askQuestion: true });

const paused = await agent.send('Book me a weekend away');
const [pending] = await agent.approvals.list();
if (paused.approvalId && pending?.kind === 'question') {
  console.log(pending.question?.text, pending.question?.options);
  const result = await agent.approvals.answer({ id: paused.approvalId, answer: 'Lisbon' });
  console.log(result.text);
}

// Scripted: answer every question in code.
const scripted = createAgent({
  provider,
  askQuestion: true,
  approve: (request) => (request.kind === 'question' ? 'Lisbon' : false),
});
```

قاعدة `permissions` اللي تعمل `allow` لـ `ask_question` تتخطى الوقفة،
فيفشل الـ call بـ "No answer"؛ خلّي الـ tool على الافتراضي.

الـ tool اللي يحتاج المستخدم يسجّل دخوله لـ OAuth provider يوقف بنفس
الطريقة، مع `kind: 'sign-in'` والرابط في `signIn`؛ شوف
[الأدوات التي تحتاج إلى تسجيل دخول](/ar/oauth#أدوات-تحتاج-تسجيل-دخول).

## متقدم: الـ executor API

وكلاء `createAgent()` يستخدمون `agent.approvals` (شوف
[وكلاء `createAgent()`](#وكلاء-createagent)). لما تستخدم
`AgentExecutor.execute()` مباشرة (شوف [الـ executor API](/ar/executor-api))،
مرّر `approvalStore`. عند call يحتاج approval، الـ executor يحفظ
`ExecutionSnapshot` بدل ما ينادي الـ tool. استأنف بعدين، حتى بعد restart
حقيقي إذا أردت، بـ `resumeAfterApproval()`:

```ts
import { AgentExecutor, resumeAfterApproval } from '@lousho/build-ai-agent/executor';
import { StorageServiceApprovalStore } from '@lousho/build-ai-agent/utils';

const approvalStore = new StorageServiceApprovalStore(storage);

const paused = await AgentExecutor.execute({
  agent, input, provider, toolRegistry, approvalStore,
});
// paused.finishReason === 'awaiting-approval', paused.approvalId is set

// ...later, from any process, after a human approves...
const result = await resumeAfterApproval(
  { id: paused.approvalId!, approved: true },
  approvalStore,
  toolRegistry,
  provider,
);
```

`resumeAfterApproval(decision, store, registry, provider, options?, checkpointStore?)`
ياخد أغلب خيارات التنفيذ تبع `execute()` (مثل `signal` و`onAgentEvent`
و`exporter`). مع `sessionId` + `checkpointStore`، الوقفة كمان تتسجّل كـ
checkpoint، و`execute()` بنفس الـ `sessionId` يرمي
`SessionAwaitingApprovalError` حتى ينحسم الـ approval، فما تقدر تتخطى
approval معلّق (شوف [Durable execution](/ar/durable-execution)).
و`streamResumeAfterApproval()` ياخد نفس الوسائط ويعمل stream للـ run
المكمَّل كـ `AgentRun` (شوف [البث بعد الموافقة](/ar/streaming#الـ-streaming-بعد-الـ-approval)).

| الـ store | أين تعيش الوقفة |
| ----- | --------------------- |
| `InMemoryApprovalStore` | الـ process هذي بس؛ الافتراضي لـ `createAgent()`. |
| `StorageServiceApprovalStore(storage)` | ملفات JSON عبر `StorageService`. |
| `fileStore(dir)` | ملف JSON لكل وقفة، `<dir>/approvals/<id>.json`، على جهاز واحد؛ الـ approval ينحسم من process واحدة بس (شوف [اختيار المخزن](/ar/sessions#choosing-a-store)). |
| `SqliteStore.approvals` | ملف SQLite واحد، تتشاركه عدة processes بأمان؛ الـ approval ينحسم من وحدة منهم بس. |

## في مواضع أخرى

- **Sub-agents.** الـ tool اللي يحتاج approval داخل sub-agent يوقف run الـ
  lead؛ `agent.approvals` تبع الـ lead يحسمه. شوف
  [الموافقات داخل وكيل فرعي](/ar/sub-agents#approvals-inside-a-sub-agent).
- **أدوات مساحة العمل.** الـ shell tool عليه approval افتراضيًا. شوف
  [أدوات مساحة العمل](/ar/workspace-tools).
- **MCP.** الأدوات اللي عليها approval ما تقدر تتوافَق عبر MCP؛ شوف
  [تقديم وكيل عبر MCP](/ar/mcp-integration#تشغيل-agent-كسيرفر-mcp).
- **Agent Forge** يعرض الـ approvals المعلّقة كبطاقات داخل الشات تبعه؛
  شوف [Agent Forge](/ar/agent-forge).
