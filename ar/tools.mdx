الـ tool هو دالة typed يستطيع الـ model استدعاءها. عرّفه بـ `defineTool()`: تُستنتج أنواع الوسائط والنتيجة من zod `input`، وتمر الوسائط على validation قبل أن تعمل `execute`، ويمكن وضع النتيجة في أي مكان يقبل tools (`createAgent({ tools: [...] })`، `ToolRegistry.register(tool)`، `AgentBuilder.addTool(tool)`).

> تترك الأمثلة في هذه الصفحة بعض الأسماء لك: `provider` هو أي `LLMProvider` (بدون إنترنت: `createMockProvider()`).

```ts
import { defineTool, createAgent, type ToolInput, type ToolOutput } from 'lousho';
import { z } from 'zod';

const weather = defineTool({
  name: 'weather', // 1-64 chars: letters, digits, _ and -
  description: 'Get weather information',
  input: z.object({ location: z.string(), units: z.enum(['celsius', 'fahrenheit']) }),
  execute: async ({ location, units }) => ({ temperature: 72, conditions: 'sunny' }),
});

type WeatherArgs = ToolInput<typeof weather>;   // { location: string; units: 'celsius' | 'fahrenheit' }
type WeatherResult = ToolOutput<typeof weather>; // { temperature: number; conditions: string }

const agent = createAgent({ instructions: '...', provider, tools: [weather] });
```

الـ tools التي يشغّلها الـ provider نفسه (web search، code interpreter، file search) تضعها في قائمة `tools` نفسها؛ انظر [Hosted provider tools](/ar/hosted-tools).

إذا كانت لديك tools كثيرة، فعلّمها بـ `deferLoading` لكي يجدها الـ model عبر `tool_search` (tool مدمج) بدلًا من أن يستلم كل التعريفات في كل call؛ انظر [Tool search](/ar/tool-search).

الـ tools المكتوبة لـ Vercel AI SDK (`tool({ description, inputSchema, execute })`) تتحوّل بـ `fromAiSdkTools({ weather, sendEmail })`، ومعها `needsApproval`؛ انظر [الانتقال من AI SDK](/ar/migrating-from-ai-sdk#الـ-tools-fromaisdktools).

## خيارات `defineTool()`

| الخيار | مطلوب | الوصف |
| ------ | -------- | ----------- |
| `name` | نعم | الاسم الذي يستدعي به الـ model الـ tool. يجب أن يطابق `^[a-zA-Z0-9_-]{1,64}$` (الحد الذي يفرضه مزوّدو LLM على أسماء الدوال). |
| `description` | نعم | ما يفعله الـ tool. يقرأه الـ model لكي يقرر متى يستدعيه. |
| `input` | نعم | zod schema للوسائط (zod 3 أو zod 4، أو أي Standard Schema آخر يوفّر `~standard.jsonSchema`). تستلم `execute` و`needsApproval` و`sandboxExecute` نوعه بعد الـ parsing (نوع الـ output). |
| `execute(args, ctx)` | نعم | يشغّل الـ tool. `ctx` فيه `toolCallId` و`abortSignal` الخاصين بالـ call. نوع القيمة الراجعة يبقى على الـ tool (`ToolOutput`). |
| `displayName` | لا | اسم يظهر في الواجهات. الافتراضي `name`. |
| `needsApproval` | لا | `true` أو predicate معرّفة الأنواع من `input`، توقف الـ call إلى أن يقرر إنسان قبل أن يعمل. انظر [Approvals](/ar/approvals). |
| `annotations` | لا | تلميحات MCP (`readOnlyHint`، `destructiveHint`، ...) تُخزَّن في `metadata.mcp.annotations`. `readOnlyHint: true` تجعل الـ tool يعمل في [plan mode](/ar/permission-modes#أي-الـ-tools-read-only). |
| `deferLoading` | لا | يحجب تعريف الـ tool عن الـ model إلى أن يجده بـ `tool_search`. انظر [Tool search](/ar/tool-search). |
| `editsFiles` | لا | الـ tool يعدّل ملفات: [`permissionMode: 'acceptEdits'`](/ar/permission-modes#تعديل-الملفات-علامة-editsfiles) يشغّل الـ calls بدون سؤال. تُخزَّن في `metadata.editsFiles`. |
| `timeoutMs` | لا | أطول وقت يمكن أن يستغرقه الـ call، بالـ ms. الـ call الذي ما زال يعمل بعده يفشل بـ tool error يراه الـ model، ويُلغى الـ `abortSignal` الخاص به، ويستمر الـ run بدونه. لا ينطبق على tool يبث (`async function*`). |
| `requiresSandbox` | لا | يشغّل الـ tool عبر `SandboxAdapter` المُعدّ بدلًا من تشغيله في العملية نفسها (يحتاج `sandboxExecute`). انظر [Guardrails و sandboxing](/ar/guardrails#sandboxed-tools). |
| `sandboxExecute(args, sandbox)` | لا | مسار التنفيذ داخل الـ sandbox، يُستخدم عندما تكون `requiresSandbox` true. |

تفحص `defineTool()` الاسم والوصف وzod `input` عند استدعائها، وترمي خطأً يخبرك كيف تصلح القيمة الخاطئة. تسجيل toolين بالاسم نفسه يرمي خطأً يسمّي التعارض.

أي خيار غير موجود في الجدول أعلاه يُعتبر خطأً (`LOUSHO_CONFIG_INVALID`) مع اقتراح، لكي لا يجعل خيارُ أمانٍ مكتوبٌ خطأً tool يعمل بدون approval: `requireApproval: true` يعطي `'requireApproval' is not a known option (did you mean 'needsApproval'?)`، و`inputSchema` أو `parameters` يرشدانك إلى `input`. ويُقبل الـ tool المعرّف إذا أعدته عبر spread (`defineTool({ ...tool, execute })`).

وترفض أيضًا (`LOUSHO_CONFIG_INVALID`) أي `input` لا يستطيع أي model تلبيته:

- **يجب أن يكون الجذر object.** يرسل الـ providers وسائط الـ tool كـ JSON object، لذلك يُرفض `z.string()` أو `z.array(...)` في الجذر. غلّفه: `z.object({ value: z.string() })`.
- **لا حقول `z.date()` ولا `z.bigint()`.** يكتب الـ model هناك نص ISO أو رقمًا، وهذه الـ schemas ترفض الاثنين، فيفشل كل call. استخدم `z.coerce.date()` (أو `z.iso.datetime()` إذا أردت الإبقاء على النص) و`z.coerce.bigint()` (أو `z.number().int()`).

الـ tool المعرّف هو `ToolDescriptor` عادي: يحمل الـ schema في `inputSchema` (الـ schema نفسها الموجودة في `input`) ودالة `execute` مباشرة. أما حقل `.tool` (كائن `{ description, parameters, execute }` من `ai` v4) فقديم: ما زال مقبولًا للتوافق، ويُقرأ حقلًا حقلًا — الـ descriptor المكتوب يدويًا بدون `inputSchema` يستخدم `tool.parameters` كـ fallback، والذي بدون `execute` يستخدم `tool.execute` كـ fallback، كلٌّ على حدة.

## ماذا يحدث عندما يستدعي الـ model أداة (tool)

- **الـ validation أولًا.** تُحلَّل وسائط الـ model بـ `inputSchema` (تُطبَّق الـ defaults والـ coercions والـ transforms) قبل أن تراها الـ hooks و`needsApproval` و`execute`. الوسائط التي لا تطابق لا تصل إلى `execute` أبدًا: يستلم الـ model نتيجة `ToolArgumentsValidationError` منظّمة ويستطيع إجراء retry.
- **الأخطاء نتائج.** الـ tool الذي يرمي خطأً يعطي الـ model `{ error, toolName, message, kind }` (بدون stack trace) ويستمر الـ run. انظر [الأخطاء](#الأخطاء).
- **Calls متوازية.** تعمل عدة calls في model turn واحد بالتوازي؛ حدّها بـ `toolConcurrency` (`1` للتسلسل الكامل). تصل النتائج إلى الـ transcript بترتيب calls الـ model. انظر [الـ tool calls المتوازية](/ar/runs#tool-calls-متوازية).
- **حد الحجم.** النتيجة التي يتجاوز طول الـ JSON الخاص بها `maxToolResultChars` (`createAgent({ maxToolResultChars })`، الافتراضي `50_000` حرف، أي نحو 12k token) تصل إلى الـ model، وإلى الـ transcript، كبدايتها ونهايتها مع علامة تذكر عدد الأحرف المحذوفة. `Infinity` تعطّل الحد. تستلم `onToolResult` والـ hooks وأحداث `tool.done` النتيجة كاملة.
- **الإلغاء.** يصل الـ `AbortSignal` الخاص بالـ run إلى كل call كـ `ctx.abortSignal`، فيستطيع العمل الطويل أن يتوقف مبكرًا.
- **التقدّم.** `execute` المكتوبة كـ `async function*` تبث snapshots من مخرجاتها أثناء عملها؛ وآخر snapshot هو النتيجة. انظر [Streaming للنتائج الجزئية](#streaming-للنتائج-الجزئية).
- **Calls كثيرة في خطوة واحدة.** مع `createAgent({ codeMode })` يستطيع الـ model أيضًا استدعاء tools من برنامج JavaScript قصير (`run_code`)، ويمر كل call بالفحوص نفسها. انظر [Code mode](/ar/code-mode).
- **Retry بعد crash.** مع durable execution قد يعمل الـ tool أكثر من مرة عبر crash؛ استخدم `ctx.toolCallId` كـ idempotency key. انظر [Durable execution](/ar/durable-execution#at-least-once-tools-اجعل-الـ-side-effects-idempotent).

## سياق `execute`

تستلم `execute(args, ctx)` دائمًا وسيطًا ثانيًا حقيقيًا، نوعه `ToolExecutionContext` (exported من جذر الحزمة؛ ويحل محل `ToolExecutionOptions` الخاص بـ `ai` SDK)، في كل مسار يشغّل tool: الحلقة الرئيسية، والـ call الذي يعمل بعد approval، والـ tools التي تعمل في sandbox (`sandboxExecute(args, sandbox, ctx)`)، وnode استدعاء الـ tool في flow.

| الحقل | القيمة |
| --- | --- |
| `ctx.toolCallId` | الـ id الذي أعطاه الـ model لهذا الـ call. يبقى كما هو عندما يُعاد الـ call نفسه بعد crash، لكن الـ crash الذي يحدث قبل تسجيل الـ call قد يجعل الـ model ينشئ call جديدًا بـ id جديد، لذلك فهو ليس idempotency key على مستوى الأعمال (انظر [At-least-once tools](/ar/durable-execution#at-least-once-tools-اجعل-الـ-side-effects-idempotent)). الـ call الذي لا يقف خلفه model turn (node في flow) يأخذ id مولّدًا. |
| `ctx.messages` | نسخة read-only من الـ transcript الذي رآه الـ model قبل أن ينشئ الـ call: بدون system prompt وبدون turn المساعد الذي أنشأ الـ call. فارغة لـ node في flow. |
| `ctx.abortSignal` | الـ `AbortSignal` الخاص بالـ run، يُعيَّن عندما يكون للـ run واحد. |
| `ctx.sessionId` | الـ session id الخاص بالـ run — الـ id في `agent.session({ id })` أو `sessionId` الممرر إلى `send()` / `AgentExecutor.execute()` (`send({ sessionId })` يحتاج `createAgent({ store })` مع checkpoints، وإلا يرمي `LOUSHO_CONFIG_MISSING_CHECKPOINT_STORE`)؛ يغيب عندما لا توجد session. |
| `ctx.principal` | من يعمل الـ run نيابةً عنه (المستدعي في route auth، مرسل القناة)، frozen؛ يغيب عندما لا يوجد. انظر [Principals في الـ tools والـ approvals](/ar/auth#principals-in-tools-and-approvals). |
| `ctx.approval` | يُعيَّن عندما يعمل الـ call لأن إنسانًا وافق عليه: `id` الـ approval (يمنع تكرار محاولات تشغيل call واحد تقرّر، انظر [Cloudflare Workers](/ar/cloudflare-workers#البتّ-في-approval-واحد-مرتين)؛ الـ model turn الذي يُعاد يأخذ approval جديدة، لذلك يحتاج الـ side effect الذي يجب أن يحدث مرة واحدة أيضًا إلى key من بياناتك أنت، مثل claim id)، و`note` الخاصة بالقرار، و`by` أي من قرّر، عندما يسمّيه القرار. |

الدالة `sandboxExecute(args, sandbox)` التي تتجاهل الوسيط الثالث تظل تعمل.

## الأخطاء

أي طريقة يفشل بها tool call تصل إلى الـ model بالنتيجة نفسها، لذلك يكفي فحص واحد في كل الحالات (ومنها الـ call الذي يعمل بعد approval):

```json
{ "error": "TypeError", "toolName": "search", "message": "query must not be empty", "kind": "execution" }
```

- `error`: اسم الخطأ (`TypeError`، `ToolArgumentsValidationError`، ...)، أو الاسم الافتراضي للـ kind عندما لا يكون الفشل خطأً مرميًا.
- `toolName` و`message`: الرسالة فقط، بلا stack أبدًا، بحد أقصى 2,000 حرف (`... (truncated)` علامة القص).
- `kind`: سبب فشل الـ call.
- بعض الأنواع تضيف حقولًا: `issues` لـ `validation`، `note` لـ `rejected`، `reason` لـ `denied`.

رسالة الـ transcript تحمل `isError: true`؛ وترى أحداث `tool-result` و`onToolResult` وhooks الـ `postToolCall` وأحداث `tool.error` الـ call فاشلًا.

| `kind` | `error` | متى |
| ------ | ------- | ---- |
| `execution` | اسم الخطأ المرمي | `execute` (أو `needsApproval`) رمت خطأ. |
| `validation` | `ToolArgumentsValidationError` | الوسائط لم تطابق `inputSchema`؛ `execute` لم تعمل. تضيف `issues`. |
| `not-found` | `ToolNotFoundError` | استدعى الـ model tool غير موجود في الـ registry (أو لا يوجد registry في الـ run). |
| `rejected` | `ToolRejectedError` | رفض مراجعٌ الـ call عند approval. يضيف `note` عندما تُعطى. |
| `not-run` | `ToolNotRunError` | لم يبدأ الـ call أصلًا (run مستأنف خُزّنت الـ approval الخاصة به بدون الـ calls المتبقية). |
| `mcp` | `McpToolError` | ردّ سيرفر MCP بـ `isError: true`؛ `message` هو نص السيرفر. |
| `sandbox` | `SandboxRequiredError` | الـ tool فيه `requiresSandbox` لكن لا يوجد `sandboxExecute`، فرُفض بدلًا من أن يعمل بدون sandbox. |
| `denied` | `ToolDeniedError` | [قاعدة صلاحيات](/ar/approvals#سياسات-الصلاحيات) من نوع `deny` رفضت الـ call، أو أرجعت `needsApproval` الخاصة بالـ tool القيمة `'deny'`، أو `deny` من hook `preToolCall`، أو رفض الـ permission mode الـ call؛ `execute` لم تعمل. يضيف `reason` عندما يُعطى. |

**إخفاء نص الاستثناء.** تصل رسالة الخطأ المرمي إلى الـ model كما هي، فـ `new Error('DB password=hunter2 connection refused')` يصله حرفيًا. مرّر `toolErrorMessage` إلى `createAgent` لكي تستبدل نص أخطاء `execution`:

```ts
import { createAgent } from 'lousho';

const agent = createAgent({
  instructions: 'You answer questions about orders.',
  model: 'openai/gpt-4o-mini',
  tools: [],
  toolErrorMessage: (error, { toolName, toolCallId }) => {
    console.error(`tool ${toolName} (${toolCallId}) failed`, error); // the original error stays here
    return `${toolName} failed. Try again later or use another approach.`;
  },
});
```

يصبح النص `message` في النتيجة أعلاه (ويظل الـ `kind` هو `execution`). يصل النص نفسه إلى أحداث `tool.error` و`onToolResult` وhooks الـ `postToolCall`، فلا يحمل الـ stream الذي يصل إلى العميل النص الأصلي أبدًا؛ دالتك وحدها ترى الخطأ المرمي. ترثه الـ sub-agents. لا يمس أخطاء `validation` (لأنها تصف وسائط الـ model الخاطئة نفسها) ولا الأنواع الأخرى. إذا رمت الدالة خطأً أو أرجعت شيئًا ليس نصًا، تصبح الرسالة `The tool failed.` ويستمر الـ run. وبدون الخيار، لا يتغير شيء.

**الـ validation الخاصة بالوسائط.** تُحلَّل وسائط الـ model بـ zod `inputSchema` الخاصة بالـ tool (وللـ descriptor القديم، `tool.parameters`) قبل أن يعمل الـ tool، لذلك تستلم hooks ما قبل الـ tool و`needsApproval` و`execute` كلها القيمة **المحلَّلة** (parsed). الـ tools التي لا تملك zod schema تمر وسائطها كما هي. إذا لم تطابق الوسائط، لا تُستدعى `execute` وتُتخطّى hooks الـ `preToolCall`، لأنه لا يوجد call صالح. يستلم الـ model نتيجة `validation` يستطيع إجراء retry بناءً عليها:

```json
{
  "error": "ToolArgumentsValidationError",
  "toolName": "sendEmail",
  "message": "Invalid arguments for tool 'sendEmail': 2 issues (to: Required; count: Expected number, received string)",
  "kind": "validation",
  "issues": [
    { "path": "to", "message": "Required" },
    { "path": "count", "message": "Expected number, received string" }
  ]
}
```

`ToolArgumentsValidationError` (مع مصفوفة `issues` typed) exported من جذر الحزمة.

تبني `toolErrorResult({ toolName, error, kind?, toolCallId?, details? })` هذه النتيجة؛ استخدمها في الـ wrappers الخاصة بك لكي تُخرج الشكل نفسه. يستطيع الخطأ المرمي اختيار الـ kind الخاص به بحمل خاصية `toolErrorKind`. أما الخطأ الذي يرث `PropagatingToolError` فليس نتيجة: إنه يوقف الـ run.

### الـ calls الفاشلة في النتيجة

يرى الـ model كل call فاشل وقد يجيب مع ذلك كأنه نجح، وينهي الـ run بـ `finishReason: 'stop'`. يعدّ `result.toolErrors` الـ tool calls في الـ run التي نتيجتها خطأ (أي `kind` مما سبق ما عدا `not-run`)؛ ويغيب عندما لا يفشل شيء. يعدّ فقط calls الـ run نفسه: الـ calls التي فشلت داخل الـ [sub-agents](/ar/sub-agents) التابعة له تُعدّ في `result.usage.delegated.toolErrors`. افحصه قبل أن تثق في `text`، أو ضع له حدًا بـ `limits.maxToolErrors`: بمجرد أن يفشل هذا العدد من الـ calls، يتوقف الـ run قبل الـ model call التالي بـ `finishReason: 'budget-exceeded'` وتكون قيمة `result.budget.limit` هي `'maxToolErrors'` (أو يرفض بـ `BudgetExceededError` مع `onExceeded: 'throw'`، انظر [الميزانيات](/ar/configuration#الميزانيات)).

```ts
import { createAgent, defineTool } from 'lousho';
import { z } from 'zod';

const stats = defineTool({ name: 'stats', description: 'Weekly stats', input: z.object({}), execute: async () => (await fetch('https://stats.example.com/week')).json() });
const agent = createAgent({ provider, tools: [stats], limits: { maxToolErrors: 3 } });
const result = await agent.send('Summarise this week');
if (result.budget?.limit === 'maxToolErrors') throw new Error('The stats tool keeps failing.');
if (result.toolErrors) console.warn(`${result.toolErrors} tool call(s) failed; the answer may be incomplete.`);
```

## Tools مدمجة

| التصدير | الـ tool |
| ------ | ---- |
| `httpTool`, `createHttpTool(options)` | `http_request`: طلبات HTTP (أي method، headers، body)، مع حماية من SSRF: تُرفض وجهات loopback والخاصة وlink-local في كل hop، ويذهب الاتصال إلى العنوان الذي فُحص. Node فقط. |
| `webFetchTool`, `createWebFetchTool(options)` | `web_fetch`: `GET` لصفحة ويب عامة واحدة ويُرجعها نصًا، بحماية SSRF نفسها وبحدود على الـ redirects والحجم والوقت. Node فقط؛ انظر أدناه. |
| `currentDateTool`, `dayNameTool` | التاريخ والوقت الحاليين (ISO، UTC) ويوم الأسبوع. |
| `createTodoTools()` | `todo_write` / `todo_read` لكي يخطط الـ agent لعمل متعدد الخطوات؛ انظر [Todo tools](#todo-tools). |
| `askQuestionTool()`, `createAgent({ askQuestion: true })` | `ask_question`: يسأل الـ agent المستخدم شيئًا ويتوقف الـ run حتى `agent.approvals.answer()`؛ انظر [سؤال المستخدم](/ar/approvals#سؤال-المستخدم). |
| `createFsTools()`, `createShellTool()` | tools لنظام الملفات والـ shell للـ coding agents؛ انظر [Workspace tools](/ar/workspace-tools). |
| `createEmailTool()`, `createSlackTool()`, `createGitHubTools()`, `createJiraTools()` (من `lousho/integrations`) | تكاملات تحتاج credentials، لذلك تُبنى بخيارات. تقرأ `createSlackTool()` رابط الـ webhook من `SLACK_WEBHOOK_URL` إلا إذا مرّرت `webhookUrl`؛ وتأخذ `createJiraTools()` القيم `baseUrl` و`email` و`apiToken` صراحةً (عادةً من `JIRA_BASE_URL` و`JIRA_EMAIL` و`JIRA_API_TOKEN`). |
| `createAgent({ mcpServers })`, `connectMcp(servers)` | كل tools سيرفرات MCP المعطاة في الإعداد (`command` لـ stdio أو `url` لـ HTTP)، بأسماء `<server>__<tool>`؛ انظر [استخدام سيرفرات MCP في agent](/ar/mcp-integration#استخدام-سيرفرات-mcp-داخل-agent). |
| `openApiTools(document, options)` | tool لكل operation في مستند OpenAPI 3.0 / 3.1؛ العمليات التي تغيّر البيانات تطلب approval. انظر [OpenAPI tools](/ar/openapi-tools). |
| `loadMcpTools(client, name)` | كل tools سيرفر MCP متصل؛ انظر [MCP tools](/ar/mcp-integration#tools-من-client-اتصلت-به-بنفسك). |

تُمرَّر الـ descriptors المدمجة keyed بالاسم الذي يستخدمه الـ agent: `createAgent({ tools: { current_date: currentDateTool } })`. تشير ملفات الـ spec إلى `http` و`web-fetch` و`current-date` و`day-name` بالاسم (انظر [الإعدادات](/ar/configuration#الـ-tools-التي-يمكن-للـ-spec-الإشارة-إليها)).

كيف ترفض `http_request` و`web_fetch` الوجهات الخاصة: يُفحص الـ host المكتوب كـ IP صريح قبل الطلب؛ ويُحَل اسم الـ host مرة واحدة عند فتح الاتصال، ويُفحص كل عنوان ينتج عنه (loopback، RFC 1918، link-local ومنه عنوان cloud metadata، CGNAT، نطاقات multicast والمحجوزة، IPv4-mapped IPv6، NAT64 و6to4)، ويتصل الـ socket بالعنوان الذي فُحص. تُتبع الـ redirects يدويًا ويُفحص كل hop بالطريقة نفسها. والاسم الذي يُجري DNS rebinding — يجيب بعنوان عام أولًا ثم بعنوان خاص — لا يجد lookup ثانيًا يجيب فيه. وعندما تعمل `http_request` عبر sandbox، يُحَل الـ host ويُفحص في عملية الـ agent، وتتصل العملية داخل الـ sandbox بالعنوان نفسه. تأخذ الأداتان `allowPrivate` (أنماط hosts مثل `intranet.example` أو `*.corp.example`) للـ hosts التي قد تُحَل إلى عناوين خاصة.

تأخذ `web_fetch` القيمة `{ url }` (`http:` أو `https:`، بدون `user:password@`) وتُرجع `{ url, finalUrl, status, contentType, content, truncated }`. ترسل `GET` فقط، بلا body ولا cookies ولا headers يختارها المستدعي. يتحول الـ HTML إلى نص عادي (تُزال الـ scripts والـ styles وما شابهها، وكل عنصر block في سطر، وروابط الـ URL بين قوسين، وتُفك الـ entities)؛ ويُرجَع JSON و`text/*` كما أُرسلا؛ أما الأنواع الأخرى (صور، PDF، binaries) فتُرجع ملاحظة بدلًا من المحتوى. يُرجَع رد 4xx أو 5xx مع الـ body الخاص به ولا يُرمى كخطأ، لكي يقرأ الـ model صفحة الخطأ. الرفض والـ timeouts وكثرة الـ redirects والـ URLs الخاطئة هي tool errors تسمّي الـ host. الصفحة input غير موثوق: يخبر وصف الـ tool الـ model بذلك، و`readOnlyHint` و`openWorldHint` مضبوطان. خيارات `createWebFetchTool()` (البادئة `vendor/` في الـ model هي التي تختار الـ provider؛ مع OpenRouter استخدم `openrouter/<vendor>/<model>` مثل `openrouter/openai/gpt-4o-mini`):

```ts
import { createAgent, createWebFetchTool } from 'lousho';

const webFetch = createWebFetchTool({
  timeoutMs: 30_000, // whole request: redirects and body included
  maxRedirects: 10, // each hop is checked again
  maxBytes: 2 * 1024 * 1024, // read from the network, then stop (truncated: true)
  maxChars: 50_000, // characters of text returned to the model
  allowedHosts: ['*.example.com', 'example.com'], // `*.` matches subdomains only, so list the bare host too; when set, any other host is refused before DNS
  blockedHosts: ['private.example.com'], // always refused, before DNS
  allowPrivate: [], // hosts allowed to resolve to private addresses
  userAgent: 'lousho-web-fetch',
});

const agent = createAgent({ model: 'openai/gpt-4o-mini', tools: [webFetch] });
```

لكل `createWebFetchTool()` connection pool خاصة بها، تبقى ما دامت الـ tool موجودة وتُحرَّر معها بالـ garbage collection (لا توجد دالة close). `web_fetch` غير موجودة في بناء Cloudflare Worker، و`http_request` الخاصة بالـ Worker هي tool مختلفة تصل فقط إلى أسماء الـ hosts المدرجة في binding `LOUSHO_HTTP_ALLOW`؛ انظر [Cloudflare Workers](/ar/cloudflare-workers#providers-and-tools).

## Todo tools

تعطي `createTodoTools(options?)` الـ agents طويلة العمل plan تتبعه: `todo_write` تستبدل القائمة كلها (عناصر `{ id?, content, status }`، والحالة `pending` | `in_progress` | `completed`، بحد أقصى عنصر `in_progress` واحد) وتُرجع القائمة مع الأعداد؛ و`todo_read` تُرجعها. تُعيَّن الـ ids تلقائيًا وتظل ثابتة عندما تكرر كتابة لاحقة محتوى عنصر. القوائم غير الصالحة (مثل `in_progress` مرتين) تصل إلى الـ model كـ tool error منظّم لكي يُجري retry. تعيش القائمة في الذاكرة لكل call؛ مرّر `store` (`{ get, set }`) لكي تحفظها، و`onChange` لكي تحدّث UI. كل `todo_write` ناجحة تُصدر أيضًا حدث stream `todo.updated` بالقائمة الجديدة وأعدادها (انظر [Stream events](/ar/stream-events))، وروابط [React](/ar/react#todos) و[Vue](/ar/vue#todos) و[Svelte](/ar/svelte#todos) تحوّله إلى `useTodos()` / `loushoTodos()`، فتعرض الـ UI الخطة مباشرة بدون `onChange`.

```ts
import { createAgent, createTodoTools, type TodoStore } from 'lousho';

const todos = createTodoTools({ onChange: (list) => console.log(list.length, 'todos') });
const planner = createAgent({ instructions: 'Plan multi-step work, then do it.', provider, tools: todos.tools });

await planner.send('Migrate the repo to ESM');
console.log(await todos.getTodos()); // [{ id: 'todo_1', content: '...', status: 'completed' }, ...]

// Persist the list somewhere else:
let saved: Awaited<ReturnType<TodoStore['get']>> = [];
createTodoTools({ store: { get: () => saved, set: (next) => void (saved = next) } });
```

## متقدم: `ToolRegistry`

تبني `createAgent()` registry لك؛ املأ واحدًا بنفسك فقط مع `AgentExecutor.execute()` (انظر [executor API](/ar/executor-api)) أو لكي تشارك tools بين agents: `register(tool)` لناتج `defineTool()`، و`register(name, descriptor)` لـ `ToolDescriptor` خام (tool مدمجة، أو tool من MCP، أو `tool()` جاهزة من `ai` SDK)، و`registerMany()` لـ record من descriptors أو مصفوفة من tools معرّفة.

```ts
import { ToolRegistry } from 'lousho/tools';
import { currentDateTool, defineTool } from 'lousho';
import { z } from 'zod';

const lookupOrder = defineTool({
  name: 'lookup_order',
  description: 'Look up an order',
  input: z.object({ orderId: z.string() }),
  execute: async ({ orderId }) => ({ orderId, status: 'shipped' }),
});

const tools = new ToolRegistry();
tools.register(lookupOrder);
tools.register('current_date', currentDateTool);
```

مرّره في `toolRegistry` إلى `AgentExecutor.execute()`؛ وتسمّي خريطة `tools` في إعداد الـ agent الـ tools التي يستطيع استخدامها.

## Streaming للنتائج الجزئية

الـ tool الطويلة (تبني تقريرًا، أو تبحث في مصادر كثيرة) تستطيع عرض التقدم أثناء عملها: اكتب `execute` كـ `async function*`. كل `yield` هو snapshot كامل للمخرجات حتى تلك اللحظة، يحل محل ما قبله، ويصل إلى أحداث الـ run كـ `tool.partial` (انظر [Stream events](/ar/stream-events)). آخر قيمة تُمرَّر بـ `yield` هي نتيجة الـ tool: يستلمها الـ model، وهي `result` الخاصة بالـ call في `tool.done`، لذلك يظهر الـ snapshot الأخير مرتين (آخر `tool.partial` وفي `tool.done`). تُتجاهل قيمة `return`؛ والـ generator الذي لا يمرّر شيئًا نتيجته `null`، وكذلك أي tool يُرجع `undefined`: يرى الـ transcript والـ model و`tool.done` جميعًا `null`.

```ts
import { createAgent, defineTool, type ToolOutput } from 'lousho';
import { z } from 'zod';

const buildReport = defineTool({
  name: 'build_report',
  description: 'Builds a report from several sources',
  input: z.object({ topic: z.string() }),
  async *execute({ topic }, ctx) {
    const sections: string[] = [];
    for (const source of ['news', 'papers', 'forums']) {
      if (ctx.abortSignal?.aborted) return;
      sections.push(`${source}: notes on ${topic}`);
      yield { topic, sections: [...sections], done: false };
    }
    yield { topic, sections, done: true };
  },
});
type Report = ToolOutput<typeof buildReport>; // { topic: string; sections: string[]; done: boolean }

const agent = createAgent({ model: 'openai/gpt-4o-mini', tools: [buildReport] });
for await (const event of agent.stream('Write a report on solar power.')) {
  if (event.type === 'tool.partial') console.log(`step ${event.index}`, event.output);
}
```

ما يجب أن تعرفه:

- **النتيجة وحدها تُخزَّن.** لا تُرسل الـ snapshots إلى الـ model، ولا تُضاف إلى الـ transcript ولا الـ session، ولا يُحفظ لها checkpoint ولا تُسجَّل في trace spans. ترى الـ hooks (`postToolCall`، `onToolResult`) النتيجة فقط.
- **الـ crash يضيّعها.** المخرجات الجزئية ليست durable: بعد crash لا تكون للـ call نتيجة بعد، فيعمل من البداية من جديد (`tool.start` جديد، و`index` من 0). والتوقف لـ[تسجيل دخول](/ar/oauth) داخل الـ generator يعيده من البداية أيضًا، لكن الـ run المستأنف يبلّغ `tool.resume` وليس `tool.start` ثانيًا، و`index` من 0 كذلك. تبقى الـ snapshots التي بُثّت في سجل الأحداث؛ ويجب على الـ UI أن تتخلص منها عندما يتوقف الـ call أو يبدأ من جديد ([روابط الـ UI](/ar/react) تفعل ذلك).
- **الـ approvals والصلاحيات أولًا.** الـ generator tool الذي يحتاج approval يعمل، ويبث، فقط بعد القرار (وكذلك عند resume مبثوث، `agent.approvals.streamResolve()`).
- **الإلغاء.** عندما يُلغى الـ run، يتوقف الـ SDK عن قراءة الـ generator فورًا، ويختم الـ call كملغى ويستدعي `return()` الخاصة به، فتعمل كتل `finally` — بعد أن ينتهي الـ `await` الذي يقف عنده، لذلك مرّر `ctx.abortSignal` إلى العمل الذي تنتظره.
- **تُحجب الـ tokens في الـ snapshots أيضًا.** الـ snapshot الذي يحتوي token أخذه الـ tool من `ctx.getToken()` يُستبدل بـ `[REDACTED]`، كما في النتيجة. الـ hook `postToolCall` الذي يعيد كتابة النتيجة لا يرى الـ snapshots: إذا كانت مخرجات tool يجب أن تُفلتَر بـ hook، فافلترها داخل الـ tool أو لا تبثّها.
- **أي القيم تُبث.** فقط القيمة التي تملك `next()` وهي أيضًا async iterable (ما تُرجعه `async function*`) هي التي تُبث. أما النتيجة التي هي async iterable فقط، مثل `ReadableStream`، فهي نتيجة عادية.
- **الـ run كله محسوب.** يحجز `toolConcurrency` الـ slot حتى ينتهي الـ generator. إذا استدعيت `execute` الخاصة بالـ tool بنفسك فسيُرجع لك الـ generator.
- **أين.** الحلقة الرئيسية، والـ call الذي يعمل بعد approval، وnode استدعاء الـ tool في الـ flow (التي تحتفظ بالنتيجة فقط) كلها تمر على الـ generator؛ أما `sandboxExecute` الخاصة بالـ tool فلا تبث. في AI SDK UI stream، الـ snapshots هي مخرجات tool أولية (انظر [AI SDK UI](/ar/ai-sdk-ui#event-mapping)).
