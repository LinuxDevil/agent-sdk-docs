الـ tool هو دالة typed يقدر الـ model يستدعيها. عرّفه بـ `defineTool()`: أنواع الوسائط والنتيجة تُستنتج من zod `input`، الوسائط تمر على validation قبل ما `execute` تشتغل، والنتيجة تنحط في أي مكان يقبل tools (`createAgent({ tools: [...] })`، `ToolRegistry.register(tool)`، `AgentBuilder.addTool(tool)`).

```ts
import { defineTool, createAgent, type ToolInput, type ToolOutput } from '@lousho/build-ai-agent';
import { z } from 'zod';

const weather = defineTool({
  name: 'weather', // 1-64 chars: letters, digits, _ and -
  description: 'Get weather information',
  input: z.object({ location: z.string(), units: z.enum(['celsius', 'fahrenheit']) }),
  execute: async ({ location, units }) => ({ temperature: 72, conditions: 'sunny' }),
});

type WeatherArgs = ToolInput<typeof weather>;   // { location: string; units: 'celsius' | 'fahrenheit' }
type WeatherResult = ToolOutput<typeof weather>; // { temperature: number; conditions: string }

const agent = createAgent({ prompt: '...', provider, tools: [weather] });
```

الـ tools اللي الـ provider نفسه يشغّلها (web search، code interpreter، file search) تحطها في نفس قائمة `tools`؛ شوف [Hosted provider tools](/ar/hosted-tools).

لو عندك tools كثيرة، علّمها `deferLoading` عشان الـ model يلاقيها بـ `tool_search` (tool مدمج) بدل ما يستلم كل التعريفات في كل call؛ شوف [Tool search](/ar/tool-search).

## خيارات `defineTool()`

| الخيار | مطلوب | الوصف |
| ------ | -------- | ----------- |
| `name` | نعم | الاسم اللي الـ model ينادي به الـ tool. لازم يطابق `^[a-zA-Z0-9_-]{1,64}$` (الحد اللي يفرضه مزوّدو LLM على أسماء الدوال). |
| `description` | نعم | اللي الـ tool يسوّيه. الـ model يقرأه عشان يقرر متى يستدعيها. |
| `input` | نعم | zod schema للوسائط (zod 3 أو zod 4، أو أي Standard Schema ثاني يوفّر `~standard.jsonSchema`). `execute` و`needsApproval` و`sandboxExecute` يستلموا نوعه بعد الـ parsing (نوع الـ output). |
| `execute(args, ctx)` | نعم | يشغّل الـ tool. `ctx` فيه `toolCallId` و`abortSignal` الخاصين بالـ call. نوع القيمة الراجعة يبقى على الـ tool (`ToolOutput`). |
| `displayName` | لا | اسم يظهر في الواجهات. الافتراضي `name`. |
| `needsApproval` | لا | `true` أو predicate معرّفة الأنواع من `input`، توقّف الـ call لحد ما إنسان يقرر قبل ما يشتغل. شوف [Approvals](/ar/approvals). |
| `annotations` | لا | تلميحات MCP (`readOnlyHint`، `destructiveHint`، ...) تتخزّن في `metadata.mcp.annotations`. `readOnlyHint: true` تخلّي الـ tool يشتغل في [plan mode](/ar/permission-modes#أي-الـ-tools-read-only). |
| `deferLoading` | لا | يحجب تعريف الـ tool عن الـ model لحد ما يلاقيه بـ `tool_search`. شوف [Tool search](/ar/tool-search). |
| `editsFiles` | لا | الـ tool يعدّل ملفات: [`permissionMode: 'acceptEdits'`](/ar/permission-modes#تعديل-الملفات-علامة-editsfiles) يشغّل الـ calls بدون سؤال. تتخزّن في `metadata.editsFiles`. |
| `requiresSandbox` | لا | يشغّل الـ tool عبر `SandboxAdapter` المعدّ بدل ما يشتغل في العملية نفسها (يحتاج `sandboxExecute`). شوف [Guardrails و sandboxing](/ar/guardrails#sandboxed-tools). |
| `sandboxExecute(args, sandbox)` | لا | مسار التنفيذ داخل الـ sandbox، يُستخدم لما `requiresSandbox` تكون true. |

`defineTool()` تفحص الاسم والوصف وzod `input` لما تستدعيها، وترمي خطأ يقول لك كيف تصلّح القيمة الغلط. تسجيل toolين بنفس الاسم يرمي خطأ يسمّي التعارض.

الـ tool المعرف هو `ToolDescriptor` عادي: يحمل الـ schema في `inputSchema` (نفس الـ schema اللي في `input`) ودالة `execute` مباشرة. أما حقل `.tool` (كائن `{ description, parameters, execute }` من `ai` v4) فقديم: لسّا يتبنى للتوافق، ويُقرأ حقل حقل — descriptor مكتوب بإيدك بدون `inputSchema` يسوّي fallback على `tool.parameters`، وواحد بدون `execute` يسوّي fallback على `tool.execute`، كل واحد لحاله.

## ماذا يحدث لما الـ model يستدعي tool

- **الـ validation أول.** وسائط الـ model تتحلل بـ `inputSchema` (الـ defaults والـ coercions والـ transforms تتطبّق) قبل ما الـ hooks و`needsApproval` و`execute` يشوفوها. الوسائط اللي ما تطابق ما توصل `execute` أبد: الـ model يستلم نتيجة `ToolArgumentsValidationError` منظّمة ويقدر يسوّي retry.
- **الأخطاء نتائج.** الـ tool اللي يرمي يعطي الـ model `{ error, toolName, message, kind }` (بدون stack trace) والـ run يكمل. شوف [الأخطاء](#الأخطاء).
- **Calls متوازية.** أكثر من call في model turn واحد يشتغلوا بالتوازي؛ حدّهم بـ `toolConcurrency` (`1` للتسلسل الكامل). النتائج توصل الـ transcript بترتيب calls الـ model. شوف [الـ tool calls المتوازية](/ar/runs#tool-calls-متوازية).
- **الإلغاء.** الـ `AbortSignal` الخاص بالـ run يوصل كل call كـ `ctx.abortSignal`، فيقدر الشغل الطويل يوقف بدري.
- **التقدّم.** `execute` مكتوبة كـ `async function*` تبث snapshots من مخرجاتها وهي شغالة؛ آخر snapshot هو النتيجة. شوف [Streaming للنتائج الجزئية](#streaming-للنتائج-الجزئية).
- **Calls كثيرة في خطوة وحدة.** مع `createAgent({ codeMode })` يقدر الـ model كمان يستدعي tools من برنامج JavaScript قصير (`run_code`)، وكل call يمر بنفس الفحوص. شوف [Code mode](/ar/code-mode).
- **Retry بعد crash.** مع durable execution ممكن الـ tool يشتغل أكثر من مرة عبر crash؛ استخدم `ctx.toolCallId` كـ idempotency key. شوف [Durable execution](/ar/durable-execution#at-least-once-tools-خلّي-الـ-side-effects-idempotent).

## سياق `execute`

`execute(args, ctx)` تستلم دايمًا وسيط ثاني حقيقي، نوعه `ToolExecutionContext` (exported من جذر الحزمة؛ يحل محل `ToolExecutionOptions` حق `ai` SDK)، في كل مسار يشغّل tool: اللوب الرئيسية، والـ call اللي يشتغل بعد approval، والـ tools اللي تشتغل في sandbox (`sandboxExecute(args, sandbox, ctx)`)، وnode استدعاء الـ tool في flow.

| الحقل | القيمة |
| --- | --- |
| `ctx.toolCallId` | الـ id اللي الـ model أعطاه لهذا الـ call. يبقى نفسه لما الـ call يتعاد بعد crash. الـ call اللي ما فيه model turn وراه (node في flow) ياخذ id مولّد. |
| `ctx.messages` | نسخة read-only من الـ transcript اللي الـ model شافه قبل ما يسوّي الـ call: بدون system prompt وبدون turn المساعد اللي سوّى الـ call. فاضية لـ node في flow. |
| `ctx.abortSignal` | الـ `AbortSignal` الخاص بالـ run، يتضبط لما يكون للـ run واحد. |
| `ctx.sessionId` | الـ session id الخاص بالـ run — الـ id في `agent.session({ id })` أو `sessionId` الممرر لـ `send()` / `AgentExecutor.execute()`؛ يغيب لما ما في session. |
| `ctx.principal` | مين الـ run يشتغل بالنيابة عنه (المستدعي في route auth، مرسل القناة)، frozen؛ يغيب لما ما فيه واحد. شوف [Principals في الـ tools والـ approvals](/ar/auth#principals-in-tools-and-approvals). |
| `ctx.approval` | يتضبط لما الـ call يشتغل لأن إنسان وافق عليه: `note` حق القرار، و`by` أي مين قرّر، لما القرار يسمّيه. |

الدالة `sandboxExecute(args, sandbox)` اللي تتجاهل الوسيط الثالث تظل شغالة.

## الأخطاء

أي طريقة يفشل فيها tool call توصل الـ model بنفس النتيجة، ففحص واحد يكفي في كل الحالات (ومنها الـ call اللي يشتغل بعد approval):

```json
{ "error": "TypeError", "toolName": "search", "message": "query must not be empty", "kind": "execution" }
```

- `error`: اسم الخطأ (`TypeError`، `ToolArgumentsValidationError`، ...)، أو الاسم الافتراضي للـ kind لما الفشل مو خطأ مرمي.
- `toolName` و`message`: الرسالة بس، ما في stack أبد، بحد أقصى 2,000 حرف (`... (truncated)` علامة القص).
- `kind`: سبب فشل الـ call.
- بعض الأنواع تزيد حقول: `issues` لـ `validation`، `note` لـ `rejected`، `reason` لـ `denied`.

رسالة الـ transcript تحمل `isError: true`؛ أحداث `tool-result` و`onToolResult` وhooks الـ `postToolCall` وأحداث `tool.error` تشوف الـ call فاشل.

| `kind` | `error` | متى |
| ------ | ------- | ---- |
| `execution` | اسم الخطأ المرمي | `execute` (أو `needsApproval`) رمت خطأ. |
| `validation` | `ToolArgumentsValidationError` | الوسائط ما طابقت `inputSchema`؛ `execute` ما اشتغلت. تزيد `issues`. |
| `not-found` | `ToolNotFoundError` | الـ model استدعى tool مو موجود في الـ registry (أو الـ run ما فيه registry). |
| `rejected` | `ToolRejectedError` | مراجع رفض الـ call عند approval. يزيد `note` لما تُعطى. |
| `not-run` | `ToolNotRunError` | الـ call ما بدأ أصلًا (run مستأنف اتخزّن الـ approval حقه بدون الـ calls الباقية). |
| `mcp` | `McpToolError` | سيرفر MCP جاوب `isError: true`؛ `message` هو نص السيرفر. |
| `sandbox` | `SandboxRequiredError` | الـ tool فيه `requiresSandbox` بس ما فيه `sandboxExecute`، فانرفض بدل ما يشتغل بدون sandbox. |
| `denied` | `ToolDeniedError` | [قاعدة صلاحيات](/ar/approvals#سياسات-الصلاحيات) من نوع `deny` رفضت الـ call، أو `needsApproval` حق الـ tool رجّعت `'deny'`، أو `deny` من hook `preToolCall`، أو الـ permission mode رفض الـ call؛ `execute` ما اشتغلت. يزيد `reason` لما يُعطى. |

**الـ validation حق الوسائط.** وسائط الـ model تتحلل بـ zod `inputSchema` الخاصة بالـ tool (للـ descriptor القديم، `tool.parameters`) قبل ما الـ tool يشتغل، فـ hooks ما قبل الـ tool و`needsApproval` و`execute` كلهم يستلموا القيمة **المتحللة** (parsed). الـ tools اللي بدون zod schema وسائطها تعدي زي ما هي. لو الوسائط ما طابقت، `execute` ما يتنادى وhooks الـ `preToolCall` تتخطى، لأنه ما في call صالح. الـ model يستلم نتيجة `validation` يقدر يسوّي منها retry:

```json
{
  "error": "ToolArgumentsValidationError",
  "toolName": "sendEmail",
  "message": "Invalid arguments for tool 'sendEmail': 2 issues (to: Required; count: Expected number, received string)",
  "kind": "validation",
  "issues": [
    { "path": "to", "message": "Required" },
    { "path": "count", "message": "Expected number, received string" }
  ]
}
```

`ToolArgumentsValidationError` (مع مصفوفة `issues` typed) exported من جذر الحزمة.

`toolErrorResult({ toolName, error, kind?, toolCallId?, details? })` تبني هذه النتيجة؛ استخدمها في الـ wrappers حقك عشان تطلع نفس الشكل. الخطأ المرمي يقدر يختار kindه بحمل خاصية `toolErrorKind`. أما الخطأ اللي يورث `PropagatingToolError` فمو نتيجة: يوقّف الـ run.

## Tools مدمجة

| التصدير | الـ tool |
| ------ | ---- |
| `httpTool`, `createHttpTool(options)` | `http_request`: طلبات HTTP (أي method، headers، body)، مع حماية من SSRF: وجهات loopback والخاصة وlink-local تنرفض في كل hop، والاتصال يروح للعنوان اللي اتفحص. Node بس. |
| `webFetchTool`, `createWebFetchTool(options)` | `web_fetch`: `GET` لصفحة ويب عامة وحدة ويرجعها نص، بنفس حماية SSRF وبحدود على الـ redirects والحجم والوقت. Node بس؛ شوف تحت. |
| `currentDateTool`, `dayNameTool` | التاريخ والوقت الحاليين (ISO، UTC) ويوم الأسبوع. |
| `createTodoTools()` | `todo_write` / `todo_read` عشان الـ agent يخطط شغل متعدد الخطوات؛ شوف [Todo tools](#todo-tools). |
| `askQuestionTool()`, `createAgent({ askQuestion: true })` | `ask_question`: الـ agent يسأل المستخدم شي والـ run يوقف لحد `agent.approvals.answer()`؛ شوف [سؤال المستخدم](/ar/approvals#سؤال-المستخدم). |
| `createFsTools()`, `createShellTool()` | tools لنظام الملفات والـ shell للـ coding agents؛ شوف [Workspace tools](/ar/workspace-tools). |
| `createEmailTool()`, `createSlackTool()`, `createGitHubTools()`, `createJiraTools()` (من `@lousho/build-ai-agent/integrations`) | تكاملات تحتاج credentials، فتتبنى بخيارات. |
| `createAgent({ mcpServers })`, `connectMcp(servers)` | كل tools سيرفرات MCP المعطاة في الإعداد (`command` لـ stdio أو `url` لـ HTTP)، بأسماء `<server>__<tool>`؛ شوف [استخدام سيرفرات MCP في agent](/ar/mcp-integration#استخدام-سيرفرات-mcp-داخل-agent). |
| `openApiTools(document, options)` | tool لكل operation في مستند OpenAPI 3.0 / 3.1؛ العمليات اللي تغيّر بيانات تطلب approval. شوف [OpenAPI tools](/ar/openapi-tools). |
| `loadMcpTools(client, name)` | كل tools سيرفر MCP متصل؛ شوف [MCP tools](/ar/mcp-integration#tools-من-client-اتصلت-به-بنفسك). |

الـ descriptors المدمجة تتمرر keyed بالاسم اللي الـ agent يستخدمه: `createAgent({ tools: { current_date: currentDateTool } })`. ملفات الـ spec تشير لـ `http` و`web-fetch` و`current-date` و`day-name` بالاسم (شوف [الإعدادات](/ar/configuration#الـ-tools-التي-يمكن-للـ-spec-الإشارة-إليها)).

كيف `http_request` و`web_fetch` يرفضوا الوجهات الخاصة: الـ host اللي مكتوب IP صريح ينفحص قبل الطلب؛ اسم الـ host ينحل مرة وحدة لما الاتصال ينفتح، وكل عنوان يطلع منه ينفحص (loopback، RFC 1918، link-local ومنه عنوان cloud metadata، CGNAT، نطاقات multicast والمحجوزة، IPv4-mapped IPv6، NAT64 و6to4)، والـ socket يتصل بالعنوان اللي اتفحص. الـ redirects تتبع يدوي وكل hop ينفحص بنفس الطريقة. اسم يسوّي DNS rebinding — يجاوب عنوان عام أول وبعدين خاص — ما يلقى lookup ثاني يجاوب فيه. ولما `http_request` تشتغل عبر sandbox، الـ host ينحل وينفحص في عملية الـ agent، والعملية داخل الـ sandbox تتصل بنفس العنوان. الأداتين ياخذوا `allowPrivate` (أنماط hosts زي `intranet.example` أو `*.corp.example`) لـ hosts ممكن تنحل لعناوين خاصة.

`web_fetch` تاخذ `{ url }` (`http:` أو `https:`، بدون `user:password@`) وترجع `{ url, finalUrl, status, contentType, content, truncated }`. ترسل `GET` بس، بدون body ولا cookies ولا headers يختارها المستدعي. الـ HTML يتحول لنص عادي (الـ scripts والـ styles وشبهها تتشال، عناصر الـ block كل وحدة في سطر، روابط الـ URL بين قوسين، والـ entities تتفك)؛ JSON و`text/*` يرجعوا زي ما انبعثوا؛ الأنواع الثانية (صور، PDF، binaries) ترجع ملاحظة بدل المحتوى. رد 4xx أو 5xx يرجع مع bodyه وما ينرمي كخطأ، عشان الـ model يقرأ صفحة الخطأ. الرفض والـ timeouts وكثرة الـ redirects والـ URLs الخاطئة هي tool errors تسمّي الـ host. الصفحة input غير موثوق: وصف الـ tool يقول هذا للـ model، و`readOnlyHint` و`openWorldHint` مضبوطين. خيارات `createWebFetchTool()` (بادئة `vendor/` في الـ model هي اللي تختار الـ provider؛ مع OpenRouter استخدم `openrouter/<vendor>/<model>` زي `openrouter/openai/gpt-4o-mini`):

```ts
import { createAgent, createWebFetchTool } from '@lousho/build-ai-agent';

const webFetch = createWebFetchTool({
  timeoutMs: 30_000, // whole request: redirects and body included
  maxRedirects: 10, // each hop is checked again
  maxBytes: 2 * 1024 * 1024, // read from the network, then stop (truncated: true)
  maxChars: 50_000, // characters of text returned to the model
  allowedHosts: ['*.example.com', 'example.com'], // `*.` matches subdomains only, so list the bare host too; when set, any other host is refused before DNS
  blockedHosts: ['private.example.com'], // always refused, before DNS
  allowPrivate: [], // hosts allowed to resolve to private addresses
  userAgent: 'lousho-web-fetch',
});

const agent = createAgent({ model: 'openai/gpt-4o-mini', tools: [webFetch] });
```

كل `createWebFetchTool()` لها connection pool خاصة فيها، تبقى ما دامت الـ tool موجودة وتتحرر معها بالـ garbage collection (ما في دالة close). `web_fetch` مو موجودة في بناء Cloudflare Worker، و`http_request` حق الـ Worker هي tool مختلفة توصل بس لأسماء الـ hosts المدرجة في binding `LOUSHO_HTTP_ALLOW`؛ شوف [Cloudflare Workers](/ar/cloudflare-workers#providers-and-tools).

## Todo tools

`createTodoTools(options?)` تعطي الـ agents طويلة الشغل plan يتبعوه: `todo_write` تستبدل القائمة كلها (عناصر `{ id?, content, status }`، الحالة `pending` | `in_progress` | `completed`، بحد أقصى `in_progress` وحدة) وترجع القائمة مع الأعداد؛ `todo_read` ترجعها. الـ ids تتعين تلقائي وتظل ثابتة لما كتابة بعدها تكرر محتوى عنصر. القوائم الغلط (زي `in_progress` مرتين) توصل الـ model كـ tool error منظّم عشان يسوّي retry. القائمة تعيش في الذاكرة لكل call؛ مرّر `store` (`{ get, set }`) عشان تدّخرها، و`onChange` عشان تحدّث UI. كل `todo_write` ناجحة تصدر كمان حدث stream `todo.updated` بالقائمة الجديدة وأعدادها (شوف [Stream events](/ar/stream-events))، وروابط [React](/ar/react#todos) و[Vue](/ar/vue#todos) و[Svelte](/ar/svelte#todos) تحوله لـ `useTodos()` / `loushoTodos()`، فالـ UI يعرض الخطة مباشرة بدون `onChange`.

```ts
import { createAgent, createTodoTools, type TodoStore } from '@lousho/build-ai-agent';

const todos = createTodoTools({ onChange: (list) => console.log(list.length, 'todos') });
const planner = createAgent({ prompt: 'Plan multi-step work, then do it.', provider, tools: todos.tools });

await planner.send('Migrate the repo to ESM');
console.log(await todos.getTodos()); // [{ id: 'todo_1', content: '...', status: 'completed' }, ...]

// Persist the list somewhere else:
let saved: Awaited<ReturnType<TodoStore['get']>> = [];
createTodoTools({ store: { get: () => saved, set: (next) => void (saved = next) } });
```

## متقدم: `ToolRegistry`

`createAgent()` تبني registry لك؛ عبّي واحد بنفسك بس مع `AgentExecutor.execute()` (شوف [executor API](/ar/executor-api)) أو عشان تشارك tools بين agents: `register(tool)` لناتج `defineTool()`، و`register(name, descriptor)` لـ `ToolDescriptor` خام (tool مدمجة، tool من MCP، أو `tool()` جاهزة من `ai` SDK)، و`registerMany()` لـ record من descriptors أو مصفوفة من tools معرفة.

```ts
import { ToolRegistry } from '@lousho/build-ai-agent/tools';
import { currentDateTool, defineTool } from '@lousho/build-ai-agent';
import { z } from 'zod';

const lookupOrder = defineTool({
  name: 'lookup_order',
  description: 'Look up an order',
  input: z.object({ orderId: z.string() }),
  execute: async ({ orderId }) => ({ orderId, status: 'shipped' }),
});

const tools = new ToolRegistry();
tools.register(lookupOrder);
tools.register('current_date', currentDateTool);
```

مرّره في `toolRegistry` لـ `AgentExecutor.execute()`؛ خريطة `tools` في إعداد الـ agent تسمّي الـ tools اللي يقدر يستخدمها.

## Streaming للنتائج الجزئية

الـ tool الطويلة (تبني تقرير، بحث على مصادر كثيرة) تقدر تورّي التقدم وهي شغالة: اكتب `execute` كـ `async function*`. كل `yield` هو snapshot كامل للمخرجات لحد هذيك اللحظة، يحل محل اللي قبله، ويوصل أحداث الـ run كـ `tool.partial` (شوف [Stream events](/ar/stream-events)). آخر قيمة تتمرر بـ `yield` هي نتيجة الـ tool: الـ model يستلمها، وهي `result` حق الـ call في `tool.done`، فالـ snapshot الأخير يظهر مرتين (آخر `tool.partial` وفي `tool.done`). قيمة `return` تتجاهل؛ والـ generator اللي ما يمرر شي نتيجته `null`، وكذلك أي tool يرجع `undefined`: الـ transcript والـ model و`tool.done` كلهم يشوفوا `null`.

```ts
import { createAgent, defineTool, type ToolOutput } from '@lousho/build-ai-agent';
import { z } from 'zod';

const buildReport = defineTool({
  name: 'build_report',
  description: 'Builds a report from several sources',
  input: z.object({ topic: z.string() }),
  async *execute({ topic }, ctx) {
    const sections: string[] = [];
    for (const source of ['news', 'papers', 'forums']) {
      if (ctx.abortSignal?.aborted) return;
      sections.push(`${source}: notes on ${topic}`);
      yield { topic, sections: [...sections], done: false };
    }
    yield { topic, sections, done: true };
  },
});
type Report = ToolOutput<typeof buildReport>; // { topic: string; sections: string[]; done: boolean }

const agent = createAgent({ model: 'openai/gpt-4o-mini', tools: [buildReport] });
for await (const event of agent.stream('Write a report on solar power.')) {
  if (event.type === 'tool.partial') console.log(`step ${event.index}`, event.output);
}
```

اللي لازم تعرفه:

- **بس النتيجة تتخزّن.** الـ snapshots ما تتبعت للـ model، ما تتضاف للـ transcript ولا الـ session، وما يتعملها checkpoint ولا تتسجل في trace spans. الـ hooks (`postToolCall`، `onToolResult`) تشوف بس النتيجة.
- **الـ crash يضيّعها.** المخرجات الجزئية مو durable: بعد crash الـ call ما فيه نتيجة لسّا ويشتغل من الأول من جديد (`tool.start` جديد، `index` من 0). وقفة لـ[تسجيل دخول](/ar/oauth) جوّا الـ generator تعيده من الأول كمان، بس الـ run المستأنف يبلّغ `tool.resume` مو `tool.start` ثاني، وبرضو `index` من 0. الـ snapshots اللي انبثّت تبقى في سجل الأحداث؛ الـ UI لازم يرميها لما الـ call يوقف أو يبدأ من جديد ([روابط الـ UI](/ar/react) تسوّي كذا).
- **الـ approvals والصلاحيات أول.** الـ generator tool اللي يحتاج approval يشتغل، ويبث، بس بعد القرار (وكمان على resume مبثوث، `agent.approvals.streamResolve()`).
- **الإلغاء.** لما الـ run يتلغي، الـ SDK يوقف قراءة الـ generator فورًا، ويختم الـ call كملغي وينادي `return()` حقته، فبلوكات `finally` تشتغل — بعد ما الـ `await` اللي هو فيه يخلص، فمرّر `ctx.abortSignal` للشغل اللي تنتظره.
- **الـ tokens تتحجب في الـ snapshots كمان.** الـ snapshot اللي فيه token الـ tool أخذه من `ctx.getToken()` ينستبدل بـ `[REDACTED]`، زي النتيجة. الـ hook `postToolCall` اللي يعيد كتابة النتيجة ما يشوف الـ snapshots: لو مخرجات tool لازم تتفلتر بـ hook، فلترها جوّا الـ tool أو ما تبثّها.
- **أي قيم تبث.** بس القيمة اللي فيها `next()` وهي كمان async iterable (اللي `async function*` ترجعه) هي اللي تبث. نتيجة async iterable بس، زي `ReadableStream`، هي نتيجة عادية.
- **الـ run كله محسوب.** `toolConcurrency` يحجز الـ slot لحد ما الـ generator يخلص. لو ناديت `execute` حق الـ tool بنفسك يرجع لك الـ generator.
- **وين.** اللوب الرئيسية، والـ call اللي يشتغل بعد approval، وnode استدعاء الـ tool في الـ flow (اللي تحتفظ بس بالنتيجة) كلهم يمشوا على الـ generator؛ `sandboxExecute` حق الـ tool ما يبث. في AI SDK UI stream، الـ snapshots هي مخرجات tool أولية (شوف [AI SDK UI](/ar/ai-sdk-ui#event-mapping)).
