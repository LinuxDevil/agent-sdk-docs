الـ **channel** يوصّل الـ agent بطرف واحد: JSON API، أو webhook، أو تطبيق
محادثة. هو اللي يحدد المصادقة تبع الطلب الوارد، ولأي محادثة ينتمي، وكيف
يرجع رد الـ agent (أو الـ approval اللي وقف عليه) لنفس الطرف.
`mountChannels()` تقدّم قنواتك كلها وراء handler واحد `(req, res)` وتشغّل
كل طلب بنفس الطريقة:

```text
POST <basePath>/<name>  ->  verify  ->  parse  ->  session turn  ->  reply (or onApproval)
```

الـ channels تحل محل [trigger adapters](/ar/triggers) اللي صارت deprecated
(`WebhookTriggerAdapter` يستخدم `webhookChannel()` للمصادقة والـ parsing).
وتضيف الشي اللي ينقص الـ triggers: كل محادثة على الطرف هي
[session](/ar/sessions) (جلسة)، والـ approvals والأسئلة ترجع للطرف.

على host من نوع Fetch مثل Cloudflare Worker، `mountFetchChannels()` تقدّم
نفس المسارات: يدخلها `Request` وتطلع `Response` (و`ctx.waitUntil` تبع الـ
host يخلّي الـ turn يعيش بعد ما الـ webhook انرد عليه). و
`lousho build --target=cloudflare-worker` يركّب مجلد `channels/` تبع
agent directory تحت `/channels` بها.

## البداية السريعة

`httpChannel()` هو الـ channel المرجعي: `{ sessionKey, input }` داخل، JSON
خارج.

```ts
import * as http from 'node:http';
import { createAgent, createMockProvider, httpChannel, mountChannels } from '@lousho/build-ai-agent';

const agent = createAgent({ instructions: 'You are helpful.', provider: createMockProvider() });
const channels = mountChannels(agent, [httpChannel()]);

const server = http.createServer((req, res) => {
  void channels(req, res).then((handled) => {
    if (!handled) res.writeHead(404).end();
  });
});
server.listen(3000);
```

```bash
curl -s localhost:3000/channels/http -d '{"sessionKey":"user-42","input":"Hi, I am Ali"}'
# {"sessionId":"http_user-42-...","text":"...","finishReason":"stop"}
```

الـ handler يرجع `true` لما يخدم الطلب، و`false` (بدون ما يكتب شيء) لأي مسار
ثاني، مثل مسارات `/chat` في `lousho dev`. يعني تقدر تركّبه جنب مساراتك.

## العقد

`defineChannel({ ... })` تفحص الاسم وترجع التعريف:

| الحقل | الوصف |
| ----- | ----------- |
| `name` | جزء المسار: `POST <basePath>/<name>`. حروف وأرقام و`_` و`-`. |
| `verify(req)` | اختياري. يتحقق من الطلب (توقيع، token). رجّع `true`/`false` أو `{ ok, reason? }`؛ و`false` ترجع `401 {"error":"Unauthorized"}` قبل ما ينعمل parsing أو تشغيل لأي شيء. |
| `parse(req, respond, ctx)` | الرسالة: `{ sessionKey, input, metadata?, principal?, replyTo, event? }`؛ أو `{ decision: { id, approved?, note?, answer? } }` لحسم توقف وقف عليه turn هذي القناة (كليك زر)؛ أو `null` للإقرار بالطلب بدون turn (رسالة من البوت نفسه، retry). استدعِ `respond(status, body)` عشان ترد قبل ما يشتغل الـ turn (طرف مهلته قصيرة، handshake). |
| `reply(ctx)` | يوصّل الرد: `ctx.text`، زائد `inbound` و`sessionId` و`result` و`events` و`approval`، و`respond(status, body)` ما دام الطلب مفتوح. |
| `onApproval(ctx)` | اختياري. يعرض التوقف (أزرار، فورم). الافتراضي: `reply` مع prompt نصي في `ctx.text` والطلب في `ctx.approval`. |
| `onError(error, { channel, stage, sessionId? })` | اختياري. يستلم الأعطال اللي تصير بعد ما الطلب انقرّ (رد ما انوصّل، turn فاشل، أو متابعة approval فاشلة). الافتراضي: `mountChannels({ onError })`، وإلا `console.error` مع القناة والمرحلة ومعرّف الـ session ورمز خطأ SDK (ولا token أبدًا). والـ turn الفاشل يقول للمستخدم "Sorry, that request failed." في المحادثة (best effort). |
| `stream` | اختياري. `true` ينادي `reply` مع `partial: true` والنص اللي انكتب لحد الآن أثناء ما الـ model يكتب، وبعدين مرة أخيرة بالنص النهائي. |
| `sessionId(inbound)` | اختياري. الـ session تبع الرسالة. الافتراضي: `` `${name}:${sessionKey}` ``. |

`metadata` تروح للـ turn كـ `metadata` تبع `send()` (دوال scope الذاكرة
ودوال `model` / `instructions` / `tools` تشوفها). و`principal` هو المتصل
المتحقق منه في الـ turn، ويمر في نفس مكان `principal` تبع `send()`. لا تضبط
`principal` إلا من بيانات `verify` ضمنتها.

`ctx` (`ChannelContext`) يخلّي `parse` يسأل الـ host بدل ما يخزّن state:
`ctx.approval(id)` (الاستدعاء المعلّق)، `ctx.sessionId(key)`،
`ctx.hasSession(key)` (يعني في session محفوظة لذاك المفتاح في الـ `store`)،
و`ctx.pendingQuestion(key)` (معرّف الـ `ask_question` اللي session ذاك
المفتاح تنتظره، أو `undefined`؛ ويلاقي كمان سؤال اتسأل قبل إعادة تشغيل لما
تكون الـ sessions والـ checkpoints والـ approvals في durable stores (مخازن
تنجو من إعادة التشغيل)، ويربطه بالـ session فتنضم turn الإجابة للـ
transcript). استدعِ `pendingQuestion` بس لرسالة ترجعها كإجابة،
`{ decision: { id, answer: text }, inbound }`: المعرّف ينعطى مرة وحدة لحد
ما تشتغل تلك الإجابة. و`{ decision }` يقدر يحمل `inbound` (المحادثة كما
يسمّيها الكليك نفسه، فيبقى التوقف قائم بعد إعادة التشغيل) و`approver` (مين
قرر؛ يمر لـ `mountChannels({ onDecision })` لسجل التدقيق تبعك).

`req` هو `ChannelRequest` مستقل عن أي framework: `method` و`url` و`headers`
(أسماء بأحرف صغيرة) و`rawBody` (البايتات كما وصلت بالضبط: تحقق التواقيع
عليها هي، أبدًا مش على JSON أعيدت سلسَلته) و`text` و`native` (طلب الـ host).

الرد اللي ما يستدعي `respond` يتبعه `200 {"ok":true}`. والطرف اللي يوصّل
الردود خارج الطلب (ينشر على chat API مثلاً) يكفيه يقرّ بالطلب. وخطأ يرميه
`parse` يُرد عليه بـ 400 لو `SyntaxError` (JSON غلط) وبـ 500 غير كذا؛ وجسم
فوق 1MB ياخذ 413.

```ts
import { createAgent, defineChannel, mountChannels } from '@lousho/build-ai-agent';

const agent = createAgent({ instructions: 'You answer text messages.', provider });

interface SmsEvent {
  from: string;
  body: string;
}

const sms = defineChannel<SmsEvent>({
  name: 'sms',
  async verify(req) {
    return req.headers['x-api-key'] === process.env.SMS_API_KEY;
  },
  async parse(req) {
    const event = JSON.parse(req.text) as SmsEvent;
    return { sessionKey: event.from, input: event.body, replyTo: event.from, event };
  },
  async reply({ inbound, text }) {
    console.log(`SMS to ${inbound.event?.from}: ${text}`); // call your SMS API here
  },
});

const handler = mountChannels(agent, [sms], { basePath: '/hooks' }); // POST /hooks/sms
```

## Sessions

الرسائل اللي لها نفس `sessionKey` على نفس الـ channel تتشارك session وحدة،
فيشوف الـ agent التبادلات اللي قبلها؛ وturns الـ session الواحدة تشتغل وحدة
وحدة. معرّفات الـ sessions تقبل بس `A-Za-z0-9_-`، فمعرّف فيه حروف ثانية
(والافتراضي `` `${name}:${sessionKey}` `` فيه `:` دائمًا) تُستبدل الحروف
بـ `_` وينلحق بها hash للمعرّف الأصلي: `sms:+1555` يصير
`sms__1555-<hash>`. رجّع معرّف صالح من `sessionId()` عشان يُستخدم كما هو.

الـ transcripts تنحفظ في `mountChannels(agent, channels, { store })`:
`SessionStore` أو `{ sessions, checkpoints }` مثل `SqliteStore` (مرّر نفس
الـ store اللي عطيته لـ `createAgent({ store })`). وبدون `store`، الـ
handler يحتفظ بيها في الذاكرة.

## approvals والأسئلة

لما turn يتوقف على tool يحتاج approval (موافقة)، أو على استدعاء
[`ask_question`](/ar/approvals)، الـ handler ينادي `onApproval` (الافتراضي
`reply` مع prompt مثل `Approve send_email {"to":"sam@example.com"}?
(approval id: ...)`). احسمها بإحدى طريقتين؛ والمتابعة ترجع عبر `reply` تبع
نفس القناة (أو `onApproval` مرة ثانية لو توقفت ثاني):

- `handler.resolveApproval({ id, approved, note? })` أو
  `handler.resolveApproval({ id, answer })` من الكود تبعك، مثلاً من callback
  زر في الطرف.
- `POST <basePath>/<name>/approvals/<id>` مع `{ approved, note? }` أو
  `{ answer }`. `verify` تبع القناة يشتغل أول؛ ومعرّف القناة ما توقفت عليه
  ياخذ 404.

```ts
import { createAgent, defineChannel, mountChannels } from '@lousho/build-ai-agent';

const agent = createAgent({ instructions: 'You are helpful.', provider, askQuestion: true });

const chat = defineChannel({
  name: 'chat',
  async parse(req) {
    const { room, text } = JSON.parse(req.text) as { room: string; text: string };
    return { sessionKey: room, input: text, replyTo: room };
  },
  async reply({ inbound, text }) {
    console.log(`to room ${String(inbound.replyTo)}: ${text}`);
  },
  async onApproval({ approval }) {
    console.log(`[Approve] [Reject] buttons for ${approval.toolName}, id ${approval.id}`);
  },
});

const channels = mountChannels(agent, [chat]);
// Later, from the button's callback:
await channels.resolveApproval({ id: 'the-approval-id', approved: true });
```

## القنوات الجاهزة

| القناة | الطلب | الرد |
| ------- | ------- | -------- |
| `httpChannel({ name?, verify? })` | JSON `{ sessionKey, input }` (`input` نص أو content parts)؛ أي شيء ثاني 400 | `200 { sessionId, text, finishReason }`؛ ولما يتوقف، `approval` كمان و`text` هو الـ prompt |
| `webhookChannel({ secret?, auth?, name?, principal? })` | نص `input` في جسم JSON، أو الجسم كله؛ session لمرة وحدة إلا لو الجسم فيه `sessionKey` | `200` مع `ExecutionResult` تبع الـ turn، نفس رد `WebhookTriggerAdapter` |
| `slackChannel({ signingSecret, botToken, name?, fetch?, approvers?, onError? })` | طلبات Slack Events API والتفاعلات (راجع [Slack](#slack)) | `200` فورًا؛ الردود تُنشر في الـ thread على Slack |
| `discordChannel({ publicKey, applicationId, botToken?, name?, fetch?, approvers?, onError? })` | تفاعلات slash command والأزرار في Discord (راجع [Discord](#discord)) | ack مؤجّل فورًا؛ الرد يعدّل الرد الأصلي |
| `telegramChannel({ botToken, secretToken, botUsername?, name?, fetch?, approvers?, onError? })` | تحديثات webhook البوت في Telegram: رسائل ونقرات على inline keyboard (راجع [Telegram](#telegram)) | `200` فورًا؛ الردود تُرسل بـ `sendMessage` كنص عادي |
| `githubChannel({ webhookSecret, botName, token?, app?, name?, apiUrl?, fetch?, triggers?, approvers?, onError? })` | تعليقات GitHub على issues وpull requests والـ reviews اللي تذكر `@<botName>` (راجع [GitHub](#github)) | `200` فورًا؛ الردود تُنشر كتعليقات في نفس الـ thread |
| `teamsChannel({ appId, appPassword, tenantId?, name?, fetch?, approvers?, onError? })` | رسائل Microsoft Teams ونقرات أزرار Adaptive Card من Azure Bot (راجع [Microsoft Teams](#microsoft-teams)) | `200` فورًا؛ الردود تُنشر عبر Bot Framework Connector كـ Markdown |

`webhookChannel({ secret })` تفحص توقيع HMAC-SHA256 للجسم الخام في
`x-signature-256: sha256=<hex>`؛ و`auth` ياخذ أي
[مصادقة webhook](/ar/triggers#مصادقة-webhook) (خيارات HMAC مع حماية من
replay، bearer token، أو مخصص). الفحوصات والـ 401 العام هي نفسها اللي
يستخدمها `WebhookTriggerAdapter`. و`principal` هي
`(body, req) => Principal | undefined` تسمّي متصل الـ turn من الطلب اللي
تحقق (نظام التنبيهات اللي أرسل الـ hook، مستخدم تكامل)؛ و`body` هو جسم JSON
بعد الـ parsing، أو `undefined` لو مش JSON.

```ts
import { createAgent, httpChannel, mountChannels, webhookChannel } from '@lousho/build-ai-agent';

const agent = createAgent({ instructions: 'You are helpful.', provider });

const handler = mountChannels(agent, [
  httpChannel({ verify: async (req) => req.headers.authorization === `Bearer ${process.env.API_TOKEN}` }),
  webhookChannel({ secret: process.env.WEBHOOK_SECRET ?? '' }),
]);
```

## داخل agent directory

[agent directory](/ar/agent-directories#channels) يقدر يخزّن قنواته في
`channels/*.ts`، قناة وحدة default-exported في كل ملف. المسار اللي ينخدم هو
`POST /channels/<name>`، و`<name>` هو `name` تبع القناة نفسها؛ واسم الملف
ينطبق بس على export ما له اسم — وكل factory جاهز يضبط اسم
(`webhookChannel()` ← `webhook`، `slackChannel()` ← `slack`، ...)، فملف
`channels/support.ts` اللي يصدّر `webhookChannel()` يُخدَّم على
`/channels/webhook` مش `/channels/support`. `resolveAgentDir()` ترجعهم كـ
`channels`، وسيرفر node اللي `lousho build` يطلعه يركّبهم
(`createDeployedServer(agent, { channels })`، helper داخلي).

## من يقدر يوافق (Slack و Discord)

القناتين تاخذ `approvers`: قائمة بمعرّفات مستخدمي المنصة، أو دالة
`(user: { id, name?, roles? }, { toolName, input, sessionId, principal? }) => boolean | Promise<boolean>`
(Discord يعبّي `roles` بمعرّفات أدوار العضو؛ و`principal` هو المرسل اللي
توقف turnه). المستخدم اللي ينقر ينسجَّل كـ approver (`ctx.approval.by` داخل
الـ tool، راجع [المصادقة](/ar/auth#من-وافق))؛ والـ tool يظل يشتغل لصالح
المرسل. ونقرة من أي شخص ثاني ما تحسم الـ approval: يوصله تنبيه مؤقت "غير
مسموح" والـ approval يظل معلّق.

**ملاحظة أمنية.** بدون `approvers`، بس المستخدم اللي بدأ الـ turn (كاتب
الرسالة على Slack، مستخدم الأمر على Discord) يقدر يوافق. في الإصدارات اللي
قبل كان أي واحد يشوف الرسالة يقدر؛ و`approvers: () => true` ترجع ذاك
السلوك، وما تسوي كذا إلا في قناة خاصة. ودالة `approvers` تشوف الاستدعاء
المعلّق بعد إعادة التشغيل كمان: `ctx.approval(id)` يسأل الـ approval store
الدائم لما هذي العملية مش هي اللي توقفت على المعرّف، فيقرر بنفس الطريقة اللي
قرر فيها قبل. وبس مع approval store محلي للعملية (الافتراضي
`InMemoryApprovalStore` — وقتها أصلاً ما في شيء ينجو من إعادة التشغيل) يفشل
fail-closed. وإجابات `ask_question` غير مقيّدة: الرسالة التالية (Slack) أو
`/ask` (Discord) في المحادثة هي الإجابة. ومين قرر يروح لـ
`mountChannels(agent, channels, { onDecision({ approver, decision, sessionId, channel }) {} })`.
وقناة Telegram تاخذ نفس `approvers` (معرّفات مستخدمي Telegram كنصوص؛
والدالة تاخذ `{ id, name }`، و`name` هو اسم المستخدم أو الاسم الأول).

الأعطال اللي تصير بعد الإقرار تروح لـ `onError` (خيار في القناة، أو في
`mountChannels`)؛ راجع العقد فوق.

## Slack

`slackChannel({ signingSecret, botToken, name?, fetch? })` توصّل تطبيق
Slack. كل thread في Slack هو session وحدة: منشن للبوت يبدأ session الـ
thread (أو يكملها)، ومفتاحها الـ workspace والقناة و`ts` رسالة الجذر؛
والرسائل اللاحقة في thread له session تكملها بدون منشن (الـ session store
ينسأل، فهذا يظل شغال بعد إعادة التشغيل). ورسالة مباشرة للبوت تبدأ session
مفتاحها قناة الـ DM. الردود تُنشر في الـ thread بـ `chat.postMessage`
(`fetch` عادي، بدون Slack SDK؛ مرّر `fetch` عشان تحقن واحد في الاختبارات).

- توقيع كل طلب ينفحص (`v0` HMAC-SHA256 بـ Web Crypto، نافذة replay خمس
  دقائق)؛ والفشل يرد بـ 401.
- الطلب يُرد عليه فورًا (`200`، أو تحدي `url_verification`) والـ turn
  يشتغل بعد الرد، ضمن حد Slack اللي هو 3 ثواني.
- الـ retries (`X-Slack-Retry-Num`) ورسائل البوتات (بما فيها رسائل البوت
  نفسه) ونسخة `message` تبع المنشن: كلها تُقَر وتتجاوز، فما في turn يشتغل
  مرتين.
- approval الـ tool يُنشر في الـ thread مع زرّي **Approve** و**Deny**؛
  والنقرة تستأنف الـ session والمتابعة تُنشر في الـ thread. الرسالة
  المنقورة تُستبدل بالنتيجة ("Approved by @user") فتختفي أزرارها. والنقرة
  تحمل قناتها وthreadها والمستخدم اللي يقدر يقرر، فتشتغل بعد إعادة تشغيل.
  و`ask_question` يُنشر كنص، والرسالة التالية في الـ thread هي الإجابة،
  بعد إعادة تشغيل كمان (انظر تحت).

أعدّ التطبيق في [api.slack.com/apps](https://api.slack.com/apps):

1. **OAuth & Permissions**: scopes البوت `app_mentions:read` و`chat:write`
   و`channels:history` (مع `groups:history` للقنوات الخاصة) للمتابعات بدون
   منشن، و`im:history` للرسائل المباشرة. ثبّت التطبيق وانسخ الـ bot token
   (`xoxb-...`).
2. **Event Subscriptions**: الـ Request URL هو
   `https://<host>/channels/slack`؛ وأحداث البوت `app_mention`
   و`message.channels` (`message.groups` للقنوات الخاصة)، و`message.im`
   للرسائل المباشرة (وفعّل **Messages Tab** في App Home عشان المستخدمين
   يقدرون يراسلون البوت).
3. **Interactivity & Shortcuts**: الـ Request URL هو
   `https://<host>/channels/slack` (نفس المسار).
4. **Basic Information**: انسخ الـ signing secret.

```ts
import * as http from 'node:http';
import { createAgent, mountChannels, slackChannel } from '@lousho/build-ai-agent';

const agent = createAgent({ instructions: 'You are a helpful Slack bot.', provider });

const channels = mountChannels(agent, [
  slackChannel({
    signingSecret: process.env.SLACK_SIGNING_SECRET ?? '',
    botToken: process.env.SLACK_BOT_TOKEN ?? '',
  }),
]);

http.createServer((req, res) => {
  void channels(req, res).then((handled) => handled || res.writeHead(404).end());
}).listen(3000);
```

الـ threads النشطة مصدرها الـ `store` اللي تمرّره لـ `mountChannels()`.
والـ approvals المعلّقة تنحسم من النقرة نفسها. و`ask_question` معلّق ينجو
من إعادة تشغيل لما تكون الـ session والـ checkpoints والـ approvals في
durable stores (مثلاً `mountChannels(agent, channels, { store: sqlite })`
مع `SqliteStore`، و`approvalStore` تبع الـ agent): الرسالة التالية في الـ
thread تظل هي الإجابة، والـ turn يكمل، والسؤال والإجابة والرد ينلحقوا بـ
transcript الـ session. ورسالة في thread الـ session تبعه تنتظر approval
على tool ما تحسمه؛ بس الأزرار تحسمه. ونقرة زر بعد إعادة تشغيل تنربط بـ
session الـ thread أول — لازم النقرة تسمّي thread الـ turn المحفوظ في
checkpoint ينتظر بالضبط ذاك الـ approval — فالمتابعة تنضم لـ transcript الـ
session، ونقرة مُعادة (replay) ما تشغّل الـ tool مرتين، ونقرة في thread
ثاني تُرفض.

## Discord

`discordChannel({ publicKey, applicationId, botToken?, name?, fetch? })`
توصّل تطبيق Discord عبر HTTP Interactions endpoint (بدون اتصال gateway
وبدون مكتبة Discord؛ Web Crypto و`fetch` بس، فتشتغل حتى على Workers). الأمر
المتوقع هو `/ask prompt:<text>`: خيار نصي واحد، وخيار `prompt` (أو أول خيار
نصي) هو الرسالة.

- في كل طلب ينتحقق `X-Signature-Ed25519` / `X-Signature-Timestamp` على
  `timestamp + body`؛ وتوقيع ناقص أو غلط يرد بـ 401، زي ما يشترط Discord.
  و`PING` يُرد عليه بـ `PONG`.
- الأمر يُقَر فورًا برد مؤجّل (ضمن حد Discord اللي هو 3 ثواني)؛ وبعدين
  الرد يعدّل الرد الأصلي
  (`PATCH /webhooks/{applicationId}/{token}/messages/@original`). والنص
  اللي فوق 2000 حرف يكمل في رسائل متابعة.
- الأوامر في نفس القناة تتشارك session وحدة، مفتاحها الـ guild والقناة
  (والـ thread لو الأمر داخل thread).
- approval الـ tool يُنشر مع زرّي **Approve** و**Deny** (بس `approvers` —
  افتراضيًا مستخدم الأمر — يقدرون ينقرونهم)؛ والنقرة تستأنف الـ session
  والمتابعة تجي كرسالة متابعة. والنقرة تحمل المحادثة، فتشتغل بعد إعادة
  تشغيل. و`ask_question` يُنشر كنص، و`/ask` التالي في تلك القناة هو
  الإجابة، بعد إعادة تشغيل كمان (انظر تحت).
- interaction tokens تعيش 15 دقيقة، فرد (أو نقرة) بعدها يفشل. و`botToken`
  محجوز لاستدعاءات REST تبع البوت؛ والردود تحتاج بس الـ interaction token.

أعدّ التطبيق في
[discord.com/developers/applications](https://discord.com/developers/applications):

1. **General Information**: انسخ الـ application id والمفتاح العام.
2. **Interactions Endpoint URL**: `https://<host>/channels/discord`
   (Discord يرسل `PING` موقَّع لما تحفظ).
3. **Installation**: يكفي scope `applications.commands` (أضف `bot` بس لو
   تريد مستخدم البوت في السيرفر).
4. سجّل الأمر مرة وحدة (أمر الـ guild يظهر فورًا؛ استخدم
   `/applications/{id}/commands` لأمر عام):

```sh
curl -X POST "https://discord.com/api/v10/applications/$APP_ID/guilds/$GUILD_ID/commands"   -H "Authorization: Bot $BOT_TOKEN" -H "Content-Type: application/json"   -d '{"name":"ask","description":"Ask the agent","options":[{"type":3,"name":"prompt","description":"Your message","required":true}]}'
```

```ts
import * as http from 'node:http';
import { createAgent, discordChannel, mountChannels } from '@lousho/build-ai-agent';

const agent = createAgent({ instructions: 'You are a helpful Discord bot.', provider });

const channels = mountChannels(agent, [
  discordChannel({
    publicKey: process.env.DISCORD_PUBLIC_KEY ?? '',
    applicationId: process.env.DISCORD_APPLICATION_ID ?? '',
  }),
]);

http.createServer((req, res) => {
  void channels(req, res).then((handled) => handled || res.writeHead(404).end());
}).listen(3000);
```

الـ approvals المعلّقة تنحسم من نقرة الزر والـ approval store. وزي Slack،
`ask_question` معلّق ينجو من إعادة تشغيل لو الـ sessions والـ checkpoints
والـ approvals في durable stores: `/ask` التالي في القناة هو الإجابة والـ
turn المكمل ينضم لـ transcript الـ session. ونقرة زر بعد إعادة تشغيل تسمّي
محادثتها، فتنربط بتلك الـ session قبل ما الـ approval ينحسم — المتابعة تنضم
للـ transcript، ونقرة قديمة أو منسوخة ما تحسم شيء.

ملفات `channels/*.ts` في [agent directory](/ar/agent-directories) تنحمل
كقنوات كمان، وسيرفر node يركّبها. و`SlackTriggerAdapter` (راجع
[Triggers](/ar/triggers))، اللي يرد عبر webhook وارد، deprecated: استخدم
`slackChannel()`. أما `verifySlackSignature()` فمش deprecated.

## Telegram

`telegramChannel({ botToken, secretToken, botUsername?, name?, fetch?, approvers?, onError? })`
تحط agent وراء بوت Telegram عبر webhooks (بدون long polling وبدون مكتبة
Telegram؛ Web Crypto و`fetch` بس، فتشتغل حتى على Workers).

- ترويسة `X-Telegram-Bot-Api-Secret-Token` في كل طلب تنقارن بـ
  `secretToken` في زمن ثابت؛ وقيمة ناقصة أو غلط ترد بـ 401. القناة ما لها
  وضع بدون مصادقة، فمرّر `secret_token` دائمًا لـ `setWebhook`.
- التحديث يُقَر بـ `200` فورًا والـ turn يشتغل بعده، فـ Telegram ما يعيد
  إرسال الـ webhook.
- في المحادثة الخاصة، كل رسالة نصية (أو caption صورة أو مستند) هي رسالة
  للـ agent. وفي مجموعة أو supergroup بس أمر `/ask` (أو
  `/ask@<botUsername>`)، أو رسالة فيها `@<botUsername>`، أو رد على رسالة من
  رسائل البوت نفسه يوقظ البوت؛ والأمر والمنشن ينحذفوا من النص وكل رسالة
  ثانية تتجاهل. ورسائل البوتات تتجاهل. اضبط `botUsername` (بدون `@`) عشان
  تستخدم قواعد المجموعات اللي تحتاجه.
- session وحدة لكل محادثة، ووحدة لكل topic في supergroup منتدى. والردود
  تروح لنفس المحادثة والـ topic، كرد على الرسالة اللي أطلقت الـ turn.
- الردود نص عادي (بدون `parse_mode`)، فالـ Markdown اللي يطلعه الـ model ما
  يقدر يخلّي Telegram يرفض الرسالة. والنص اللي فوق 4096 حرف ينقسم عند فواصل
  الأسطر لعدة رسائل.
- approval الـ tool يُنشر مع inline keyboard فيها **Approve** و**Deny**. بس
  `approvers` (الافتراضي: المستخدم اللي رسالته بدأت الـ turn) يقدرون
  ينقرونهم؛ وغيرهم يوصلهم تنبيه والـ approval يظل معلّق. والنقرة تجاوب الـ
  callback، تعدّل الرسالة فتضيف "Approved by ..." أو "Denied by ..." وتحذف
  لوحة المفاتيح، والمتابعة تُرسل كرسالة جديدة. والنقرة تحمل محادثتها،
  فتشتغل بعد إعادة تشغيل. وTelegram يحد `callback_data` بـ 64 بايت: يحمل
  `a:` أو `d:` ومعرّف مستخدم اللي بدأ ومعرّف الـ approval (حوالي 55 بايت).
  ولو تجاوز 64 بايت، يُحذف معرّف البادئ، ووقتها بس قائمة `approvers` أو دالة
  يقدرون يوافقون (الافتراضي يرفض الكل).
- `ask_question` يُرسل كنص مع `force_reply`، والرسالة التالية في المحادثة
  هي الإجابة (في المجموعة لازم تكون موجّهة للبوت، وهذا اللي يسويه الرد على
  السؤال).
- المرفقات ما تنقرا بعد: بس النص أو الـ caption يوصل للـ agent.

أعدّ البوت عبر [@BotFather](https://t.me/BotFather):

1. أرسل `/newbot`، اختر اسم واسم مستخدم، وانسخ الـ bot token. وللاستخدام في
   المجموعات، `/setprivacy` يحدد إذا البوت يشوف كل رسالة؛ `/ask`
   والمنشنات والردود تشتغل في الحالتين.
2. اختر secret token عشوائي (من 1 لحد 256 حرف من `A-Z` و`a-z` و`0-9` و`_`
   و`-`).
3. سجّل الـ webhook مرة وحدة، الـ bot token في الـ URL والـ secret token في
   الجسم (خلّي الاثنين بعيد عن history الـ shell والسجلات):

```sh
curl -X POST "https://api.telegram.org/bot$TELEGRAM_BOT_TOKEN/setWebhook" -H "Content-Type: application/json" -d '{"url":"https://<host>/channels/telegram","secret_token":"'"$TELEGRAM_SECRET_TOKEN"'","allowed_updates":["message","callback_query"]}'
```

```ts
import * as http from 'node:http';
import { createAgent, mountChannels, telegramChannel } from '@lousho/build-ai-agent';

const agent = createAgent({ instructions: 'You are a helpful Telegram bot.', provider });

const channels = mountChannels(agent, [
  telegramChannel({
    botToken: process.env.TELEGRAM_BOT_TOKEN ?? '',
    secretToken: process.env.TELEGRAM_SECRET_TOKEN ?? '',
    botUsername: 'my_agent_bot',
  }),
]);

http.createServer((req, res) => {
  void channels(req, res).then((handled) => handled || res.writeHead(404).end());
}).listen(3000);
```

الـ bot token جزء من كل URL في Bot API، فالقناة تبني رسائل الخطأ من اسم
الدالة وحالة HTTP بس: الـ token ما يوصل أبدًا لـ `onError` ولا لسطر السجل
الافتراضي.

الـ approvals المعلّقة تنحسم من النقرة والـ approval store. وزي Slack
وDiscord، `ask_question` معلّق ينجو من إعادة تشغيل لو الـ sessions
والـ checkpoints والـ approvals في durable stores: الرسالة التالية في
المحادثة هي الإجابة والـ turn المكمل ينضم لـ transcript الـ session. وزي
نقرة الزر في القنوات الثانية، نقرة بعد إعادة تشغيل تنفحص مقابل الـ turn
المحفوظ في checkpoint تبع session المحادثة، فالمتابعة تنضم للـ transcript
ونقرة مُعادة ما تشغّل الـ tool مرتين.

## GitHub

`githubChannel({ webhookSecret, botName, token?, app?, name?, apiUrl?, fetch?, triggers?, approvers?, onError? })`
تخلّي الناس ينادون agent بـ `@<botName>` في تعليق على issue أو pull request
أو review في GitHub؛ والـ agent يجاوب بتعليق في نفس الـ thread. يقرا webhooks
تطبيق GitHub (أو مستودع واحد) وينشر عبر REST API بـ `fetch` وWeb Crypto بس
(بدون `node:*` import وبدون مكتبة GitHub)، فتشتغل حتى على Workers.

- ترويسة `X-Hub-Signature-256` في كل طلب تنفحص مقابل الجسم الخام بـ
  `webhookSecret` (HMAC-SHA256، مقارنة في زمن ثابت) قبل ما الجسم ينعمل
  parse؛ وتوقيع ناقص أو غلط يرد بـ 401. القناة ما لها وضع بدون مصادقة.
- الـ webhook يُقَر بـ `200` فورًا والـ turn يشتغل بعده: GitHub ينتظر 10
  ثواني وما يعيد المحاولة، والرد البطيء يُنشر كتعليق جديد. و`ping` يُقَر
  بدون turn.
- تعليق على issue، أو على pull request (تبويب المحادثة)، أو review comment
  (على سطر من الـ diff) فيه `@<botName>` ككلمة كاملة (بدون حساسية لحالة
  الحروف) يبدأ turn، والمنشن ينحذف من النص. وأول ما يصير للـ thread session،
  كل تعليق لاحق فيه يُعد متابعة وما يحتاج منشن. وتتجاهل التعليقات المعدّلة
  والمحذوفة، وتعليقات البوتات (`user.type` هو `Bot`)، وتعليقات
  `<botName>[bot]`، وتعليقات `botLogin`، وأي تعليق نشرته القناة نفسها — فالـ
  agent ما يجاوب نفسه أبدًا. والأحداث الثانية (فتح issues، pushes،
  reactions، check runs) تتجاهل.
- session وحدة لكل issue أو pull request (`<owner>/<repo>#<number>`)،
  ووحدة لكل review thread (review comment والردود تحته).
- الرد تعليق جديد: تعليق في timeline الـ issue أو الـ pull request، أو رد في
  الـ review thread. والنص اللي فوق 60,000 حرف (حد GitHub هو 65,536) ينقسم
  عند فواصل الأسطر لعدة تعليقات. وكل تعليق يحمل علامة مخفية (تعليق HTML)
  تعرفها القناة.
- approval الـ tool هو تعليق فيه الـ tool ووسائطها في fenced block وسطر
  "Reply `/approve <id>` or `/deny <id>`.". تعليق **سطره الأول** هو
  `/approve <id>` أو `/deny <id>` (بأي حالة حروف) يحسمها؛ واللي بعد السطر
  الأول ملاحظة للـ model. واقتباس الـ prompt، أو الأمر في أي مكان غير السطر
  الأول، ما يحسم شيء. القناة تجاوب "Approved by @login." أو "Denied by
  @login." والـ run يكمل بتعليق جديد. والمعرّف هو معرّف الـ approval
  المعلّق، فأمر قديم (webhook أعيد تسليمه، أو تعليق approval انحسم قبل) ما
  يقدر يحسم approval لاحق.
- `ask_question` يُنشر كتعليق والتعليق التالي في ذاك الـ thread هو الإجابة
  (بدون منشن، من أي واحد `triggers` تسمح له). وسؤال معلّق ينجو من إعادة
  تشغيل لو الـ sessions والـ checkpoints والـ approvals في durable stores،
  زي Slack وDiscord؛ والثمن lookup واحد في الـ store لكل تعليق مش منشن في
  thread ما له session.

**ملاحظة أمنية.** تعليق GitHub نص يكتبه أي واحد يقدر يعلّق على المستودع،
وفي مستودع عام يعني الكل. يعني هو إدخال مش موثوق للـ agent، زي أي رسالة
مستخدم، ويقدر يحاول يوجّهه (prompt injection)؛ ونص الـ issue والـ pull
request اللي يشير له مش موثوق بنفس القدر. عطِ الـ agent بس tools اللي تقبل
أسوأ استخدام لها، وخلّي `needsApproval` على اللي تكتب أو تصرف. في خيارين
يحددون مين الموثوق، والاثنين صريحين:

- `triggers` (الافتراضي: كل اللي يقدرون يعلّقون) يحدد مين يقدر يبدأ turn أو
  يجاوب على سؤال: قائمة logins، أو دالة
  `({ login, association }) => boolean`. وفي مستودع عام قيّده (مثلاً لـ
  `association` من `OWNER` أو `MEMBER` أو `COLLABORATOR`) إلا لو تريد
  الغرباء يصرفون رصيد الـ models تبعك.
- `approvers` يحدد مين يقدر `/approve` و`/deny`، و**افتراضه مغلق**: بدونه
  بس معلّق `author_association` تبعه `OWNER` أو `MEMBER` أو `COLLABORATOR`
  يقدر يقرر. وهذا يختلف عن Slack وDiscord بقصد: thread GitHub مرئي لكل واحد
  يقدر يقرا المستودع، واللي بدأ الـ turn ممكن يكون أي واحد، فكاتب الطلب مش
  موثوق يوافق عليه. والأمر المرفوض يوصله "@login is not allowed to
  approve this request." والـ approval يظل معلّق. ومع قائمة logins (بدون
  حساسية لحالة الحروف) بس أولئك المستخدمين يقررون، مهما كانت الـ association
  تبعهم. ومع دالة `(user, { toolName, input, sessionId }) => boolean`،
  `user.id` هو الـ login و`user.roles` هو `[author_association]`.

الـ association تُقرأ من webhook تعليق الأمر نفسه، فالقرار مبني على اللي
أبلغ عنه GitHub لما انكتب ذاك التعليق (الطلب أصلي بفضل التوقيع)، مش على
العضوية اللي كانت للمعلّق لما انطلب الـ approval: متعاون انحذف قبل ما ينشر
`/approve` ينرفض. وهي snapshot تُخذ عند الأمر، مش فحص صلاحية حي؛ فلو لازم
سحب الصلاحية يسري داخل تلك النافذة، استخدم `approvers` بدالة تسأل GitHub API
(مثلاً صلاحية المتعاون) قبل ما ترجع `true`. ودالة `approvers`، زي القنوات
الثانية، تشوف الاستدعاء المعلّق بعد إعادة تشغيل كمان (الـ approval store
الدائم ينسأل)، وتفشل fail-closed بس مع approval store محلي للعملية.

أعدّ تطبيق GitHub:

1. أنشئ التطبيق (Settings ← Developer settings ← GitHub Apps ← New GitHub
   App). وتحت Webhook، اضبط الـ URL على `https://<host>/channels/github`،
   خلّيه مفعّل، واختر secret عشوائي طويل (هذا هو `webhookSecret`).
2. الصلاحيات: Issues قراءة وكتابة، وPull requests قراءة وكتابة. واشترك في
   **Issue comment** و**Pull request review comment**.
3. ولّد private key (GitHub ينزّله كـ PKCS#1 PEM، `BEGIN RSA PRIVATE KEY`؛
   وPKCS#8 يشتغل كمان) ودوّن الـ App ID. ثبّت التطبيق على المستودعات اللي
   لازم يجاوب فيها. كل webhook يسمّي الـ installation تبعه، والقناة تبدل JWT
   موقَّع بـ installation token لكل واحد وتخزّنه مؤقت لحد 5 دقائق قبل ما
   تنتهي صلاحيته.
4. `botName` هو الـ slug تبع التطبيق: `@my-agent` في تعليق ينشن التطبيق
   `my-agent`، اللي ينشر باسم `my-agent[bot]`.

لمستودع واحد تقدر تتخطى التطبيق: أضف webhook للمستودع (content type
`application/json`، نفس الحدثين، نفس الـ URL والـ secret) ومرّر `token` —
fine-grained personal access token بقراءة وكتابة على Issues وPull requests
في ذاك المستودع (أو دالة ترجع token). والردود وقتها تُنشر باسم مستخدم الـ
token، فمرّر كمان `botLogin` بـ login ذاك المستخدم. وبدونه، بس العلامة
المخفية تبع القناة تمنع الـ agent من الإجابة على تعليقاته.

```ts
import * as http from 'node:http';
import { createAgent, githubChannel, mountChannels } from '@lousho/build-ai-agent';

const agent = createAgent({ instructions: 'You answer questions about this repository.', provider });

const channels = mountChannels(agent, [
  githubChannel({
    webhookSecret: process.env.GITHUB_WEBHOOK_SECRET ?? '',
    botName: 'my-agent',
    app: { appId: process.env.GITHUB_APP_ID ?? '', privateKey: process.env.GITHUB_APP_PRIVATE_KEY ?? '' },
    triggers: ({ association }) => ['OWNER', 'MEMBER', 'COLLABORATOR'].includes(association),
  }),
]);

http.createServer((req, res) => {
  void channels(req, res).then((handled) => handled || res.writeHead(404).end());
}).listen(3000);
```

`apiUrl` يوجّه القناة لـ GitHub Enterprise Server
(`https://<host>/api/v3`). والـ token والـ private key والـ JWT ما ينحطّ
أبدًا في رسالة خطأ أو سطر سجل: استدعاء فاشل يُبلَّغ عنه لـ `onError`
بالاستدعاء وحالة HTTP بس (`LOUSHO_CHANNEL_REQUEST_FAILED`).

الـ approvals المعلّقة تنحسم من تعليق الأمر والـ approval store.
و`ask_question` معلّق ينحفظ في الذاكرة لحد التعليق التالي، وينجو من إعادة
تشغيل لو الـ stores durable، زي القنوات الثانية. وبعد إعادة تشغيل، الأمر
يسمّي threadه، فمع durable checkpoints ينربط بـ session ذاك الـ thread قبل
ما الـ approval ينحسم: المتابعة تنضم لـ transcript الـ session، ومعرّف الـ
thread ما تنتظره (انحسم خلاص، أو approval لـ thread ثاني) يفشل بتعليق
"Sorry, that request failed." العام.

## Microsoft Teams

`teamsChannel({ appId, appPassword, tenantId?, name?, fetch?, approvers?, onError? })`
تحط agent وراء Azure Bot في Microsoft Teams: المحادثات الشخصية والمنشنات في
القنوات تبدأ session أو تكملها، والردود ترجع عبر Bot Framework Connector،
وapproval الـ tool بطاقة Adaptive Card فيها زرّي Approve وDeny. تستخدم
`fetch` وWeb Crypto بس (بدون `node:*` import وبدون مكتبة Bot Framework)،
فتشتغل حتى على Workers.

- كل طلب لازم يحمل Bot Framework token في `Authorization: Bearer`. ينتحقق
  قبل parsing الجسم: توقيع RS256 ينفحص مقابل مجموعة المفاتيح اللي تشير لها
  بيانات OpenID الثابتة تبع Bot Framework
  (`https://login.botframework.com/v1/.well-known/openidconfiguration`)
  (مخزّنة مؤقت، وأبدًا ما تؤخذ من URL داخل الـ token)، والـ issuer
  `https://api.botframework.com`، والـ audience `appId`، وتسامح انحراف ساعة
  5 دقائق. ومطالبة `serviceurl` في الـ token لازم تساوي `serviceUrl` في الـ
  activity كمان، فـ token صالح لعنوان خدمة واحد ما ينعاد استخدامه عشان البوت
  ينشر في مكان ثاني. وأي فشل يرد بـ 401. القناة ما لها وضع بدون مصادقة،
  ومُحاكي Bot Framework بدون مصادقة مش مدعوم.
- الـ activity يُقَر بـ `200` فورًا والـ turn يشتغل بعده. بس activities من
  نوع `message` توصل للـ agent؛ `conversationUpdate` و`typing` و`invoke`
  ورسائل البوت نفسه تتجاهل.
- المحادثة الشخصية تبدأ session أو تكملها دائمًا. وفي محادثة جماعية أو قناة
  بس رسالة تسوي `@mention` للبوت تسوي كذا؛ والمنشن ينحذف من النص وكل رسالة
  ثانية تتجاهل.
- session وحدة لكل محادثة (`conversation.id`؛ وفي قناة Teams يشمل رسالة
  جذر الـ thread، فكل thread session مستقلة). والمرسل (`from.aadObjectId`،
  وإلا `from.id`) هو `principal` تبع الـ run (`authenticator: 'teams'`،
  `issuer`: الـ tenant)، زي القنوات الثانية.
- الردود Markdown تُنشر على
  `{serviceUrl}/v3/conversations/{id}/activities/{replyToId}`، بـ
  `serviceUrl` اللي ضمنه الـ token (`https` بس). والنص اللي فوق 25,000 حرف
  ينقسم عند فواصل الأسطر. والـ access token الصادر يجي من تدفق
  client-credentials بـ `appId` و`appPassword` ويُخزَّن مؤقت لحد 5 دقائق
  قبل انتهائه.
- approval الـ tool بطاقة Adaptive Card (الإصدار 1.4) فيها الـ tool
  ووسائطها (تنقطع عند 2,000 حرف) وزرّي `Action.Submit`. بس `approvers`
  (معرّفات مستخدمي Teams زي `from.id`، أو دالة) يقدرون يستخدمونهم؛
  افتراضيًا بس المستخدم اللي بدأ الـ turn. وأي واحد ثاني يوصله "You are not
  allowed to approve this request." والـ approval يظل معلّق. والنقرة تستبدل
  البطاقة بـ "Approved by &lt;name>." أو "Denied by &lt;name>." (بدون
  أزرار) والـ run يكمل برسالة جديدة. والزر يحمل المحادثة اللي اننشر فيها،
  ونقرة محادثتها مختلفة (مرجع منسوخ) ما تحسم شيء؛ ومعرّف الـ approval هو
  معرّف المعلّق، فبطاقة قديمة ما تقدر تحسم approval لاحق، وبطاقة مستخدمة
  خلاص ما تسوي شيء، حتى بعد إعادة تشغيل.
- `ask_question` يُنشر كنص والرسالة التالية في المحادثة هي الإجابة. وسؤال
  معلّق ينجو من إعادة تشغيل لو الـ sessions والـ checkpoints والـ approvals
  في durable stores، زي Slack وDiscord.

أعدّ البوت:

1. أنشئ Azure Bot (single-tenant أو multi-tenant) ودوّن الـ Microsoft App
   ID (`appId`). وتحت Configuration، اضبط الـ messaging endpoint على
   `https://<host>/channels/teams`.
2. وتحت Manage Password، أنشئ client secret (`appPassword`). ولبوت
   single-tenant مرّر كمان `tenantId` (وقتها الـ secret يُطلب من الـ tenant
   تبعك).
3. وتحت Channels، فعّل Microsoft Teams.
4. أنشئ manifest لتطبيق Teams يكون مدخل `bots` فيه `botId` مساوي للـ App ID
   مع الـ scopes اللي تريدها (`personal` و`team` و`groupChat`)، وثبّته.

```ts
import * as http from 'node:http';
import { createAgent, mountChannels, teamsChannel } from '@lousho/build-ai-agent';

const agent = createAgent({ instructions: 'You help the team with questions.', provider });

const channels = mountChannels(agent, [
  teamsChannel({
    appId: process.env.MICROSOFT_APP_ID ?? '',
    appPassword: process.env.MICROSOFT_APP_PASSWORD ?? '',
    tenantId: process.env.MICROSOFT_TENANT_ID,
  }),
]);

http.createServer((req, res) => {
  void channels(req, res).then((handled) => handled || res.writeHead(404).end());
}).listen(3000);
```

لا الـ app password ولا الـ access token ينحطّ في رسالة خطأ أو سطر سجل:
استدعاء فاشل يُبلَّغ عنه لـ `onError` بالاستدعاء وحالة HTTP بس
(`LOUSHO_CHANNEL_REQUEST_FAILED`). ونقرة على بطاقة تشتغل على عملية معاد
تشغيلها، لأنها تسمّي المحادثة والـ approval نفسه؛ ومع durable checkpoints
النقرة تنربط بـ turn الـ session المعلّق أول، فالمتابعة تنضم لـ transcript
الـ session ونقرة الـ session ما تنتظرها ما تحسم شيء.
