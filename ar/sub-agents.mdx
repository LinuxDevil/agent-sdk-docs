الـsub-agent (وكيل فرعي) هو agent مستقل — تعليمات وmodel وtools وskills
خاصة فيه — الـlead (الوكيل الرئيسي) يسلّمه مهمة مكتفية بحالها.
يبدأ بسياق نظيف: يشوف بس الـprompt اللي إنت تعطيه إياه، ومحادثة الـlead
ما يشوفها أبدًا. يشتغل بالخطوات اللي يحتاجها، وجوابه النهائي يرجع
للـlead كنتيجة tool واحدة.

## Sub-agent ولا skill ولا flow؟

| استعمل | لما |
| --- | --- |
| **Skills** ([docs](/ar/skills)) | الـagent *نفسه* يحتاج تعليمات زيادة لبعض المهام. رخيصة: الـskill نص ينضاف للمحادثة الحالية. |
| **Sub-agents** | المهمة تحتاج tools مختلفة، أو model مختلف، أو استكشاف طويل مليان tool calls ما تريده في سياق الـlead. الـlead يقرر وقت الـrun إذا يفوّض وماذا يفوّض؛ والمهام المستقلة تشتغل بالتوازي. |
| **Handoffs** ([docs](/ar/handoffs)) | agent ثاني يتولى المحادثة ويرد على المستخدم بنفسه (فرز على متخصص)، بدل ما يرجع نتيجة للـlead. |
| **Flows** | الخطوات وترتيبها معروفة من الأول (pipeline)، فما ينفع تتركها لتقدير الـmodel. |

## بداية سريعة

أعطِ كل sub-agent حقل `description` (model الـlead يقرأه حتى يختار)،
وبعدين مرّرهم للـlead تحت `subagents`:

```ts
import { createAgent } from '@lousho/build-ai-agent';

const researcher = createAgent({
  provider,
  instructions: 'You research a question and report your sources.',
  description: 'Finds and summarizes sources',
});
const writer = createAgent({
  provider,
  instructions: 'You write clear, short articles.',
  description: 'Turns notes into a polished article',
});

const lead = createAgent({
  provider,
  instructions: 'You coordinate research and writing.',
  subagents: { researcher, writer },
});

const { text } = await lead.send('Write a short article about the history of the bicycle.');
```

`AgentExecutor.execute()` ياخذ نفس خيارات `subagents` و`maxSubagentDepth`.
استخدمه لما تحتاج hooks أو tracing على run الـlead — الـsub-agents يرثونهم
(راجع [ما يرثه الـsub-agent](#what-a-sub-agent-inherits)). والـapprovals (الموافقات) تشتغل
من `createAgent()` كمان (راجع [Approvals](#approvals-inside-a-sub-agent)).

## كيف يشتغل

مع `subagents`، الـlead ياخذ:

1. بلوك **Available sub-agents** في الـsystem prompt: سطر لكل
   sub-agent (`- name: description`)، وجملة تقول إن الـsub-agent
   يشوف بس الـprompt اللي يستلمه.
2. tool وحدة بس، `task`، إدخالها
   `{ agent: <one of the names>, prompt: string, description: string, background?: boolean, taskId?: string, mode?: 'new' | 'resume' | 'fork' }`
   (`description` اسم مختصر من 3 إلى 5 كلمات يُستخدم في الـevents والـhooks؛
   و`taskId` و`mode` يكملون مهمة سابقة، راجع [تكملة مهمة](#تكملة-مهمة)).
3. ثلاث tools للمهام الخلفية: `agent_status` و`agent_await` و`agent_cancel`
   (راجع [Sub-agents في الخلفية](#sub-agents-في-الخلفية)).

لما الـlead يستدعي `task`، الـsub-agent المسمّى يشتغل على `prompt` وحده.
نتيجة الـtool هي النص النهائي للـsub-agent، ومعها سطر footer صغير يقدر
الـlead يستفيد منه:

```text
The first bicycles appeared in the 1810s ...

[sub-agent 'researcher': 3 step(s), finish reason 'stop', taskId 'task_1']
```

إذا الـsub-agent ما خلّص — رمى خطأ، أو استهلك كل `maxSteps`، أو انقطع —
الـlead ياخذ نتيجة خطأ (`isError: true`) تشرح السبب، مثل
`Sub-agent 'researcher' used all 10 of its steps (maxSteps) without
giving a final answer.` واسم agent مجهول كمان يرجع نتيجة خطأ تعدّد
الأسماء الصحيحة. استهلاك الـsub-agent من الـtokens ينضاف لـ`result.usage`
الخاصة بالـlead، واستهلاك الـ[remote sub-agent](#remote-sub-agents) كمان.

أخطاء الإعداد تُرمى ومعها طريقة الحل: sub-agent بدون `description`،
أو قيمة ليست agent من `createAgent()`، أو tool من عندك اسمها أصلًا
`task` (أو `agent_status` أو `agent_await` أو `agent_cancel`).

## تكملة مهمة

كل استدعاء `task` يشتغل في محادثة فرعية لها `taskId` (`task_1`،
`task_2`، ... في الـfooter). والـlead يقدر يرجع لها:

| إدخال `task` | اللي يشتغل |
| --- | --- |
| بدون `taskId` (`mode: 'new'`) | sub-agent جديد، مثل فوق، بـ`taskId` جديد. |
| `taskId` (`mode: 'resume'`، الافتراضي مع `taskId`) | نفس الـsub-agent مع كامل الـtranscript الخاص فيه (الـprompts السابقة والـtool calls والإجابات)، و`prompt` يدخل كدور مستخدم جديد. النتيجة تحتفظ بنفس الـ`taskId`. |
| `taskId` مع `mode: 'fork'` | مهمة جديدة (`taskId` جديد) تبدأ من نسخة من ذلك الـtranscript. المهمة الأصلية تبقى مثل ما هي وتقدر تستأنفها بعدين. |

الـmodel يعرف هذا من وصف الـtool `task` نفسه، فسؤال المتابعة ما يحتاج
أي كود. لكن lead يحتفظ بشغله عبر الدورات أو إعادات التشغيل يحتاج
store وsession (جلسة):

```ts
import { createAgent } from '@lousho/build-ai-agent';
import { SqliteStore } from '@lousho/build-ai-agent/sqlite';

const store = new SqliteStore('./.lousho/agent.db');
const researcher = createAgent({ provider, instructions: 'You research.', description: 'Finds and summarizes sources' });
const lead = createAgent({ provider, instructions: 'You coordinate research.', store, subagents: { researcher } });

const chat = lead.session({ id: 'user-42' });
await chat.send('Research the history of the bicycle.'); // the lead calls task -> taskId 'task_1'
await chat.send('Ask the researcher which source it trusted most.'); // the lead calls task({ taskId: 'task_1', ... })
```

أين تتخزن المحادثات:

- مع `createAgent({ store })` (`store.sessions`) وrun للـlead له
  `sessionId` (سواء `send(message, { sessionId })` مع checkpoints أو دور
  في session)، كل مهمة تتحفظ في `store.sessions` بعد ما يخلص run المهمة،
  تحت مفتاح مُهشّم (hashed) من معرّف session الـlead ومن `taskId`.
  وهي تعيش أطول من run الـlead: الدورات اللاحقة في نفس الـsession، وlead
  مُستأنف بـ`agent.resume()` أو `approvals.resolve()`، وprocess جديدة على
  نفس الـdurable store (مخزن يبقى بعد إعادة تشغيل الـprocess) — كلهم
  يقدرون يكملونها. `taskId` من session لـlead
  ثاني ما يطابق أبدًا. الـsession store ما فيه list API، فالمدخلات هذه ما
  تنسرد ولا تنحذف مع session الـlead؛ احذف بيانات الـstore لتتخلص منها.
  ومع `AgentExecutor.execute()` عيّن الـstore بـ
  `withSubagentOptions(subagents, { sessions })`.
- في باقي الحالات (ما فيه session store، أو run للـlead بدون
  `sessionId`)، المهمة تعيش بالذاكرة لذلك الاستدعاء الواحد لـ`execute()` /
  `send()`: run يوقف على approval ويُستأنف يبدأ بدون أي مهمة. الـsub-agent
  اللي الـapproval نفسها تستأنفه يظل يرد على الـlead (كنتيجة `task` أو
  `agent_await`)، لكن ما تقدر تكمله بـ`taskId` بعدها؛ استخدم session store
  لهذا.

بس المهام اللي خلصت (`stop` أو `length` أو `max-steps`) هي اللي تتحفظ،
فالمهمة اللي فشلت أو انلغت ما تقدر تكملها. والأخطاء توصل للـlead كـ
tool errors منظمة: `taskId` مجهول، أو تابع لـsession لـlead ثاني، أو تابع
لـsub-agent ثاني، يفشل بـ`LOUSHO_SUBAGENT_TASK_NOT_FOUND`؛ ومهمة ما زالت
شغالة (مهمة background ما خلصت) تفشل بـ`LOUSHO_SUBAGENT_TASK_BUSY`، وتقول
للـmodel يستدعي `agent_await` أو `agent_cancel` عليها قبل.

المهمة المستأنفة أو المفروعة (forked) هي استدعاء `task` عادي في الباقي:
تقدر تشغلها بالخلفية (وتحتفظ بنفس الـ`taskId`)، والـapproval داخلها توقف
الـlead وتستأنفه مثل أي approval لـsub-agent، واستهلاكها ينحسب ضمن
`usage` و`limits` الخاصة بالـlead. والـsub-agent يشوف كامل الـtranscript
من جديد مع كل resume، فالمهمة طويلة العمر تكلّف tokens أكثر كل مرة.

## مهام بالتوازي

الـtool calls في دور model واحد تشتغل مع بعض (راجع `toolConcurrency`)،
فلما الـlead يستدعي `task` أكثر من مرة في دور واحد، الـsub-agents
يشتغلون بالتوازي. النتائج توصل لـtranscript الـlead بنفس الترتيب اللي
الـmodel سوّى فيه الاستدعاءات. حط سقف بـ`toolConcurrency` على الـlead
(`1` يشغلهم واحد واحد).

## Sub-agents في الخلفية

مع `background: true`، `task` يبدأ الـsub-agent ويرجع فورًا بـ
`{ taskId, status: 'running', agent }`، فالـlead يقدر يكمل شغله (أو يبدأ
مهام ثانية) وهو شغال. بعدها الـlead يستخدم:

| الـtool | الإدخال | النتيجة |
| --- | --- | --- |
| `agent_status` | `{ taskId? }` | `{ tasks: [{ taskId, agent, status, elapsedMs, approvalId?, toolName?, error? }] }` لمهمة وحدة أو لكل المهام. `status` تكون `queued` أو `running` أو `done` أو `failed` أو `cancelled` أو `awaiting-approval`. |
| `agent_await` | `{ taskId }` أو `{ taskIds }`، و`timeoutMs` اختياري | تنتظر انتهاء المهمة أو المهام. مهمة `done` تحمل `result`: نفس النص (مع الـfooter) اللي ترجعه `task` متزامنة. مهمة `failed` تحمل `error`. مهمة ما زالت شغالة بعد `timeoutMs` ترجع `status: 'timeout'`. ومع `taskIds` النتيجة `{ tasks: [...] }`. |
| `agent_cancel` | `{ taskId }` | تلغي مهمة queued أو شغالة (run الخاص فيها ينقطع) وترجع حالتها. |

بحد أقصى `maxConcurrent` sub-agent خلفي لكل run للـlead يشتغلون بنفس
الوقت (الافتراضي 3)؛ الاستدعاءات الزيادة بـ`background: true` تاخذ
`status: 'queued'` وتبدأ لما تفضى الأماكن. عيّنها بـ`subagentOptions`
في `createAgent()`:

```ts
import { createAgent } from '@lousho/build-ai-agent';

const researcher = createAgent({ provider, instructions: 'You research.', description: 'Finds and summarizes sources' });

const lead = createAgent({
  provider,
  instructions: 'You coordinate research.',
  subagents: { researcher },
  subagentOptions: { maxConcurrent: 2, awaitBackgroundOnFinish: true },
});
```

مع `AgentExecutor.execute()`، ألحق نفس الخيارات بقيمة `subagents`
بـ`withSubagentOptions(subagents, options)` اللي ترجعها. وفي `createAgent()`
تتقدّم `subagentOptions` على الخيارات الملحقة بهذه الطريقة.

الـsub-agent الخلفي يرث من run الـlead مثل المتزامن (hooks وtracing
وevent listeners وتجميع الاستهلاك)، و`maxSubagentDepth` ينطبق نفس الشي.
إيقاف signal الـlead يلغي الـsub-agents الخلفيين، سواء كانوا queued أو
شغالين.

### When the lead run ends

المهام الخلفية تتبع run واحد (استدعاء واحد `execute()` / `send()` /
`stream()`). لما الـrun يخلص، مهما كانت طريقة انتهائه، المهام اللي ما
زالت queued أو شغالة **تنلغي** افتراضيًا (runs الخاصة فيها تنقطع). مع
`awaitBackgroundOnFinish: true` الـrun بالمقابل ينتظر انتهاءها قبل ما
يكتمل (run lead منقطع أو فاشل يلغيها كمان). بالحالتين الـrun ما يكتمل إلا
بعد ما تتوقف الـruns الخاصة فيها، فما يوصل أي event لـsub-agent لمستمعي
الـrun بعدها؛ ومع `awaitBackgroundOnFinish` توصل events الخاصة فيهم قبل
`run.done` الخاص بالـlead.

النتيجة تعدّد كل مهمة خلفية في الـrun مع حالتها النهائية:

```ts
import { createAgent } from '@lousho/build-ai-agent';

const researcher = createAgent({ provider, instructions: 'You research.', description: 'Finds and summarizes sources' });
const lead = createAgent({ provider, instructions: 'You coordinate research.', subagents: { researcher } });

const result = await lead.send('Research three topics in the background.');
for (const task of result.backgroundTasks ?? []) {
  console.log(task.taskId, task.agent, task.status); // e.g. task_1 researcher cancelled
}
```

`result.backgroundTasks` تحمل `{ taskId, agent, status, elapsedMs, error?,
approvalId?, toolName? }` لكل مهمة (نفس شكل `agent_status`) وتغيب لما
الـrun ما بدأ ولا مهمة خلفية. استخدم `agent_await` في الـlead (الـsystem
prompt يطلب منه هذا) حتى توصل إجاباتهم للمحادثة.

الـhook الخاص بالـexecutor اللي وراء هذا public: `ExecuteOptions.onRunEnd`
يُستدعى مرة وحدة بالضبط لكل run، مع `{ result }` (أيًا كان `finishReason`)
أو `{ error }`؛ والـrun ينحسم بعد ما يرجع. والمهام الخلفية تتسجل في
`result` قبل ما `onRunEnd` الخاص فيك يشوفه.

القيود:

- run الـlead اللي يوقف على approval (`finishReason: 'awaiting-approval'`)
  يخلص هناك: مهامه الخلفية اللي ما زالت queued أو شغالة تنلغي (أو يُنتظر
  انتهاؤها) مثل أي نهاية ثانية، والـrun المستأنف يبدأ بدون أي مهمة.
  الـrun المستأنف run مستقل لا صلة له بمهام الـrun الموقوف (يمكن حتى
  يشتغل في process ثانية)، فما ممكن يخليهم أحياء عبر الوقفة.
- sub-agent خلفي يحتاج approval يوقف بـ`status: 'awaiting-approval'`
  (مع `approvalId` و`toolName` الخاصين بالـchild)؛ استدعاؤه ما اشتغل بعد.
  وما يكمل إلا لما الـlead ينتظره بـ`agent_await` (وصف `task` و
  `agent_status` يقولان للـmodel هذا). وقتها **الـlead يوقف** على تلك
  الـapproval، مثل sub-agent متزامن: نتيجة الـlead فيها
  `finishReason: 'awaiting-approval'`، والـapproval المعلقة تسمي استدعاء
  الـchild بـ`subagentPath: ['<agent>']`، وتنسرد في
  `agent.approvals.list()`. و`approvals.resolve()` (أو `resume()` بعد إعادة
  تشغيل، مع durable store) ينفذ أو يرفض استدعاء الـchild، ويخليه يكمل،
  والـlead المكمّل ياخذ جواب الـchild كنتيجة `agent_await`
  (`status: 'done'` مع `result`، أو `'failed'`). استهلاك الـchild ينضاف
  لاستهلاك الـlead، ومحادثته تتحفظ تحت `taskId` مثل أي مهمة، فـ
  `task({ taskId })` يقدر يكملها.
- إذا الـchild وقف مرة ثانية، الـlead يوقف مرة ثانية على الـapproval
  التالية. وإذا استدعاء `agent_await` واحد ينتظر عدة مهام كلها موقوفة،
  الـlead يوقف عليهم واحد بعد الثاني، وبعدين ذلك الاستدعاء يرجع كل
  الإجابات دفعة وحدة.
- مهمة ما زالت `awaiting-approval` لما الـlead يخلص بدون ما ينتظرها
  تتسجل في `result.backgroundTasks` بنفس الحالة وما تقدر تستأنفها:
  الـmodel اختار ما ينتظرها.

```ts
import { createAgent, defineTool } from '@lousho/build-ai-agent';
import { z } from 'zod';

const shell = defineTool({
  name: 'shell',
  description: 'Runs a shell command',
  input: z.object({ cmd: z.string() }),
  needsApproval: true,
  execute: async ({ cmd }) => `ran ${cmd}`,
});
const coder = createAgent({ provider, instructions: 'You code.', tools: [shell], description: 'Fixes code' });
const lead = createAgent({ provider, instructions: 'You lead.', subagents: { coder } });

// The lead starts `coder` with task({ background: true }), then calls agent_await on it.
const paused = await lead.send('Fix the failing test in the background, then report.');
if (paused.finishReason === 'awaiting-approval' && paused.approvalId) {
  const [pending] = await lead.approvals.list(); // { toolName: 'shell', args: { cmd: ... }, subagentPath: ['coder'] }
  console.log(pending?.toolName, pending?.args);
  const result = await lead.approvals.resolve({ id: paused.approvalId, approved: true });
  console.log(result.text); // agent_await returned the coder's answer to the lead
}
```

## Dynamic catalogs

بدل record ثابت، مرّر catalog فيه `list()` و`resolve(name)`.
`list()` تُستدعى في بداية كل run يعرض الـtool `task`، فالمجموعة تقدر
تتغير بين run وrun؛ و`resolve()` تُستدعى لما الـlead يختار اسم (رجّع
`undefined` للاسم المجهول).

```ts
import { createAgent, type SubagentCatalog } from '@lousho/build-ai-agent';

const experts = new Map([
  ['researcher', createAgent({ provider, instructions: 'You research.' })],
]);

const catalog: SubagentCatalog = {
  list: async () => [{ name: 'researcher', description: 'Finds and summarizes sources' }],
  resolve: async (name) => experts.get(name),
};

const lead = createAgent({ provider, instructions: 'You coordinate.', subagents: catalog });
```

## Remote sub-agents

`remoteAgent()` يستخدم agent إنت منشره أصلًا (`lousho build
--target=node-server` أو `docker` أو `cloudflare-worker`) كـsub-agent.
يتحط في `subagents` جنب المحليين، والـlead يفوّض له بنفس الـtool
`task`، بما فيها `background: true`.

```ts
import { createAgent, remoteAgent } from '@lousho/build-ai-agent';

const lead = createAgent({
  provider,
  instructions: 'You coordinate.',
  subagents: {
    researcher: remoteAgent({
      url: 'https://researcher.example.workers.dev',
      auth: process.env.RESEARCHER_TOKEN, // the deployment's LOUSHO_API_TOKEN; or () => string | Promise<string>
      description: 'Finds and summarizes sources',
    }),
  },
});
```

كل مهمة تفتح session جديدة على الـagent البعيد (`POST <url>/chat` مع
`{ sessionId, input }`، وتُقرأ كـstream أحداث SSE، راجع
[النشر](/ar/deployment#http-api))، ترسل prompt المهمة وترجع النص
النهائي للـagent البعيد (أو الكائن كـJSON لما يكون للـagent المنشور
`output` schema، راجع [المخرجات المنظمة](/ar/structured-output))، ووراها
footer يسمي الـsession والـ`taskId`. استدعاء `task` اللي يستأنف ذلك
الـ`taskId` يرسل لنفس الـsession البعيدة، فيكمل الـagent البعيد بالـhistory
الخاص فيه (خلّيه في store على الطرف البعيد)؛ ومهمة بعيدة ما تقدر تعملها
fork. الـagent البعيد يشوف بس ذلك الـprompt، ويشتغل بالـmodel والـtools
والـlimits الخاصة فيه، فـruntime الـlead (hooks وsandbox وapproval store)
ما توصله. وإشارة إيقاف run الـlead توقف الطلب. الخيارات: `url` و`auth`
و`name` و`description` و`headers` و`fetch` (احقن `fetch` خاصة فيك في
الاختبارات؛ agent شغال في نفس الـprocess ورا
`createRouteHandler(agent, { basePath: '/' }).handler` — الـFetch handler
المصدَّر، راجع [النشر](/ar/deployment#http-api) — يشتغل كـfake
deployment: `fetch: (input, init) => handler(new Request(input, init))`).

حالات الفشل (الـagent ما يوصله، رد 401 أو أي رد غير 2xx ثاني، stream
مشوَّه، أو run بعيد يخلص بخطأ) توصل للـlead كـtool error منظم بالكود
`LOUSHO_REMOTE_REQUEST_FAILED` (و`LOUSHO_REMOTE_UNAUTHORIZED` لـ401)؛
والـtoken أبدًا ما يكون جزء من خطأ ولا event.

استهلاك الـtokens للـrun البعيد، مثل ما يبلغ عنه الـagent البعيد في event
`run.done` الخاص فيه، ينضاف لـ`result.usage` الخاصة بالـlead: للإجماليات،
ولـ`usage.delegated`، ولـ`byModel['remote:<name>']` (`<name>` هو المفتاح
في `subagents`). البعيد ما يرسل تفصيل لكل model، فذلك الإدخال الواحد يحمل
إجمالياته وتقدير `costUsd` الخاص فيه؛ ولما البعيد ما يرسل تكلفة،
`costUsd` الخاصة بالـlead تصير `undefined`. الـlead يثق بهذه الأرقام: ما
يقدر يتأكد منها. ونشر أقدم من هذا التغيير ما يرسل usage، وعندها ما ينضاف
شي. run بعيد يوقف على approval يضيف اللي صرفه قبل الوقفة، والتكملة تضيف
بس اللي صرفته بعدها. الـusage يوصل لما الـrun البعيد يخلص، فـ`limits`
الخاصة بالـlead تشوفه بس بعد ما استدعاء `task` يرجع. `RemoteSubagent`
مكتوب باليد ياخذ الـusage لكل دور عبر خيار `onUsage` في `run()` الخاصة
فيه.

### Remote approvals

إذا الـrun البعيد وقف على approval، run الـlead يوقف عليها بالضبط مثل
sub-agent محلي: `result.finishReason` تكون `'awaiting-approval'`،
والـapproval المعلقة في `agent.approvals.list()` (وفي أزرار القنوات،
وشات التطوير، وطلبات الصلاحية في ACP) تحمل اسم الـtool البعيدة وإدخالها،
مع `subagentPath: ['researcher']`. واستدعاء `ask_question` بعيد يوصل
كسؤال (`kind: 'question'`) تجاوب عليه `agent.approvals.answer()`.
والبت فيها على الـlead (`resolve` أو `streamResolve` أو `answer`) يرسل
القرار لمسار الـapprovals عند الـagent البعيد
(`POST <url>/chat/<session>/approvals/<id>`)، ويقرأ التكملة، وجوابها
النهائي يصير نتيجة `task`؛ وتكملة توقف مرة ثانية توقف الـlead مرة ثانية.

```ts
import type { SimpleAgent } from '@lousho/build-ai-agent';
declare const lead: SimpleAgent; // the lead agent above

const paused = await lead.send('Deploy the docs site');
if (paused.finishReason === 'awaiting-approval') {
  const [pending] = await lead.approvals.list(); // e.g. { toolName: 'deploy', args: {...}, subagentPath: ['researcher'] }
  const result = await lead.approvals.resolve({ id: pending.id, approved: true });
  console.log(result.text);
}
```

الـsnapshot الخاص بالـapproval عند الـlead يحتفظ بس بمعرّف الـsession
البعيدة، ومعرّف الـapproval البعيدة، والـ`taskId`، واسم الـsub-agent، فـ
process lead جديدة على نفس الـstore تقدر تبت فيها؛ والـbearer token
أبدًا ما ينخزن (يُقرأ من خيارات `remoteAgent()` من جديد). والفشل أثناء
البت (رد 401، أو أي رد غير 2xx ثاني مثل 404 البعيد على approval ما عادت
معلقة، أو خطأ شبكة) هو الـtool error المنظم لذلك الاستدعاء `task`
بالأكواد اللي فوق، وrun الـlead يكمل. بس run بدون approval store
(`AgentExecutor` مجرد) هو اللي يظل يفشل المهمة بـ
`LOUSHO_SESSION_AWAITING_APPROVAL`، ويسمي الـsession البعيدة ومعرّف
الـapproval حتى تبت فيها على الـagent البعيد.

`remoteAgent()` يغطي agents منشورة عبر HTTP. نوع ثاني من الـsub-agent
"البعيد" هو runner من framework agents ثانية يشتغل داخل الـprocess —
ابنِ واحد على نفس العقد بـ`defineRemoteSubagent()` (تحت) أو استخدم
محوّل Pi الجاهز.

## Pi coding-agent sub-agents (`piAgent()`)

`piAgent()` يشغّل [Pi coding agent](https://github.com/earendil-works/pi)
(`@earendil-works/pi-coding-agent`، peer dependency اختيارية — `npm install
@earendil-works/pi-coding-agent`) داخل الـprocess كـsub-agent. يشتغل على
Node بس: tools الخاصة بـPi (`read` و`bash` و`edit` و`write` و...) تشتغل
على مجلد محلي.

```ts
import { createAgent, piAgent, ask, allow } from '@lousho/build-ai-agent';
import { ModelRuntime } from '@earendil-works/pi-coding-agent';

const runtime = await ModelRuntime.create(); // reads ~/.pi/agent auth, env keys
const lead = createAgent({
  model: 'openai/gpt-4o-mini',
  instructions: 'You coordinate.',
  subagents: {
    coder: piAgent({
      cwd: process.cwd(),                    // the directory Pi's tools work in
      model: runtime.getModel('openrouter', 'openai/gpt-4o-mini'),
      description: 'Edits code and runs tests in the workspace',
      permissions: [ask(['edit', 'write']), allow('*')], // same rules as createAgent()
    }),
  },
});
```

كل استدعاء `task` هو Pi session وحدة: `sessionId` الخاص بالمهمة يصير
معرّف الـPi session، فاستئناف `taskId` — والاستئناف بعد وقفة approval،
حتى في process جديدة — يفتح نفس ملف الـsession والـprompt التالي يكمل
الـtranscript. مهمة Pi ما تقدر تعملها fork (استدعاء `task` يفشل بخطأ
"cannot be copied" الخاص بالـsession البعيدة). الخيارات: `cwd` (مطلوب)،
`model`، `modelRuntime`، `description` (مطلوب)، `name`، `permissions`،
`agentDir`، `sessionDir`، `tools` (allowlist لـtools الخاصة بـPi)،
`thinkingLevel`.

قواعد `permissions` تحكم كل tool call لـPi (الـ`tool_call` extension
event الخاص بـPi يطلق قبل ما الـtool تشتغل): `deny` يرفض الاستدعاء،
و`ask` يوقف run الـlead على approval بالضبط مثل الـremote sub-agent —
`result.finishReason` تكون `'awaiting-approval'` والـapproval المعلقة
تحمل اسم tool الـPi ووسائطها و`subagentPath`. الموافقة تقول لـPi إن
الاستدعاء معتمد وتخلي ذلك الاستدعاء بالذات (نفس اسم الـtool + نفس
الوسائط) يشتغل مرة وحدة (Pi ما فيه API "شغّل الاستدعاء الموقوف"، فالـmodel
يعيد إصداره والبوابة تسمح لذلك الاستدعاء الواحد)؛ والرفض يرسل ملاحظة
القرار كدور مستخدم تالي والاستدعاء المرفوض أبدًا ما يشتغل. بدون approval
store الـ`ask` يترفض على طول. run Pi موقوف يحتفظ بالـusage الخاص فيه عند
الوقفة وتكملته تبلغ عن الباقي، نفس حسابات `remoteAgent()`.

`SubagentApprovalPause` (مصدّرة حاليًا) هي اللي يرميها adapter من هذا
النوع ليوقف الـlead؛ و`defineRemoteSubagent(impl)` تسجل أي object يطابق
`RemoteSubagent` للاستخدام في `subagents`، فاستدعاء `task` يوجهه على
المسار البعيد.

## Depth

`maxSubagentDepth` (الافتراضي `1`) يحدد عمق تداخل الـsub-agents.
بالافتراضي، الـlead يقدر يستدعي sub-agents لكن هم ما يقدرون يستدعون
sub-agents خاصة بهم: run عند الحد ببساطة ما تنعرض له الـtool `task`،
حتى لو انبنى مع `subagents`. و`maxSubagentDepth: 2` تخلي sub-agents
الـlead يفوضون مرة زيادة. قيمة الـrun الأعلى تنطبق على الشجرة كلها؛
و`maxSubagentDepth` الخاصة بـsub-agent معين ما لها أثر إلا لما يشتغل
كـagent أعلى المستوى.

## What a sub-agent inherits

الـsub-agent يحتفظ بتعليماته، والـmodel/provider الخاص فيه، والـtools
والـskills و`maxSteps` الخاصة فيه، وسياقه معزول. ومن الـrun اللي استدعاه
يرث:

| إعداد الـruntime | يُورث؟ | ملاحظات |
| --- | --- | --- |
| `signal` الإيقاف | نعم | إيقاف الـlead يوقف الـsub-agents الخاصة فيه. |
| الـtracing (`exporter`) | نعم | الـspan `invoke_agent` الخاصة بالـsub-agent وليدة span `execute_tool task` الخاصة بالـlead. و`captureContent` و`redactContent` يُورثون كمان. |
| الـhooks (`hooks`) | نعم | تشتغل على استدعاءات الـmodel والـtool calls للـsub-agent، مع `ctx.subagent` متعين (راجع تحت). hook يرمي خطأ داخل sub-agent توقف الـrun كله. |
| الـapproval store (`approvalStore`) | نعم | راجع [Approvals](#approvals-inside-a-sub-agent). |
| مستمعو الـevents (`onAgentEvent`، `createAgent({ onEvent })`) و`stream()` | نعم | events الـsub-agent تتمرر مع حقل `subagent`. |
| `toolConcurrency` | نعم، إلا إذا الـsub-agent عيّن قيمته | |
| `sandbox` | نعم | |
| استهلاك الـtokens | يتجمّع | ينضاف لـ`result.usage` الخاصة بالـlead (الإجماليات و`byModel` و`usage.delegated`)؛ وللبعيد تحت `byModel['remote:<name>']`. |
| `maxSubagentDepth` | الرصيد الباقي | راجع [Depth](#depth). |
| `permissionMode` | نعم، إلا إذا كانت الخاصة بالـlead `'default'` | الـsub-agent يشتغل تحت [permission mode](/ar/permission-modes#الـ-sub-agents) الخاصة بالـlead، وتُقرأ عند كل tool call له؛ وطالما الخاصة بالـlead `'default'` يشتغل بالخاصة فيه (sub-agent وضعه `'plan'` يظل في plan دائمًا). الـremote sub-agent ما يرثها: plan mode يرفض استدعاء `task` إليه. |
| `principal` | نعم | الطرف اللي يشتغل run الـlead لحسابه (مستدعي route auth، مرسل قناة)؛ والـremote sub-agent ما يُقال له. |
| `metadata` | نعم | `metadata` الخاصة بـrun الـlead — hooks الـsub-agent تشوفها. |
| `onLLMRequest` و`onToolCall` وباقي callbacks الخاصة بـrun واحد | لا | تصف run واحد؛ استخدم hooks أو event listener لتراقب الـsub-agents. |
| `sessionId` / `checkpointStore` | لا | الـsub-agent ما ياخذ checkpoints خاصة فيه. إذا الـprocess ماتت وsub-agent شغال، الـlead المستأنف يعيد ذلك الاستدعاء `task`. |
| `output` schema | لا | مخرجات الـsub-agent خاصة فيه: مع schema، `task` ترجع الكائن بعد الـvalidation كـJSON (راجع [المخرجات المنظمة](/ar/structured-output#sub-agents))؛ وبدونها، نص. |
| سجل المحادثة | لا | الـsub-agent يشوف بس prompt المهمة (زائد أدواره السابقة لما الـlead [يستأنف المهمة](#تكملة-مهمة)). |

### Hooks داخل sub-agents

راجع [الـhooks](/ar/hooks) لنقاط الربط والنتائج.

hooks الأب تنطبق على الـsub-agents الخاصة فيه افتراضيًا. و`ctx.subagent`
يقول للـhook إنه شغال داخل واحد — فيه `name` الـsub-agent، و`depth`
عمقه (1 لـsub-agent تابع للـrun الأعلى)، و`toolCallId` الخاص بالـlead
اللي بدأه، والـsub-agent المحيط في `parent` عند تداخل أعمق. والـhook
اللي لازم يشوف بس الـrun الأعلى يرجع مبكرًا:

```ts
import { HookRegistry } from '@lousho/build-ai-agent';

const hooks = new HookRegistry();
hooks.register({
  name: 'audit',
  preToolCall(ctx) {
    if (ctx.subagent) return; // top-level tool calls only
    console.log('tool call', ctx.toolName, ctx.args);
  },
});
```

### Events

`agent.stream()` / `AgentExecutor.stream()` على الـlead تبث run كل
sub-agent داخل نفس الـstream — الخطوات، وdeltas النص، وevents الـtools،
والأخطاء — مع حقل `subagent` على كل event منها، فواجهة المستخدم تقدر
تدجّن نشاط الـsub-agent تحت استدعاء `task` الخاص بالـlead
(`subagent.toolCallId`). راجع [Streaming: sub-agents](/ar/streaming#sub-agents).

listener على الـlead (`createAgent({ onEvent })` أو `onAgentEvent`) ياخذ
نفس الـevents، بما فيها events الـsub-agents، لحظة وقوعها. راجع
[الاستماع بدون ما تمر على الأحداث](/ar/streaming#الاستماع-بدون-iterating).

## Approvals inside a sub-agent

لما sub-agent يستدعي tool لها `needsApproval`، **الـrun كله يوقف**:
`send()` الخاص بالـlead يرجع بـ`finishReason: 'awaiting-approval'` ومعه
`approvalId`، والـapproval store يحتفظ بسجل واحد بس، استدعاؤه المعلق هو
استدعاء الـsub-agent (`toolName`، `args`) مع `subagentPath` يسمي
الـsub-agents اللي شغال داخلهم (مثل `['researcher']`). وافق عليه أو ارفضه
بـ`lead.approvals.resolve({ id, approved })` (الـlead أصلًا يعرف
`subagents` الخاصة فيه؛ والـapproval store في الذاكرة هو الافتراضي، فما
تحتاج `approvalStore`):

```ts
import { createAgent } from '@lousho/build-ai-agent';

const lead = createAgent({
  provider,
  instructions: 'You lead.',
  subagents: { researcher: createAgent({ provider, instructions: 'You research.', description: 'Researches' }) },
});

const paused = await lead.send('Go');
if (paused.finishReason === 'awaiting-approval' && paused.approvalId) {
  const result = await lead.approvals.resolve({ id: paused.approvalId, approved: true });
  console.log(result.text);
}
```

الاستئناف يشغل (أو يرفض) استدعاء الـsub-agent المعلق، ويخليه يخلص،
ويرجع جوابه النهائي للـlead كنتيجة `task`، وبعدين يكمل الـlead. إذا
الـsub-agent احتاج approval ثانية، الـrun يوقف مرة ثانية بـ`approvalId`
جديد. يشتغل على أي عمق.

خيار `approve` على الـlead يبت في استدعاءات الـsub-agents الخاصة فيه
كمان.

الضمانات والحدود:

- ولا استدعاء يشتغل مرتين ولا واحد يضيع: حالة الـsub-agent الموقوفة
  تتخزن داخل سجل الـapproval الخاص بالـlead (JSON عادي، فأي `ApprovalStore`
  يشتغل)، والاستدعاء المعتمد يشتغل مرة وحدة بالضبط، عند الاستئناف.
- استدعاءات الـtools الثانية في نفس دور الـlead اللي خلصت تحتفظ بنتائجها
  وما تشتغل من جديد.
- approval وحدة معلقة لكل run. إذا sub-agent اثنين وقفوا في نفس الدور،
  الـrun يوقف على الأول (بترتيب الاستدعاء)؛ والثاني يتوقف والـlead ياخذ
  نتيجة خطأ لذلك الاستدعاء `task` تقول إن استدعاؤه ما اشتغل، فيقدر يطلبه
  من جديد بعد الـapproval.
- hooks ما قبل وبعد الـtool الخاصة باستدعاء `task` تطلق مرة ثانية عند
  الاستئناف، مثل hooks أي tool معتمدة.
- sub-agent تغيّر تعريفه من بعد الوقفة (تعليمات أو model أو tools)
  يعالجه `onAgentDrift` الخاص بالـlead، مثل الـlead نفسه: `'error'` يرفض
  الاستئناف ويخلي الـapproval معلقة، و`'warn'` (الافتراضية) تحذّر وتطلق
  `agent.drift` مع `subagent` متعين. وsub-agent ما عاد عنده tool
  الاستدعاء المعتمد يرفض دائمًا بـ`LOUSHO_RESUME_TOOL_MISSING`. راجع
  [الاستئناف بـagent متغير](/ar/durable-execution#استئناف-run-بعد-ما-يتغير-الـ-agent).
- استهلاك الـtokens يظل يتراكم عبر الوقفة: usage الـsub-agent قبل الوقفة
  موجود في النتيجة الموقوفة، واللي يصرفه بعد الاستئناف ينضاف لـ
  `result.usage` الخاصة بالـlead المستأنف.
- approval لـsub-agent خلفي توقف الـlead لما الـlead ينتظره بـ
  `agent_await`؛ راجع [Sub-agents في الخلفية](#when-the-lead-run-ends).

#### متقدم: executor API

مع `AgentExecutor.execute()` كـlead (راجع [executor API](/ar/executor-api))،
الـrun يحتاج `approvalStore`؛ بدونه استدعاء الـsub-agent يصير نتيجة خطأ
وما يشتغل شي. استأنف بـ`resumeAfterApproval()`، ومرّر نفس خيار `subagents`
اللي استخدمه الـrun الموقوف:

```ts
import { AgentExecutor, resumeAfterApproval, ToolRegistry } from '@lousho/build-ai-agent/executor';
import { createAgent } from '@lousho/build-ai-agent';

const subagents = { researcher: createAgent({ provider, instructions: 'You research.', description: 'Researches' }) };

const paused = await AgentExecutor.execute({ agent, input: 'Go', provider, subagents, approvalStore });
if (paused.finishReason === 'awaiting-approval' && paused.approvalId) {
  const result = await resumeAfterApproval(
    { id: paused.approvalId, approved: true },
    approvalStore,
    new ToolRegistry(),
    provider,
    { subagents }
  );
  console.log(result.text);
}
```
