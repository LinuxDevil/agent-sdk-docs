الـsub-agent (وكيل فرعي) هو agent مستقل — له تعليمات وmodel وtools وskills
خاصة به — يسلّمه الـlead (الوكيل الرئيسي) مهمة مكتفية بذاتها.
يبدأ بسياق نظيف: لا يرى إلا الـprompt الذي تعطيه إياه، ولا يرى محادثة الـlead
أبدًا. يعمل بالخطوات التي يحتاجها، ثم يعود جوابه النهائي
إلى الـlead كنتيجة tool واحدة.

## Sub-agent أم skill أم flow؟

| استخدم | عندما |
| --- | --- |
| **Skills** ([docs](/ar/skills)) | يحتاج الـagent *نفسه* إلى تعليمات إضافية لبعض المهام. رخيصة: الـskill نص يُضاف إلى المحادثة الحالية. |
| **Sub-agents** | تحتاج المهمة إلى tools مختلفة، أو model مختلف، أو استكشاف طويل مليء بالـtool calls لا تريده في سياق الـlead. يقرر الـlead وقت الـrun ما إذا كان سيفوّض وماذا يفوّض؛ وتعمل المهام المستقلة بالتوازي. |
| **Handoffs** ([docs](/ar/handoffs)) | يتولى agent آخر المحادثة ويرد على المستخدم بنفسه (فرز إلى متخصص)، بدلًا من إرجاع نتيجة إلى الـlead. |
| **Flows** | الخطوات وترتيبها معروفة مسبقًا (pipeline)، لذا لا يصح تركها لتقدير الـmodel. |

## بداية سريعة

أعطِ كل sub-agent حقل `description` (يقرؤه model الـlead لكي يختار)،
ثم مرّرها إلى الـlead تحت `subagents`:

```ts
import { createAgent } from 'lousho';

const researcher = createAgent({
  provider,
  instructions: 'You research a question and report your sources.',
  description: 'Finds and summarizes sources',
});
const writer = createAgent({
  provider,
  instructions: 'You write clear, short articles.',
  description: 'Turns notes into a polished article',
});

const lead = createAgent({
  provider,
  instructions: 'You coordinate research and writing.',
  subagents: { researcher, writer },
});

const { text } = await lead.send('Write a short article about the history of the bicycle.');
```

يأخذ `AgentExecutor.execute()` خيارات `subagents` و`maxSubagentDepth` نفسها.
استخدمه عندما تحتاج إلى hooks أو tracing على run الـlead — إذ ترثها الـsub-agents
(راجع [ما يرثه الـsub-agent](#what-a-sub-agent-inherits)). وتعمل الـapprovals (الموافقات)
من `createAgent()` أيضًا (راجع [Approvals](#approvals-inside-a-sub-agent)).

## كيف يعمل

مع `subagents`، يحصل الـlead على:

1. بلوك **Available sub-agents** في الـsystem prompt: سطر لكل
   sub-agent (`- name: description`)، وجملة تذكر أن الـsub-agent
   لا يرى إلا الـprompt الذي يستلمه.
2. tool واحدة فقط، `task`، مدخلها
   `{ agent: <one of the names>, prompt: string, description?: string, background?: boolean, taskId?: string, mode?: 'new' | 'resume' | 'fork' }`
   (`description` اسم مختصر اختياري من 3 إلى 5 كلمات يُستخدم في الـevents والـhooks؛
   و`taskId` و`mode` يكملان مهمة سابقة، راجع [تكملة مهمة](#تكملة-مهمة)؛
   و`subagentOptions: { continuation: false }` يزيلهما).
3. ثلاث tools للمهام الخلفية: `agent_status` و`agent_await` و`agent_cancel`
   (راجع [Sub-agents في الخلفية](#sub-agents-في-الخلفية)).

عندما يستدعي الـlead الأداة `task`، يعمل الـsub-agent المسمّى على `prompt` وحده.
نتيجة الـtool هي النص النهائي للـsub-agent، ومعها سطر footer صغير يمكن
للـlead الاستفادة منه:

```text
The first bicycles appeared in the 1810s ...

[sub-agent 'researcher': 3 step(s), finish reason 'stop', taskId 'task_1']
```

إذا لم ينتهِ الـsub-agent — رمى خطأً، أو استهلك كل `maxSteps`، أو توقف عند حد
budget، أو انقطع — يحصل الـlead على نتيجة خطأ (`isError: true`) تشرح السبب، مثل
`Sub-agent 'researcher' used all 10 of its steps
(maxSteps) without giving a final answer.` والاسم المجهول لـagent يُرجع أيضًا نتيجة خطأ تعدّد
الأسماء الصحيحة. والجواب الذي ينقطع عند حد الـoutput tokens للـsub-agent
(finish reason `'length'`) يُرجَع رغم ذلك، ومعه سطر بعد الـfooter يذكر أنه
قد يكون ناقصًا. والـsub-agent الذي لديه `output` schema واستنفد خطواته يُجري
استدعاءً أخيرًا إجباريًا ([Out of steps](/ar/structured-output#عند-نفاد-الخطوات)): عندما
يُرجع هذا الاستدعاء كائنًا صالحًا، تكون نتيجة `task` هي هذا الكائن (finish reason
`'max-steps'` في الـfooter، ومعه سطر يذكر أن الخطوات نفدت)، وليست خطأً.
يُضاف استهلاك الـsub-agent من الـtokens إلى `result.usage` الخاصة بالـlead،
وكذلك استهلاك الـ[remote sub-agent](#remote-sub-agents). أما `result.toolErrors`
الخاصة بالـlead نفسه فلا تعدّ إلا الـtool calls الخاصة به؛ وأما الاستدعاءات التي فشلت
داخل الـsub-agents التابعة له (وداخل الـsub-agents التابعة لها) فتُحتسب في
`result.usage.delegated.toolErrors`.

تُرمى أخطاء الإعداد ومعها طريقة الحل: sub-agent بدون `description`،
أو قيمة ليست agent من `createAgent()`، أو tool خاصة بك اسمها أصلًا
`task` (أو `agent_status` أو `agent_await` أو `agent_cancel`).

## تكملة مهمة

يعمل كل استدعاء `task` في محادثة فرعية لها `taskId` (`task_1`،
`task_2`، ... في الـfooter). ويمكن للـlead الرجوع إليها:

| إدخال `task` | ما يعمل |
| --- | --- |
| بدون `taskId` (`mode: 'new'`) | sub-agent جديد، كما في الأعلى، بـ`taskId` جديد. |
| `taskId` (`mode: 'resume'`، الافتراضي مع `taskId`) | الـsub-agent نفسه مع كامل الـtranscript الخاص به (الـprompts السابقة والـtool calls والإجابات)، ويدخل `prompt` كدور مستخدم جديد. تحتفظ النتيجة بالـ`taskId` نفسه. |
| `taskId` مع `mode: 'fork'` | مهمة جديدة (`taskId` جديد) تبدأ من نسخة من ذلك الـtranscript. تبقى المهمة الأصلية كما هي ويمكنك استئنافها لاحقًا. |

يعرف الـmodel ذلك من وصف الـtool `task` نفسه، لذا لا يحتاج سؤال المتابعة إلى
أي كود. لكن الـlead الذي يحتفظ بعمله عبر الدورات أو إعادات التشغيل يحتاج إلى
store وsession (جلسة):

```ts
import { createAgent } from 'lousho';
import { SqliteStore } from 'lousho/sqlite';

const store = new SqliteStore('./.lousho/agent.db');
const researcher = createAgent({ provider, instructions: 'You research.', description: 'Finds and summarizes sources' });
const lead = createAgent({ provider, instructions: 'You coordinate research.', store, subagents: { researcher } });

const chat = lead.session({ id: 'user-42' });
await chat.send('Research the history of the bicycle.'); // the lead calls task -> taskId 'task_1'
await chat.send('Ask the researcher which source it trusted most.'); // the lead calls task({ taskId: 'task_1', ... })
```

أين تُخزَّن المحادثات:

- مع `createAgent({ store })` (`store.sessions`) وrun للـlead له
  `sessionId` (سواء `send(message, { sessionId })` مع checkpoints أو دور
  في session)، تُحفظ كل مهمة في `store.sessions` بعد انتهاء run المهمة،
  تحت مفتاح مُهشّم (hashed) من معرّف session الـlead ومن `taskId`.
  وهي تبقى بعد انتهاء run الـlead: فالدورات اللاحقة في الـsession نفسها، والـlead
  المُستأنف بـ`agent.resume()` أو `approvals.resolve()`، والـprocess الجديدة على
  الـdurable store نفسه (مخزن يبقى بعد إعادة تشغيل الـprocess) — كلها
  تستطيع إكمالها. ولا يطابق `taskId` من session لـlead
  آخر أبدًا. لا يحتوي الـsession store على list API، لذا لا تُسرد هذه المدخلات
  ولا تُحذف مع session الـlead؛ احذف بيانات الـstore للتخلص منها.
  ومع `AgentExecutor.execute()` عيّن الـstore باستخدام
  `withSubagentOptions(subagents, { sessions })`.
- في بقية الحالات (لا يوجد session store، أو run للـlead بدون
  `sessionId`)، تبقى المهمة في الذاكرة لذلك الاستدعاء الواحد لـ`execute()` /
  `send()`: فالـrun الذي يتوقف بانتظار approval ثم يُستأنف يبدأ بدون أي مهمة. والـsub-agent
  الذي تستأنفه الـapproval نفسها يظل يرد على الـlead (كنتيجة `task` أو
  `agent_await`)، لكن لا يمكنك إكماله بـ`taskId` بعد ذلك؛ استخدم session store
  لهذا الغرض.

لا تُحفظ إلا المهام التي انتهت (`stop` أو `length` أو `max-steps`)،
لذا لا يمكنك إكمال المهمة التي فشلت أو أُلغيت. وتصل الأخطاء إلى الـlead كـ
tool errors منظمة: الـ`taskId` المجهول، أو التابع لـsession لـlead آخر، أو التابع
لـsub-agent آخر، يفشل بالخطأ `LOUSHO_SUBAGENT_TASK_NOT_FOUND`؛ والمهمة التي لا تزال
تعمل (مهمة background لم تنتهِ) تفشل بالخطأ `LOUSHO_SUBAGENT_TASK_BUSY`، الذي يطلب
من الـmodel أن يستدعي `agent_await` أو `agent_cancel` عليها أولًا. والخطأ الخاص
بـ`taskId` تابع لـsub-agent آخر يطلب من الـmodel حذف `taskId` لكي يبدأ مهمة
جديدة.

يمكن للـlead الذي لا يحتاج إلى متابعات أبدًا أن يزيل التكملة باستخدام
`subagentOptions: { continuation: false }`: عندها لا تحتوي الـtool `task`
على الوسيطين `taskId` و`mode`، ويبدأ كل استدعاء مهمة جديدة، ولا يذكر وصف الـtool
ولا بلوك الـprompt الـtaskIds. أحيانًا تمرّر الـmodels الأضعف للـlead
`taskId` خاصًا بـsub-agent إلى sub-agent آخر وتضيّع دورة على الخطأ؛ وهذا الخيار
يزيل هذا الاحتمال.

```ts
import { createAgent } from 'lousho';

const analyst = createAgent({ provider, instructions: 'You analyze.', description: 'Analyzes data' });
const lead = createAgent({ provider, subagents: { analyst }, subagentOptions: { continuation: false } });
```

المهمة المستأنفة أو المتفرّعة (forked) هي استدعاء `task` عادي في كل ما عدا ذلك:
يمكنك تشغيلها في الخلفية (وتحتفظ بالـ`taskId` نفسه)، والـapproval داخلها توقف
الـlead وتستأنفه مثل أي approval لـsub-agent، ويُحتسب استهلاكها ضمن
`usage` و`limits` الخاصة بالـlead. ويرى الـsub-agent كامل الـtranscript
من جديد مع كل resume، لذا تكلّف المهمة طويلة العمر tokens أكثر في كل مرة.

## مهام بالتوازي

تعمل الـtool calls في دور model واحد معًا (راجع `toolConcurrency`)،
لذا عندما يستدعي الـlead الأداة `task` أكثر من مرة في دور واحد، تعمل الـsub-agents
بالتوازي. تصل النتائج إلى transcript الـlead بالترتيب نفسه الذي
أجرى به الـmodel الاستدعاءات. ضع حدًا أقصى باستخدام `toolConcurrency` على الـlead
(`1` يشغّلها واحدًا تلو الآخر).

## Sub-agents في الخلفية

مع `background: true`، تبدأ `task` الـsub-agent وتعود فورًا بـ
`{ taskId, status: 'running', agent }`، لذا يستطيع الـlead مواصلة عمله (أو بدء
مهام أخرى) أثناء عمله. بعد ذلك يستخدم الـlead:

| الـtool | الإدخال | النتيجة |
| --- | --- | --- |
| `agent_status` | `{ taskId? }` | `{ tasks: [{ taskId, agent, status, elapsedMs, approvalId?, toolName?, error? }] }` لمهمة واحدة أو لكل المهام. تكون `status` إحدى القيم `queued` أو `running` أو `done` أو `failed` أو `cancelled` أو `awaiting-approval`. |
| `agent_await` | `{ taskId }` أو `{ taskIds }`، و`timeoutMs` اختياري | تنتظر انتهاء المهمة أو المهام. المهمة `done` تحمل `result`: النص نفسه (مع الـfooter) الذي تُرجعه `task` المتزامنة. والمهمة `failed` تحمل `error`. والمهمة التي لا تزال تعمل بعد `timeoutMs` تُرجع `status: 'timeout'`. ومع `taskIds` تكون النتيجة `{ tasks: [...] }`. |
| `agent_cancel` | `{ taskId }` | تلغي مهمة queued أو قيد التشغيل (ينقطع الـrun الخاص بها) وتُرجع حالتها. |

يعمل في الوقت نفسه بحد أقصى `maxConcurrent` sub-agent خلفي لكل run للـlead
(الافتراضي 3)؛ والاستدعاءات الزائدة بـ`background: true` تحصل على
`status: 'queued'` وتبدأ عندما تتوفر أماكن. عيّنها باستخدام `subagentOptions`
في `createAgent()`:

```ts
import { createAgent } from 'lousho';

const researcher = createAgent({ provider, instructions: 'You research.', description: 'Finds and summarizes sources' });

const lead = createAgent({
  provider,
  instructions: 'You coordinate research.',
  subagents: { researcher },
  subagentOptions: { maxConcurrent: 2, awaitBackgroundOnFinish: true },
});
```

مع `AgentExecutor.execute()`، ألحِق الخيارات نفسها بقيمة `subagents`
باستخدام `withSubagentOptions(subagents, options)` الذي يُرجعها. وفي `createAgent()`
تتقدّم `subagentOptions` على الخيارات الملحقة بهذه الطريقة.

يمكن للـlead الذي لا يحتاج إلى مهام خلفية أبدًا أن يزيلها باستخدام
`subagentOptions: { background: false }`: عندها لا يحصل الـlead إلا على الـtool
`task`، بدون وسيط `background` الخاص بها، ولا يذكر بلوك الـprompt المهام
الخلفية. وهذا يوفّر الـschemas والنصوص الخاصة بالـtools الثلاث (بضع مئات من الـtokens) في كل
طلب للـlead.

يرث الـsub-agent الخلفي من run الـlead مثل المتزامن (hooks وtracing
وevent listeners وتجميع الاستهلاك)، ويُطبَّق `maxSubagentDepth` بالطريقة نفسها.
وإيقاف signal الـlead يلغي الـsub-agents الخلفية، سواء كانت queued أو
قيد التشغيل.

### When the lead run ends

تتبع المهام الخلفية run واحدًا (استدعاء واحد لـ`execute()` / `send()` /
`stream()`). عندما ينتهي الـrun، أيًّا كانت طريقة انتهائه، **تُلغى** المهام التي لا
تزال queued أو قيد التشغيل افتراضيًا (تنقطع الـruns الخاصة بها). ومع
`awaitBackgroundOnFinish: true` ينتظر الـrun بدلًا من ذلك انتهاءها قبل أن
يكتمل (والـrun الخاص بـlead منقطع أو فاشل يلغيها أيضًا). في الحالتين لا يكتمل الـrun إلا
بعد أن تتوقف الـruns الخاصة بها، لذا لا يصل أي event لـsub-agent إلى مستمعي
الـrun بعد ذلك؛ ومع `awaitBackgroundOnFinish` تصل الـevents الخاصة بها قبل
`run.done` الخاص بالـlead.

تعدّد النتيجة كل مهمة خلفية في الـrun مع حالتها النهائية:

```ts
import { createAgent } from 'lousho';

const researcher = createAgent({ provider, instructions: 'You research.', description: 'Finds and summarizes sources' });
const lead = createAgent({ provider, instructions: 'You coordinate research.', subagents: { researcher } });

const result = await lead.send('Research three topics in the background.');
for (const task of result.backgroundTasks ?? []) {
  console.log(task.taskId, task.agent, task.status); // e.g. task_1 researcher cancelled
}
```

تحمل `result.backgroundTasks` القيمة `{ taskId, agent, status, elapsedMs, error?,
approvalId?, toolName? }` لكل مهمة (بشكل `agent_status` نفسه) وتغيب عندما
لا يبدأ الـrun أي مهمة خلفية. استخدم `agent_await` في الـlead (يطلب منه الـsystem
prompt ذلك) لكي تصل إجاباتها إلى المحادثة.

الـhook الخاص بالـexecutor الذي يقف وراء ذلك عام (public): يُستدعى `ExecuteOptions.onRunEnd`
مرة واحدة بالضبط لكل run، مع `{ result }` (أيًّا كان `finishReason`)
أو `{ error }`؛ ويُحسم الـrun بعد أن يعود. وتُسجَّل المهام الخلفية في
`result` قبل أن يراها `onRunEnd` الخاص بك.

القيود:

- run الـlead الذي يتوقف بانتظار approval (`finishReason: 'awaiting-approval'`)
  ينتهي هناك: تُلغى مهامه الخلفية التي لا تزال queued أو قيد التشغيل (أو يُنتظر
  انتهاؤها) مثل أي نهاية أخرى، ويبدأ الـrun المستأنف بدون أي مهمة.
  الـrun المستأنف run مستقل لا صلة له بمهام الـrun المتوقف (وقد
  يعمل حتى في process أخرى)، لذا لا يمكنه إبقاؤها حية عبر التوقف.
- الـsub-agent الخلفي الذي يحتاج إلى approval يتوقف بـ`status: 'awaiting-approval'`
  (مع `approvalId` و`toolName` الخاصين بالـchild)؛ ولم يُنفَّذ استدعاؤه بعد.
  ولا يكمل إلا عندما ينتظره الـlead باستخدام `agent_await` (يخبر وصفا `task` و
  `agent_status` الـmodel بذلك). عندها **يتوقف الـlead** على تلك
  الـapproval، مثل sub-agent متزامن: تحتوي نتيجة الـlead على
  `finishReason: 'awaiting-approval'`، وتسمّي الـapproval المعلقة استدعاء
  الـchild بـ`subagentPath: ['<agent>']`، وتُسرد في
  `agent.approvals.list()`. ويُنفّذ `approvals.resolve()` (أو `resume()` بعد إعادة
  التشغيل، مع durable store) استدعاء الـchild أو يرفضه، ويتركه يكمل،
  ويحصل الـlead المكمّل على جواب الـchild كنتيجة `agent_await`
  (`status: 'done'` مع `result`، أو `'failed'`). يُضاف استهلاك الـchild
  إلى استهلاك الـlead، وتُحفظ محادثته تحت `taskId` مثل أي مهمة، لذا يستطيع
  `task({ taskId })` إكمالها.
- إذا توقف الـchild مرة أخرى، يتوقف الـlead مرة أخرى على الـapproval
  التالية. وإذا كان استدعاء `agent_await` واحد ينتظر عدة مهام كلها متوقفة،
  يتوقف الـlead عليها واحدة تلو الأخرى، ثم يُرجع ذلك الاستدعاء كل
  الإجابات دفعة واحدة.
- المهمة التي لا تزال `awaiting-approval` عندما ينتهي الـlead دون أن ينتظرها
  تُسجَّل في `result.backgroundTasks` بالحالة نفسها ولا يمكنك استئنافها:
  فقد اختار الـmodel ألا ينتظرها.

```ts
import { createAgent, defineTool } from 'lousho';
import { z } from 'zod';

const shell = defineTool({
  name: 'shell',
  description: 'Runs a shell command',
  input: z.object({ cmd: z.string() }),
  needsApproval: true,
  execute: async ({ cmd }) => `ran ${cmd}`,
});
const coder = createAgent({ provider, instructions: 'You code.', tools: [shell], description: 'Fixes code' });
const lead = createAgent({ provider, instructions: 'You lead.', subagents: { coder } });

// The lead starts `coder` with task({ background: true }), then calls agent_await on it.
const paused = await lead.send('Fix the failing test in the background, then report.');
if (paused.finishReason === 'awaiting-approval' && paused.approvalId) {
  const [pending] = await lead.approvals.list(); // { toolName: 'shell', args: { cmd: ... }, subagentPath: ['coder'] }
  console.log(pending?.toolName, pending?.args);
  const result = await lead.approvals.resolve({ id: paused.approvalId, approved: true });
  console.log(result.text); // agent_await returned the coder's answer to the lead
}
```

## Dynamic catalogs

بدلًا من record ثابت، مرّر catalog يحتوي على `list()` و`resolve(name)`.
تُستدعى `list()` في بداية كل run يعرض الـtool `task`، لذا يمكن أن تتغير
المجموعة من run إلى آخر؛ وتُستدعى `resolve()` عندما يختار الـlead اسمًا (أرجع
`undefined` للاسم المجهول).

```ts
import { createAgent, type SubagentCatalog } from 'lousho';

const experts = new Map([
  ['researcher', createAgent({ provider, instructions: 'You research.' })],
]);

const catalog: SubagentCatalog = {
  list: async () => [{ name: 'researcher', description: 'Finds and summarizes sources' }],
  resolve: async (name) => experts.get(name),
};

const lead = createAgent({ provider, instructions: 'You coordinate.', subagents: catalog });
```

## Remote sub-agents

يستخدم `remoteAgent()` agent نشرته أنت أصلًا (`lousho build
--target=node-server` أو `docker` أو `cloudflare-worker`) كـsub-agent.
يوضع في `subagents` بجانب الـagents المحلية، ويفوّض إليه الـlead باستخدام الـtool
`task` نفسها، بما في ذلك `background: true`.

```ts
import { createAgent, remoteAgent } from 'lousho';

const lead = createAgent({
  provider,
  instructions: 'You coordinate.',
  subagents: {
    researcher: remoteAgent({
      url: 'https://researcher.example.workers.dev',
      auth: process.env.RESEARCHER_TOKEN, // the deployment's LOUSHO_API_TOKEN; or () => string | Promise<string>
      description: 'Finds and summarizes sources',
    }),
  },
});
```

تفتح كل مهمة session جديدة على الـagent البعيد (`POST <url>/chat` مع
`{ sessionId, input }`، وتُقرأ كـstream أحداث SSE، راجع
[النشر](/ar/deployment#http-api))، وترسل prompt المهمة وتُرجع النص
النهائي للـagent البعيد (أو الكائن بصيغة JSON عندما يكون للـagent المنشور
`output` schema، راجع [المخرجات المنظمة](/ar/structured-output))، ويليه
footer يسمّي الـsession والـ`taskId`. واستدعاء `task` الذي يستأنف ذلك
الـ`taskId` يُرسَل إلى الـsession البعيدة نفسها، فيكمل الـagent البعيد بالـhistory
الخاص به (أبقِه في store على الطرف البعيد)؛ ولا يمكنك عمل
fork لمهمة بعيدة. لا يرى الـagent البعيد إلا ذلك الـprompt، ويعمل بالـmodel والـtools
والـlimits الخاصة به، لذا لا يصل إليه runtime الـlead (hooks وsandbox وapproval store).
وإشارة إيقاف run الـlead توقف الطلب. الخيارات: `url` و`auth`
و`name` و`description` و`headers` و`fetch` (احقن `fetch` خاصة بك في
الاختبارات؛ فالـagent الذي يعمل في الـprocess نفسها خلف
`createRouteHandler(agent, { basePath: '/' }).handler` — الـFetch handler
المُصدَّر، راجع [النشر](/ar/deployment#http-api) — يعمل كـfake
deployment: `fetch: (input, init) => handler(new Request(input, init))`).

تصل حالات الفشل (تعذّر الوصول إلى الـagent، أو رد 401 أو أي رد آخر غير 2xx، أو stream
مشوَّه، أو run بعيد ينتهي بخطأ) إلى الـlead كـtool error منظم بالكود
`LOUSHO_REMOTE_REQUEST_FAILED` (و`LOUSHO_REMOTE_UNAUTHORIZED` لـ401)؛
ولا يكون الـtoken أبدًا جزءًا من خطأ أو event.

يُضاف استهلاك الـtokens للـrun البعيد، كما يُبلغ عنه الـagent البعيد في event
`run.done` الخاص به، إلى `result.usage` الخاصة بالـlead: إلى الإجماليات،
وإلى `usage.delegated`، وإلى `byModel['remote:<name>']` (`<name>` هو المفتاح
في `subagents`). لا يرسل الطرف البعيد تفصيلًا لكل model، لذا يحمل ذلك الإدخال الواحد
إجمالياته وتقدير `costUsd` الخاص به؛ وعندما لا يرسل الطرف البعيد تكلفة،
تصبح `costUsd` الخاصة بالـlead هي `undefined`. يثق الـlead بهذه الأرقام: ولا
يستطيع التحقق منها. والنشر الأقدم من هذا التغيير لا يرسل usage، وعندها لا يُضاف
أي شيء. الـrun البعيد الذي يتوقف بانتظار approval يضيف ما استهلكه قبل التوقف، والتكملة لا تضيف
إلا ما استهلكته بعده. يصل الـusage عندما ينتهي الـrun البعيد، لذا لا تراه `limits`
الخاصة بالـlead إلا بعد أن يعود استدعاء `task`. والـ`RemoteSubagent`
المكتوب يدويًا يحصل على الـusage لكل دور عبر خيار `onUsage` في `run()` الخاصة
به.

### Remote approvals

إذا توقف الـrun البعيد بانتظار approval، يتوقف run الـlead عليها تمامًا مثل
sub-agent محلي: تكون `result.finishReason` هي `'awaiting-approval'`،
وتحمل الـapproval المعلقة في `agent.approvals.list()` (وفي أزرار القنوات،
ومحادثة التطوير، وطلبات الصلاحية في ACP) اسم الـtool البعيدة ومدخلها،
مع `subagentPath: ['researcher']`. واستدعاء `ask_question` البعيد يصل
كسؤال (`kind: 'question'`) تجيب عنه باستخدام `agent.approvals.answer()`.
والبت فيها على الـlead (`resolve` أو `streamResolve` أو `answer`) يرسل
القرار إلى مسار الـapprovals لدى الـagent البعيد
(`POST <url>/chat/<session>/approvals/<id>`)، ويقرأ التكملة، ويصبح جوابها
النهائي نتيجة `task`؛ والتكملة التي تتوقف مرة أخرى توقف الـlead مرة أخرى.

```ts
import type { SimpleAgent } from 'lousho';
declare const lead: SimpleAgent; // the lead agent above

const paused = await lead.send('Deploy the docs site');
if (paused.finishReason === 'awaiting-approval') {
  const [pending] = await lead.approvals.list(); // e.g. { toolName: 'deploy', args: {...}, subagentPath: ['researcher'] }
  const result = await lead.approvals.resolve({ id: pending.id, approved: true });
  console.log(result.text);
}
```

لا يحتفظ الـsnapshot الخاص بالـapproval لدى الـlead إلا بمعرّف الـsession
البعيدة، ومعرّف الـapproval البعيدة، والـ`taskId`، واسم الـsub-agent، لذا تستطيع
process lead جديدة على الـstore نفسه البت فيها؛ ولا يُخزَّن الـbearer token
أبدًا (يُقرأ من خيارات `remoteAgent()` من جديد). والفشل أثناء
البت (رد 401، أو أي رد آخر غير 2xx مثل 404 من الطرف البعيد على approval لم تعد
معلقة، أو خطأ شبكة) هو الـtool error المنظم لذلك الاستدعاء `task`
بالأكواد المذكورة أعلاه، ويكمل run الـlead. ولا يظل يُفشل المهمة بالخطأ
`LOUSHO_SESSION_AWAITING_APPROVAL` إلا الـrun الذي لا يملك approval store
(`AgentExecutor` مجرد)، ويسمّي الخطأ الـsession البعيدة ومعرّف
الـapproval لكي تبت فيها على الـagent البعيد.

يغطي `remoteAgent()` الـagents المنشورة عبر HTTP. ونوع آخر من الـsub-agent
"البعيد" هو runner من frameworks أخرى للـagents يعمل داخل الـprocess —
ابنِ واحدًا على العقد نفسه باستخدام `defineRemoteSubagent()` (أدناه) أو استخدم
محوّل Pi الجاهز.

## Pi coding-agent sub-agents (`piAgent()`)

يشغّل `piAgent()` [Pi coding agent](https://github.com/earendil-works/pi)
(`@earendil-works/pi-coding-agent`، peer dependency اختيارية — `npm install
@earendil-works/pi-coding-agent`) داخل الـprocess كـsub-agent. لا يعمل إلا على
Node: إذ تعمل tools الخاصة بـPi (`read` و`bash` و`edit` و`write` و...)
على مجلد محلي.

```ts
import { createAgent, piAgent, ask, allow } from 'lousho';
import { ModelRuntime } from '@earendil-works/pi-coding-agent';

const runtime = await ModelRuntime.create(); // reads ~/.pi/agent auth, env keys
const lead = createAgent({
  model: 'openai/gpt-4o-mini',
  instructions: 'You coordinate.',
  subagents: {
    coder: piAgent({
      cwd: process.cwd(),                    // the directory Pi's tools work in
      model: runtime.getModel('openrouter', 'openai/gpt-4o-mini'),
      description: 'Edits code and runs tests in the workspace',
      permissions: [ask(['edit', 'write']), allow('*')], // same rules as createAgent()
    }),
  },
});
```

كل استدعاء `task` هو Pi session واحدة: يصبح `sessionId` الخاص بالمهمة
معرّف الـPi session، لذا فإن استئناف `taskId` — والاستئناف بعد توقف بانتظار approval،
حتى في process جديدة — يفتح ملف الـsession نفسه ويكمل الـprompt التالي
الـtranscript. لا يمكنك عمل fork لمهمة Pi (يفشل استدعاء `task` بخطأ
"cannot be copied" الخاص بالـsession البعيدة). الخيارات: `cwd` (مطلوب)،
`model`، `modelRuntime`، `description` (مطلوب)، `name`، `permissions`،
`agentDir`، `sessionDir`، `tools` (allowlist لـtools الخاصة بـPi)،
`thinkingLevel`.

تحكم قواعد `permissions` كل tool call لـPi (يُطلَق الـ`tool_call` extension
event الخاص بـPi قبل أن تعمل الـtool): `deny` يرفض الاستدعاء،
و`ask` يوقف run الـlead بانتظار approval تمامًا مثل الـremote sub-agent —
تكون `result.finishReason` هي `'awaiting-approval'` وتحمل الـapproval المعلقة
اسم tool الـPi ووسائطها و`subagentPath`. تخبر الموافقةُ Pi بأن
الاستدعاء معتمد وتسمح لذلك الاستدعاء بالذات (اسم الـtool نفسه + الوسائط
نفسها) بالعمل مرة واحدة (لا يملك Pi واجهة API لـ"تشغيل الاستدعاء المتوقف"، لذا يعيد الـmodel
إصداره وتسمح البوابة لذلك الاستدعاء الواحد)؛ ويرسل الرفض ملاحظة
القرار كدور مستخدم تالٍ ولا يعمل الاستدعاء المرفوض أبدًا. بدون approval
store يُرفض `ask` مباشرة. ويحتفظ run الـPi المتوقف بالـusage الخاص به عند
التوقف وتُبلغ تكملته عن الباقي، وفق حسابات `remoteAgent()` نفسها.

`SubagentApprovalPause` (المُصدَّرة حاليًا) هي ما يرميه adapter من هذا
النوع لكي يوقف الـlead؛ وتسجّل `defineRemoteSubagent(impl)` أي object يطابق
`RemoteSubagent` للاستخدام في `subagents`، لذا يوجّه استدعاء `task` إليه عبر
المسار البعيد.

## Depth

يحدد `maxSubagentDepth` (الافتراضي `1`) عمق تداخل الـsub-agents.
افتراضيًا، يستطيع الـlead استدعاء sub-agents لكنها لا تستطيع استدعاء
sub-agents خاصة بها: فالـrun الذي بلغ الحد لا تُعرض عليه الـtool `task` ببساطة،
حتى لو بُني مع `subagents`. وتسمح `maxSubagentDepth: 2` لـsub-agents
الـlead بالتفويض مرة إضافية. تُطبَّق قيمة الـrun الأعلى على الشجرة كلها؛
ولا يكون لـ`maxSubagentDepth` الخاصة بـsub-agent معيّن أثر إلا عندما يعمل
كـagent في المستوى الأعلى.

## What a sub-agent inherits

يحتفظ الـsub-agent بتعليماته، والـmodel/provider الخاص به، والـtools
والـskills و`maxSteps` الخاصة به، ويبقى سياقه معزولًا. ومن الـrun الذي استدعاه
يرث:

| إعداد الـruntime | يُورث؟ | ملاحظات |
| --- | --- | --- |
| `signal` الإيقاف | نعم | إيقاف الـlead يوقف الـsub-agents التابعة له. |
| الـtracing (`exporter`) | نعم | الـspan `invoke_agent` الخاصة بالـsub-agent ابنة لـspan `execute_tool task` الخاصة بالـlead. ويُورث `captureContent` و`redactContent` أيضًا. |
| الـhooks (`hooks`) | نعم | تعمل على استدعاءات الـmodel والـtool calls للـsub-agent، مع تعيين `ctx.subagent` (راجع أدناه). والـhook الذي يرمي خطأً داخل sub-agent يوقف الـrun كله. |
| الـapproval store (`approvalStore`) | نعم | راجع [Approvals](#approvals-inside-a-sub-agent). |
| مستمعو الـevents (`onAgentEvent`، `createAgent({ onEvent })`) و`stream()` | نعم | تُمرَّر events الـsub-agent مع حقل `subagent`. |
| `toolConcurrency` | نعم، ما لم يعيّن الـsub-agent قيمته | |
| `sandbox` | نعم | |
| استهلاك الـtokens | يتجمّع | يُضاف إلى `result.usage` الخاصة بالـlead (الإجماليات و`byModel` و`usage.delegated`، التي تعدّ `toolErrors` فيها الـtool calls الفاشلة للـsub-agents) ويُحتسب ضمن `limits` الخاصة به، حتى لو فشل الـsub-agent بعد أن استهلك tokens؛ وللطرف البعيد تحت `byModel['remote:<name>']`. |
| `limits` الـtokens والتكلفة والمدة | مشتركة | الـsub-agent مقيّد أيضًا بحدود الـlead، محسوبةً مع ما استهلكه الـlead والـsub-agents الأخرى التابعة له التي لا تزال تعمل: عندما تبلغ الحدود، يتوقف الـsub-agent (`'budget-exceeded'`) قبل استدعاء الـmodel أو الـtools التالي، ويتوقف الـlead قبل استدعاء الـmodel التالي الخاص به. راجع [Budgets](/ar/configuration#الميزانيات). |
| `maxSubagentDepth` | الرصيد المتبقي | راجع [Depth](#depth). |
| `permissionMode` | نعم، ما لم تكن قيمة الـlead هي `'default'` | يعمل الـsub-agent تحت [permission mode](/ar/permission-modes#الـ-sub-agents) الخاصة بالـlead، وتُقرأ عند كل tool call له؛ وطالما كانت قيمة الـlead هي `'default'` يعمل بالقيمة الخاصة به (الـsub-agent الذي وضعه `'plan'` يبقى في plan دائمًا). لا يرثها الـremote sub-agent: إذ يرفض plan mode استدعاء `task` إليه. |
| `principal` | نعم | الطرف الذي يعمل run الـlead لحسابه (مستدعي route auth، مرسل القناة)؛ ولا يُبلَّغ به الـremote sub-agent. |
| `metadata` | نعم | `metadata` الخاصة بـrun الـlead — تراها hooks الـsub-agent. |
| `memory` | لا | تبقى خانات الذاكرة الخاصة بالـlead للـlead. والـsub-agent الذي لديه `memory` خاصة به يسترجع منها في الـprompt الخاص به ويحصل على memory tools خاصة به، بنطاق `sessionId` و`metadata` و`principal` الخاصة بـrun الـlead (راجع [Memory](/ar/memory#القيود)). |
| `onLLMRequest` و`onToolCall` وبقية الـcallbacks الخاصة بـrun واحد | لا | تصف run واحدًا؛ استخدم hooks أو event listener لمراقبة الـsub-agents. |
| `sessionId` / `checkpointStore` | لا | لا يحصل الـsub-agent على checkpoints خاصة به. إذا توقفت الـprocess بينما يعمل sub-agent، يعيد الـlead المستأنف ذلك الاستدعاء `task`. |
| `output` schema | لا | مخرجات الـsub-agent خاصة به: مع schema، تُرجع `task` الكائن بعد الـvalidation بصيغة JSON (راجع [المخرجات المنظمة](/ar/structured-output#sub-agents))؛ وبدونها، نصًا. |
| سجل المحادثة | لا | لا يرى الـsub-agent إلا prompt المهمة (إضافةً إلى أدواره السابقة عندما [يستأنف الـlead المهمة](#تكملة-مهمة)). |

### Hooks داخل sub-agents

راجع [الـhooks](/ar/hooks) لنقاط الربط والنتائج.

تُطبَّق hooks الأب على الـsub-agents التابعة له افتراضيًا. ويُخبر `ctx.subagent`
الـhook بأنه يعمل داخل أحدها — ويحتوي على `name` الـsub-agent، و`depth`
عمقه (1 لـsub-agent تابع للـrun الأعلى)، و`toolCallId` الخاص بالـlead
الذي بدأه، والـsub-agent المحيط في `parent` عند التداخل الأعمق. والـhook
الذي يجب ألا يرى إلا الـrun الأعلى يعود مبكرًا:

```ts
import { HookRegistry } from 'lousho';

const hooks = new HookRegistry();
hooks.register({
  name: 'audit',
  preToolCall(ctx) {
    if (ctx.subagent) return; // top-level tool calls only
    console.log('tool call', ctx.toolName, ctx.args);
  },
});
```

### Events

يبث `agent.stream()` / `AgentExecutor.stream()` على الـlead الـrun الخاص بكل
sub-agent داخل الـstream نفسه — الخطوات، وdeltas النص، وevents الـtools،
والأخطاء — مع حقل `subagent` على كل event منها، لذا تستطيع واجهة المستخدم
أن تعرض نشاط الـsub-agent متداخلًا تحت استدعاء `task` الخاص بالـlead
(`subagent.toolCallId`). راجع [Streaming: sub-agents](/ar/streaming#sub-agents).

يحصل الـlistener على الـlead (`createAgent({ onEvent })` أو `onAgentEvent`) على
الـevents نفسها، بما فيها events الـsub-agents، لحظة وقوعها. راجع
[الاستماع دون المرور على الأحداث](/ar/streaming#الاستماع-بدون-iterating).

## Approvals inside a sub-agent

عندما يستدعي sub-agent أداة لها `needsApproval`، **يتوقف الـrun كله**:
يعود `send()` الخاص بالـlead بـ`finishReason: 'awaiting-approval'` ومعه
`approvalId`، ويحتفظ الـapproval store بسجل واحد فقط، استدعاؤه المعلق هو
استدعاء الـsub-agent (`toolName`، `args`) مع `subagentPath` يسمّي
الـsub-agents التي يعمل داخلها (مثل `['researcher']`). وافق عليه أو ارفضه
باستخدام `lead.approvals.resolve({ id, approved })` (فالـlead يعرف أصلًا
`subagents` الخاصة به؛ والـapproval store في الذاكرة هو الافتراضي، لذا لا
تحتاج إلى `approvalStore`):

```ts
import { createAgent } from 'lousho';

const lead = createAgent({
  provider,
  instructions: 'You lead.',
  subagents: { researcher: createAgent({ provider, instructions: 'You research.', description: 'Researches' }) },
});

const paused = await lead.send('Go');
if (paused.finishReason === 'awaiting-approval' && paused.approvalId) {
  const result = await lead.approvals.resolve({ id: paused.approvalId, approved: true });
  console.log(result.text);
}
```

يشغّل الاستئناف استدعاء الـsub-agent المعلق (أو يرفضه)، ويتركه ينتهي،
ويُرجع جوابه النهائي إلى الـlead كنتيجة `task`، ثم يكمل الـlead. إذا
احتاج الـsub-agent إلى approval أخرى، يتوقف الـrun مرة أخرى بـ`approvalId`
جديد. ويعمل ذلك على أي عمق.

خيار `approve` على الـlead يبت في استدعاءات الـsub-agents التابعة له
أيضًا.

الضمانات والحدود:

- لا يعمل أي استدعاء مرتين ولا يضيع أي استدعاء: تُخزَّن حالة الـsub-agent المتوقفة
  داخل سجل الـapproval الخاص بالـlead (JSON عادي، لذا يعمل أي `ApprovalStore`)،
  ويعمل الاستدعاء المعتمد مرة واحدة بالضبط، عند الاستئناف.
- استدعاءات الـtools الأخرى في دور الـlead نفسه التي انتهت تحتفظ بنتائجها
  ولا تعمل من جديد.
- approval واحدة معلقة لكل run. إذا توقف sub-agentان في الدور نفسه،
  يتوقف الـrun على الأول (بترتيب الاستدعاء)؛ ويُوقَف الثاني ويحصل الـlead على
  نتيجة خطأ لذلك الاستدعاء `task` تذكر أن استدعاءه لم يُنفَّذ، لذا يستطيع طلبه
  من جديد بعد الـapproval.
- تُطلَق hooks ما قبل الـtool وما بعدها الخاصة باستدعاء `task` مرة أخرى عند
  الاستئناف، مثل hooks أي tool معتمدة.
- الـsub-agent الذي تغيّر تعريفه منذ التوقف (تعليمات أو model أو tools)
  يعالجه `onAgentDrift` الخاص بالـlead، كما يعالج الـlead نفسه: `'error'` يرفض
  الاستئناف ويترك الـapproval معلقة، و`'warn'` (الافتراضية) تحذّر وتُطلق
  `agent.drift` مع تعيين `subagent`. والـsub-agent الذي لم تعد لديه tool
  الاستدعاء المعتمد يُرفض دائمًا بالخطأ `LOUSHO_RESUME_TOOL_MISSING`. راجع
  [الاستئناف بـagent متغير](/ar/durable-execution#استئناف-run-بعد-تغيّر-الـ-agent).
- يستمر تراكم استهلاك الـtokens عبر التوقف: usage الـsub-agent قبل التوقف
  موجود في النتيجة المتوقفة، وما يستهلكه بعد الاستئناف يُضاف إلى
  `result.usage` الخاصة بالـlead المستأنف.
- الـapproval الخاصة بـsub-agent خلفي توقف الـlead عندما ينتظره الـlead باستخدام
  `agent_await`؛ راجع [Sub-agents في الخلفية](#when-the-lead-run-ends).

#### متقدم: executor API

مع `AgentExecutor.execute()` بوصفه lead (راجع [executor API](/ar/executor-api))،
يحتاج الـrun إلى `approvalStore`؛ وبدونه يصبح استدعاء الـsub-agent نتيجة خطأ
ولا يُنفَّذ أي شيء. استأنف باستخدام `resumeAfterApproval()`، ومرّر خيار `subagents` نفسه
الذي استخدمه الـrun المتوقف:

```ts
import { AgentExecutor, resumeAfterApproval, ToolRegistry } from 'lousho/executor';
import { createAgent } from 'lousho';

const subagents = { researcher: createAgent({ provider, instructions: 'You research.', description: 'Researches' }) };

const paused = await AgentExecutor.execute({ agent, input: 'Go', provider, subagents, approvalStore });
if (paused.finishReason === 'awaiting-approval' && paused.approvalId) {
  const result = await resumeAfterApproval(
    { id: paused.approvalId, approved: true },
    approvalStore,
    new ToolRegistry(),
    provider,
    { subagents }
  );
  console.log(result.text);
}
```
