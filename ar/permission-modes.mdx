وضع الصلاحيات يحط الـ agent في حالة لها اسم، بدل ما تكتب rules: ينظر بس ما يلمس (`plan`)، يعدّل الملفات بدون سؤال (`acceptEdits`)، أو ما يوقف أبدًا (`dontAsk`). بدّله في نص الـ session، نفس الطريقة اللي تشتغل فيها مع coding agent: خطّط أول، بعدين خلّيه يعدّل.

```ts
import { createAgent, createFsTools, MemoryWorkspace } from '@lousho/build-ai-agent';
import { mockModel } from '@lousho/build-ai-agent/testing';

const workspace = new MemoryWorkspace({ files: { 'notes.md': '# Notes\n' } });
const agent = createAgent({
  provider: mockModel(['I would add a "Todo" section to notes.md.', 'Done.']),
  instructions: 'You are a coding agent.',
  tools: createFsTools(workspace, { needsApproval: { write_file: true, edit_file: true } }),
});

const session = agent.session({ permissionMode: 'plan' });
await session.send('Plan how to add a todo list to notes.md.'); // reads only; writes are refused
session.setPermissionMode('acceptEdits');
await session.send('Apply the plan.'); // write_file and edit_file run without asking
```

الأوضاع presets فوق [قواعد الصلاحيات](/ar/approvals#سياسات-الصلاحيات) و`needsApproval`، ما هي نظام ثاني. تنطبق في النهاية، على اللي قرّرته الـ rules والـ guardrails و`needsApproval` الخاص بالـ tool.

## الأوضاع

| الوضع | read-only tools | تعديل الملفات | tools ثانية تسأل | tools ثانية ما تسأل |
| --- | --- | --- | --- | --- |
| `'default'` | فحص عادي | فحص عادي | يوقف لطلب موافقة | يشتغل |
| `'plan'` | فحص عادي (وممكن تسأل) | مرفوضة | مرفوضة | مرفوضة |
| `'acceptEdits'` | فحص عادي | تشتغل بدون سؤال | يوقف لطلب موافقة | يشتغل |
| `'dontAsk'` | فحص عادي، بس الـ call اللي كان سيسأل يُرفض | مرفوضة إذا كانت ستسأل | مرفوضة | يشتغل |

- **`plan`**: أي call لـ tool ما هي read-only يُرفض بـ `kind: 'denied'` والسبب
  `The agent is in plan mode: it may read but not change anything. Describe the
  change instead.` — حتى لو طابقته rule من نوع `allow`. والـ run اللي يبدأ في
  plan mode ياخذ فقرة وحدة في الـ system prompt تقول للـ model إنه في plan mode.
  أما الـ call لـ tool غير موجودة فيرجع خطأ not-found المعتاد، فيشوف الـ model
  المشكلة الحقيقية.
- **`acceptEdits`**: الـ call اللي كان سيتوقف لطلب موافقة يشتغل بدون سؤال إذا
  كانت الـ tool تعديل ملفات (`editsFiles`، تحت). الباقي ما يتغيّر.
- **`dontAsk`**: الـ call اللي كان سيتوقف لطلب موافقة — rule من نوع `ask`، أو
  `needsApproval`، أو `ask_question` — يُرفض بالسبب `The agent is in dontAsk
  mode: calls that need approval are refused.` الـ calls اللي وافقت عليها rule
  `allow` واللي ما تحتاج موافقة تشتغل عادي. وما في شيء يوقف، فما يُستدعى أي
  `approve` callback أبدًا.

### أي الـ tools read-only

وضع plan يشغّل الـ tool بس إذا قالت بنفسها إنها ما تغيّر شيء. الـ tool اللي ما قالت شيء تُعامل كأداة لها side effects وتُرفض.

- tool عندها `annotations: { readOnlyHint: true }`. من الجاهزة: `read_file`،
  `list_dir`، `glob`، `grep`، `todo_read`، `current_date`، `day_name`،
  `web_fetch`، `load_skill`، وكل memory tool بصيغة `recall_<name>`،
  و`agent_status` / `agent_await` (تراقب الـ sub-agents الشغالة في الخلفية).
  الـ [OpenAPI tool](/ar/openapi-tools) لعملية `GET` عندها نفس الـ hint، والـ
  [MCP tool](/ar/mcp-integration) تحتفظ بالـ hint اللي بعثه خادمها. وهذا كلام
  الخادم بس، ما هو ضمان — فلا تربط إلا خوادم تثق فيها.
- الـ `ask_question` الجاهزة (هي بس تسأل؛ والـ call يظل واقف بانتظار الجواب)
  و`task` (الـ sub-agent الخاص بها يرث plan mode، شوف تحت).
- الـ [hosted provider tools](/ar/hosted-tools) تشتغل داخل طلب الـ provider،
  فما يُرفض أي call. وضع plan يرسل `webSearch()` و`fileSearch()` (لأنهما
  يقرآن بس) ويترك `codeInterpreter()` وكل `hostedTool()` خارج طلب الـ model؛
  الأوضاع الأخرى ترسلها كلها.

عرّف tool read-only خاصة بك هكذا:

```ts
import { defineTool } from '@lousho/build-ai-agent';
import { z } from 'zod';

const lookUpOrder = defineTool({
  name: 'look_up_order',
  description: 'Read an order by id',
  input: z.object({ id: z.string() }),
  annotations: { readOnlyHint: true },
  execute: async ({ id }) => ({ id, status: 'shipped' }),
});
```

الـ hint وعد تقطعه على الـ tool الخاصة بك: plan mode يثق فيه.

### تعديل الملفات: علامة `editsFiles`

`acceptEdits` يوافق بس على الـ tools المعلَّمة كتعديل ملفات: `write_file` و`edit_file` من `createFsTools()`، وأي tool معرَّفة بـ `editsFiles: true` (تُخزَّن كـ `metadata.editsFiles`). الـ tool ما تُحسب تعديل ملفات من اسمها بس، فلو سمّيت tool من صنعك `write_file` ما يُوافَق عليها بصمت.

```ts
import { defineTool } from '@lousho/build-ai-agent';
import { z } from 'zod';

const appendLine = defineTool({
  name: 'append_line',
  description: 'Append a line to a file in the project',
  input: z.object({ path: z.string(), line: z.string() }),
  needsApproval: true,
  editsFiles: true,
  execute: async ({ path, line }) => `appended to ${path}: ${line}`,
});
```

## ترتيب التقييم

لكل tool call، بهذا الترتيب:

1. validation للـ arguments، بعدين [hooks](/ar/hooks) الـ `preToolCall`. رفض الـ hook يوقف هنا.
2. قواعد الصلاحيات (`permissions`). rule من نوع `deny` توقف هنا.
3. [guardrails](/ar/guardrails) الـ tool. أي block ينهي الـ run.
4. `needsApproval` الخاص بالـ tool. الرفض يوقف هنا؛ وrule من نوع `allow` أو `ask` تحل محل سؤاله.
5. وضع الصلاحيات، على الباقي.

يعني ما في وضع يحوّل الرفض إلى run: رفض الـ hook، وrule `deny`، ورفض `needsApproval` يظلون رفض في كل وضع. و`acceptEdits` ما يوافق أبدًا على call حجبه guardrail.

## ضبط الوضع وتبديله

- `createAgent({ permissionMode })`: وضع الـ agent. لو مرّرت function، تُقرأ
  عند كل tool call، فالوضع اللي تبدّله والـ run شغّال ينطبق على الـ call
  التالي.
- `agent.send(message, { permissionMode })` / `agent.stream(...)`: الوضع لهذا
  الـ run فقط.
- `agent.session({ permissionMode })`، بعدين `session.setPermissionMode(mode)`
  والـ getter `session.permissionMode`. الـ session تقرأ وضعها عند كل tool
  call في الـ turn، فلو استدعيت `setPermissionMode()` وأنت داخل turn (من
  listener على `tool.start` مثلًا — يعني listener مسجّلة بـ `session.on()` أو
  loop على `stream()`) ينطبق التبديل من الـ tool call التالي في نفس الـ turn.
  والـ session تأخذ وضع الـ agent افتراضيًا.

التبديل دائمًا استدعاء صريح لـ `setPermissionMode()`. وكل تبديل يروح لـ `onPermissionModeChange` مع `{ sessionId, from, to, at }`:

```ts
import { createAgent } from '@lousho/build-ai-agent';

const agent = createAgent({
  provider,
  instructions: 'You are a coding agent.',
  onPermissionDecision: (entry) => console.log(entry.toolName, entry.decision, entry.mode),
  onPermissionModeChange: ({ sessionId, from, to, at }) => console.log(at, sessionId, `${from} -> ${to}`),
});
```

الـ system prompt يُبنى عند بداية الـ run: الـ model ما ينقال له عن الوضع إلا لو الـ run (أو الـ turn في session) بدأ في plan mode. والتبديل في نص الـ run يفرضه فحص الـ tool calls لوحده، وهذا يكفي لأن سبب الرفض في الـ call المرفوض يوصل للـ model.

## الـ audit log

طالما فيه وضع غير `'default'` مفعّل، قرار كل tool call يتسجّل — حتى لو الـ agent ما ضبط `permissions` ولا `onPermissionDecision`. القرار يروح لـ `onPermissionDecision` (إذا مضبوط) ويطلع في الـ stream كـ event اسمه `permission.decision`. وحقل `mode` في الـ entry ينضبط بس لما الوضع يغيّر نتيجة الـ call: `'plan'` أو `'dontAsk'` مع `decision: 'deny'` والـ `reason` الخاص بالوضع، و`'acceptEdits'` مع `decision: 'allow'`. ولو الوضع رفض call طابقته rule `allow`، يحتفظ الـ entry بـ `rule.index` الخاص بتلك القاعدة. تبديلات الوضع تروح لـ `onPermissionModeChange`. وثاني argument في `onPermissionDecision` هو `{ principal }`، يعني من يشتغل الـ run بالنيابة عنه؛ الـ entry والـ event ما يحملون هوية الـ caller (شوف [auth](/ar/auth#principals-in-tools-and-approvals)).

## الـ sub-agents

الـ sub-agent (أداة `task` أو task في الخلفية) يشتغل بوضع الـ lead طالما وضع الـ lead ما هو `'default'`، وإلا يشتغل بالـ `permissionMode` الخاص فيه. والـ sub-agent اللي أنشأته بـ `permissionMode: 'plan'` يبقى في plan mode مهما كان وضع الـ lead. الوضع يُقرأ عند كل tool call من الـ sub-agent، فلو بدّلت وضع session الـ lead ينطبق التبديل على sub-agent شغّال. وهذا اللي يخلي `task` آمنة في plan mode: الـ sub-agent هو أيضًا ما يقدر يغيّر شيء.

أما الـ [remote sub-agent](/ar/sub-agents) (`remoteAgent()`) فيشتغل على خادم ثاني وبصلاحيات ذلك الخادم، فما تقدر تلزمه بوضع الـ lead: في plan mode يُرفض الـ `task` call الموجّه له بدون حتى الاتصال فيه، وفي `dontAsk` الـ approval البعيد يفشّل الـ task بدل ما يوقّف الـ lead.

## الاستئناف بعد approval

الـ checkpoints وsnapshots الـ approvals ما تحفظ الوضع. الـ run اللي يكمّله `agent.approvals.resolve()` يستخدم الوضع الحالي للـ session المتوقفة لو كان الـ run المتوقف تابعًا لـ session، وإلا يستخدم وضع الـ agent (مش الوضع اللي مرّرته لـ `send()`). يعني turn توقفت في `'default'` وحُسمت بعد `session.setPermissionMode('dontAsk')` تشغّل الـ call الموافَق عليه، بعدين ترفض الـ calls اللي بعدها واللي كانت ستسأل. وفي plan mode ينرفض الـ call الموافَق عليه نفسه أيضًا لو الـ tool ما كانت read-only.

الاستئناف في process ثانية يستخدم الوضع اللي عند الـ agent أو الـ session اللي تستأنف.
