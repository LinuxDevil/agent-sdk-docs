**هندسة المراحل** هي خط مراحل حتمي يملأ فيه النموذج كل مرحلة، بينما يعود *الترتيب* و*البوابة* وتعريف *الاكتمال* إلى الـ harness. هذا هو الشكل الذي تقوم عليه مستودعات مسارات العمل الوكيلية (phases-oss وleeovery/agentic-workflows):

```text
discuss ──► spec ──► plan ──► implement ──► PROOF GATE ──► report ──► done
                               ▲               │
                               └── retry ──────┘ FAIL (bounded by maxRetries)
                                               │ PASS
```

بُني بالكامل على `FlowBuilder` و`FlowExecutor`: كل مرحلة هي `llmCall` تكتب متغيرًا مسمّى، وبوابة الإثبات هي `toolCall` تُجري فحصًا حقيقيًا، و`oneOf` يتفرّع بحسب الحكم.

## ما تعلّمه هذا المثال عن المنفِّذ

تختلف مجموعة العقد في وقت التشغيل عن أشكال المحرّر، ومن المفيد معرفة ذلك قبل كتابة مسارات العمل يدويًا:

- **لا توجد عقدة `loop` ولا خروج مبكر.** العقدة `loop` خاصة بالمحرّر، و`sequence` تنفّذ *كل* خطوة، و`return` تكتفي بحلّ قيمة. سلّم إعادة المحاولة المحدود هنا هو سلسلة من عقد `oneOf`، تحرس كل واحدة منها محاولة تنفيذ وفحص بالشرط `!check.startsWith('PASS')`. وبعد النجاح تصبح المحاولات المتبقية بلا أثر.
- **استبدال المتغيرات `{{var}}` في الموجّه مسطّح المفاتيح** (`\w+`، فلا يوجد `{{check.feedback}}`)، بينما تستخدم شروط `oneOf` قواعد التعابير الكاملة (`check.startsWith('PASS')` و`check.passed === true`). وإبقاء حكم البوابة نصًا من الشكل `'PASS: …' / 'FAIL: …'` يخدم الواجهتين معًا.
- **تأخذ `return` و`setVariable` مراجع `$var` إلى المتغير كاملًا**، لا حزم `{{spec}}` داخل كائنات حرفية، ولذلك تؤلّف مرحلة *التقرير* الأخيرة الناتج النهائي، ثم `return: '$deliverable'`.

لتشغيله:

```bash
npm run example:phase-pipeline    # offline, scripted phases + real node -e check
OPENROUTER_API_KEY=… npx tsx examples/phase-pipeline/index.ts
```
