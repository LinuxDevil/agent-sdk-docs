## handoffs ولا sub-agents؟

| استخدم | ما الذي يحدث |
| --- | --- |
| **Handoffs** | الـ target يتولى الأمور. يشوف المحادثة (أو ما يبقيه `inputFilter`)، يجاوب المستخدم بنفسه، ويظل الـ agent النشط في الـ session إلى أن يسلّم لغيره أو يرجّع. الـ agent الذي سلّم ما يشوف الرد. |
| **[Sub-agents](/ar/sub-agents)** | الـ lead يظل هو المسؤول. الـ sub-agent يشوف فقط الـ task prompt الذي كتبه الـ lead، ينفذ الشغل، ويرجع نتيجة للـ lead، والـ lead هو الذي يجاوب المستخدم. |

## البداية السريعة

أعطِ كل target `name` و`description` (الـ model يقرأ الـ description ليقرر
متى يسلّم)، وبعدها مرّرها للـ triage agent في `handoffs`. بادئة `vendor/`
في الـ model تختار الـ provider. مع OpenRouter استخدم
`openrouter/<vendor>/<model>` (مثال `openrouter/openai/gpt-4o-mini`):

```ts
import { createAgent, defineTool } from '@lousho/build-ai-agent';
import { z } from 'zod';

const lookupCharges = defineTool({
  name: 'lookup_charges',
  description: "Lists the user's recent charges",
  input: z.object({}),
  execute: async () => [{ date: '2026-09-01', amountUsd: 9.99 }],
});

const billing = createAgent({
  name: 'billing',
  description: 'Handles charges, refunds and subscriptions',
  instructions: 'You are the billing desk. Answer in one or two sentences.',
  model: 'openai/gpt-4o-mini',
  tools: [lookupCharges],
});

const techSupport = createAgent({
  name: 'tech-support',
  description: 'Handles logins, passwords and technical problems',
  instructions: 'You are tech support. Answer in one or two sentences.',
  model: 'openai/gpt-4o-mini',
});

const triage = createAgent({
  name: 'triage',
  instructions: 'Route the user: billing questions to billing, technical questions to tech-support.',
  model: 'openai/gpt-4o-mini',
  handoffs: [billing, techSupport],
});

const result = await triage.send('I was charged twice for my subscription.');
console.log(result.agentName, result.text); // 'billing', the billing desk's answer
```

كل target يُعرض على الـ model كـ tool واحدة اسمها `transfer_to_<name>`
(`transfer_to_billing` و`transfer_to_tech-support`). لما الـ model يستدعيها،
يكمل الـ run كـ target داخل نفس استدعاء `send()` / `stream()`.
و`result.agentName` هو اسم الـ agent الذي أنتج الرد الأخير.

الـ target لازم يجي من `createAgent()` ويكون له `name` (فريد بين الـ
handoffs) و`description` (أو `description` داخل `handoff()`). وإلا يرمي
`createAgent()` الخطأ `LOUSHO_CONFIG_INVALID`. واسم أداة الـ handoff ما
يجوز يطابق اسم أي tool من tools الـ agent.

## خيارات `handoff()`

غلّف الـ target بـ `handoff()` لتضبطه:

```ts
import { createAgent, handoff, handoffFilters } from '@lousho/build-ai-agent';
import { z } from 'zod';

const refunds = createAgent({ name: 'refunds', description: 'Issues refunds', model: 'openai/gpt-4o-mini' });

const triage = createAgent({
  name: 'triage',
  model: 'openai/gpt-4o-mini',
  handoffs: [
    handoff(refunds, {
      toolName: 'escalate_refund',
      description: 'Hand off when the user asks for money back',
      input: z.object({ orderId: z.string() }),
      inputFilter: handoffFilters.removeToolCalls,
      onHandoff: ({ from, to, args }) => console.log(`${from} -> ${to}`, args),
      isEnabled: ({ metadata }) => metadata?.plan === 'pro',
    }),
  ],
});
```

| الخيار | الافتراضي | ما الذي يفعله |
| --- | --- | --- |
| `toolName` | `transfer_to_<name>` | الـ tool الذي يستدعيه الـ model. |
| `description` | `description` الخاص بالـ target | وصف الـ tool. |
| `input` | `{ reason?: string }` | الوسائط التي يمرّرها الـ model (zod schema أو أي Standard Schema). وسائط لا تطابق تعطي الـ model خطأ tool، ولا يحدث handoff. |
| `inputFilter` | كل شيء | ما يشوفه الـ target (انظر [Input filters](#input-filters)). |
| `onHandoff` | لا شيء | يُستدعى مع `{ messages, from, to, args, sessionId }` بمجرد ما ينحسم الـ handoff، قبل أول استدعاء model من الـ target. |
| `isEnabled` | `true` | هل يُعرض الـ handoff؛ الدالة تستلم `{ input, metadata, principal, sessionId }` الخاصة بالـ run. أداة الـ handoff المعطّلة لا تُرسل للـ model. |

## Input filters

الـ target يشوف المحادثة كما يرجعها `inputFilter`، تحت الـ system prompt
الخاص به (system prompt الـ agent الذي سلّم يُستبدل، ولا يُحفظ أبدًا). الـ
filter يستلم `{ messages, from, to, args }`. و`messages` هي السجل حتى تلك
اللحظة بدون الـ system prompt، وتنتهي باستدعاء الـ handoff ونتيجته
و**routing note**: رسالة system يضيفها الـ run حتى يعرف الـ target مَن
حُوِّل وأي `args` اجتازت الـ validation
(`[routing note - not from the user] handoff triage -> billing: reason="..."`).
الرسالة موسومة بـ `metadata.handoff`، فيقدر الـ filter يتعرف عليها. احذفها
أو استبدلها وشكّل سياق الـ target بنفسك. في فلترين جاهزين:

- `handoffFilters.removeToolCalls`: يبقي نصوص المستخدم والـ assistant
  (والـ routing note)، ويحذف الـ tool calls ونتائجها.
- `handoffFilters.lastUserMessage`: يبقي آخر رسالة من المستخدم فقط.

```ts
import { handoffFilters, type HandoffInputData } from '@lousho/build-ai-agent';

// The last four messages, without tool traffic.
const recent = (data: HandoffInputData) => handoffFilters.removeToolCalls(data).slice(-4);
```

ما يرجعه الـ filter يصير سجل الـ run: `result.messages` وتاريخ الـ session
يكملان منه. الـ filter لازم يبقي رسالة واحدة على الأقل. الـ approvals
(الموافقات) المتذكَّرة بـ `once()` في الجزء الأقدم من السجل تُسقط عند الـ
handoff، فترجع tools الـ target تطلب الموافقة من جديد.

## ماذا يتغيّر وماذا يبقى

| عند الـ handoff، ما يخص الـ target نفسه | ما يخص الـ run، طوال مدته |
| --- | --- |
| الـ instructions (الـ system prompt) والـ model والـ provider | `hooks` و`limits` والإنفاق حتى الآن (ميزانية واحدة) |
| الـ tools والـ hosted tools والـ skills والـ sub-agents | `maxSteps`، ويُحسب عبر الـ agents كلهم |
| `reasoning` | إشارة الإلغاء (abort signal) |
| `handoffs` الخاصة به | الـ stores الخاصة بالـ approval والـ checkpoint والـ token |
| الـ guardrails وقواعد الصلاحيات: قواعد الـ lead أولًا ثم قواعد الـ target | `onEvent` و`exporter` |
| | `output`: نتيجة الـ run تكون typed حسب schema الـ lead (`output` الخاص بالـ target لا يُستخدم) |
| | وضع الصلاحيات والـ principal (مَن يعمل الـ run نيابة عنه) |
| | إعداد الـ approval: `approve` و`approvalStore` و`approvalTtlMs` و`onPermissionDecision` |

الـ agent الذي بدأ به الـ run هو الـ lead. الـ target لا يحصل على tools
الـ lead ولا sub-agents ولا خانات [memory](/ar/memory)؛ وخانات الـ memory
الخاصة به نفسها لا تُستخدم أيضًا (مثل الـ sub-agent). وتعليمات `output`
الخاصة بالـ lead تُضاف إلى system prompt كل target.

ولأن الـ approvals على مستوى الـ run، خيارات مثل `approve` و`approvalStore`
و`permissionMode` و`approvalTtlMs` و`store` على الـ target لا تُقرأ أبدًا
بعد الـ handoff. `createAgent()` يحذّر مرة واحدة (لكل target) إذا كان
target يمكن الوصول إليه قد أُنشئ بها. اضبطها على الـ agent الذي تبدأ به
الـ runs.

## Sessions

في الـ session، الـ agent النشط هو آخر واحد استلم المحادثة (قيمة `to` في
آخر علامة `metadata.handoff`). فالـ `session.send()` /
`session.stream()` التالي يشغّل ذلك الـ agent:

```ts
import { createAgent } from '@lousho/build-ai-agent';

const billing = createAgent({ name: 'billing', description: 'Handles charges and refunds', model: 'openai/gpt-4o-mini' });
const triage = createAgent({ name: 'triage', model: 'openai/gpt-4o-mini', handoffs: [billing] });

const session = triage.session();
await session.send('I was charged twice.'); // triage hands off; billing answers
const next = await session.send('Can you refund one?'); // billing answers again
console.log(next.agentName); // 'billing'
```

`agent.send()` بدون session يبدأ دائمًا من الـ lead.

الـ target يرجّع المحادثة عبر `handoffs` الخاصة به. ولأن الـ lead يُنشأ
بعد الـ targets، أعطِ الـ target مصفوفة وأضف الـ lead إليها لاحقًا
(المصفوفة تُقرأ في كل run):

```ts
import { createAgent, handoff, type Handoff } from '@lousho/build-ai-agent';

const billingHandoffs: Handoff[] = [];
const billing = createAgent({
  name: 'billing',
  description: 'Handles charges and refunds',
  instructions: 'For anything that is not about billing, hand back to triage.',
  model: 'openai/gpt-4o-mini',
  handoffs: billingHandoffs,
});
const triage = createAgent({
  name: 'triage',
  description: 'Routes the user to the right desk',
  model: 'openai/gpt-4o-mini',
  handoffs: [billing],
});
billingHandoffs.push(handoff(triage));
```

الأسماء هي التي تعرّف الـ agents: كل agent يمكن الوصول إليه عبر `handoffs`
لازم يكون له اسمه الخاص. إذا الـ agent الذي يذكره السجل لم يعد reachable،
يشتغل الـ lead.

## Approvals والاستئناف بعد handoff

tool تابعة للـ target تحتاج approval توقف الـ run في الـ approval store
الخاص بالـ lead، و`agent.approvals.resolve()` على الـ lead يكمله كـ
target. الـ run الذي له checkpoint (`send(message, { sessionId })` أو
session لها store) إذا وقع بعد handoff يُستأنف كـ target بـ
`agent.resume(id)` أو `session.resume()`. وفحص الـ drift عند الاستئناف
(`onAgentDrift`، انظر [Durable execution](/ar/durable-execution#استئناف-run-بعد-ما-يتغير-الـ-agent))
يقارن مع بصمة الـ target المحفوظة.

إذا كانت الخطوة فيها استدعاء handoff بجانب استدعاء يتوقف بانتظار approval،
الـ handoff ينتظر: الـ run يتوقف بصفة الـ agent الذي سلّم، ويحدث الـ
handoff بعد ما تُحسم الـ approval وتنفّذ بقية الاستدعاءات في الخطوة.

استدعاء `transfer_to_*` نفسه يمر بنفس بوابة أي tool call. قواعد
`permissions` تنطبق عليه: `deny` تعطي الـ model خطأ tool من نوع
`kind: 'denied'` ولا يحدث handoff، و`ask` توقف الـ run لأجل approval
وبعد حسمها الاستدعاء إما يسلّم أو يبلّغ الرفض. و`preToolCall` hooks تقدر
ترفضه أو تعيد كتابة وسائطه، والـ routing note والـ target يشوفان المدخل
المعدّل. والقرار يُوثَّق في `onPermissionDecision` / `permission.decision`
مثل أي tool call.

## الأحداث

الـ run يبلّغ عن الـ handoff بين `tool.start` / `tool.done` الخاصين
باستدعاء الـ handoff وأول `step.start` للـ target:

```ts
import { createAgent } from '@lousho/build-ai-agent';

const billing = createAgent({ name: 'billing', description: 'Handles charges and refunds', model: 'openai/gpt-4o-mini' });
const triage = createAgent({ name: 'triage', model: 'openai/gpt-4o-mini', handoffs: [billing] });

for await (const event of triage.stream('I was charged twice.')) {
  if (event.type === 'handoff') console.log(`${event.from} -> ${event.to}`); // triage -> billing
}
```

`handoff` يحمل `from` و`to` و`toolCallId`. وللـ run حدث `run.start` واحد
و`run.done` واحد مهما كثرت الـ handoffs. انظر الـ
[event schema](/ar/stream-events).

## القيود

- handoff واحد فقط في الدورة الواحدة للـ model: إذا استدعت الدورة عدة
  tools تسليم، يُنفَّذ الأول وتحصل البقية على خطأ tool.
- `maxHandoffs` (خيار في `createAgent()`، الافتراضي 5) يحد عدد handoffs
  الـ run الواحد، لمنع الـ agents من تمرير المحادثة ذهابًا وإيابًا. أي
  استدعاء handoff يتجاوز الحد يحصل على خطأ tool والـ agent يجاوب بنفسه.
  الـ run الذي يُستأنف بعد approval أو بعد سقوط يعد من الصفر من جديد.
- الـ remote agents (`remoteAgent()`) لا يمكن أن تكون targets للـ handoff؛
  استخدمها كـ sub-agents.
- الـ target لا يرجّع التسليم من نفسه في نهاية دورته؛ أعطِه handoff إلى
  الـ lead (انظر [Sessions](#sessions)).

## executor API

`AgentExecutor.execute()` يستلم `handoffs` (`ResolvedHandoff[]`: `name`
و`toolName` و`description` و`input` و`spec(input)` الذي يرجع إعداد run
الـ target وhandoffs الخاصة به، و`inputFilter` و`onHandoff`) و`maxHandoffs`.
`createAgent()` يبنيها. مرّرها بنفسك فقط لما تشغّل الـ executor مباشرة.
