مرّر `store` لـ`createAgent()` ومرّر `sessionId` لـ`send()`، والـ run يكمل رغم crash، أو restart، أو abort، أو approval (موافقة) من إنسان ياخد أيام. ولا شيء هنا يعتمد على host معيّن: أي `CheckpointStore` — `memoryStore()`، أو `SqliteStore`، أو store الـ Cloudflare KV اللي يوصّله build `cloudflare-worker`، أو تنفيذك الخاص بثلاث دوال — وأي `ApprovalStore` يشتغلون بنفس الطريقة.

```ts
import { createAgent } from 'lousho';
import { SqliteStore } from 'lousho/sqlite';

const agent = createAgent({ provider, store: new SqliteStore('./.lousho/jobs.db') });

// First message of a conversation.
await agent.send('Book a table for 2 tonight', { sessionId: 'chat-42' });

// Later - same process or another one - the next message of the same conversation.
await agent.send('Make it 3 people', { sessionId: 'chat-42' });

// After a crash: finish the interrupted run, if there is one (`null` when nothing is pending).
const finished = await agent.resume('chat-42');
```

خيار `store` هو اللي يسوي التوصيل كله: `store.checkpoints` يحمل checkpoints الـ run، و`store.approvals` يحمل توقفات الـ approval، و`agent.approvals.resolve()` تكمل تكتب checkpoints للـ run تحت `sessionId` حقه. `stream()` تاخذ `sessionId` أيضًا. والـ sessions (الجلسات) لها checkpoints هي كذلك: `agent.session({ id })` تحفظ checkpoint لكل turn، و`agent.resume(id)` (أو `session.resume()`) تنهي session انقطعت — شوف [durable sessions](/ar/sessions#durable-sessions).

تحت الغطاء، `createAgent()` تشغّل `AgentExecutor.execute()` مع `sessionId` و`checkpointStore`. السلوك الموصوف تحت هو سلوك الـ executor، و[القسم المتقدم](#متقدم-executor-api) يورّيك استدعاءاته.

## ماذا يُحفَظ في الـ checkpoint، ومتى

الـ checkpoint هو كامل transcript الـ run، زائد عدد خطواته و`usage` و`businessState` و`status`. `send()` (و`stream()`) تكتبه تحت `sessionId`:

| اللحظة | `status` |
| ------ | -------- |
| مباشرة بعد كل رد من الـ model يطلب tools، وقبل ما تشتغل أي tool | `'in-progress'` |
| كل مرة تتسجل نتيجة tool (النتائج تتسجل بترتيب الاستدعاء) | `'in-progress'` |
| لما يتوقف الـ run بـ abort (`signal`) | `'in-progress'` |
| لما يوقف الـ run على approval (لـ tool call خاصة فيه، أو خاصة بـ[sub-agent](/ar/sub-agents)، وأيضًا لما sub-agent مستأنف يوقف مرة ثانية) | `'awaiting-approval'` (مع `approvalId`) |
| لما يخلص الـ run (الـ model وقف ينادي tools، أو خلص `maxSteps`) | `'finished'` |

الـ run اللي يفشل (خطأ من الـ provider، أو hook يرمي خطأ، أو `PropagatingToolError`، أو crash في الـ process) يحتفظ بآخر checkpoint بـ`'in-progress'`. ولما يفشل برفض (وليس بـ crash)، الـ checkpoint ياخذ كمان الخطأ في `lastError` وعدد المحاولات الفاشلة في `attempts`، حتى تقدر [`agent.pending()`](#الاستعادة-بعد-crash) تميّز run يفشل مرة بعد مرة عن run قطعه crash. وأول checkpoint يحفظه الـ run بعدها (يعني تقدّم) يشيل الاثنين.

خلال ما يشتغل [sub-agent](/ar/sub-agents)، اللي صرفه إلى الآن ينحفظ على checkpoint الـ lead بعد كل نداء للـ model وكل نتيجة tool عنده (`delegatedInFlight`). الـ sub-agent نفسه ما ينحفظ له checkpoint: لو الـ lead صار له crash في منتصف sub-agent وبعدين استؤنف، نداء `task` يشتغل من جديد والـ sub-agent يبدأ من الصفر، لكن نداءات الـ model في المحاولة المنقطعة تبقى محسوبة في `usage` حق الـ run المستأنف (كـ run مفوَّض إضافي).

## ماذا يصير لو ترسل مرة ثانية بنفس `sessionId`

نتيجة نداء `send()` مرة ثانية بنفس `sessionId` (أو `execute()` عند الـ executor) تعتمد على `status` المحفوظة:

- **run غير مكتمل** (`'in-progress'`: صار crash، أو انقطع بـ abort، أو كتابة في الـ store فشلت). الـ run يستأنف (`agent.resume(sessionId)` تسوي نفس الشيء بدون input جديد). لو آخر turn للـ model فيها tool calls بدون نتيجة، هي بالضبط اللي تشتغل أول، عبر مسار الـ tools العادي (validation للـ arguments، hooks، `needsApproval`، `toolConcurrency`)، **بدون ما تنادي الـ model مرة ثانية**. بعدها تكمل الحلقة باللي باقي من ميزانية `maxSteps`، و`usage` يكمل من الإجماليات المحفوظة في الـ checkpoint (نفس الشيء بعد `agent.approvals.resolve()`، من الـ snapshot).
  - الـ `input` الجديد ينضاف كرسالة user بعد نتائج الـ tools هذي. وما ينحط أبدًا بين turn فيها tool calls ونتائجها، فيبقى الـ transcript صالح لكل provider. هذا اللي يخلي الـ user يقاطع run (بـ abort) ويوجّهه برسالة جديدة.
  - `input` يعيد إرسال نفس الرسالة اللي بدأ منها الـ run — وهذا الطبيعي لما تبغى retry لنفس الطلب بعد crash — ينعامل كـ retry وما ينضاف مرة ثانية. و`input: []` كمان بس يستأنف.
- **run مكتمل** (`'finished'`). الـ session تكمل كمحادثة: الرسائل المحفوظة تبقى، و`input` يصير turn الـ user التالية. مرّر بس الرسائل الجديدة؛ لو أعدت إرسال السجل المحفوظ وبعده رسائل جديدة، السجل يتعرف عليه وما يتكرر. `steps` و`usage` و`toolCalls` في النتيجة تعد من صفر للـ run الجديد؛ `messages` هي المحادثة كلها.
- **موقوف على approval** (`'awaiting-approval'`). `send()` ترمي `SessionAwaitingApprovalError` (فيها `sessionId` و`approvalId`) وما تنادي الـ model ولا أي tool: input جديد ما يجوز يتخطى قرار معلّق. احسمه أول بـ`agent.approvals.resolve()`، بعدين أرسل الرسالة الجديدة.

رسائل الـ system في `input` تتجاهل لما ينضاف `input` لـ session محفوظة (عندها الـ system prompt حقها أصلًا). لو تريد تنهي session وتبدأ من جديد بنفس الـ id، نادِ `store.checkpoints.delete(sessionId)`.

```ts
import { createAgent, memoryStore, SessionAwaitingApprovalError } from 'lousho';

const agent = createAgent({ provider, store: memoryStore() });

try {
  await agent.send('Are you done?', { sessionId: 'chat-42' });
} catch (error) {
  if (error instanceof SessionAwaitingApprovalError) {
    console.log(`Waiting on approval ${error.approvalId} - resolve it with agent.approvals.resolve() first.`);
  }
}
```

## approval في منتصف batch من tool calls

لما turn واحدة للـ model تطلب عدة tools وبعضها يحتاج approval، الـ calls اللي ما تحتاج approval تشتغل وتتسجل، والـ run يوقف مرة وحدة على كل call تحتاج approval (`approvalIds`، وسجل approval واحد لكل وحدة؛ شوف [عدة calls في خطوة واحدة](/ar/approvals#عدة-calls-في-خطوة-واحدة)). الـ calls اللي منعها steer من إنها تبدأ، وcalls الـ handoff في الـ turn، تتسجل في الـ approval snapshot (`remainingToolCalls`). أول ما تنحسم آخر call موقوفة، `agent.approvals.resolve()` — وتحتها الدالة المصدّرة `resumeAfterApproval()` — تسوي:

1. تسجل نتيجة كل call موقوفة، بترتيب الاستدعاء: نتيجة الـ tool لو انوافق عليها، أو نتيجة رفض منظمة `{ error, note }` لو انرفضت؛
2. تشغّل الـ calls الباقية بنفس منطق الـ batch: يمكن تشتغل، أو تفشل في الـ validation، أو توقف الـ run مرة ثانية على approval ثاني (`approvalId` جديد؛ احسمه بنفس الطريقة، وكرر قد ما لزم)؛
3. تنادي الـ model أول ما يصير لكل call في الـ turn نتيجة واحدة بالضبط.

```ts
import { createAgent, memoryStore } from 'lousho';

const agent = createAgent({ provider, store: memoryStore() });

const paused = await agent.send('Email the whole team', { sessionId: 'chat-42' });

if (paused.finishReason === 'awaiting-approval') {
  // ...a human decides, possibly days later, in another process (same store)...
  const result = await agent.approvals.resolve({ id: paused.approvalId!, approved: true });
  console.log(result.finishReason); // 'stop', or 'awaiting-approval' again for the next gated call
}
```

الـ run المستأنف يستخدم نفس `approvalStore` لأي approval لاحق، إلا لو مررت واحد ثاني في الخيارات.

## الاستعادة بعد crash

الـ run اللي انقطع (الـ process صار لها crash أو انقتلت في منتصف turn)، أو الموقوف على approval، يبقى في `store.checkpoints` لين أحد يكمّله. `agent.pending()` تعرض هذه الـ runs عبر كل session وكل id من `send(msg, { sessionId })`، فالـ process اللي أعيد تشغيلها تقدر تلقاها:

```ts
import { createAgent, fileStore } from 'lousho';

const agent = createAgent({ provider, store: fileStore('./.lousho') });

// At startup, before taking traffic:
for (const run of await agent.pending()) {
  if (run.status === 'in-progress') {
    // Finishes the turn without re-running recorded steps (tools that were mid-call run again: make them idempotent).
    await agent.resume(run.sessionId);
  } else {
    // 'awaiting-approval': hand run.approvalId to a human, or decide it here.
    console.log(`session ${run.sessionId} waits on approval ${run.approvalId}`);
  }
}
```

`agent.resume()` ترجع الـ `ExecutionResult` المكتمل (أو `null` لو ما في شيء معلّق)؛ وما ترجع stream. لو تبغى تتابع أحداث run مستأنف، سوّ له stream بدلها: `agent.stream([], { sessionId })` تستأنف checkpoint غير مكتمل من نوع `kind: 'run'` بدون input جديد (شوف [فوق](#ماذا-يصير-لو-ترسل-مرة-ثانية-بنفس-sessionid)) وترجع الـ `AgentRun` المعتاد. والـ run الموقوف يتبث بـ`agent.approvals.streamResolve()`.

`pending()` تقرأ من الـ checkpoint store المشترك، فتعرض كمان runs شغّالة الحين في process ثانية أو replica ثانية (كـ`'in-progress'`، بدون `lastError`)، وليس بس اللي صار لها crash. شوف تحت ليش استئناف وحدة منها آمن.

كل مدخل شكله `{ sessionId, kind, checkpointId, status, approvalId?,
approvalKind?, step, lastError?, attempts? }`:

- `sessionId` هو اللي تاخذه `agent.resume()`: id الـ `agent.session()` لـ turn في session (`kind: 'session'`، وcheckpoint حقها `<id>.turn-<n>`)، أو id الـ `send(msg, { sessionId })` (`kind: 'run'`، ويشمل الـ forks).
- `status` تكون `'in-progress'` (انقطع) أو `'awaiting-approval'` (احسم `approvalId` بـ`agent.approvals.resolve()`؛ و`agent.approvals.list()` تعرض الـ call).
- `lastError` يتعين لما آخر محاولة لـ turn في session، أو لـ run من `send(msg, { sessionId })` (`kind: 'run'`)، فشلت؛ و`attempts` يعد المحاولات اللي فشلت ورا بعض. مع `retryable: false` (مثلًا 400 من الـ provider) بيفشل مرة ثانية: صلّح السبب قبل `agent.resume()`، أو تخلّص منه بـ`agent.session({ id }).discardPending()` (للـ run: `store.checkpoints.delete(id)`). ومدخل `'in-progress'` بدون `lastError` يعني إنه انقطع (crash)، أو إنه لسا شغّال.

والـ run اللي لسا شغّال في أي process ينعرض هو كمان كـ`'in-progress'`. واستئنافه آمن: الـ run ماسك lease (شوف [Run leases](#run-leases))، فـ`agent.resume()` تفشل بـ`LOUSHO_SESSION_BUSY` قبل ما يشتغل أي شيء، بدل ما تشغّل الـ tool calls حقه مرة ثانية.

الـ checkpoint اللي ما ينقرأ (كتابة انقطعت بسبب انقطاع كهرباء على store ما عنده كتابات durable) ينعرض كـ`'in-progress'` مع `lastError.code` بقيمة `LOUSHO_CHECKPOINT_CORRUPT` (`retryable: false`)، وهو نفس الخطأ اللي تفشل به `send()` و`resume()`؛ تخلّص منه بـ`discardPending()` (أو `clear()`)، أو بـ`store.checkpoints.delete(id)` لو كان run.

### الاستعادة التلقائية

`agent.recover()` تطبّق هذه الوصفة عنك، في الخلفية: كل `intervalMs` (الافتراضي 30 ثانية) تجيب قائمة `agent.pending()` وتنادي `agent.resume()` على كل run بـ`'in-progress'`. شغّلها مرة وحدة لكل process، جنب الكود اللي يخدم الـ traffic:

```ts
import { createAgent, defineTool, memoryStore, PropagatingToolError } from 'lousho';
import { mockModel } from 'lousho/testing';
import { z } from 'zod';

let charges = 0;
let attempts = 0;
const tools = [
  defineTool({ name: 'charge', description: 'Charge the card', input: z.object({}), execute: async () => `charged ${++charges}` }),
  // Stands in for the process dying mid-step: it fails the first time only.
  defineTool({
    name: 'ship',
    description: 'Ship the order',
    input: z.object({}),
    execute: async () => {
      if (++attempts === 1) throw new PropagatingToolError('process died');
      return 'shipped';
    },
  }),
];
const agent = createAgent({
  provider: mockModel([{ toolCalls: [{ name: 'charge' }] }, { toolCalls: [{ name: 'ship' }] }, 'Order charged and shipped.']),
  tools,
  store: memoryStore(),
});
await agent.send('Charge and ship order 7', { sessionId: 'order-7' }).catch(() => undefined); // interrupted after the charge

const recovery = agent.recover({
  intervalMs: 1_000,
  onRecovered: (run, result) => {
    console.log(`${run.sessionId}: ${result.text}`); // order-7: Order charged and shipped.
    void recovery.stop(); // a server keeps it running and stops it on shutdown (or passes `signal`)
  },
  onError: (error, run) => console.error('recovery failed', run?.sessionId, error),
});
await recovery.done; // resolves once the loop stopped
console.log(charges); // 1: the completed charge step did not run again
```

ماذا يسوي كل sweep مع كل run معلّق:

- `'in-progress'`: يستأنف من آخر checkpoint حقه، فالخطوات المكتملة ما تتعاد أبدًا (الـ tool اللي كانت في منتصف call تشتغل من جديد: خلّها idempotent).
- `'awaiting-approval'` (approval لـ tool أو `ask_question`): يتركه؛ الإنسان يحسمه بـ`agent.approvals.resolve()`.
- run الـ `lastError` حقه فيه `retryable: false`: يتركه، لأنه بيفشل بنفس الطريقة؛ و`agent.pending()` تظل تعرضه.
- run لسا شغّال في process ثانية، أو run الـ [run lease](#run-leases) حق الـ process اللي صار لها crash ما انتهت صلاحيته إلى الآن: استئنافه يُرفض بـ`LOUSHO_SESSION_BUSY` قبل ما يشتغل أي شيء، بصمت، وsweep لاحق يحاول مرة ثانية أول ما يتحرر الـ lease. فالـ run اللي صار له crash يكتمل خلال انتهاء lease واحد زائد `intervalMs` واحد بعد الـ crash بالأكثر، وكل replica تقدر تشغّل `recover()`: الـ leases تضمن إن وحدة بس منها تستأنف الـ run. والحلقة كمان ما تبدأ أبدًا استئناف ثاني لـ run هي أصلًا تستأنفه.

`onError(error, run?)` يتبلّغ عن sweep ما قدر يقرأ قائمة الـ store (`run` بقيمة undefined) وعن استئناف فشل (`run` متعيّن)؛ والحلقة تكمل في الحالتين. و`onRecovered(run, result)` ياخذ كل run كمّلته. إلغاء `signal` (أو `stop()`) يوقف الـ polling ويسوي abort للاستئنافات الجارية (الـ checkpoints حقها تبقى للتشغيل الجاي)؛ و`done` تكتمل أول ما يستقر كل شيء. الحلقة تبقي الـ process حيّة لين توقفها. ومثل `pending()`، `recover()` ترمي `LOUSHO_CONFIG_MISSING_CHECKPOINT_STORE` لو ما في checkpoint store. ومع store مخصص ما عنده leases (`acquireLease`)، ما في شيء يمنعها من استئناف run لسا شغّال في process ثانية: شغّلها في process وحدة بس.

## Run leases

خلال ما يشتغل run عنده checkpoints (turn في session، أو run من `send(msg, { sessionId })`، أو استئناف بعد approval)، يمسك lease على id الـ checkpoint حقه في الـ checkpoint store: owner id وانتهاء صلاحية بعد 30 ثانية، يتجدد كل 10 ثواني. أي process ثانية أو replica ثانية أو store object ثاني يحاول يشغّل أو يستأنف نفس الـ id خلال هالوقت — `send()` كانت بتستأنف الـ turn المعلّقة أول، أو `agent.resume()`، أو `agent.approvals.resolve()` — يفشل بـ`LOUSHO_SESSION_BUSY` قبل ما تشتغل أي tool أو ينادى أي model (والـ approval المحسومة تبقى معلّقة). فـ replicaين ورا load balancer ما يشغّلون أبدًا tool calls نفس الـ turn مرتين.

الـ lease اللي ماسكه مات ينأخذ أول ما تنتهي صلاحيته. انتهاء الصلاحية ينحكم عليه بساعة الـ process اللي تبغى الـ lease مقابل وقت الانتهاء اللي كتبه الماسك بساعته هو، فالـ file store وSQLite store ينتظرون فترة lease إضافية (30 ثانية) بعده: الـ run اللي تركته process صار لها crash على جهاز ثاني ينأخذ بعد 30 إلى 60 ثانية من آخر heartbeat له، والـ replicas اللي ساعاتها تختلف بأقل من 50 ثانية تقريبًا ما تاخذ أبدًا الـ runs الحية حق بعضها. خلّ ساعات الـ replicas متزامنة (NTP)؛ فرق أكبر ممكن يخلي replicaين يشغّلون نفس الـ turn.

الـ file store وSQLite store ياخذون الـ lease فورًا، بدون انتظار، بس لما يكون ثابت إن ماسكه راح:

- run من نفس الـ process (نفس الـ thread ونفس نسخة الـ SDK) ما عاد شغّال، فمسار «أعد التشغيل واستأنف» المعتاد ما ينتظر؛
- على Linux، process خرجت، على نفس الـ host ونفس الـ boot ونفس الـ PID namespace (الـ lease يسجل الـ boot id والـ PID namespace ووقت بداية الـ process، فـ process id اتعاد استخدامه ما ينحسب حي أو ميت بالغلط)؛
- على macOS وWindows، process id على نفس الـ host ما عاد موجود.

run من worker thread ثاني في نفس الـ process، أو من container ثاني بنفس الـ hostname على volume مشترك (أو process أعيد تشغيلها في container جديد)، ما ينأخذ مبكرًا أبدًا: ينتظر انتهاء الصلاحية.

owner id حق الـ lease للـ run هو fencing token. الـ heartbeat يجدد الـ lease بس طول ما الـ run ماسكه (وما يسترجع أبدًا lease أخذته process ثانية، ولا lease انحرر بعد ما process ثانية كمّلت الـ run)، وكل checkpoint يحفظه الـ run ينكتب بس لو الـ run لسا ماسك الـ lease، بشكل atomic مع هالفحص في الـ file store وSQLite store والـ in-memory store. فلو run علّق مدة أطول من الـ lease حقه (الـ process توقفت مؤقتًا، أو الـ event loop انحجز) وprocess ثانية أخذته، الـ run المعلّق يوقف بـ`LOUSHO_SESSION_BUSY` عند الـ checkpoint التالي بدل ما يكتب فوق تقدم الماسك الجديد، والنتيجة المتأخرة لـ turn في session ما تنضاف للـ transcript. أما tool call كان الـ run المعلّق يسويها لما خسر الـ lease فما تنلغى: خلّ الـ tools idempotent في أي مكان ممكن يصير فيه تعليق.

الـ file store وSQLite store والـ in-memory store ياخذون الـ leases بشكل atomic. KV ما عنده compare-and-swap: `KVStore` يكتب الـ lease، ينتظر 50 ms ويقرأه من جديد، وهذا يرتّب الطلبات في موقع واحد لكن مو عبر edge locations ضمن تأخير الانتشار حق KV؛ والـ saves المحمية (fenced) عنده قراءة ثم كتابة. الـ `CheckpointStore` المخصص يشارك لو نفّذ `acquireLease(id, owner, ttlMs)` (عملية atomic: «خذ أو جدّد إلا لو owner ثاني ماسك lease ما انتهت صلاحيته»، ترجع `true` لما ينأخذ) و`releaseLease(id, owner)`؛ وبدونها الـ runs تشتغل بدون leases. ويقدر يضيف `renewLease(id, owner, ttlMs)` (يجدد بس الـ lease حق الـ owner نفسه) و`saveIfLeased(id, checkpoint, owner)` (يحفظ بس طول ما الـ owner ماسك الـ lease، بشكل atomic)؛ وبدونها الـ run يجدد الـ lease حقه بـ`acquireLease` قبل كل save مباشرة، وهذا يترك نافذة قصيرة.

خلال rolling upgrade من إصدار ما فيه run leases، الـ replicas القديمة لا تاخذ leases ولا تحترمها، فالـ turn ممكن تظل تشتغل على replica قديمة وجديدة بنفس الوقت لين كل الـ replicas تشغّل الإصدار الجديد. وملف SQLite database ينفتح بهذا الإصدار يتعمل له migration (جدول `leases`) وبعدها الإصدارات الأقدم ترفضه؛ للرجوع، استرجع نسخة من الملف.

الـ schedules تستخدم نفس الآلية: `fireSchedule()` (وبالتالي `startSchedules()`) تحجز وقت الإطلاق لكل schedule في الـ checkpoint store حق الـ agent أول، فالـ replicas اللي تطلق نفس الـ tick تشغّله مرة وحدة.

`agent.pending()` تحتاج checkpoint store فيه `list()`: الـ file store وSQLite store والـ in-memory store وKV store كلهم فيهم وحدة (`KVStore` يعرض القائمة بس لو الـ namespace binding حقه فيه `list`، مثل الحقيقي). على `CheckpointStore` مخصص، `list({ status? })` ترجع `{ sessionId, status, checkpoint }` لأحدث checkpoint لكل id؛ و`listCheckpoints(entries, options)` تسوي الفلترة والترتيب عنك. وبدونها `agent.pending()` ترمي `LOUSHO_CONFIG_INVALID`؛ وبدون checkpoint store أصلًا، ترمي `LOUSHO_CONFIG_MISSING_CHECKPOINT_STORE`.

## الضمانات

- **كل tool call تاخذ نتيجة واحدة بالضبط، بترتيب الاستدعاء**، مهما تتابعت الـ crashes والـ aborts والتوقفات والاستئنافات. (الـ call اللي انقطعت بـ abort تاخذ نتيجة "cancelled"؛ والـ call المرفوضة تاخذ نتيجة رفض.)
- **ما في call بنتيجة مسجلة يتعاد تنفيذه أبدًا.** كل نتيجة تنحفظ في الـ checkpoint بالـ `toolCallId` حقها أول ما تخلص الـ call — حتى لو خلصت ورا call أبطأ قبلها في نفس الـ turn — فالـ run المستأنف يشغّل بس الـ calls اللي ما عندها نتيجة مسجلة.
- **turn الـ model المحفوظ في checkpoint ما يتولّد من جديد أبدًا.** لو الـ process ماتت بعد ما الـ model رد، الـ run المستأنف ينفذ الـ tool calls اللي في الرد بدل ما يسأل الـ model مرة ثانية (ولا تكلفة زيادة ولا خطة مختلفة).
- **الـ provider يستقبل دائمًا transcript صالح**: نتائج الـ tools تجي مباشرة ورا turn الـ tool calls حقها، ورسائل الـ user الجديدة تجي بعدها.
- **الـ call الموافق عليها تشتغل مرة وحدة بالأكثر.** حسم الـ approval يحتفظ بـ checkpoint الـ run الموقوف: ينحفظ من جديد كـ`'in-progress'` والـ call الموافق عليها معلَّمة إنها بدأت (`startedToolCallIds`) قبل ما تشتغل، وينحفظ مرة ثانية مع نتيجتها قبل ما يكمل الـ run. لو الـ process ماتت والـ call الموافق عليها شغّالة، الـ turn ما تضيع: `pending()` تعرضها، واستئنافها ما يشغّل الـ call مرة ثانية. الـ call تاخذ نتيجة خطأ (`kind: 'interrupted'`) تقول للـ model إنها ممكن صار لها أثر وممكن لا، فيقدر الـ model يتحقق أو يسأل بدل ما يكررها بصمت — الإنسان وافق عليها مرة، مو مرتين.
- **الـ approval القديمة ما ترجع أبدًا.** الـ approval تكمّل الـ run حقها بس طول ما checkpoint هذا الـ run لسا ينتظرها. لو الـ checkpoint انحذف (`checkpoints.delete(id)`، أو `discardPending()`، أو prune) أو انستبدل بـ run أحدث تحت نفس الـ id، حسمها يفشل بـ`LOUSHO_APPROVAL_ORPHANED` ويسحبها، بدون ما يشغّل الـ tool أو يلمس الـ run الأحدث. و`discardPending()` تسحب approvals الـ turn اللي تخلّصت منها فورًا.

## تشغيل job مرة وحدة (إعادة تسليم الـ webhook)

الـ webhook أو الـ queue يسلّم مرة وحدة على الأقل، فنفس الـ payload ممكن يوصل مرتين. وإرساله مرة ثانية بنفس `sessionId` **مو** no-op: أول ما يصير الـ run الأول `'finished'`، الـ `send()` الثانية تصير turn جديدة في المحادثة وتنادي الـ model من جديد (في اختبار عند مستهلك، أعادت تشغيل سبع نداءات للـ model). لو تبغى تشغّل الـ job مرة وحدة، اشتق الـ `sessionId` من id التسليم وشوف الـ checkpoint قبل ما ترسل:

```ts
import { createAgent, memoryStore } from 'lousho';

const store = memoryStore();
const agent = createAgent({ provider, store });

export async function handleDelivery(deliveryId: string, payload: string) {
  const sessionId = `job-${deliveryId}`;
  const checkpoint = await store.checkpoints?.load(sessionId);

  if (checkpoint?.status === 'finished') return; // already done: acknowledge the redelivery
  if (checkpoint?.status === 'awaiting-approval') return; // paused: resolve it with agent.approvals.resolve()
  if (checkpoint) {
    await agent.resume(sessionId); // 'in-progress': a crash left it half done; finish it
    return;
  }
  await agent.send(payload, { sessionId });
}
```

الفحص ثم الإرسال مو atomic: تسليمين متزامنين ممكن الاثنين ما يلقون checkpoint. رتّب التسليمات لكل id ورا بعض (queue مفتاحها `deliveryId`، أو unique-insert في الـ database حقك) وخلّ الـ run lease شغّال (شوف [Run leases](#run-leases)) حتى تفشل الـ process الثانية بـ`LOUSHO_SESSION_BUSY` بدل ما تشغّل الـ job مرتين. والـ tools اللي تشتغل من جديد عند الاستئناف لازم تظل idempotent، فمرّر كمان `toolCallId` حق الـ call كـ idempotency key لكل side effect (شوف القسم التالي).

## At-least-once tools: خلّي الـ side effects idempotent

الـ tool اللي كانت **شغّالة** لما ماتت الـ process ما عندها نتيجة مسجلة، فتشتغل من جديد عند الاستئناف. يعني تنفيذ الـ tools هو at-least-once، وليس exactly-once. الـ tools اللي لها side effects (سحب مبلغ من بطاقة، إرسال إيميل): إما تحطها ورا `needsApproval` وإما تخليها idempotent. `toolCallId` حق كل call — وهو id الـ model للـ call، وما يتغير لما تنعاد نفس الـ call في الاستئناف — ينمرّر لـ`execute`، فيشتغل كـ idempotency key ضد إعادة تشغيل call وحدة:

```ts
import { defineTool } from 'lousho';
import { z } from 'zod';

declare const payments: { charge(amount: number, opts: { idempotencyKey: string }): Promise<{ id: string }> };

const chargeCard = defineTool({
  name: 'charge_card',
  description: 'Charge the customer',
  input: z.object({ amount: z.number() }),
  execute: async ({ amount }, { toolCallId }) =>
    payments.charge(amount, { idempotencyKey: toolCallId }), // a re-run cannot charge twice
});
```

(`toolCallId` يتعين في كل run لـ tool، بما فيها الـ tools اللي تمر عبر `sandboxExecute`.)

الـ file tools المدمجة آمنة لإعادة التشغيل. `write_file` تكتب نفس المحتوى مرة ثانية؛ و`edit_file` اللي تعديلها موجود أصلًا في الملف (`old_string` اختفى، و`new_string` غير فاضي موجود) تنجح وتقول إن التعديل مطبّق أصلًا، بدل ما تقول للـ model إن تعديل مطبّق فشل. ومع `WorkspaceCheckpoints`، الـ backup حق كل تغيير ينحفظ قبل ما ينكتب الملف، وإعادة التشغيل تحتفظ بأول backup، فـ`rewind()` يرجّع المحتوى الأصلي حتى بعد crash (شوف [Workspace tools](/ar/workspace-tools#الأدوات)). أما tool الـ `shell` فمو آمنة: الأمر اللي كان شغّال لما ماتت الـ process يشتغل من جديد.

`toolCallId` (و`ctx.approval.id` للـ call الموافق عليها) يحدد call وحدة سواها الـ model، ويحمي بس من إن هالـ call تشتغل مرتين. لو الـ process ماتت قبل ما تتسجل الـ call، الـ model ممكن يسوي نفس الـ call من جديد كـ call **جديدة** بـ id جديد وapproval جديدة، والـ id ما عاد يطابق. والـ side effect اللي لازم يصير مرة وحدة لكل حدث business (claim واحد، فاتورة وحدة) يحتاج idempotency key من بياناتك أنت، مثل id الـ claim في الـ arguments، تفحصه أو تمرره للنظام اللي تكتب فيه:

```ts
import { defineTool } from 'lousho';
import { z } from 'zod';

declare const claims: { file(claim: { claimId: string }, opts: { idempotencyKey: string }): Promise<{ id: string }> };

const fileClaim = defineTool({
  name: 'file_claim',
  description: 'File an insurance claim',
  input: z.object({ claimId: z.string() }),
  needsApproval: true,
  execute: async ({ claimId }) => claims.file({ claimId }, { idempotencyKey: `claim:${claimId}` }), // a new call for the same claim cannot file twice
});
```

## Checkpoint history

سجل الـ checkpoint يتكتب فوقه مع كل save، فخطوات الـ run الأقدم تروح أول ما يتقدم. الـ store يقدر أيضًا يحتفظ بـ history محدود لكل session: كل `save()` يضيف السجل لـ ring (أحدث `historyLimit` حفظة، والافتراضي 50؛ الأقدم ينحذف). وهذا اللي تتبني عليه إعادة replay لـ run أو عمل fork له من خطوة أقدم.

الـ stores اللي تحتفظ بـ history:

| Store | History | الخيار |
| --- | --- | --- |
| `memoryStore()` | نعم | `memoryStore({ historyLimit })` |
| `SqliteStore` | نعم (جدول `checkpoint_history`) | `new SqliteStore(path, { historyLimit })` |
| `LocalStorageCheckpointStore` | نعم | `new LocalStorageCheckpointStore(storage, { historyLimit })` |
| `fileStore(dir)` (ملفات JSON) | نعم (`checkpoint-history/<id>.json`) | `fileStore(dir, { historyLimit })` |
| `KVCheckpointStore` / `KVStore` (Cloudflare Workers KV، من `lousho/kv`) | نعم (شوف تحت) | `new KVStore(kv, { historyLimit })` |
| `FileCheckpointStore` حق Agent Forge | نعم | `new FileCheckpointStore(dir, { historyLimit })` |
| `CheckpointStore` مخصص | بس لو ينفذ `history()` | - |

مثال، مع store الذاكرة:

```ts
import { getCheckpointHistory, memoryStore } from 'lousho';

const { checkpoints } = memoryStore({ historyLimit: 20 }); // default 50, 0 keeps none
// new SqliteStore(path, { historyLimit }), new LocalStorageCheckpointStore(storage, { historyLimit })

// ... after a run with sessionId 'chat-42' ...
const history = await getCheckpointHistory(checkpoints, 'chat-42', { limit: 10 });
for (const { step, savedAt, status, checkpoint } of history ?? []) {
  console.log(step, status, savedAt, checkpoint.messages.length);
}

// Clear the checkpoint but keep its history (by default delete() clears both).
await checkpoints.delete('chat-42', { keepHistory: true });
```

- `history(sessionId, { limit? })` ترجع مدخلات `{ step, savedAt, status, checkpoint }`، الأحدث أول (`step` هو `checkpoint.stepIndex`، `savedAt` timestamp بصيغة ISO، و`status` تكون `'in-progress'` لـ checkpoint ما عنده حالة). الـ executor يحفظ بعد كل turn للـ model وكل batch من الـ tools، فكل session عندها مدخل لكل save. المدخلات فيها checkpoints كاملة، فخفّض `historyLimit` للـ transcripts الطويلة. session غير معروفة ترجع `[]`.
- `history` اختيارية في `CheckpointStore`: store مخصص بدونها يكمل يشتغل، و`getCheckpointHistory()` ترجع له `undefined` بدل ما ترمي.
- `KVCheckpointStore` يحتفظ بمفتاح index واحد لكل session (`<prefix><sessionId>#history`، وفيه ids المدخلات من الأقدم للأحدث) وبمفتاح واحد لكل مدخل (`<prefix><sessionId>#history/<id>`)، فما في قيمة تكبر مع الـ history. أحدث checkpoint يبقى عند `<prefix><sessionId>`، فـ store مكتوب قبل ما يوجد الـ history يتحمّل عادي. الـ save يكتب الـ checkpoint، بعدين المدخل، بعدين الـ index، بعدين يحذف المدخلات اللي أسقطها: crash بين كتابتين يترك بالأسوأ مدخل ما هو مدرج في الـ index (تنتهي صلاحيته مع الـ TTL)، وما يترك أبدًا store غير قابل للقراءة. KV ما عنده transactions، فحفظتين متزامنتين لنفس الـ session يمكن تضيّع تحديث واحد للـ index (المدخل يغيب عن `history()`)، ويمكن مدخل يغيب فترة في edge location ثانية (eventual consistency؛ و`history()` تتخطاه). وجّه طلبات الـ session لموقع واحد لما هذا يفرق. كل save يكلف `get` واحدة و`put`ين إضافية؛ و`historyLimit: 0` يطفيها.
- الـ file store حق Agent Forge يكتب الـ history ملف واحد لكل session (`.lousho/agents/<id>/checkpoint-history/<session>.json`، والاستبدال atomic). الملف اللي تلف من crash يتقري كأنه بدون history، والـ save التالية تبنيه من جديد.
- `SqliteStore` يحتفظ بالـ history في جدول جديد `checkpoint_history` يُضاف لما ينفتح ملف database موجود. و`prune()` تشيل مدخلات الـ history الأقدم من الـ cutoff حقها.

## Fork و replay

`agent.fork(sessionId, { fromStep, patch? })` تبدأ session جديدة من خطوة في history لـ session ثانية: «ماذا لو الـ tool أعادت شيء ثاني في الخطوة 1؟». تاخذ أحدث مدخل في الـ history للخطوة `fromStep`، تطبق `patch`، تحفظ الناتج كـ checkpoint بـ`'in-progress'` للـ session الجديدة على `store.checkpoints`، وترجع `{ sessionId, step, checkpoint }`. استأنف الـ fork مثل أي run غير مكتمل بـ`agent.resume(fork.sessionId)`:

```ts
import { createAgent, compareTrajectories, memoryStore } from 'lousho';

const store = memoryStore();
const assistant = createAgent({ provider, store });
await assistant.send('Plan my trip', { sessionId: 'trip' });

const fork = await assistant.fork('trip', { fromStep: 1, patch: { appendInput: 'It will rain, plan for that.' } });
// fork.sessionId is 'trip.fork-1'; the 'trip' checkpoint and history are unchanged.
const result = await assistant.resume(fork.sessionId);

const original = await store.checkpoints?.load('trip');
const replayed = await store.checkpoints?.load(fork.sessionId);
if (original && replayed) {
  const { divergedAt, a, b, drift } = compareTrajectories(original, replayed);
  console.log(divergedAt, a.length, b.length, drift); // 2, then each run's steps and the tool-call diff
}
```

`AgentExecutor.fork()` هي نفس العملية على الـ executor؛ شوف [القسم المتقدم](#متقدم-executor-api).

`agent.fork()` تسوي fork لـ run واحد من الـ checkpoint history حقه. لو تريد تفرّع محادثة `agent.session()` متعددة الـ turns، استخدم `session.history()` و`session.fork({ fromStep })`، والاثنين يشتغلون من الـ transcript المحفوظ للـ session مع أي store (الـ turns المنتهية ما تحتفظ بـ checkpoint history)؛ شوف [عمل fork للـ session](/ar/sessions#forking-a-session).

- `patch` يتطبق بهذا الترتيب: `messages(messages)` يعيد كتابة الـ transcript؛ `businessState` يستبدل القيمة المحفوظة؛ `toolResult: { toolCallId, result }` يستبدل نتيجة هالـ call في مكانها — نفس الموضع ونفس الـ call id ونفس اسم الـ tool، فيبقى الـ transcript صالح لكل provider — أو يسجلها لو الـ call ما عندها نتيجة إلى الآن؛ `appendInput` يضع رسالة user في الانتظار، تترسل بعد أي tool calls ما زالت معلقة.
- الـ fork يحتفظ بعدد خطوات الـ checkpoint المصدر و`usage` حقها، فينطبق عليه اللي باقي من ميزانية `maxSteps`. نتائج الـ tools المسجلة ما تتعاد؛ والـ tool calls اللي بدون نتيجة تشتغل أول، مثل أي استئناف (يعني fork لمدخل `'awaiting-approval'` يمر على `needsApproval` من جديد؛ و`approvalId` القديم ما ينتقل).
- `newSessionId` يسمي الـ fork؛ الافتراضي `<sessionId>.fork-<n>`، و`n` أول رقم ما عنده checkpoint. `newSessionId` اللي عنده checkpoint أصلًا يُرفض.
- خطوة ما هي موجودة في الـ history — الـ session غير معروفة، أو الخطوة ما اشتغلت أبدًا، أو انحذفت بعد ما تجاوزت `historyLimit` — ترمي `SDKError` بكود [`LOUSHO_CHECKPOINT_NOT_FOUND`](/ar/errors#lousho_checkpoint_not_found)، ورسالته تعدّد الخطوات المحفوظة. وstore بدون `history()` ما يقدر يسوي fork (`ConfigurationError`).
- `compareTrajectories(a, b)` تاخذ checkpointين أو transcriptين وترجع خطوات كل run — خطوة لكل turn للـ assistant: نصها وtool callsها مع نتائجها — و`divergedAt` (أول خطوة تختلف، بغض النظر عن ids الـ tool calls)، و`drift`، وهو فروق ترتيب الـ tools والـ arguments وعدد الخطوات وسبب الإنهاء، بنفس شكل `lousho eval --drift`.

## استئناف run بعد ما يتغير الـ agent

كل checkpoint وكل approval snapshot يحمل **fingerprint للـ agent** (بصمة): id الـ model، واسم كل tool مع hash للـ JSON input schema حق مدخلها، وhash لتعليمات النظام — زائد SHA-256 قصير على كل الأجزاء، محسوب بـ Web Crypto. الدوال والقيم اللي ما تنسلسل (`execute` حق الـ tool، الـ hooks، الـ callbacks) ما هي جزء منها، فتعديل الكود بس ما ينحسب تغيير أبدًا. الأجزاء تنحفظ كل واحد لحاله، حتى الـ mismatch يقدر يقول بالضبط ماذا تغيّر.

لما يستأنف run — `agent.resume(id)`، أو `session.resume()`، أو `execute()` لاحقة على `sessionId` غير مكتمل، أو `agent.approvals.resolve()` والنسخ الـ streamed — fingerprint الـ agent اللي يستأنف تتقارن بالمحفوظة، قبل أي نداء للـ model أو تشغيل tool. و`onAgentDrift` على `createAgent()` (وعلى `AgentExecutor.execute()` / الدالة المصدّرة `resumeAfterApproval()`) يقرر ماذا يسوي الاختلاف:

| `onAgentDrift` | لو الـ model أو الـ tools أو التعليمات اختلفت |
| -------------- | ------------------------------------------- |
| `'warn'` (الافتراضي) | `console.warn` يسمي اللي تغير وحدث `agent.drift` (`model`، `toolsAdded`، `toolsRemoved`، `toolsChanged`، `instructions`)؛ والـ run يكمل. |
| `'error'` | يرفض بـ[`LOUSHO_AGENT_DRIFT`](/ar/errors#lousho_agent_drift). الـ checkpoint يبقى مثل ما كان؛ والـ approval ترجع مكانها، فيقدر الـ agent الصحيح يحسمها بعدين. |
| `'ignore'` | لا شيء. |

tool call معلّقة الـ tool حقها ما عادت موجودة — آخر turn للـ model نادتها وما لها نتيجة إلى الآن، أو الإنسان وافق عليها — ترفض دائمًا بـ[`LOUSHO_RESUME_TOOL_MISSING`](/ar/errors#lousho_resume_tool_missing)، مهما كان الخيار.

```ts
import { createAgent, memoryStore } from 'lousho';
import type { LLMProvider } from 'lousho';

declare const provider: LLMProvider;

// After a deploy that renamed a tool or changed the model, refuse to continue old runs.
const agent = createAgent({ provider, store: memoryStore(), onAgentDrift: 'error' });
const result = await agent.resume('job-1');
```

ملاحظات:

- checkpoints وsnapshots مكتوبة قبل ما توجد هذه الميزة ما عندها fingerprint، وتستأنف بالضبط مثل قبل، بدون تحذير.
- run لـ[dynamic agent](/ar/api-overview#dynamic-config) يحفظ `ctx` والـ model اللي اختاره في الـ checkpoint (`runConfig`)، والاستئناف بعد crash يستخدمهما: الـ model المحفوظ، وtools وتعليمات تتحسب من جديد بالـ`ctx` المحفوظ (قبل كان الحساب يصير بـ`input: []` وبدون `metadata`).
- الـ fingerprint تغطي tools الـ agent نفسه والـ model والتعليمات حقه، وليس الـ tools اللي تضيفها `subagents` و`skills`. الـ sub-agent اللي يوقف على approval عنده fingerprint خاصة فيه في الـ snapshot المتداخلة. وعند الاستئناف، كل مستوى موقوف — الـ lead، والـ sub-agent، وsub-agent تابع لذلك الـ sub-agent — يتقارن بتعريفه الحالي من `subagents`، تحت `onAgentDrift` حق الـ lead. مع `'warn'` حدث `agent.drift` يحمل `subagent`. ولما فحص sub-agent يرفض، approval الـ lead وcheckpoint الـ`'awaiting-approval'` حقه يرجعون مكانهم، فينفع تصلّح الـ sub-agent وتحسم من جديد. أما [remote sub-agent](/ar/sub-agents#remote-sub-agents) فما يتقارن: توقفه يبقى محفوظ عند الطرف البعيد.
- الـ run اللي يستأنف بعد approval يكمل بالتعليمات اللي بدأ فيها (هي في الـ transcript حقه)، فالـ checkpoints اللي تجي بعد تسجل نفس التعليمات.

## متقدم: executor API

`createAgent()` مبنية فوق `AgentExecutor`، وهو يبقى متاح لما تريد تمسك التوصيل بنفسك: الـ provider والـ `ToolRegistry` والـ stores ونداءات الـ resume كلها صريحة (شوف [executor API](/ar/executor-api)). كل snippet تحت يقول استدعاء `createAgent()` اللي يقابله.

`AgentExecutor.execute()` مع `sessionId` و`checkpointStore` هي `agent.send(message, { sessionId })`:

```ts
import { AgentExecutor } from 'lousho/executor';
import { LocalStorageCheckpointStore } from 'lousho/utils';

const checkpoints = new LocalStorageCheckpointStore(storage);

// First message of a conversation.
await AgentExecutor.execute({ agent, input: 'Book a table for 2 tonight', provider, sessionId: 'chat-42', checkpointStore: checkpoints });

// Later - same process or another one - the next message of the same conversation.
await AgentExecutor.execute({ agent, input: 'Make it 3 people', provider, sessionId: 'chat-42', checkpointStore: checkpoints });
```

وهي ترمي `SessionAwaitingApprovalError` على session موقوفة، مثل ما تسوي `send()`:

```ts
import { AgentExecutor } from 'lousho/executor';
import { SessionAwaitingApprovalError, memoryStore } from 'lousho';

const { checkpoints } = memoryStore();

try {
  await AgentExecutor.execute({ agent, input: 'Are you done?', provider, sessionId: 'chat-42', checkpointStore: checkpoints });
} catch (error) {
  if (error instanceof SessionAwaitingApprovalError) {
    console.log(`Waiting on approval ${error.approvalId} - resolve it with resumeAfterApproval() first.`);
  }
}
```

الدالة المصدّرة `resumeAfterApproval()` هي اللي تناديها `agent.approvals.resolve()`:

```ts
import { AgentExecutor, resumeAfterApproval } from 'lousho/executor';

const paused = await AgentExecutor.execute({
  agent, input, provider, toolRegistry, approvalStore, sessionId: 'chat-42', checkpointStore,
});

if (paused.finishReason === 'awaiting-approval') {
  // ...a human decides, possibly days later, in another process...
  const result = await resumeAfterApproval(
    { id: paused.approvalId!, approved: true },
    approvalStore,
    toolRegistry,
    provider,
    {},
    checkpointStore, // clears the 'awaiting-approval' mark and keeps checkpointing
  );
  console.log(result.finishReason); // 'stop', or 'awaiting-approval' again for the next gated call
}
```

`AgentExecutor.fork()` هي `agent.fork()`؛ و`execute()` مع `input: []` على `sessionId` الـ fork هي `agent.resume(fork.sessionId)`:

```ts
import { AgentExecutor } from 'lousho/executor';
import { compareTrajectories, memoryStore } from 'lousho';

const { checkpoints } = memoryStore();
await AgentExecutor.execute({ agent, provider, toolRegistry, input: 'Plan my trip', sessionId: 'trip', checkpointStore: checkpoints });

const fork = await AgentExecutor.fork({
  sessionId: 'trip',
  fromStep: 1,
  checkpointStore: checkpoints,
  patch: { toolResult: { toolCallId: 'call_weather', result: { forecast: 'rain' } } },
});
// fork.sessionId is 'trip.fork-1'; the 'trip' checkpoint and history are unchanged.
await AgentExecutor.execute({ agent, provider, toolRegistry, input: [], sessionId: fork.sessionId, checkpointStore: checkpoints });

const original = await checkpoints.load('trip');
const replayed = await checkpoints.load(fork.sessionId);
if (original && replayed) {
  const { divergedAt, a, b, drift } = compareTrajectories(original, replayed);
  console.log(divergedAt, a.length, b.length, drift); // 1, then each run's steps and the tool-call diff
}
```


## التوافق مع البيانات المخزنة

- checkpoints مكتوبة قبل ما توجد `status` تنعامل كـ`'in-progress'` (قبل هذا التغيير، الـ runs المنتهية كانت تحذف الـ checkpoint حقها، فما كان ينحفظ إلا runs غير مكتملة).
- sessions محفوظة قبل ما الـ store يحتفظ بـ history يكون الـ history حقها فاضي لين الـ save التالية.
- approval snapshots مكتوبة قبل ما يوجد `remainingToolCalls` تستأنف مثل ما كانت: الـ calls اللي بعد الموقوفة ما تشتغل. كل واحدة منها تاخذ نتيجة خطأ تقول إنها ما اشتغلت، فيبقى الـ transcript صالح.

## القيود

- `sessionId` يعرّف محادثة منطقية واحدة. نداءات `agent.send()` / `agent.stream()` المتزامنة بنفس `sessionId` على store واحد للـ agent تشتغل ورا بعض، بترتيب الاستدعاء، في هذه الـ process. أما processين (أو store objectين على نفس البيانات) على نفس الـ id بنفس الوقت فالـ run lease يرفضها بـ`LOUSHO_SESSION_BUSY` (best effort على KV، شوف [Run leases](#run-leases))؛ ومع store مخصص ما عنده leases، آخر save هي اللي تفوز.
- id الـ run (`sessionId` حق `send()` / `stream()`) يكون من 1 إلى 200 حرف من الحروف والأرقام و`_` و`-` و`.`، وما يبدأ ولا ينتهي بـ`.`، على كل store، وما يجوز ينتهي بـ`.turn-<n>` أو `.paused` (مفاتيح الـ checkpoint الخاصة بالـ session) أو `.fire` (حجز الإطلاق حق schedule). وأي شيء ثاني يفشل بـ`LOUSHO_SESSION_ID_INVALID`. أما id الـ session (`agent.session({ id })`، و`sessionId` في الـ routes) فقاعدته أشد: من 1 إلى 128 حرف من `A-Za-z0-9_-`، بدون `.`.
- لو ناديت `resumeAfterApproval()` (الدالة اللي ورا `agent.approvals.resolve()`) بدون `checkpointStore`، الـ session تحتفظ بعلامة `'awaiting-approval'` ونداءات `send()` (أو `execute()`) اللاحقة تظل ترمي `SessionAwaitingApprovalError`؛ مرّر الـ store (أو احذف الـ checkpoint). `agent.approvals.resolve()` تمرره عنك.
- Workers KV عنده eventual consistency عبر المواقع — شوف [النشر](/ar/deployment) لتفاصيل هذا التحفّظ.
- صرف الـ sub-agent اللي كان لسا شغّال لما صار crash للـ lead ينحفظ للـ sub-agents اللي داخل الـ process بس، حسب آخر نداء model أو نتيجة tool عنده: الـ [remote sub-agent](/ar/sub-agents#remote-sub-agents) يبلّغ عن الـ usage حقه لما يخلص، فنداءات الواحد المنقطع ما تنحسب، والـ sub-agent اللي يشتغل في الخلفية ولسا شغّال بعد ما الـ lead وقف أو خلص ما يكتب في checkpoint الـ lead. وحدودهم تنفحص مقابل usage الـ sub-agent بس لما يرجع.
