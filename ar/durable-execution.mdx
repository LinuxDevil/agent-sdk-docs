مرّر `store` لـ`createAgent()` ومرّر `sessionId` لـ`send()`، والـ run يكمل رغم crash، أو restart، أو abort، أو approval (موافقة) من إنسان ياخد أيام. ولا شيء هنا يعتمد على host معيّن: أي `CheckpointStore` — `memoryStore()`، أو `SqliteStore`، أو store الـ Cloudflare KV اللي يوصّله build `cloudflare-worker`، أو تنفيذك الخاص بثلاث دوال — وأي `ApprovalStore` يشتغلون بنفس الطريقة.

```ts
import { createAgent } from '@lousho/build-ai-agent';
import { SqliteStore } from '@lousho/build-ai-agent/sqlite';

const agent = createAgent({ provider, store: new SqliteStore('./.lousho/jobs.db') });

// First message of a conversation.
await agent.send('Book a table for 2 tonight', { sessionId: 'chat-42' });

// Later - same process or another one - the next message of the same conversation.
await agent.send('Make it 3 people', { sessionId: 'chat-42' });

// After a crash: finish the interrupted run, if there is one (`null` when nothing is pending).
const finished = await agent.resume('chat-42');
```

خيار `store` هو اللي يسوي التوصيل كله: `store.checkpoints` يحمل checkpoints الـ run، و`store.approvals` يحمل توقفات الـ approval، و`agent.approvals.resolve()` تكمل تكتب checkpoints للـ run تحت `sessionId` حقه. `stream()` تاخذ `sessionId` أيضًا. والـ sessions (الجلسات) لها checkpoints هي كذلك: `agent.session({ id })` تحفظ checkpoint لكل turn، و`agent.resume(id)` (أو `session.resume()`) تنهي session انقطعت — شوف [durable sessions](/ar/sessions#durable-sessions).

تحت الغطاء، `createAgent()` تشغّل `AgentExecutor.execute()` مع `sessionId` و`checkpointStore`. السلوك الموصوف تحت هو سلوك الـ executor، و[القسم المتقدم](#متقدم-executor-api) يورّيك استدعاءاته.

## ماذا يُحفَظ في الـ checkpoint، ومتى

الـ checkpoint هو كامل transcript الـ run، زائد عدد خطواته و`usage` و`businessState` و`status`. `send()` (و`stream()`) تكتبه تحت `sessionId`:

| اللحظة | `status` |
| ------ | -------- |
| مباشرة بعد كل رد من الـ model يطلب tools، وقبل ما تشتغل أي tool | `'in-progress'` |
| كل مرة تتسجل نتيجة tool (النتائج تتسجل بترتيب الاستدعاء) | `'in-progress'` |
| لما يتوقف الـ run بـ abort (`signal`) | `'in-progress'` |
| لما يوقف الـ run على approval (لـ tool call خاصة فيه، أو خاصة بـ[sub-agent](/ar/sub-agents)، وأيضًا لما sub-agent مستأنف يوقف مرة ثانية) | `'awaiting-approval'` (مع `approvalId`) |
| لما يخلص الـ run (الـ model وقف ينادي tools، أو خلص `maxSteps`) | `'finished'` |

الـ run اللي يفشل (خطأ من الـ provider، أو hook يرمي خطأ، أو `PropagatingToolError`، أو crash في الـ process) يحتفظ بآخر checkpoint بـ`'in-progress'`.

## ماذا يصير لو ترسل مرة ثانية بنفس `sessionId`

نتيجة نداء `send()` مرة ثانية بنفس `sessionId` (أو `execute()` عند الـ executor) تعتمد على `status` المحفوظة:

- **run غير مكتمل** (`'in-progress'`: صار crash، أو انقطع بـ abort، أو كتابة في الـ store فشلت). الـ run يستأنف (`agent.resume(sessionId)` تسوي نفس الشيء بدون input جديد). لو آخر turn للـ model فيها tool calls بدون نتيجة، هي بالضبط اللي تشتغل أول، عبر مسار الـ tools العادي (validation للـ arguments، hooks، `needsApproval`، `toolConcurrency`)، **بدون ما تنادي الـ model مرة ثانية**. بعدها تكمل الحلقة باللي باقي من ميزانية `maxSteps`، و`usage` يكمل من الإجماليات المحفوظة في الـ checkpoint (نفس الشيء بعد `agent.approvals.resolve()`، من الـ snapshot).
  - الـ `input` الجديد ينضاف كرسالة user بعد نتائج الـ tools هذي. وما ينحط أبدًا بين turn فيها tool calls ونتائجها، فيبقى الـ transcript صالح لكل provider. هذا اللي يخلي الـ user يقاطع run (بـ abort) ويوجّهه برسالة جديدة.
  - `input` يعيد إرسال نفس الرسالة اللي بدأ منها الـ run — وهذا الطبيعي لما تبغى retry لنفس الطلب بعد crash — ينعامل كـ retry وما ينضاف مرة ثانية. و`input: []` كمان بس يستأنف.
- **run مكتمل** (`'finished'`). الـ session تكمل كمحادثة: الرسائل المحفوظة تبقى، و`input` يصير turn الـ user التالية. مرّر بس الرسائل الجديدة؛ لو أعدت إرسال السجل المحفوظ وبعده رسائل جديدة، السجل يتعرف عليه وما يتكرر. `steps` و`usage` و`toolCalls` في النتيجة تعد من صفر للـ run الجديد؛ `messages` هي المحادثة كلها.
- **موقوف على approval** (`'awaiting-approval'`). `send()` ترمي `SessionAwaitingApprovalError` (فيها `sessionId` و`approvalId`) وما تنادي الـ model ولا أي tool: input جديد ما يجوز يتخطى قرار معلّق. احسمه أول بـ`agent.approvals.resolve()`، بعدين أرسل الرسالة الجديدة.

رسائل الـ system في `input` تتجاهل لما ينضاف `input` لـ session محفوظة (عندها الـ system prompt حقها أصلًا). لو تريد تنهي session وتبدأ من جديد بنفس الـ id، نادِ `store.checkpoints.delete(sessionId)`.

```ts
import { createAgent, memoryStore, SessionAwaitingApprovalError } from '@lousho/build-ai-agent';

const agent = createAgent({ provider, store: memoryStore() });

try {
  await agent.send('Are you done?', { sessionId: 'chat-42' });
} catch (error) {
  if (error instanceof SessionAwaitingApprovalError) {
    console.log(`Waiting on approval ${error.approvalId} - resolve it with agent.approvals.resolve() first.`);
  }
}
```

## approval في منتصف batch من tool calls

لما turn واحدة للـ model تطلب عدة tools ووحدة منها تحتاج approval، الـ calls اللي قبلها تشتغل وتتسجل، والـ run يوقف عندها. الـ approval snapshot يسجل الـ calls اللي بعدها (`remainingToolCalls`). بعدها `agent.approvals.resolve()` — وتحتها الدالة المصدّرة `resumeAfterApproval()` — تسوي:

1. تسجل نتيجة الـ call الموقوفة: نتيجة الـ tool لو انوافق عليها، أو نتيجة رفض منظمة `{ error, note }` لو انرفضت؛
2. تشغّل الـ calls الباقية بنفس منطق الـ batch: يمكن تشتغل، أو تفشل في الـ validation، أو توقف الـ run مرة ثانية على approval ثاني (`approvalId` جديد؛ احسمه بنفس الطريقة، وكرر قد ما لزم)؛
3. تنادي الـ model أول ما يصير لكل call في الـ turn نتيجة واحدة بالضبط.

```ts
import { createAgent, memoryStore } from '@lousho/build-ai-agent';

const agent = createAgent({ provider, store: memoryStore() });

const paused = await agent.send('Email the whole team', { sessionId: 'chat-42' });

if (paused.finishReason === 'awaiting-approval') {
  // ...a human decides, possibly days later, in another process (same store)...
  const result = await agent.approvals.resolve({ id: paused.approvalId!, approved: true });
  console.log(result.finishReason); // 'stop', or 'awaiting-approval' again for the next gated call
}
```

الـ run المستأنف يستخدم نفس `approvalStore` لأي approval لاحق، إلا لو مررت واحد ثاني في الخيارات.

## الضمانات

- **كل tool call تاخذ نتيجة واحدة بالضبط، بترتيب الاستدعاء**، مهما تتابعت الـ crashes والـ aborts والتوقفات والاستئنافات. (الـ call اللي انقطعت بـ abort تاخذ نتيجة "cancelled"؛ والـ call المرفوضة تاخذ نتيجة رفض.)
- **ما في call بنتيجة مسجلة يتعاد تنفيذه أبدًا.** النتائج تنحفظ في الـ checkpoints كلما طالت سلسلة الـ calls المخلّصة بالترتيب؛ والـ run المستأنف يشغّل بس الـ calls اللي ما عندها نتيجة مسجلة.
- **turn الـ model المحفوظ في checkpoint ما يتولّد من جديد أبدًا.** لو الـ process ماتت بعد ما الـ model رد، الـ run المستأنف ينفذ الـ tool calls اللي في الرد بدل ما يسأل الـ model مرة ثانية (ولا تكلفة زيادة ولا خطة مختلفة).
- **الـ provider يستقبل دائمًا transcript صالح**: نتائج الـ tools تجي مباشرة ورا turn الـ tool calls حقها، ورسائل الـ user الجديدة تجي بعدها.

## At-least-once tools: خلّي الـ side effects idempotent

الـ tool اللي كانت **شغّالة** لما ماتت الـ process ما عندها نتيجة مسجلة، فتشتغل من جديد عند الاستئناف. يعني تنفيذ الـ tools هو at-least-once، وليس exactly-once. الـ tools اللي لها side effects (سحب مبلغ من بطاقة، إرسال إيميل): إما تحطها ورا `needsApproval` وإما تخليها idempotent. `toolCallId` حق كل call — وهو id الـ model للـ call، وما يتغير لما يعاد تنفيذه في الاستئناف — ينمرّر لـ`execute`، فيشتغل كـ idempotency key:

```ts
import { defineTool } from '@lousho/build-ai-agent';
import { z } from 'zod';

declare const payments: { charge(amount: number, opts: { idempotencyKey: string }): Promise<{ id: string }> };

const chargeCard = defineTool({
  name: 'charge_card',
  description: 'Charge the customer',
  input: z.object({ amount: z.number() }),
  execute: async ({ amount }, { toolCallId }) =>
    payments.charge(amount, { idempotencyKey: toolCallId }), // a re-run cannot charge twice
});
```

(`toolCallId` يتعين في كل run لـ tool، بما فيها الـ tools اللي تمر عبر `sandboxExecute`.)

## Checkpoint history

سجل الـ checkpoint يتكتب فوقه مع كل save، فخطوات الـ run الأقدم تروح أول ما يتقدم. الـ store يقدر أيضًا يحتفظ بـ history محدود لكل session: كل `save()` يضيف السجل لـ ring (أحدث `historyLimit` حفظة، والافتراضي 50؛ الأقدم ينحذف). وهذا اللي تتبني عليه إعادة replay لـ run أو عمل fork له من خطوة أقدم.

الـ stores اللي تحتفظ بـ history:

| Store | History | الخيار |
| --- | --- | --- |
| `memoryStore()` | نعم | `memoryStore({ historyLimit })` |
| `SqliteStore` | نعم (جدول `checkpoint_history`) | `new SqliteStore(path, { historyLimit })` |
| `LocalStorageCheckpointStore` | نعم | `new LocalStorageCheckpointStore(storage, { historyLimit })` |
| `fileStore(dir)` (ملفات JSON) | نعم (`checkpoint-history/<id>.json`) | `fileStore(dir, { historyLimit })` |
| `KVCheckpointStore` / `KVStore` (Cloudflare Workers KV، من `@lousho/build-ai-agent/kv`) | نعم (شوف تحت) | `new KVStore(kv, { historyLimit })` |
| `FileCheckpointStore` حق Agent Forge | نعم | `new FileCheckpointStore(dir, { historyLimit })` |
| `CheckpointStore` مخصص | بس لو ينفذ `history()` | - |

مثال، مع store الذاكرة:

```ts
import { getCheckpointHistory, memoryStore } from '@lousho/build-ai-agent';

const { checkpoints } = memoryStore({ historyLimit: 20 }); // default 50, 0 keeps none
// new SqliteStore(path, { historyLimit }), new LocalStorageCheckpointStore(storage, { historyLimit })

// ... after a run with sessionId 'chat-42' ...
const history = await getCheckpointHistory(checkpoints, 'chat-42', { limit: 10 });
for (const { step, savedAt, status, checkpoint } of history ?? []) {
  console.log(step, status, savedAt, checkpoint.messages.length);
}

// Clear the checkpoint but keep its history (by default delete() clears both).
await checkpoints.delete('chat-42', { keepHistory: true });
```

- `history(sessionId, { limit? })` ترجع مدخلات `{ step, savedAt, status, checkpoint }`، الأحدث أول (`step` هو `checkpoint.stepIndex`، `savedAt` timestamp بصيغة ISO، و`status` تكون `'in-progress'` لـ checkpoint ما عنده حالة). الـ executor يحفظ بعد كل turn للـ model وكل batch من الـ tools، فكل session عندها مدخل لكل save. المدخلات فيها checkpoints كاملة، فخفّض `historyLimit` للـ transcripts الطويلة. session غير معروفة ترجع `[]`.
- `history` اختيارية في `CheckpointStore`: store مخصص بدونها يكمل يشتغل، و`getCheckpointHistory()` ترجع له `undefined` بدل ما ترمي.
- `KVCheckpointStore` يحتفظ بمفتاح index واحد لكل session (`<prefix><sessionId>#history`، وفيه ids المدخلات من الأقدم للأحدث) وبمفتاح واحد لكل مدخل (`<prefix><sessionId>#history/<id>`)، فما في قيمة تكبر مع الـ history. أحدث checkpoint يبقى عند `<prefix><sessionId>`، فـ store مكتوب قبل ما يوجد الـ history يتحمّل عادي. الـ save يكتب الـ checkpoint، بعدين المدخل، بعدين الـ index، بعدين يحذف المدخلات اللي أسقطها: crash بين كتابتين يترك بالأسوأ مدخل ما هو مدرج في الـ index (تنتهي صلاحيته مع الـ TTL)، وما يترك أبدًا store غير قابل للقراءة. KV ما عنده transactions، فحفظتين متزامنتين لنفس الـ session يمكن تضيّع تحديث واحد للـ index (المدخل يغيب عن `history()`)، ويمكن مدخل يغيب فترة في edge location ثانية (eventual consistency؛ و`history()` تتخطاه). وجّه طلبات الـ session لموقع واحد لما هذا يفرق. كل save يكلف `get` واحدة و`put`ين إضافية؛ و`historyLimit: 0` يطفيها.
- الـ file store حق Agent Forge يكتب الـ history ملف واحد لكل session (`.lousho/agents/<id>/checkpoint-history/<session>.json`، والاستبدال atomic). الملف اللي تلف من crash يتقري كأنه بدون history، والـ save التالية تبنيه من جديد.
- `SqliteStore` يحتفظ بالـ history في جدول جديد `checkpoint_history` يُضاف لما ينفتح ملف database موجود. و`prune()` تشيل مدخلات الـ history الأقدم من الـ cutoff حقها.

## Fork و replay

`agent.fork(sessionId, { fromStep, patch? })` تبدأ session جديدة من خطوة في history لـ session ثانية: «ماذا لو الـ tool أعادت شيء ثاني في الخطوة 1؟». تاخذ أحدث مدخل في الـ history للخطوة `fromStep`، تطبق `patch`، تحفظ الناتج كـ checkpoint بـ`'in-progress'` للـ session الجديدة على `store.checkpoints`، وترجع `{ sessionId, step, checkpoint }`. استأنف الـ fork مثل أي run غير مكتمل بـ`agent.resume(fork.sessionId)`:

```ts
import { createAgent, compareTrajectories, memoryStore } from '@lousho/build-ai-agent';

const store = memoryStore();
const assistant = createAgent({ provider, store });
await assistant.send('Plan my trip', { sessionId: 'trip' });

const fork = await assistant.fork('trip', { fromStep: 1, patch: { appendInput: 'It will rain, plan for that.' } });
// fork.sessionId is 'trip.fork-1'; the 'trip' checkpoint and history are unchanged.
const result = await assistant.resume(fork.sessionId);

const original = await store.checkpoints?.load('trip');
const replayed = await store.checkpoints?.load(fork.sessionId);
if (original && replayed) {
  const { divergedAt, a, b, drift } = compareTrajectories(original, replayed);
  console.log(divergedAt, a.length, b.length, drift); // 2, then each run's steps and the tool-call diff
}
```

`AgentExecutor.fork()` هي نفس العملية على الـ executor؛ شوف [القسم المتقدم](#متقدم-executor-api).

`agent.fork()` تسوي fork لـ run واحد من الـ checkpoint history حقه. لو تريد تفرّع محادثة `agent.session()` متعددة الـ turns، استخدم `session.history()` و`session.fork({ fromStep })`، والاثنين يشتغلون من الـ transcript المحفوظ للـ session مع أي store (الـ turns المنتهية ما تحتفظ بـ checkpoint history)؛ شوف [عمل fork للـ session](/ar/sessions#forking-a-session).

- `patch` يتطبق بهذا الترتيب: `messages(messages)` يعيد كتابة الـ transcript؛ `businessState` يستبدل القيمة المحفوظة؛ `toolResult: { toolCallId, result }` يستبدل نتيجة هالـ call في مكانها — نفس الموضع ونفس الـ call id ونفس اسم الـ tool، فيبقى الـ transcript صالح لكل provider — أو يسجلها لو الـ call ما عندها نتيجة إلى الآن؛ `appendInput` يضع رسالة user في الانتظار، تترسل بعد أي tool calls ما زالت معلقة.
- الـ fork يحتفظ بعدد خطوات الـ checkpoint المصدر و`usage` حقها، فينطبق عليه اللي باقي من ميزانية `maxSteps`. نتائج الـ tools المسجلة ما تتعاد؛ والـ tool calls اللي بدون نتيجة تشتغل أول، مثل أي استئناف (يعني fork لمدخل `'awaiting-approval'` يمر على `needsApproval` من جديد؛ و`approvalId` القديم ما ينتقل).
- `newSessionId` يسمي الـ fork؛ الافتراضي `<sessionId>.fork-<n>`، و`n` أول رقم ما عنده checkpoint. `newSessionId` اللي عنده checkpoint أصلًا يُرفض.
- خطوة ما هي موجودة في الـ history — الـ session غير معروفة، أو الخطوة ما اشتغلت أبدًا، أو انحذفت بعد ما تجاوزت `historyLimit` — ترمي `SDKError` بكود [`LOUSHO_CHECKPOINT_NOT_FOUND`](/ar/errors#lousho_checkpoint_not_found)، ورسالته تعدّد الخطوات المحفوظة. وstore بدون `history()` ما يقدر يسوي fork (`ConfigurationError`).
- `compareTrajectories(a, b)` تاخذ checkpointين أو transcriptين وترجع خطوات كل run — خطوة لكل turn للـ assistant: نصها وtool callsها مع نتائجها — و`divergedAt` (أول خطوة تختلف، بغض النظر عن ids الـ tool calls)، و`drift`، وهو فروق ترتيب الـ tools والـ arguments وعدد الخطوات وسبب الإنهاء، بنفس شكل `lousho eval --drift`.

## استئناف run بعد ما يتغير الـ agent

كل checkpoint وكل approval snapshot يحمل **fingerprint للـ agent** (بصمة): id الـ model، واسم كل tool مع hash للـ JSON input schema حق مدخلها، وhash لتعليمات النظام — زائد SHA-256 قصير على كل الأجزاء، محسوب بـ Web Crypto. الدوال والقيم اللي ما تنسلسل (`execute` حق الـ tool، الـ hooks، الـ callbacks) ما هي جزء منها، فتعديل الكود بس ما ينحسب تغيير أبدًا. الأجزاء تنحفظ كل واحد لحاله، حتى الـ mismatch يقدر يقول بالضبط ماذا تغيّر.

لما يستأنف run — `agent.resume(id)`، أو `session.resume()`، أو `execute()` لاحقة على `sessionId` غير مكتمل، أو `agent.approvals.resolve()` والنسخ الـ streamed — fingerprint الـ agent اللي يستأنف تتقارن بالمحفوظة، قبل أي نداء للـ model أو تشغيل tool. و`onAgentDrift` على `createAgent()` (وعلى `AgentExecutor.execute()` / الدالة المصدّرة `resumeAfterApproval()`) يقرر ماذا يسوي الاختلاف:

| `onAgentDrift` | لو الـ model أو الـ tools أو التعليمات اختلفت |
| -------------- | ------------------------------------------- |
| `'warn'` (الافتراضي) | `console.warn` يسمي اللي تغير وحدث `agent.drift` (`model`، `toolsAdded`، `toolsRemoved`، `toolsChanged`، `instructions`)؛ والـ run يكمل. |
| `'error'` | يرفض بـ[`LOUSHO_AGENT_DRIFT`](/ar/errors#lousho_agent_drift). الـ checkpoint يبقى مثل ما كان؛ والـ approval ترجع مكانها، فيقدر الـ agent الصحيح يحسمها بعدين. |
| `'ignore'` | لا شيء. |

tool call معلّقة الـ tool حقها ما عادت موجودة — آخر turn للـ model نادتها وما لها نتيجة إلى الآن، أو الإنسان وافق عليها — ترفض دائمًا بـ[`LOUSHO_RESUME_TOOL_MISSING`](/ar/errors#lousho_resume_tool_missing)، مهما كان الخيار.

```ts
import { createAgent, memoryStore } from '@lousho/build-ai-agent';
import type { LLMProvider } from '@lousho/build-ai-agent';

declare const provider: LLMProvider;

// After a deploy that renamed a tool or changed the model, refuse to continue old runs.
const agent = createAgent({ provider, store: memoryStore(), onAgentDrift: 'error' });
const result = await agent.resume('job-1');
```

ملاحظات:

- checkpoints وsnapshots مكتوبة قبل ما توجد هذه الميزة ما عندها fingerprint، وتستأنف بالضبط مثل قبل، بدون تحذير.
- run لـ[dynamic agent](/ar/api-overview#dynamic-config) يحفظ `ctx` والـ model اللي اختاره في الـ checkpoint (`runConfig`)، والاستئناف بعد crash يستخدمهما: الـ model المحفوظ، وtools وتعليمات تتحسب من جديد بالـ`ctx` المحفوظ (قبل كان الحساب يصير بـ`input: []` وبدون `metadata`).
- الـ fingerprint تغطي tools الـ agent نفسه والـ model والتعليمات حقه، وليس الـ tools اللي تضيفها `subagents` و`skills`. الـ sub-agent اللي يوقف على approval عنده fingerprint خاصة فيه في الـ snapshot المتداخلة. وعند الاستئناف، كل مستوى موقوف — الـ lead، والـ sub-agent، وsub-agent تابع لذلك الـ sub-agent — يتقارن بتعريفه الحالي من `subagents`، تحت `onAgentDrift` حق الـ lead. مع `'warn'` حدث `agent.drift` يحمل `subagent`. ولما فحص sub-agent يرفض، approval الـ lead وcheckpoint الـ`'awaiting-approval'` حقه يرجعون مكانهم، فينفع تصلّح الـ sub-agent وتحسم من جديد. أما [remote sub-agent](/ar/sub-agents#remote-sub-agents) فما يتقارن: توقفه يبقى محفوظ عند الطرف البعيد.
- الـ run اللي يستأنف بعد approval يكمل بالتعليمات اللي بدأ فيها (هي في الـ transcript حقه)، فالـ checkpoints اللي تجي بعد تسجل نفس التعليمات.

## متقدم: executor API

`createAgent()` مبنية فوق `AgentExecutor`، وهو يبقى متاح لما تريد تمسك التوصيل بنفسك: الـ provider والـ `ToolRegistry` والـ stores ونداءات الـ resume كلها صريحة (شوف [executor API](/ar/executor-api)). كل snippet تحت يقول استدعاء `createAgent()` اللي يقابله.

`AgentExecutor.execute()` مع `sessionId` و`checkpointStore` هي `agent.send(message, { sessionId })`:

```ts
import { AgentExecutor } from '@lousho/build-ai-agent/executor';
import { LocalStorageCheckpointStore } from '@lousho/build-ai-agent/utils';

const checkpoints = new LocalStorageCheckpointStore(storage);

// First message of a conversation.
await AgentExecutor.execute({ agent, input: 'Book a table for 2 tonight', provider, sessionId: 'chat-42', checkpointStore: checkpoints });

// Later - same process or another one - the next message of the same conversation.
await AgentExecutor.execute({ agent, input: 'Make it 3 people', provider, sessionId: 'chat-42', checkpointStore: checkpoints });
```

وهي ترمي `SessionAwaitingApprovalError` على session موقوفة، مثل ما تسوي `send()`:

```ts
import { AgentExecutor } from '@lousho/build-ai-agent/executor';
import { SessionAwaitingApprovalError, memoryStore } from '@lousho/build-ai-agent';

const { checkpoints } = memoryStore();

try {
  await AgentExecutor.execute({ agent, input: 'Are you done?', provider, sessionId: 'chat-42', checkpointStore: checkpoints });
} catch (error) {
  if (error instanceof SessionAwaitingApprovalError) {
    console.log(`Waiting on approval ${error.approvalId} - resolve it with resumeAfterApproval() first.`);
  }
}
```

الدالة المصدّرة `resumeAfterApproval()` هي اللي تناديها `agent.approvals.resolve()`:

```ts
import { AgentExecutor, resumeAfterApproval } from '@lousho/build-ai-agent/executor';

const paused = await AgentExecutor.execute({
  agent, input, provider, toolRegistry, approvalStore, sessionId: 'chat-42', checkpointStore,
});

if (paused.finishReason === 'awaiting-approval') {
  // ...a human decides, possibly days later, in another process...
  const result = await resumeAfterApproval(
    { id: paused.approvalId!, approved: true },
    approvalStore,
    toolRegistry,
    provider,
    {},
    checkpointStore, // clears the 'awaiting-approval' mark and keeps checkpointing
  );
  console.log(result.finishReason); // 'stop', or 'awaiting-approval' again for the next gated call
}
```

`AgentExecutor.fork()` هي `agent.fork()`؛ و`execute()` مع `input: []` على `sessionId` الـ fork هي `agent.resume(fork.sessionId)`:

```ts
import { AgentExecutor } from '@lousho/build-ai-agent/executor';
import { compareTrajectories, memoryStore } from '@lousho/build-ai-agent';

const { checkpoints } = memoryStore();
await AgentExecutor.execute({ agent, provider, toolRegistry, input: 'Plan my trip', sessionId: 'trip', checkpointStore: checkpoints });

const fork = await AgentExecutor.fork({
  sessionId: 'trip',
  fromStep: 1,
  checkpointStore: checkpoints,
  patch: { toolResult: { toolCallId: 'call_weather', result: { forecast: 'rain' } } },
});
// fork.sessionId is 'trip.fork-1'; the 'trip' checkpoint and history are unchanged.
await AgentExecutor.execute({ agent, provider, toolRegistry, input: [], sessionId: fork.sessionId, checkpointStore: checkpoints });

const original = await checkpoints.load('trip');
const replayed = await checkpoints.load(fork.sessionId);
if (original && replayed) {
  const { divergedAt, a, b, drift } = compareTrajectories(original, replayed);
  console.log(divergedAt, a.length, b.length, drift); // 1, then each run's steps and the tool-call diff
}
```


## التوافق مع البيانات المخزنة

- checkpoints مكتوبة قبل ما توجد `status` تنعامل كـ`'in-progress'` (قبل هذا التغيير، الـ runs المنتهية كانت تحذف الـ checkpoint حقها، فما كان ينحفظ إلا runs غير مكتملة).
- sessions محفوظة قبل ما الـ store يحتفظ بـ history يكون الـ history حقها فاضي لين الـ save التالية.
- approval snapshots مكتوبة قبل ما يوجد `remainingToolCalls` تستأنف مثل ما كانت: الـ calls اللي بعد الموقوفة ما تشتغل. كل واحدة منها تاخذ نتيجة خطأ تقول إنها ما اشتغلت، فيبقى الـ transcript صالح.

## القيود

- `sessionId` يعرّف محادثة منطقية واحدة؛ تشغيل نداءين `send()` (أو نداءين `execute()`) على نفس الـ id بنفس الوقت غير مدعوم.
- لو ناديت `resumeAfterApproval()` (الدالة اللي ورا `agent.approvals.resolve()`) بدون `checkpointStore`، الـ session تحتفظ بعلامة `'awaiting-approval'` ونداءات `send()` (أو `execute()`) اللاحقة تظل ترمي `SessionAwaitingApprovalError`؛ مرّر الـ store (أو احذف الـ checkpoint). `agent.approvals.resolve()` تمرره عنك.
- Workers KV عنده eventual consistency عبر المواقع — شوف [النشر](/ar/deployment) لتفاصيل هذا التحفّظ.
