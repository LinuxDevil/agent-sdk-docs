الأمر `npx lousho build --target=cloudflare-worker --agent=agent.yaml` يولّد module Worker باسم `worker.ts`، و`wrangler.toml`، وbundle هو `dist/worker.js` يفحصه الـ build بحثًا عن استيرادات `node:`. يحتاج `tsup` و`wrangler` مثبتين، ويأخذ [ملف agent spec](/ar/configuration) أو [agent directory](/ar/agent-directories) (`npx lousho build ./my-agent --target=cloudflare-worker`). الـ Worker يقدّم نفس [HTTP API](/ar/deployment#http-api) التي تقدّمها الأهداف الثانية. هذا الهدف هو الأضيق حدودًا بين الثلاثة، فنبدأ بحدوده.

## ما يعمل وما لا يعمل


| الميزة | Cloudflare Worker | `node-server` / `docker` |
| ------- | ----------------- | ------------------------ |
| ملفات agent spec | نعم | نعم |
| [مجلدات agent](/ar/agent-directories) | نعم: config و`instructions.md` و`tools/` و`skills/` و`subagents/` و`schedules/` (قواعد cron في Worker) و`channels/` (تُركَّب تحت `/channels`) و`memory/` (`kvMemory()`، أو `inMemoryMemory()` لكل isolate) و`projectInstructions` (تُضمَّن وقت الـ build) | نعم، كلها |
| Providers | `mock` و`openai` و`anthropic` و`openrouter` | `mock` و`openai` و`anthropic` و`ollama` و`openrouter` |
| Tools مدمجة | `current-date` و`day-name` و`http` (أسماء الـ hosts المدرجة فقط، من الـ binding `LOUSHO_HTTP_ALLOW`) | كلها، بما فيها `http` و`web-fetch` |
| Tools مكتوبة بـ TypeScript | نعم، داخل agent directory: بلا Node builtins، ومن `@lousho/build-ai-agent` فقط الأسماء المذكورة تحت [مجلدات agent على Worker](#build-and-deploy) | نعم، داخل agent directory |
| تشغيل tools داخل sandbox | لا (الـ build يستبدل الـ sandbox بـ shim يفشل عند استخدامه) | نعم |
| خوادم MCP عبر stdio | لا (الـ child process لا يقدر يبدأ؛ والـ shim يفشل عند استخدامه) | نعم |
| [Code mode](/ar/code-mode) (`codeMode`) | لا (الـ build يستبدل QuickJS بـ shim يُفشل الـ run من بدايته) | نعم |
| خوادم MCP عبر HTTP | لم يُتحقق منه | نعم |
| Sessions وcheckpoints وapprovals | KV namespace واحد، `AGENT_CHECKPOINTS` (eventually consistent) | الذاكرة أو الملفات أو SQLite |
| Schedules | cron triggers فقط، بتوقيت UTC، خمسة حقول، بدقة دقيقة واحدة | تعبيرات cron كاملة مع time zone |
| الـ bundle | `lousho build` يفحص Node builtins ويبلّغ عن حجمه | لا يُفحص |
| [Route auth](/ar/auth) | الـ Bearer token `LOUSHO_API_TOKEN` فقط | التوكن، أو قائمة مرتبة (`jwt()` و`oidc()` و`basic()` و...) من `auth.ts` في agent directory |

`lousho build` يرفض spec يكون الـ provider أو الـ tool فيه خارج عمود Worker، ويرفض agent directory فيه مجلد أو إعداد لا يذكره عمود Worker. الخطأ `LOUSHO_DEPLOY_FAILED` يسمّي العنصر ويقترح `--target=node-server` أو `--target=docker`.

### Providers and tools

أسباب صفوف الـ providers والـ tools:

- الـ providers: `mock` و`openai` و`anthropic` و`openrouter`. الـ providers الحقيقية مبنية على
  `generateText`/`streamText` من `ai` SDK تبع Vercel
  مع `@ai-sdk/openai`/`@ai-sdk/anthropic` (و`openrouter` هو
  `@ai-sdk/openai` موجّه إلى `https://openrouter.ai/api/v1`)، وكلها
  مبنية على `fetch()` ومعايير الويب فقط بلا أي استيراد `node:*`،
  فتُجمَّع وتشتغل على Workers بنظافة؛ والـ leak check في الـ build يتحقق من
  كل bundle. الـ provider `ollama` **غير مدعوم** هنا: الـ endpoint الافتراضي
  محلي `http://localhost:11434` والـ Worker لا يصل إليه؛ استخدم
  `node-server` أو `docker` له؛
- الـ tools: `current-date` و`day-name` و`http`. الـ tool `web-fetch` **غير
  مدعومة**. على Node ترفض `http` و`web-fetch` الوجهات الخاصة
  عبر DNS lookup خاص بها (`node:dns` داخل `Agent` من `undici`)
  يفحص كل عنوان يُحلّ إليه الـ host ويتصل بالعنوان الذي فحصه،
  فهجوم DNS rebinding لا يتجاوز الفحص. الـ Worker لا يملك أيًّا
  من الاثنين: `fetch()` يحلّ الأسماء داخل شبكة Cloudflare
  ولا يعطي أي hook لرؤية العنوان أو تثبيته. الذي يقدر الـ Worker يفحصه هو
  الـ URL (الـ scheme، واسم الـ host، والـ host بصيغة IP literal)؛ والذي لا
  يقدر يضمنه هو إلى أين يتصل اسم الـ host، فاسم يُحلّ إلى
  عنوان داخلي لن يُكتشف. لذلك `http` على الـ Worker (بنفس اسم الـ tool
  `http_request` ونفس المدخلات كما على Node) هي tool مختلفة:
  توصل فقط إلى أسماء الـ hosts التي تدرجها. عند أول URL وعند كل
  redirect ترفض:
  - أي scheme غير `http:` و`https:`؛
  - host بصيغة IP (`http://10.0.0.1/` و`http://[::1]/`)، حتى لو كان
    مدرجًا: لا يوجد فحص للعناوين، فالمسموح أسماء فقط؛
  - host لا يطابق الـ binding `LOUSHO_HTTP_ALLOW`، وهو قائمة مفصولة بفواصل
    من أسماء الـ hosts (`api.github.com`) وwildcards بـ `*.`
    (`*.example.com`، وهي تطابق الـ subdomains فقط، لا `example.com` نفسه).
    إذا كان الـ binding غير مضبوط أو فارغًا يُرفض كل طلب (fail closed)؛ وإدخال
    ليس اسم host يُفشل كل طلب بخطأ يسمّيه.

  يعني الـ model لا يقدر يختار host عشوائي ولا host يستغل DNS rebinding،
  لأن الأسماء التي أدرجتها وحدها تمر؛ والاسم المدرج موثوق أينما
  حُلّ، فلا تدرج إلا hosts تتحكم بهم أو تثق بهم. TLS يُتحقق منه دائمًا
  (لا يوجد خيار `validateSSL`) والـ tool تشتغل بلا sandbox. أما tool
  من كتابتك تستدعي `fetch()` داخل Worker فلا تحصل على أي حماية
  من SSRF من الـ SDK.

## Build and deploy

الـ build يولّد module Worker (`export default { fetch }`، ومعه `scheduled` حين
يعلن المصدر cron triggers) ويجمّعه كـ ES module
لمنصة المتصفح؛ ويفشل الـ build إذا انتهى أي استيراد `node:` داخل
`dist/worker.js`. حقل `main` في `wrangler.toml` يشير إلى `dist/worker.js`
مع `no_bundle = true`، فيُرفع بالضبط الـ bundle الذي تم التحقق منه. يُبنى ويشتغل
مع `ai` v4 (التثبيت الافتراضي) أو `ai` v7 (مع
`@ai-sdk/openai`/`@ai-sdk/anthropic` v4) مثبتة، بلا أي
compatibility flag (يعني بلا `nodejs_compat`):

```bash
cd .lousho/build/cloudflare-worker
npx wrangler dev       # local workerd runtime
npx wrangler deploy    # requires a Cloudflare account (`wrangler login`)
```

مفاتيح API الخاصة بالـ providers تُقرأ من Worker bindings بأسماء `<TYPE>_API_KEY` (مثلًا
`wrangler secret put OPENAI_API_KEY` أو `wrangler secret put ANTHROPIC_API_KEY` أو
`wrangler secret put OPENROUTER_API_KEY`). والـ peer packages (`@ai-sdk/openai` لكل من
`openai` و`openrouter`، و`@ai-sdk/anthropic` لـ `anthropic`، و`ai`) يجب أن تكون
مثبتة بجانب `@lousho/build-ai-agent` كي يجمّعها `lousho build`.

**مجلدات agent على Worker.** الـ Worker لا يملك file system ولا يقدر يستورد
ملفًا بمساره وقت التشغيل، لذلك الـ build يقرأ
[agent directory](/ar/agent-directories) على Node ويكتب `agent.module.ts`:
استيراد ثابت لكل ملف `tools/*.ts` و`schedules/*.ts` و`channels/*.ts` و
`memory/*.ts` (ولإعدادات `agent.ts` / `agent.js` إن وُجدت)، وبشكل recursive
لكل مجلد `subagents/<name>/`، مع نسخ `instructions.md` وإعدادات JSON/YAML
والـ skills وملف `projectInstructions` كـ JSON. والـ Worker يبني الـ agent
بنفس قواعد `resolveAgentDir()` (مفاتيح الإعدادات، وصادرات
الـ tools، وأسماء الـ tools المكررة):

```bash
npx lousho build ./my-agent --target=cloudflare-worker
cd .lousho/build/cloudflare-worker && npx wrangler deploy
```

- يجب أن يسمّي `model` في الإعدادات provider من الجدول أعلاه (`"model": "openai/gpt-4o-mini"`)،
  ومفتاحه في الـ binding `OPENAI_API_KEY`؛ أو أن يضبط `agent.ts` الخاصية `provider` على instance.
  بادئة `vendor/` في الـ model تختار الـ provider؛ ومع OpenRouter استخدم
  `openrouter/<vendor>/<model>` (مثل `openrouter/openai/gpt-4o-mini`).
  لا توجد بيئة تعطي model افتراضي، لذلك يُرفض المجلد الذي يخلو من الاثنين.
- إعدادات JSON/YAML يفحصها `lousho build` (وإعدادات الـ sub-agent أيضًا، حين لا تكون
  كود)؛ أما إعدادات `agent.ts` فتُفحص عند إقلاع الـ Worker، فيبلّغ `wrangler deploy`
  عن المشكلة.
- مجلدات `subagents/<name>/` تُضمَّن بشكل recursive، وبنفس قواعد التخطيط المتبعة في
  مجلد الأب. كل واحد يحتاج `description` في إعداداته (يقرأها model الأب ليقرر
  متى يفوّض)؛ وtools الأب تكسب tool باسم `delegate_to_<name>` تشغّل turn الـ
  sub-agent. والـ sub-agent يرث model الأب ما لم تضبط إعداداته model خاصًا به.
- ملفات `schedules/` تصير [cron triggers](#scheduled-runs): الـ build يقيّم
  كل ملف ليكتب تعبير cron الخاص به في `[triggers] crons` ضمن `wrangler.toml`
  (نفس قواعد triggers الـ spec: UTC وخمسة حقول وأسماء الأيام)،
  والـ Worker المولَّد يصدّر handler باسم `scheduled()` يشغّلها. وبدون `schedules/`
  لا يوجد `scheduled()`.
- قنوات `channels/` تُركَّب تحت `/channels` (`POST /channels/<name>` و
  `POST /channels/<name>/approvals/:id`): نفس المسارات والقواعد التي يطبقها
  `mountChannels()` على Node، على Fetch API. والقنوات تصادق نفسها بنفسها
  (`verify`)، فـ `LOUSHO_API_TOKEN` لا يغطيها. والـ turn الذي يعيش أطول من
  الـ webhook الذي أُقرّ به يكمل العمل تحت `ctx.waitUntil`.
- خانات `memory/` تحتاج provider يشتغل بلا file system. `kvMemory()` يحفظ عناصر
  الخانة تحت مفاتيح `memory/<scope>` في KV namespace المسمى
  `AGENT_CHECKPOINTS` (أو في الـ binding الذي يسمّيه خيار `binding`)؛ وبدون ذلك
  الـ binding تعيش العناصر في ذاكرة isolate واحد. `inMemoryMemory()` يعمل بنفس
  الطريقة؛ أما `fileMemory()` فلا يمكن تشغيله هنا.
- `projectInstructions: true` يقرأ أقرب `AGENTS.md` / `CLAUDE.md` **وقت
  الـ build** ويضمّن نصه؛ وكائن الخيارات (`cwd` و`files`) في إعدادات
  JSON/YAML يُحترم بنفس الطريقة. أما في إعدادات `agent.ts` فيمكن تضمين
  `true` فقط — كائن الخيارات يُرفض عند إقلاع الـ Worker.
- ملفات الـ tools تُجمَّع من مكانها، فتنحلّ استيراداتها النسبية و
  `node_modules` الخاصة بها كما في التطوير. والـ tool التي تستورد Node builtin تُفشل
  الـ leak check في الـ build، الذي يسمّي الملف.
- داخل tool أو `agent.ts`، تكون `@lousho/build-ai-agent` subset آمنًا للـ Worker من الحزمة:
  `defineTool` و`isDefinedTool` و`always` و`never` و`once` و`defineSkill` و`defineSchedule` و
  `isDefinedSchedule` و`defineChannel` و`httpChannel` و`slackChannel` و`discordChannel` و
  `telegramChannel` و`githubChannel` و`teamsChannel` و`defineMemory` و`inMemoryMemory` و
  `kvMemory` و`createMockProvider` و`MockLLMProvider` و`OpenAIProvider` و`AnthropicProvider` و
  `OpenRouterProvider` و`fromAiSdk` و`LLMProviderRegistry` و`textOf` و`SDKError` و
  `ConfigurationError` و`ToolExecutionError` و`ValidationError`. واستيراد أي اسم آخر
  يُفشل الـ build مع عرض هذه القائمة؛ أما type-only imports فتعمل لكل type.

إلى ماذا تصل الـ tool على Worker: ملف الـ tool يشتغل داخل isolate الـ Worker، لا داخل
sandbox، وبنفس صلاحيات باقي الـ Worker. يقدر يستدعي `fetch()` لأي host
(`LOUSHO_HTTP_ALLOW` يقيّد الـ tool المدمجة `http` فقط، لا كودك)، ويشارك
ذاكرة الـ isolate مع كل session يخدمها الـ isolate (وبدون
`AGENT_CHECKPOINTS` يشمل ذلك الـ sessions نفسها). الـ SDK لا يعطي الـ tool كائن
`env` تبع الـ Worker (مفاتيح API الخاصة بالـ providers و`LOUSHO_API_TOKEN` والـ KV namespace)،
والـ build لا يحلّ استيرادات `cloudflare:`، فيفشل الـ build عند
`import { env } from 'cloudflare:workers'`؛ لكن الكود داخل isolate واحد ليس حدًّا أمنيًا. لا تنشر إلا كود
tools تثق فيه مع هذه الـ bindings.

## Bindings

الـ Worker يقدّم [HTTP API](/ar/deployment#http-api): `GET /health`، و`POST /chat`
مبثوثًا كـ SSE (`ReadableStream`)، و`GET /chat/:sessionId`، وendpoint
الـ approvals، وجسم `{ "message" }` المُهمَل. وقنوات `channels/` في agent
directory تضيف مساراتها تحت `/channels` (انظر أعلاه). الـ bindings تبعه:

| الـ binding | النوع | وظيفته |
| ------- | ---- | ------------ |
| `LOUSHO_API_TOKEN` | secret (`npx wrangler secret put LOUSHO_API_TOKEN`) | يجعل كل route عدا `/health` يشترط `Authorization: Bearer <token>` (مقارنة constant-time، وإلا يرجع `401` بـ JSON). بدونه يكون الـ Worker مفتوحًا لأي شخص يعرف رابطه، لذلك **اضبطه قبل النشر**. |
| `AGENT_CHECKPOINTS` | KV namespace | يحفظ الـ sessions والـ checkpoints والـ approvals الموقوفة وعناصر `kvMemory()` في namespace واحد، كـ `KVStore` (أدناه). بدونه تعيش في ذاكرة isolate واحد تعيد Cloudflare تدويره متى شاءت: مناسب لتجربة deploy، لا للإنتاج. |
| `LOUSHO_HTTP_ALLOW` | variable (`[vars]` في `wrangler.toml`) | أسماء الـ hosts التي يجوز للـ tool `http` الوصول إليها، مفصولة بفواصل: `api.github.com`، أو `*.example.com` للـ subdomains فقط. إذا كان غير مضبوط أو فارغًا يُرفض كل طلب `http`. راجع [Providers and tools](#providers-and-tools). |

يُولَّد `wrangler.toml` وكتلة `[[kv_namespaces]]` الخاصة بـ
`AGENT_CHECKPOINTS` فيه معلّقة، مع أوامر إنشاء الـ namespace
(`npx wrangler kv namespace create AGENT_CHECKPOINTS`، ونسخة
`--preview` منها) ومكان لصق الـ ids الناتجة. أزل التعليق عنها واملأ الـ ids.
وإذا كانت الـ spec تدرج `http` ففيه أيضًا كتلة `[vars]` معلّقة من أجل
`LOUSHO_HTTP_ALLOW`؛ أزل التعليق عنها واذكر الـ hosts تبعك:

```toml
[vars]
LOUSHO_HTTP_ALLOW = "api.github.com,*.example.com"
```

```bash
cd .lousho/build/cloudflare-worker
npx wrangler secret put LOUSHO_API_TOKEN
npx wrangler secret put OPENAI_API_KEY
npx wrangler deploy
curl -N https://<your-worker>.workers.dev/chat \
  -H "Authorization: Bearer $LOUSHO_API_TOKEN" -H 'Content-Type: application/json' \
  -d '{ "sessionId": "alice", "input": "Hello" }'
```

## Sessions, checkpoints and approvals

`KVStore(kvBinding, { prefix?, ttl?, historyLimit?, tokenKey? })` هو الـ `AgentStore` الذي
يبنيه الـ Worker المولَّد من الـ binding. أما الـ Worker المكتوب باليد فيستورده من
الـ subpath `/kv`، الذي لا يحتوي أي استيراد `node:*` في أي موضع من dependency graph تبعه،
مع تعريف الـ binding بالنوع `KVBinding` (الجزء `get`/`put`/`delete` من
`KVNamespace` في Cloudflare، فلا تحتاج `@cloudflare/workers-types`). و`createAgent` يأتي
من الـ subpath `/worker` — راجع [كتابة Worker بنفسك](#كتابة-worker-بنفسك):

```ts
import { createAgent } from '@lousho/build-ai-agent/worker';
import { KVStore, type KVBinding } from '@lousho/build-ai-agent/kv';

interface Env {
  AGENT_KV: KVBinding;
}

export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    const agent = createAgent({ provider, store: new KVStore(env.AGENT_KV) });
    const { sessionId, input } = (await request.json()) as { sessionId: string; input: string };
    const { text } = await agent.session({ id: sessionId }).send(input);
    return Response.json({ text });
  },
};
```

`/kv` يصدّر أيضًا `KVCheckpointStore` (للـ checkpoints فقط) و
`CHECKPOINT_KV_BINDING` (`'AGENT_CHECKPOINTS'`، وهو اسم الـ binding الذي يقرؤه الـ Worker
المولَّد). مفاتيح `KVStore`، وقبل كل منها `prefix` اختياري:

| المفتاح | القيمة |
| --- | ----- |
| `sessions/<id>` | الـ transcript كـ JSON (بايتات الصور والملفات كـ `{ "$bytes": "<base64>" }`، مثل `FileSessionStore`). |
| `checkpoints/<id>` | الـ `Checkpoint` الخاص بـ durable run أو turn لـ session (`KVCheckpointStore`، وسجلّه تحت `checkpoints/<id>#history`). |
| `approvals/<id>` | approval موقوف والـ snapshot الذي يستأنفه (يُحذف عند البتّ فيه). |
| `oauth/tokens/<key>` و`oauth/pending/<state>` | OAuth tokens وعمليات تسجيل دخول معلّقة، مشفّرة بـ `tokenKey` (الـ secret `LOUSHO_TOKEN_KEY` في الـ Worker المولَّد)؛ راجع [OAuth](/ar/oauth#تخزين-tokens). |
| `memory/<scopeKey>` | عناصر خانة ذاكرة `kvMemory()` (`global` أو `session:<id>` أو مفتاح scope مخصص) — يكتبها الـ provider نفسه، لا `KVStore`. |

`ttl: { sessions?, checkpoints?, approvals? }` (بالثواني، وKV يقبل 60 فأكثر)
يجعل كل نوع سجل ينتهي بعد هذه المدة من آخر كتابة؛ وافتراضيًا
تبقى السجلات حتى تُحذف.

يمكن البتّ في approval أوقف turn في طلب ما، عبر طلب لاحق
على isolate آخر: الـ session ذات الـ checkpoint تسمّي الـ approval المعلّق،
وendpoint الـ approvals يتابعه من KV. والمتابعة تُبث كـ run مستأنف عادي:
`tool.resume` و`tool.done` للاستدعاء الذي بُتّ فيه (`tool.error` عند الرفض)،
ثم أحداث الـ turn، وتنتهي بـ `run.done` يحمل النص النهائي.

الـ `POST /chat { "message", "sessionId"? }` المُهمَل يحتفظ بسلوكه القديم
على Workers: مع `sessionId` يُحفَظ الـ run كـ checkpoint في
`checkpoints/<sessionId>` بعد كل نتيجة tool، وطلب لاحق
يعيد استخدام `sessionId` يستعيده (بعد crash أو إعادة تدوير isolate).

## Scheduled runs

الـ cron triggers في الـ spec (`triggers: [{ type: 'cron', cron: '0 9 * * MON', input: '...' }]`)
تصير `[triggers] crons = [...]` في `wrangler.toml`، والـ Worker المولَّد
يصدّر handler باسم `scheduled()` يشغّلها كـ turns للـ agent (الـ session
`schedule-<name>`، راجع [Schedules](/ar/schedules#على-cloudflare-workers)). وملفات `schedules/` في agent
directory تعمل بنفس الطريقة: الـ build يقيّمها لاستخراج التعابير ويولّد تصدير
`scheduled()`. Cloudflare تقيّم
التعابير بتوقيت **UTC** وبدقة دقيقة واحدة؛ والـ build يرفض
`timezone` أو حقل ثوانٍ أو اختصار `@daily` أو يوم أسبوع
رقمي (`LOUSHO_SCHEDULE_INVALID`).

وفي Worker تكتبه بنفسك، اربط agent معرَّفًا في الكود عبر
`handleScheduled(agent, schedules, controller, ctx)` (مُصدَّرة من
`@lousho/build-ai-agent/worker` —
فالمحدِّد `@lousho/build-ai-agent/deploy-runtime-worker` في الكود المولَّد
محدِّد virtual لا يحلّه إلا الـ bundler تبع `lousho build`؛ لا تستورده بنفسك). تشغّل الـ schedules التي
يساوي `cron` فيها `controller.cron` داخل `ctx.waitUntil()` ولا ترمي أي شيء؛
وعليك أنت إدراج التعابير نفسها تحت `[triggers] crons`. أعطِ الـ agent store —
فبدونها تعيش session `schedule-<name>` الخاصة بالـ run المجدول في ذاكرة isolate واحد
وتختفي عند إعادة تدويره:

```ts
import { createAgent, createMockProvider, defineSchedule, handleScheduled } from '@lousho/build-ai-agent/worker';
import type { ScheduledContext, ScheduledController } from '@lousho/build-ai-agent/worker';
import { KVStore, type KVBinding } from '@lousho/build-ai-agent/kv';

interface Env {
  AGENT_CHECKPOINTS: KVBinding;
}

const schedules = [defineSchedule({ name: 'weekly', cron: '0 9 * * MON', prompt: 'Summarise last week.' })];

export default {
  scheduled: (controller: ScheduledController, env: Env, ctx: ScheduledContext) => {
    const agent = createAgent({
      instructions: 'You write reports.',
      provider: createMockProvider(),
      store: new KVStore(env.AGENT_CHECKPOINTS), // keeps sessions, checkpoints and paused approvals
    });
    return handleScheduled(agent, schedules, controller, ctx);
  },
};
```

## كتابة Worker بنفسك

استورد من `@lousho/build-ai-agent/worker`، لا من جذر الحزمة. المدخل الجذر
يصدّر أيضًا file stores ومحمّل agent directory وMCP عبر stdio وsandboxes
ووحدات ثانية خاصة بـ Node، فتجميعه لـ `platform: 'browser'` يفشل بـ
`Could not resolve "async_hooks"` وأمثاله. أما `/worker` فهو `createAgent`
زائد السطح الآمن للـ Worker، مبني بنفس الـ shims التي
يطبقها `lousho build`، فلا يحمل أي استيراد `node:` يقدر يتعثر فيه الـ bundler تبعك:

```ts
import {
  createAgent, createMockProvider, defineSchedule, defineTool, handleScheduled,
  memoryStore, serveFetch, OpenAIProvider, AnthropicProvider, OpenRouterProvider,
  LLMProviderRegistry, SDKError, /* ... */
} from '@lousho/build-ai-agent/worker';
import { KVStore } from '@lousho/build-ai-agent/kv'; // also re-exported from /worker
```

الصادرات: `createAgent` (وأنواع إعداداته)، و`memoryStore`، ومخازن KV
(`KVStore` و`KVCheckpointStore` و`CHECKPOINT_KV_BINDING`)، ومساعدات الـ schedules
(`defineSchedule` و`handleScheduled` وأنواعهما)، و`serveFetch`
(واجهة [`/chat` HTTP](/ar/deployment#http-api) كـ fetch handler،
لـ Worker يريد نفس المسارات التي يقدّمها الـ Worker المولَّد)،
والـ providers التي يقدر الـ Worker يشغّلها (`mock` و`openai` و`anthropic` و
`openrouter`)، وكل ما يجوز لكود agent directory استيراده (`defineTool` و
`isDefinedTool` و`always` و`never` و`once` و`defineSkill` و`defineChannel` و
الـ channel factories و`defineMemory` و`inMemoryMemory` و`kvMemory` و`fromAiSdk` و
`textOf` وأصناف الأخطاء).

نقطتان تعرفهما:

- `ai` و`zod` و`@opentelemetry/api` وحزم الـ providers
  (`@ai-sdk/openai` و`@ai-sdk/anthropic`) *لا* تُجمَّع داخل `/worker` —
  تنحلّ من تثبيتك كي تتشارك نسخة `ai` الخاصة بك. ثبّت الـ peer الذي يحتاجه
  الـ provider تبعك (لا شيء لـ `mock`)؛ وإذا ظل الـ bundler يحاول حلّ واحدة لم تثبّتها،
  فعلّمها `external` — الـ `import()` الكسول لا يشتغل أبدًا لـ provider لا
  تنشئه أصلًا.
- الميزات التي لا يقدر الـ Worker يشغّلها — project instructions، وfile session
  store، وguardrail patches، وtools داخل sandbox، وcode mode،
  والـ provider `ollama` — تُحمَّل كـ shims تفشل عند استدعائها، تمامًا كما في
  الـ Worker المولَّد. وكذلك `mcpServers` (stdio وstreamable HTTP): المدخل
  المنشور لا يقدر يحتفظ بمحدِّد external للـ peer الاختيارية
  `@modelcontextprotocol/sdk`، فيفشل الاتصال عند أول استخدام — استخدم
  `lousho build` (الـ Worker المولَّد) أو هدف Node لأجل MCP. كل شيء آخر، بما
  فيه turn من `createAgent({ provider, store })`، يشتغل دون تعديل؛ ولا حاجة إلى
  flag `nodejs_compat`.

## الاتساق

عمر الطلب في Worker أقصر من أن يناسب `CheckpointStore` في الذاكرة أو
معتمدًا على file system (راجع
[الإعدادات](/ar/configuration) / `src/execution/checkpoint.ts` لتعرف
ما هو `CheckpointStore` ولماذا يحتاج الـ run إليه لينجو من crash أو
من توقف عند بوابة approval). و`AGENT_CHECKPOINTS` هو هذا الـ store، مدعومًا بـ KV
(`KVCheckpointStore`)، والـ binding الواحد أعلاه يكفي لتفعيله.

**لماذا KV لا D1 ولا Durable Objects:** الـ `Checkpoint` هو blob JSON واحدة مفتاحها
`sessionId`، تُقرأ وتُكتب كاملة — وهذا بالضبط الشكل الذي بُني له Workers KV،
بلا أي بنية تحتية إضافية سوى binding إلى namespace. أما D1
فكانت ستعطيك قدرة استعلام relational لا يحتاجها هذا الـ store؛ وأما Durable Object
فكانت ستعطيك اتساقًا صارمًا لكل session على حساب إعداد
DO class وmigration ودفع كلفة object ذي حالة لكل session. إذا كان
حملك فعلًا يحتاج read-after-write consistency صارمة عبر
مواقع الـ edge (راجع الملاحظة أدناه)، فـ `CheckpointStore` مدعومًا بـ Durable Object
هو مسار الترقية الطبيعي — بتنفيذ واجهة `CheckpointStore` نفسها
(`save`/`load`/`delete`) على namespace لـ Durable Object
بدل namespace لـ KV.

**الـ eventual consistency — اقرأ هذا قبل الاعتماد عليها في مسارات
الـ approvals:** Workers KV مخزن *eventually consistent*. الـ `put()`
يظهر فورًا لموقع الـ edge الذي كتبه، لكنه قد يستغرق حتى
~60 ثانية لينتشر إلى باقي مواقع edge في Cloudflare عالميًا. عمليًا
يعني هذا: إذا كُتب checkpoint لـ session في موقع edge ووصل بعده بقليل طلب
لنفس `sessionId` إلى موقع edge *مختلف*، فقد يرى ذلك الطلب
بيانات قديمة (checkpoint أقدم، أو لا شيء) بدل ما كُتب للتو.
وهذا يهم أكثر في توقفات الـ approvals، لأن التوقف
والاستئناف الذي يطلقه approval الإنسان لاحقًا طلبان منفصلان بطبيعتهما
قد يصلان إلى موقعين مختلفين. هذا الـ SDK لا يَعِد — وفي ظل
ضمانات KV لا يقدر أن يَعِد — بـ read-after-write consistency صارمة هنا.
إذا كان مسار الـ approval عندك لا يحتمل هذه النافذة، وجّه طلبات الـ session الواحدة
إلى موقع Cloudflare واحد بنفسك (مثلًا عبر توجيه طلبات مبني على
Durable Object) أو استخدم store قوي الاتساق
بدل `AGENT_CHECKPOINTS`/KV. وينطبق الشيء نفسه على الـ sessions: طلبان من
نفس الـ session في اللحظة نفسها قد يكتب أحدهما فوق turn الآخر، لأن
read-modify-write في KV ليست atomic.

## حجم الـ bundle ووحدات Node المدمجة

مخازن KV (`KVStore` و`KVCheckpointStore` و`CHECKPOINT_KV_BINDING`،
المُصدَّرة من `@lousho/build-ai-agent/kv`) لا تحتوي أي إشارة `node:*` في
أي موضع من dependency graph تبعها، وكذلك مدخل `@lousho/build-ai-agent/worker` الذي
يجمّعه Worker مكتوب باليد (بناؤه يُفحص بنفس الطريقة؛ راجع [كتابة Worker
بنفسك](#كتابة-worker-بنفسك)). الـ Worker يشغّل الـ spec كـ agent من `createAgent()`،
والـ build يوجّه استيراداتها الخاصة بـ Node فقط (project instructions، وfile session
store، وguardrail patches، وMCP عبر stdio) إلى shim يفشل عند استخدامه
(`src/deploy/shims/node.worker.ts`). ثم تُفحص حزمة `dist/worker.js` المبنية
بحثًا عن `node:` وعن محدِّدات وحدات Node المدمجة المجرّدة ضمن `lousho build`،
ويفشل الـ build إن وُجد منها شيء؛ وحين يكون أحدها قد استُورد (من tool في agent
directory مثلًا) يسمّي الخطأ الملف المستورِد. استثناء واحد: `ai` v7 و
`@ai-sdk/provider-utils` v5 يبحثان عن `node:module` و`node:dns` و
`node:diagnostics_channel` و`node:async_hooks` وقت التشغيل عبر
`process.getBuiltinModule()`، وفقط حين يكتشفان Node، ويرجعان إلى
`fetch()` (أو يتخطيان telemetry tracing) في غيره. وهذه الـ ids الأربعة
تُقبل وسيطًا لاستدعاء كهذا ولا تُقبل في أي موضع آخر. والـ bundle أكبر من Worker
بـ turn واحد (نحو 1.7 MB خام و340 KB بـ gzip لـ agent `mock` على `ai` v4؛ ونحو 3.4 MB
خام و630 KB بـ gzip على `ai` v7): `lousho build` يبلّغ عن
حجمه، و`describe()` تقارنه بحد حجم السكربت في Cloudflare.
