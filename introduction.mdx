---

Most agent code starts as a loop around a model call, and then production asks for more: a human has to approve the refund before it is sent, the process restarts halfway through a run, the conversation has to continue tomorrow from another server, and somebody wants a test that fails when the agent stops calling the right tool.

`@lousho/build-ai-agent` is that loop with those answers built in. It is a library, with no web framework and no hosted runtime: a typed tool-calling loop with approvals, sessions, streaming, sub-agents, skills, MCP and a CLI. The same agent runs in a script, a Node server, a Docker container or a Cloudflare Worker.

```mermaid
flowchart LR
    A["your code<br/>send() or stream()"] --> B["agent run<br/>model step, tool calls, repeat"]
    B --> C{"tool needs<br/>approval?"}
    C -- no --> B
    C -- yes --> D["run pauses<br/>state is saved to a store"]
    D -- "approved, from any process" --> B
    B --> E["result<br/>text, typed object,<br/>usage and cost"]
```

```ts
import { createAgent } from '@lousho/build-ai-agent';

const agent = createAgent({ model: 'openai/gpt-4o-mini', instructions: 'You are a helpful assistant.' });
const { text } = await agent.send('Hello!');
console.log(text);
```

## The building blocks

Each block is one function or one option on `createAgent()`. Use the ones you need; none of them requires the others.

| Block | What you write | What you get |
| ----- | -------------- | ------------ |
| [Tools](/tools) | `defineTool()` with a zod `input` | Arguments typed and validated, calls run in parallel |
| [Approvals](/approvals) | `needsApproval`, or `permissions` rules | A run that pauses for a human, then continues with `agent.approvals.resolve()` |
| [Sessions](/sessions) | `agent.session({ id })` | A multi-turn conversation kept in memory, files or SQLite |
| [Memory](/memory) | `defineMemory()` slots | Facts recalled into the prompt across sessions, per user or globally |
| [Structured output](/structured-output) | `output: zodSchema` | A typed, validated `result.object`, with one repair step |
| [Streaming](/streaming) | `agent.stream()` | Typed, versioned JSON events, ready for SSE |
| [Sub-agents](/sub-agents) | `subagents: { researcher, writer }` | One `task` tool for the lead; sub-agents run in parallel, locally or remotely |
| [Skills](/skills) | `loadSkills()` | Instructions the agent loads only when a task needs them |
| [Providers](/providers) | a `provider/model` string | OpenAI, Anthropic, OpenRouter, Ollama or a mock, with retry and fallback |

## Where an agent can live

The agent is the same object everywhere. What changes is the surface in front of it.

<CardGroup cols={2}>
  <Card title="In a web app" icon="browser" href="/react">
    `useLoushoAgent()` for React and Vue, a store for Svelte, the Vercel AI SDK's `useChat`, or `createRouteHandler(agent)` in any Fetch-API framework.
  </Card>
  <Card title="In chat and on a schedule" icon="message-square" href="/channels">
    Slack, Discord, webhooks and plain HTTP channels map messages to sessions and send approvals back. Cron schedules start runs on their own.
  </Card>
  <Card title="In an editor" icon="code" href="/acp">
    `lousho acp` serves your agent to Zed and other Agent Client Protocol editors, with tool calls and permission prompts.
  </Card>
  <Card title="As a deployed service" icon="rocket" href="/deployment">
    `lousho build` produces a Node server, a Docker image or a Cloudflare Worker from one spec.
  </Card>
</CardGroup>

`@lousho/build-ai-agent` sits one layer above a model call: like LangGraph, Mastra or the OpenAI Agents SDK it runs a full agent loop, but as a library with no required platform, web framework or hosted runtime — and unlike the raw AI SDK, it ships the production pieces (durability, approvals, sessions) rather than leaving them to you.

| Capability | `@lousho/build-ai-agent` | Vercel AI SDK | LangChain / LangGraph | Mastra | OpenAI Agents SDK |
| ---------- | ---------------------- | ------------- | --------------------- | ------ | ----------------- |
| Typed event stream | Yes — `agent.stream()` emits versioned, sequenced JSON events for runs, steps, tokens and tool calls, SSE-ready | Partial — typed `streamText` parts; the run loop is yours | Yes — node/graph events via `streamEvents` | Yes — agent and workflow streams | Yes — streamed run events |
| Durable execution, checkpoints | Yes — checkpoints in pluggable stores (memory, files, SQLite, Cloudflare KV); a crashed or paused run resumes in another process | No — state lives in memory; you persist it | Yes — checkpointer saves thread state | Yes — workflow suspend/resume snapshots | Partial — sessions keep history; mid-run resume across processes is not built in |
| Approvals (human-in-the-loop) | Yes — `needsApproval` pauses the run; `agent.approvals.resolve()` continues it from any process | Build it — you gate the tool call | Yes — `interrupt()` and human nodes | Yes — human steps in workflows | Partial — approvals exist for hosted tools; arbitrary tool gating is manual |
| Channels | Yes — `mountChannels()` serves HTTP, webhook, Slack and Discord surfaces, with approvals back to the channel | No | No — community adapters only | Partial — some deploy/chat integrations | No |
| Deploy targets | `lousho build` emits a Node server, Docker image or Cloudflare Worker from one spec | BYO — runs wherever your app runs | BYO, or LangGraph Platform (hosted) | `mastra build` targets Node, Vercel, Netlify, Workers | BYO — the loop runs in your process |
| Sessions | Yes — `agent.session({ id })` over memory, file or SQLite stores | No — you keep the message array | Yes — threads and chat-history helpers | Yes — threads and memory | Yes — session objects keep conversation history |
| MCP | Client (`mcpServers`) and server (`serveMcp`) | Client only (`experimental_createMCPClient`) | Client via community adapters | Yes — MCP client and server | Yes — MCP servers as tool sources |
| Guardrails | Yes — input/output/tool-argument guardrails, prompt-injection and moderation checks, sandboxed tools | No — compose your own | Partial — community guardrails and LangSmith evaluators | Yes — input/output processors | Yes — input/output guardrails |

When something else fits better: if you only need to stream model text in a Next.js route, the AI SDK alone is less surface; if your team is on Python or already runs LangGraph Platform, staying in that ecosystem avoids a second stack. `@lousho/build-ai-agent` is aimed at TypeScript teams that want a durable, approvable agent loop inside their own process without adopting a platform.
